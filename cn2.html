PART 01

Transport Layer Services & Multiplexing

Extending host-to-host delivery (done by the network layer) into process-to-process delivery — this is the whole job of the transport layer.

What is the transport layer?

The transport layer provides logical communication between application processes running on different hosts. "Logical" is the key word — the two end-hosts might be many router-hops apart, but from the transport layer's point of view they appear to be directly connected.

The transport-layer protocol runs only in the end systems (not in routers in the network core):

  • Sender side: breaks application messages into segments, and passes each segment to the network layer.
  • Receiver side: reassembles segments back into messages, and passes them up to the application layer.

Two transport protocols are available to Internet applications: TCP and UDP.

KEY POINT Network layer provides logical communication between hosts. Transport layer provides logical communication between processes — it relies on, and enhances, network-layer services.

Transport vs. network layer — the household analogy

Think of 12 kids in Ann's house sending letters to 12 kids in Bill's house:

  • Hosts = houses
  • Processes = kids
  • Application messages = letters in envelopes

The postal service (network layer) only needs to get mail from house to house. Once inside the house, a family member — the transport layer — must sort each letter to the right kid.

Network layer
  • Logical communication between hosts
Transport layer
  • Logical communication between processes
  • Relies on and enhances network-layer services

Transport layer actions

Sender: the transport layer is passed an application-layer message; it determines the segment's header field values, creates the segment, and passes it down to the network (IP) layer.

Receiver: the transport layer receives a segment from IP, checks the header field values, extracts the application-layer message, and demultiplexes the message up to the right application via a socket.

Fig. Sender-side transport actions create the segment; receiver-side actions check header values, extract the message and demultiplex it up to the correct socket.

Principal Internet transport-layer protocols

TCP — Transmission Control Protocol
  • Reliable, in-order delivery
  • Congestion control
  • Flow control
  • Connection setup
UDP — User Datagram Protocol
  • Unreliable, unordered delivery
  • "No-frills" extension of best-effort IP
KEY POINT Services not available from either TCP or UDP: delay guarantees, bandwidth guarantees. Neither protocol can promise you a certain speed or a certain latency — that's simply not part of the Internet's best-effort transport model.

Multiplexing & demultiplexing

Every host can run many application processes, but there is only one network-layer connection to that host, carrying data for all of them. Multiplexing/demultiplexing is how the transport layer shares that one connection among many sockets.

  • Multiplexing at the sender: handle data from multiple sockets, add a transport header (used later for demultiplexing).
  • Demultiplexing at the receiver: use header information to deliver received segments to the correct socket.
Fig. Multiplexing at the sender combines several sockets' data onto one wire; demultiplexing at the receiver splits it back out using header fields.

How demultiplexing works — the segment header

Every host receives IP datagrams, each with a source and destination IP address, carrying exactly one transport-layer segment. Each segment has source and destination port numbers, which the host uses (together with the IP addresses) to direct the segment to the appropriate socket.

Fig. TCP/UDP segment format — the first 32 bits always hold source and destination port numbers.
KEY POINT Each port number ranges from 0 to 65535. Port numbers from 0–1023 are well-known ports (restricted/reserved).

Connectionless (UDP) demultiplexing: when creating a socket, the process must specify a host-local port number. When the receiving host gets a UDP segment, it checks the destination port # in the segment and directs it to the socket bound to that port. IP/UDP datagrams with the same destination port but different source IP addresses and/or source port numbers are all directed to the same socket at the receiving host.

Connection-oriented (TCP) demultiplexing

A TCP socket is identified by a 4-tuple: source IP address, source port number, destination IP address, destination port number. A server host may support many simultaneous TCP sockets, each identified by its own 4-tuple — so web servers keep a different socket for every connecting client (non-persistent HTTP even opens a fresh socket per request).

KEY POINT UDP demultiplexes using the destination port number only. TCP demultiplexes using the full 4-tuple. Why the difference? UDP has no notion of an ongoing "connection" to distinguish — every datagram is independent. TCP tracks per-connection state, so it needs the full tuple to know which connection's state a segment belongs to.
Worked example Three segments all destined to IP address B, port 80, are demultiplexed to three different sockets because each carries a distinct 4-tuple — e.g. (A, 9157, B, 80) goes to one socket, while (C, 5775, B, 80) and (C, 9157, B, 80) — same client IP C, different source ports — land on two more, entirely separate sockets. This proves TCP looks at the whole 4-tuple, not just the source IP: one client machine can hold multiple independent connections to the same server.

Q. How many TCP connections can a server handle?
Answer
A server can handle a large number of TCP connections, usually limited by RAM, file descriptors, and CPU — not by a fixed port limit. Since a connection is identified by the 4-tuple (server IP, server port, client IP, client port), a server is not restricted to only 65535 total TCP connections.

PART 02

Socket Programming with UDP & TCP

Building client/server applications that communicate using sockets.

Sockets — the basics

A socket is the door between an application process and the end-to-end transport protocol. Everything above the socket (the application process) is controlled by the app developer; everything below it (transport, network, link, physical) is controlled by the operating system.

There are two socket types for the two transport services:

  • UDP: unreliable datagram
  • TCP: reliable, byte-stream oriented
Running example used throughout 1. Client reads a line of characters from its keyboard and sends the data to the server. 2. Server receives the data and converts characters to uppercase. 3. Server sends the modified data back to the client. 4. Client receives the modified data and displays it on screen.

Socket programming with UDP

UDP has no "connection" between client and server: there's no handshaking before sending data. The sender explicitly attaches the destination IP address and port # to each packet, and the receiver extracts the sender's IP address and port # from the received packet. Data may be lost or arrive out of order. From the application's point of view, UDP provides unreliable transfer of "datagrams" between client and server.

ServerClient
Create socket, port = x:
serverSocket = socket(AF_INET, SOCK_DGRAM)		Create socket:
clientSocket = socket(AF_INET, SOCK_DGRAM)

Python UDPClient
from socket import *
serverName = 'hostname'
serverPort = 12000
clientSocket = socket(AF_INET, SOCK_DGRAM)
message = input('Input lowercase sentence:')
clientSocket.sendto(message.encode(), (serverName, serverPort))
modifiedMessage, serverAddress = clientSocket.recvfrom(2048)
print(modifiedMessage.decode())
clientSocket.close()
Python UDPServer
from socket import *
serverPort = 12000
serverSocket = socket(AF_INET, SOCK_DGRAM)
serverSocket.bind(('', serverPort))
print('The server is ready to receive')
while True:
    message, clientAddress = serverSocket.recvfrom(2048)
    modifiedMessage = message.decode().upper()
    serverSocket.sendto(modifiedMessage.encode(), clientAddress)

Socket programming with TCP

The client must contact the server: the server process must already be running, and must have a created socket (a "door") that welcomes the client's contact. When contacted, TCP creates a new socket for the server process to talk to that particular client — this is what lets one server handle multiple clients simultaneously; the client's source port # and IP address are used to distinguish clients.

The client contacts the server by creating a TCP socket, specifying the server's IP address and port number. When the client creates its socket, the client's TCP establishes a connection to the server's TCP.

Application viewpoint: TCP provides a reliable, in-order byte-stream transfer (a "pipe") between the client and server processes.

Fig. Client/server socket interaction over TCP — connection is established before any request/reply data flows.
Python TCPClient
from socket import *
serverName = 'servername'
serverPort = 12000
clientSocket = socket(AF_INET, SOCK_STREAM)
clientSocket.connect((serverName, serverPort))
sentence = input('Input lowercase sentence:')
clientSocket.send(sentence.encode())
modifiedSentence = clientSocket.recv(1024)
print('From Server:', modifiedSentence.decode())
clientSocket.close()
Python TCPServer
from socket import *
serverPort = 12000
serverSocket = socket(AF_INET, SOCK_STREAM)
serverSocket.bind(('', serverPort))
serverSocket.listen(1)
print('The server is ready to receive')
while True:
    connectionSocket, addr = serverSocket.accept()
    sentence = connectionSocket.recv(1024).decode()
    capitalizedSentence = sentence.upper()
    connectionSocket.send(capitalizedSentence.encode())
    connectionSocket.close()
KEY POINTThe TCP server process has two sockets: the "welcoming" serverSocket that only ever listens for new connections, and a fresh connectionSocket created per client by accept() — this is exactly what lets the server talk to many clients at once.

PART 03

UDP — Connectionless Transport [RFC 768]

The "no frills," "bare bones" Internet transport protocol.

Why does UDP exist?

UDP offers "best effort" service — segments may be lost, or delivered out of order to the app. It's connectionless: there's no handshaking between sender and receiver, and each UDP segment is handled independently of the others.

Why UDP is useful
  • No connection establishment (which can add RTT delay)
  • Simple — no connection state at sender or receiver
  • Small header size
  • No congestion control — UDP can blast away as fast as desired!
  • Can function in the face of congestion
Typical UDP use cases
  • Streaming multimedia apps (loss-tolerant, rate-sensitive)
  • DNS
  • SNMP
  • HTTP/3

If reliable transfer is needed over UDP (e.g. HTTP/3), the needed reliability and congestion control are added at the application layer instead.

UDP segment header

Fig. UDP segment format — a fixed 8-byte header (four 16-bit fields) followed by the payload.
KEY POINTThe UDP header is always exactly 8 bytes — versus a minimum of 20 bytes for TCP. Even though the header is fixed-size, a length field is still needed because the payload is variable-length and UDP keeps no connection state anywhere — each datagram must be entirely self-describing. The length field counts the whole UDP segment (header included), not just the payload.

UDP checksum — computing it in 5 steps

Goal: detect "errors" (e.g. flipped bits) in a transmitted segment.

#StepDetail
1Split the segment into 16-bit wordsHeader fields and data, all treated as plain 16-bit integers
2Add the words togetherOrdinary binary addition, one word at a time
3Handle the wraparound carryAny carry out of the most significant bit is added back into the low end — this is the step everyone forgets
4That result is the SUMKeep going until every word has been added in
5Flip every bit — that is the CHECKSUMOne's complement of the sum; this is what goes in the header field
Worked example — adding two 16-bit integers 
1110011001100110
1101010101010101
--------------------------- (wraparound carry added back in)
1101110111011011
sum:      1011101110111100
checksum: 0100010001000011

A carry-out from the most significant bit needs to be added back into the result — that's the "wraparound" step.

KEY POINTThe receiver adds up everything, including the checksum field itself, and simply tests for all ones — instead of recomputing and comparing. That's exactly why the sender transmits the complement of the sum rather than the sum itself.

What the checksum catches — and what it misses

Always caught
  • Any single bit flip, anywhere in the segment
  • ANY pattern of 1 to 15 bit flips confined to a single 16-bit word
  • Any burst error shorter than 16 bits
  • Most multi-word errors — they only cancel in very specific offsetting patterns
Can slip through
  • Two bits flipping in opposite directions in different words — the errors cancel in the sum ("weak protection")
  • Any set of errors across words whose net effect on the sum is zero
  • One degenerate case: flipping all 16 bits of a word that was all-zeros or all-ones
KEY POINTThe checksum is strong within a word and weak across words. Errors confined to one 16-bit word are essentially always caught — the vulnerability needs errors spread over two or more words in offsetting directions.
Q. Name the four fields of the UDP header, in order, and its total size.
Answer
Source port #, destination port #, length, checksum — 8 bytes total (four 16-bit fields), versus a minimum of 20 bytes for TCP.

PART 04

Principles of Reliable Data Transfer

How to deliver application data correctly on top of a network that can lose, corrupt, reorder, and duplicate packets.

Why do we need reliable data transfer?

The goal is to deliver application data correctly even when the network underneath is unreliable. Real networks present several distinct challenges:

  • Bit errors (packet corruption)
  • Packet loss
  • ACK loss
  • Packet duplication
  • Unknown receiver state — the sender and receiver do not know each other's "state" unless it is communicated via a message (e.g. was a message actually received?)

The complexity of any reliable-data-transfer protocol depends strongly on the characteristics of the underlying unreliable channel: does it lose data, corrupt data, or reorder it?

Fig. The reliable-service abstraction: applications see a perfectly reliable channel; underneath, rdt protocols run over the actual unreliable network.

The six core mechanisms of reliable data transfer

MechanismPurpose
ChecksumDetect bit errors
ACKPositive acknowledgement
NAKNegative acknowledgement
Sequence numberDetect duplicates
Timer & timeoutRecover from lost packets
RetransmissionResend missing packets

Every rdt protocol — however sophisticated — is built by combining these six primitives in different ways.

rdt3.0 — the alternating-bit protocol

Since the underlying channel can corrupt and lose packets (both data packets and ACKs), rdt3.0 adds a sequence number that alternates between 0 and 1 — which is exactly why it is nicknamed the alternating-bit protocol. Only one packet is ever in flight at a time (stop-and-wait).

ScenarioWhat happens
(a) No lossSender sends pkt0, receiver ACKs it (ack0); sender sends pkt1, receiver ACKs it (ack1); repeat, alternating 0/1
(b) Packet lossSender's timer expires with no ACK received → resend the same packet; receiver eventually gets it and ACKs normally
(c) ACK lossSender's timer expires (even though the receiver did get the packet and did send an ACK, which was lost) → sender resends; receiver detects the duplicate by sequence number, re-sends the ACK, but does not deliver the data twice
(d) Premature timeout / delayed ACKThe timeout fires before the ACK actually arrives → sender retransmits unnecessarily; the receiver, seeing a duplicate sequence number, discards the duplicate data but still re-ACKs it so the sender's window can move on
KEY POINTBecause packet sequence numbers alternate strictly between 0 and 1, protocol rdt3.0 is sometimes known as the alternating-bit protocol. Its key elements — checksums, sequence numbers, timers, and positive/negative acknowledgement packets — each play a crucial and necessary role in the operation of the protocol.

Performance of rdt3.0 (stop-and-wait)

Usender: utilization — the fraction of time the sender is actually busy sending.

Worked example — 1 Gbps link, 15 ms one-way propagation delay, 8000-bit packet
D_trans = L / R = 8000 bits / 10⁹ bits/sec = 8 microseconds
Sender utilization
U_sender = (L/R) / (RTT + L/R)
= 0.008 / 30.008 = 0.00027
KEY POINTrdt3.0's stop-and-wait performance is terrible — the sender is busy only 0.027% of the time! The protocol is what limits the performance of the underlying infrastructure (channel), not the channel itself.

Pipelining — the fix

The solution is simple: rather than operate stop-and-wait, allow the sender to send multiple packets without waiting for acknowledgements. Since many in-transit sender-to-receiver packets can be visualized as filling a pipeline, this technique is known as pipelining.

  • The range of sequence numbers must be increased (each in-flight packet needs a unique sequence number, and there may be several unacknowledged at once).
  • Buffering is required at the sender and/or receiver.
KEY POINT3-packet pipelining increases utilization by roughly a factor of 3 over stop-and-wait, for the same link and RTT.

PART 05

Go-Back-N & Selective Repeat

Two concrete pipelined protocols that put the "multiple packets in flight" idea into practice.

Go-Back-N — sender & receiver rules

The sender maintains a window of up to N consecutive transmitted-but-unACKed packets, using a k-bit sequence number in the packet header.

  • Cumulative ACK: ACK(n) acknowledges all packets up to and including sequence # n. On receiving ACK(n), the sender moves its window forward to begin at n+1.
  • One timer, for the oldest in-flight packet. timeout(n): retransmit packet n and all higher sequence-numbered packets currently in the window.

Receiver (ACK-only): always sends an ACK for the correctly received packet with the highest in-order sequence number so far — this may generate duplicate ACKs, and the receiver need only remember rcv_base.

  • On receipt of an out-of-order packet: the receiver can either discard it (don't buffer) or buffer it — this is an implementation decision.
  • Either way, it re-ACKs the packet with the highest in-order sequence number.

Go-Back-N in action

With window size N = 4, sender sends pkt0–pkt3; pkt3 is lost. The receiver gets pkt0 and pkt1 fine (sends ack0, ack1), but pkt3 arrives out of order and is discarded — the receiver keeps re-sending ack1. When pkt2 eventually times out, the sender goes back and resends pkt2, pkt3, pkt4, pkt5 (everything from the timed-out packet onward) — hence the name Go-Back-N.

Worked example — every 5th transmission lost, 10 packets to send, window size 10

Round 1 — send packets 1–10 (transmissions 1–10): 1–4 delivered; 5 LOST; 6–9 arrive but discarded (out of order); 10 LOST. Receiver has 1–4. Sender times out and goes back to packet 5.

Round 2 — resend 5–10 (transmissions 11–16): 5–8 delivered; 9 LOST; 10 arrives but discarded. Receiver now has 1–8. Go back to packet 9.

Round 3 — resend 9–10 (transmissions 17–18): neither 17 nor 18 is a multiple of 5, so both succeed. Done.

Total transmissions = 18.

Selective Repeat — sender & receiver rules

Pipelining, but the receiver individually acknowledges every correctly-received packet, buffering out-of-order packets as needed for eventual in-order delivery to the upper layer.

SenderReceiver
Data from above: if the next available seq # is in the window, send the packetPacket n in [rcvbase, rcvbase+N-1]: send ACK(n). If out-of-order, buffer it. If in-order, deliver it (plus any buffered in-order packets) and advance the window to the next not-yet-received packet
Timeout(n): resend only packet n, restart its timerPacket n in [rcvbase-N, rcvbase-1]: just ACK(n) again (it was already delivered)
ACK(n) in [sendbase, sendbase+N]: mark packet n as received. If n is the smallest unACKed packet, advance the window base to the next unACKed sequence #Otherwise: ignore
KEY POINTThe sender maintains a conceptual timer per unACKed packet — a timeout retransmits only that one packet, not the whole window (unlike GBN).

Selective Repeat in action

With window size N = 4: pkt3 is lost, but pkt4 and pkt5 (which arrive fine) are individually buffered and ACKed (ack4, ack5) instead of being discarded. When pkt2 times out and is resent, the receiver can now deliver pkt2, pkt3, pkt4, and pkt5 all at once, and send ack2.

What happens when ack2 finally arrives at the sender? The window lurches forward by four positions in one step: packet 2 is marked ACKed and its timer stops; the base then advances past every consecutively-ACKed packet (2 ✓, 3 ✓, 4 ✓, 5 ✓), moving from 2 → 6. The window becomes [6, 7, 8, 9], and the sender can immediately transmit pkt6–pkt9 — four new packets at once.
Worked example — every 5th transmission lost, 10 packets to send, window size 10 (Selective Repeat) Because only the individually-lost packet needs to be retransmitted (not the whole window), the total comes out to just 12 transmissions — far fewer than Go-Back-N's 18 for the identical loss pattern.

The Selective-Repeat window-size dilemma

Example: sequence numbers 0,1,2,3 (base-4 counting), window size = 3.

(a) No problem: sender sends pkt0–pkt2, receiver ACKs each; when pkt0 is later retransmitted after a timeout, the receiver's window has already moved on and correctly treats it as old/duplicate.

(b) Oops! If the window size is too large relative to the sequence-number space, a retransmitted old pkt0 can look indistinguishable from a new pkt0 to the receiver — the receiver's window and sequence numbers wrap around and the receiver ends up "willing to accept a packet with sequence number 0" that is actually stale data from a previous round.

KEY POINTTo avoid this ambiguity, Selective Repeat requires: window size ≤ (sequence number space) / 2. This guarantees the receiver can always tell a genuinely new packet apart from a retransmitted old one.

The SACK (TCP Selective Acknowledgment, RFC 2018) option lets the receiver report exactly which blocks arrived, pushing TCP further toward Selective-Repeat behaviour.

PART 06

TCP In Depth

Segment structure, sequencing, timeouts, flow control and connection management. RFCs: 793, 1122, 1323, 2018, 2581

TCP — overview

  • Point-to-point: one sender, one receiver.
  • Reliable, in-order byte stream: no "message boundaries."
  • Full duplex data: bi-directional data flow in the same connection.
  • MSS: maximum segment size.
  • Cumulative ACKs with pipelining — TCP congestion and flow control set the window size.
  • Connection-oriented: handshaking (exchange of control messages) initializes sender and receiver state before data exchange.
  • Flow controlled: the sender will not overwhelm the receiver.

TCP segment structure

Fig. TCP segment structure — a minimum 20-byte header plus optional fields and payload.

Sequence numbers & ACKs

  • Sequence numbers: the byte-stream "number" of the first byte in the segment's data.
  • Acknowledgements: the sequence # of the next byte expected from the other side — a cumulative ACK.
KEY POINTQ: How does the receiver handle out-of-order segments? A: The TCP spec doesn't say — it's left up to the implementor.
Simple telnet scenario User types 'C' → Host A sends Seq=42, ACK=79, data='C'. Host B ACKs receipt of 'C' and echoes it back → Seq=79, ACK=43, data='C'. Host A ACKs receipt of the echoed 'C' → Seq=43, ACK=80.

RTT estimation & timeout

Q: how to estimate RTT? SampleRTT: the measured time from segment transmission until ACK receipt (retransmissions are ignored when sampling). Since SampleRTT varies, we want a smoother EstimatedRTT — an average of several recent measurements rather than just the latest sample.

Exponential Weighted Moving Average (EWMA)
EstimatedRTT = (1 − α)·EstimatedRTT + α·SampleRTT
typical value: α = 0.125 — the influence of past samples decreases exponentially fast

Timeout interval = EstimatedRTT plus a "safety margin." A large variation in EstimatedRTT means we want a larger safety margin.

Timeout interval
TimeoutInterval = EstimatedRTT + 4·DevRTT
DevRTT = (1 − β)·DevRTT + β·|SampleRTT − EstimatedRTT|
typically, β = 0.25
KEY POINT Why not just set the timeout to the measured RTT? RTT varies constantly — too short causes needless retransmissions that add load to an already-struggling network; too long wastes time reacting to real loss. The 4×DevRTT margin is a safety cushion that widens automatically when the network gets erratic. Why 4 times the deviation, rather than 1 or 2? It's an engineering constant, tuned empirically for a conservative margin.

TCP sender / receiver actions (simplified)

TCP Sender
  • Data received from application: create a segment with a seq # (the byte-stream number of the first data byte). Start the timer if it isn't already running (think of the timer as being for the oldest unACKed segment); expiration interval = TimeOutInterval.
  • Timeout: retransmit the segment that caused the timeout; restart the timer.
  • ACK received: if it acknowledges previously-unACKed segments, update what is known to be ACKed, and start the timer if unACKed segments remain.
TCP Receiver — ACK Generation
EventAction
In-order segment, expected seq #, all prior data already ACKedDelayed ACK — wait up to 500ms for next segment; if none arrives, send ACK
In-order segment, expected seq #, one other segment has an ACK pendingImmediately send a single cumulative ACK, ACKing both in-order segments
Out-of-order segment, higher than expected seq # — gap detectedImmediately send a duplicate ACK, indicating the seq # of the next expected byte
Segment that partially or completely fills a gapImmediately send ACK, provided the segment starts at the lower end of the gap

Retransmission scenarios

Lost ACK scenario

Host A sends Seq=92 (8 bytes). Host B receives it and replies ACK=100 — but that ACK is lost. Host A's timer expires, so it retransmits Seq=92. Host B, seeing the duplicate, resends ACK=100. Host A's SendBase then advances from 92 → 100.

Premature timeout

Host A sends Seq=92, then Seq=100 (20 bytes). A's timer for the first segment fires before its ACK arrives (premature timeout), so A needlessly resends Seq=92. Host B's cumulative ACK for everything received so far (ACK=120) covers both segments, so A's SendBase jumps straight to 120.

Cumulative ACK covering an earlier lost ACK Host A sends Seq=92 (8 bytes) then Seq=100 (20 bytes). Host B's ACK=100 for the first segment is lost, but when Host B later sends ACK=120 for the second segment, that single cumulative ACK covers both segments — so Host A never needs to retransmit anything.

TCP fast retransmit

If the sender receives 3 additional (duplicate) ACKs for the same data ("triple duplicate ACKs"), it resends the unACKed segment with the smallest sequence number — without waiting for the timeout. Receipt of three duplicate ACKs indicates that three segments were received after a missing one, so a lost segment is highly likely — hence: retransmit immediately.

Fast retransmit trigger
3 duplicate ACKs (same ACK # repeated 4 times total) ⇒ retransmit immediately, don't wait for timeout

TCP flow control

Q: what happens if the network layer delivers data faster than the application layer removes it from the socket buffers? A: flow control — the receiver controls the sender, so the sender won't overflow the receiver's buffer by transmitting too much, too fast.

The TCP receiver "advertises" its free buffer space in the rwnd field of the TCP header. RcvBuffer size is set via socket options (typical default: 4096 bytes), though many operating systems auto-adjust it. The sender limits the amount of unACKed ("in-flight") data to the most recently received rwnd — this guarantees the receive buffer will not overflow.

Receive-window bookkeeping
LastByteRcvd − LastByteRead ≤ RcvBuffer
rwnd = RcvBuffer − [LastByteRcvd − LastByteRead]

TCP connection management

Before exchanging data, sender and receiver must "handshake": agree to establish a connection (each knowing the other is willing), and agree on connection parameters (e.g. starting sequence numbers).

Fig. The TCP 3-way handshake — SYN, SYN+ACK, ACK.
KEY POINTBoth sides move to state ESTAB only after this exchange completes, and both sides now track connection variables: sequence numbers in each direction and receive-buffer sizes at server and client.

Closing a TCP connection

Client and server each close their own side of the connection by sending a TCP segment with FIN bit = 1. A received FIN is responded to with an ACK — and that ACK can be combined with the receiver's own FIN. Simultaneous FIN exchanges are also handled.

Fig. TCP connection teardown — each side sends its own FIN, and the client's TIMED_WAIT holds state for 2× the maximum segment lifetime before finally closing.

PART 07

DNS — Domain Name System

The distributed database that translates human-readable names into IP addresses — a core Internet function, implemented as an application-layer protocol.

Why DNS? DNS services

People have many identifiers (SSN, name, passport #). Internet hosts and routers have an IP address (32-bit, used for addressing datagrams) and a "name" (e.g. cs.umass.edu, used by humans). DNS maps between the two, in both directions.

DNS is a distributed database implemented in a hierarchy of many name servers, plus the application-layer protocol that lets hosts and name servers communicate to resolve names.

  • Hostname-to-IP-address translation
  • Host aliasing — canonical and alias names (e.g. www.abc.example.com → canonical host name, www.example.com → alias name)
  • Mail-server aliasing
  • Load distribution — replicated web servers: many IP addresses correspond to one name
KEY POINT Q: Why not centralize DNS? A: it doesn't scale — a single point of failure, unmanageable traffic volume, a distant centralized database (slow lookups from far away), and impossible maintenance. Comcast's DNS servers alone handle ~600 billion queries per day; Akamai's, ~2.2 trillion.

A distributed, hierarchical database

Fig. DNS is organized as a hierarchy: Root → Top-Level Domain (TLD) → Authoritative servers.

Example: a client wants the IP address for www.amazon.com. First approximation: the client queries the root server to find the .com DNS server; queries the .com DNS server to get the amazon.com DNS server; queries the amazon.com DNS server to finally get the IP address.

DNS zone vs domain

DNS is organized according to zones. A zone groups contiguous domains and subdomains on the domain tree, and assigns management authority to a single entity. There can be multiple DNS zones — one per country, for instance — and each zone keeps records of who the authority is for each of its subdomains. The zone for example.com contains only the DNS records for hostnames that don't belong to any subdomain (like mail.example.com, which would be its own zone if delegated).

KEY POINT A domain is the naming subtree (e.g. everything under example.com); a zone is an administrative boundary — who actually manages and maintains the records for a piece of that tree. One domain can be split into many independently-managed zones — e.g. a CSE department can manage its own cse.pes.edu records without needing central IT to make every change, and a mistake in one zone doesn't take down the others.

Root, TLD, and authoritative servers

Root name servers: the official contact-of-last-resort for name servers that can't resolve a name — an incredibly important Internet function (the Internet couldn't function without it!). There are 13 logical root name "servers" worldwide, each replicated many times (~200 servers in the US alone). ICANN (Internet Corporation for Assigned Names and Numbers) manages the root DNS domain.

TLD (Top-Level Domain) servers: responsible for .com, .org, .net, .edu, .aero, .jobs, .museums, and country-code domains (.cn, .uk, .fr, .ca, .jp). Network Solutions is the authoritative registry for .com/.net; Educause is the .edu TLD authority.

Authoritative DNS servers: an organization's own DNS server(s), providing authoritative hostname-to-IP mappings for that organization's named hosts — can be maintained by the organization itself, or by a service provider.

KEY POINTOrder: Root → TLD → Authoritative. Root points to the right TLD; TLD points to the right organization's authoritative server; the authoritative server has the actual answer.

Local DNS name servers

A local DNS server does not strictly belong to the hierarchy. Each ISP (residential ISP, company, university) has its own local DNS server — also called the "default name server." (Check yours: macOS — scutil --dns; Windows — ipconfig /all.)

When a host makes a DNS query, the query is sent to its local DNS server, which returns a reply either from its local cache of recent name-to-address translation pairs (which may be out of date!) or by acting as a proxy that forwards the query into the hierarchy.

Iterated vs recursive queries

Example: a host at engineering.nyu.edu wants the IP address for gaia.cs.umass.edu.

Iterated query

Each contacted server replies with the name of the next server to contact ("I don't know this name, but ask this server"). The requesting host / local DNS server does all the walking itself — the load is distributed, since every hop only answers what it knows.

Recursive query

Puts the burden of full name resolution on the contacted name server ("...let me ask for you"). Each contacted server does the extra work on the client's behalf — but this concentrates heavy load at the upper levels of the hierarchy.

Iterated QueryRecursive Query

Q. Which DNS flag in a response tells you whether a server is willing to do recursive resolution for you?
Answer
The RA (Recursion Available) flag. Root and TLD servers never set it — by design, they only operate iteratively.

Caching & updating DNS records (TTL)

Suppose apricot.nyu.edu queries dns.nyu.edu for the IP address of cnn.com. An hour later, another NYU host, kiwi.nyu.edu, queries the same. Once any name server learns a mapping, it caches it and immediately returns the cached mapping for future queries — improving response time. Cache entries time out (disappear) after some time, the TTL (time-to-live); TLD servers are typically cached in local name servers, so root name servers are not often visited.

KEY POINT Cached entries may be out of date — DNS is best-effort. If a host changes its IP address, that change may not be known Internet-wide until all TTLs expire. An update/notify mechanism was proposed as an IETF standard (RFC 2136). The standard operational fix for minimizing disruption during a planned IP change: lower the TTL well in advance, wait for the old (long) TTL to fully drain everywhere, make the change, then raise the TTL back — this bounds the worst-case staleness window rather than eliminating it.

DNS message format

DNS query and reply messages share the same format. The 12-byte header contains: a 16-bit identification field (the reply to a query reuses the same number), and 16 bits of flags — query(0)/reply(1), recursion desired, recursion available, whether the reply is authoritative.

Header count fieldMeaning
# questionsNumber of questions in the "questions" section
# answer RRsNumber of resource records in the "answers" section

  • Questions (variable #): name and type fields for a query.
  • Answers (variable # of RRs): RRs in response to the query — type (e.g. A, NS, CNAME, MX), value, and TTL.
  • Authority (variable # of RRs): records for authoritative servers.
  • Additional info (variable # of RRs): extra helpful information that may be used.

DNSSEC — why it matters

Plain DNS has no authentication — a response claiming to be from an authoritative server could be forged (cache poisoning / spoofing). DNSSEC adds digital signatures (RRSIG records) to DNS responses, so a resolver can verify a record actually came from the zone's authoritative server. Trust is chained: Root → TLD → Authoritative — each level signs the key of the level below it.

KEY POINTDNSSEC provides authentication and integrity, not confidentiality — DNS queries are still visible in plaintext. It solves a different problem than TTL/caching does: it says nothing about the staleness of a legitimately-changed record (that's still governed by TTL) — it only prevents a forged/poisoned answer from being trusted.

Answer

PART 08

P2P Architecture & Other Application-Layer Protocols

Rounding out the application layer: peer-to-peer systems, and the everyday protocols behind file transfer, email, address assignment, network management, and remote access.

Peer-to-peer (P2P) architecture

No centralized server — arbitrary end systems directly communicate. Peers request service from other peers, and provide service in return to other peers.

Advantages
  • Self scalability — new peers bring new service capacity, and new service demands
  • Efficient resource sharing
  • Cost-effective, high availability
  • Load is distributed among peers
Challenges
  • Peers are intermittently connected and change IP addresses
  • Complex management

Examples: P2P file sharing (BitTorrent), media streaming (Spotify), VoIP (Skype), blockchain and cryptocurrencies, video and content distribution.

FTP — File Transfer Protocol

  • Used to exchange large files on the Internet.
  • Runs over TCP.
  • Invoked from the command prompt or a GUI.
  • Allows updating (delete, rename, move, copy) files at a server.
  • Two connections: a data connection (port 20) and a separate control connection (port 21).

SMTP — Simple Mail Transfer Protocol

  • An Internet standard for e-mail transmission.
  • Connections are secured with SSL (Secure Socket Layer).
  • Messages are stored and then forwarded to the destination (relay).
  • Uses TCP port 25.

DHCP — Dynamic Host Configuration Protocol

  • Assigns IP addresses to computers in a network dynamically.
  • IP addresses may change even while a computer remains in the network (DHCP leases).
  • Uses UDP; server port 67, client port 68.
  • Client-server model, based on a four-step exchange: Discovery, Offer, Request, ACK ("DORA").
  • Also delivers subnet mask, DNS server address, and default gateway to the client.

SNMP — Simple Network Management Protocol

Exchanges management information between network devices. Basic components and functionalities:

  • SNMP Manager
  • Managed Devices
  • SNMP Agents
  • MIB (Management Information Base)

Telnet & SSH

Both allow a user to communicate with a remote device, used mostly by network admins to remotely access and manage devices.

Telnet
  • Telnet client and server installed
  • Uses TCP port 23
  • Traffic is unencrypted
SSH
  • Uses public-key encryption
  • Uses TCP port 22 by default

Q1. Why does TCP need a connection "setup" step before any data flows, while UDP just sends?
Answer
TCP has to establish shared state between sender and receiver first (for reliability, ordering, flow/congestion control to work) — UDP has no such state to set up, which is exactly why it's called a "no-frills" extension of IP.
Q2. A segment header's first 32 bits hold two fields. What are they, and how wide is each?
Answer
Source port # and destination port #, 16 bits each.
Q3. Why is a DNS query typically sent over UDP rather than TCP?
Answer
It's a small, one-shot request/response — the overhead of a TCP connection setup isn't worth it for a single quick exchange, so UDP's speed wins out.
Q4. GBN and SR represent two different design choices. Which one did TCP pick?
Answer
Neither — it's a hybrid. Cumulative ACKs like GBN, but a single retransmission on timeout and (with the SACK option) selective recovery like SR.
Q5. What problem does DNSSEC solve that TTL/caching does not?
Answer
Authenticity and integrity — DNSSEC lets a resolver verify a response actually came from the real authoritative server (via signed records, chained root → TLD → authoritative), preventing forged/poisoned answers. It says nothing about the staleness of a legitimately-changed record — that's still governed by TTL.
