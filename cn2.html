Cover & "Application Layer" Slides 1–2

  • Slide 1: "COMPUTER NETWORKS" — Team Networks, Department of Computer Science and Engineering (PES University).
  • Slide 2: "COMPUTER NETWORKS — Application Layer" — the section-divider slide marking the start of the Application Layer unit.
EXPLANATION

These are the deck's title/divider slides. The Application Layer is the topmost layer of the network stack — the one applications (browsers, mail clients, torrent clients) talk to directly. Everything covered in this unit (DNS, P2P, sockets, FTP/SMTP/DHCP/SNMP/Telnet/SSH) lives at this single layer, even though the mechanisms look wildly different from each other.

  1. 2.3 The Domain Name System
  2. 2.4 P2P Applications
  3. 2.5 Socket Programming with TCP & UDP

EXPLANATION

DNS: Domain Name System Slide 4

  • people: many identifiers — SSN, name, passport #
  • Internet hosts, routers:
    • IP address (32 bit) — used for addressing datagrams
    • "name", e.g. cs.umass.edu — used by humans
  • Q: how to map between IP address and name, and vice versa?
  • Domain Name System: distributed database implemented in hierarchy of many name servers
  • application-layer protocol: hosts, name servers communicate to resolve names (address/name translation)
    • note: core Internet function, implemented as application-layer protocol
    • complexity at network's "edge"
EXPLANATION
  • An IPv4 address is 32 bits (e.g. 145.37.93.126) — routers only ever look at this number, never the name.
  • Names exist purely for humans; a router given cs.umass.edu directly would have no idea what to do with it.
  • Historical motivation: before DNS (pre-1983), every ARPANET host kept one shared flat file, HOSTS.TXT, manually maintained and distributed from a single site — this broke down almost immediately as the network grew past a few hundred hosts, which is exactly why a distributed, hierarchical system was designed instead.
  • "Complexity at the network's edge" is a recurring design philosophy of the Internet: routers in the middle stay simple (just forward IP packets); all the smart resolving logic sits in end systems and DNS servers at the edge.

DNS: Services, Structure Slide 5

DNS services

  • hostname to IP address translation
  • host aliasing
    • canonical, alias names
  • mail server aliasing
  • load distribution
    • replicated Web servers: many IP addresses correspond to one name
www.abc.example.com -> Canonical Host Name
www.example.com     -> Alias Name

www.abc.example.com -> Canonical Host Name
bob@example.com      -> Alias Name

Q: Why not centralize DNS?

  • single point of failure
  • traffic volume
  • distant centralized database
  • maintenance
A: DOESN'T SCALE!
Comcast DNS servers alone: 600B queries/day  ·  Akamai DNS servers alone: 2.2T queries/day
EXPLANATION
  • Host aliasing in plain terms: one server can be reachable under several names, but only one of those names is the "real" (canonical) one that the server's actual DNS record points to — the rest are just aliases (CNAME records, covered in slide 16) redirecting to it.
  • Load distribution works in the other direction — instead of many names pointing to one machine, one name (www.google.com) can resolve to many different IP addresses, and DNS can rotate which one it hands out (round-robin DNS), spreading incoming traffic across replicas without the client ever knowing.
  • Each centralization objection maps to a concrete failure mode: single point of failure = one outage kills the Internet's naming; traffic volume = literally trillions of queries/day, no single farm handles that; distant database = physically far users get slow lookups; maintenance = every domain owner in the world would need to coordinate writes to the same database.
  • This single slide is the entire justification for the tree-shaped, delegated design shown next.

DNS: A Distributed, Hierarchical Database Slide 6

Client wants IP address for www.amazon.com; 1st approximation:

  1. client queries root server to find .com DNS server
  2. client queries .com DNS server to get amazon.com DNS server
  3. client queries amazon.com DNS server to get IP address for www.amazon.com
EXPLANATION
  • Each level only needs to know about the level immediately below it — the root doesn't know Amazon's IP, only which server handles .com; the .com server doesn't know Amazon's IP either, only which server handles amazon.com. No single machine ever needs a full map of the Internet.
  • Delegation is the technical term for a parent zone handing off responsibility to a child — the .com TLD server stores an NS record for amazon.com pointing at Amazon's own servers, rather than storing Amazon's actual records itself.
  • This 3-hop walk is the cold-cache, worst-case path — in practice, caching (slide 15) means most real-world queries never reach root or TLD servers at all.

DNS Zone vs Domain Slide 7

  • DNS is organized according to zones.
  • A zone groups contiguous domains and subdomains on the domain tree.
  • Assign management authority to an entity.
  • The tree structure depicts subdomains within example.com domain.
  • Multiple DNS zones one for each country. The zone keeps records of who the authority is for each of its subdomains.
  • The zone for example.com contains only the DNS records for the hostnames that do not belong to any subdomain like mail.example.com.
EXPLANATION
  • Domain = a naming subtree (everything under example.com). Zone = an administrative boundary — who is actually responsible for maintaining a piece of that tree. One domain can be split into many independently-managed zones, exactly as shown.
  • Worked example of a real zone file's header — the SOA (Start of Authority) record, which every zone has:
@   IN  SOA   ns1.example.com. admin.example.com. (
                2024031501 ; serial   - version #, bump on every edit
                7200       ; refresh  - secondary checks primary this often
                3600       ; retry    - retry interval if refresh failed
                1209600    ; expire   - secondary discards zone if unreachable this long
                86400 )    ; minimum  - negative-caching TTL (NXDOMAIN)
  • The serial number is critical: secondary servers compare it to their own copy and only pull a fresh zone transfer if the primary's serial is higher — forgetting to bump it after an edit means secondaries silently keep serving stale data.
  • Practical reason to split zones: a CSE department can manage its own cse.university.edu zone without needing central IT to touch it for every change — and a mistake in one zone doesn't take down the others.

DNS: Root Name Servers Slide 8

  • official, contact-of-last-resort by name servers that can not resolve name
  • incredibly important Internet function
    • Internet couldn't function without it!
    • DNSSEC – provides security (authentication and message integrity)
  • ICANN (Internet Corporation for Assigned Names and Numbers) manages root DNS domain
  • 13 logical root name "servers" worldwide each "server" replicated many times (~200 servers in US)
EXPLANATION
  • Root servers are named a.root-servers.net through m.root-servers.net — 13 letters, each operated by a different organization (Verisign, USC-ISI, Cogent, University of Maryland, NASA, ICANN, U.S. Army Research Lab, Netnod, RIPE NCC, and others).
  • Each letter is anycast — physically hundreds of machines worldwide, but logically one IP address per letter; BGP routes your query to the topologically nearest instance, which is how "13 servers" handle global load without being a bottleneck.
  • They are "contact of last resort" precisely because thanks to caching (slide 15), they're rarely actually contacted — most resolvers already have the relevant TLD server cached.

DNSSEC – Why It Matters Slide 9

  • Plain DNS has no authentication — a response claiming to be from an authoritative server could be forged (cache poisoning / spoofing)
  • DNSSEC adds digital signatures (RRSIG records) to DNS responses, so a resolver can verify a record actually came from the zone's authoritative server
  • Trust is chained: Root → TLD → Authoritative — each level signs the key of the level below it
  • It provides authentication and integrity, not confidentiality — DNS queries are still visible in plaintext
EXPLANATION — HOW THE CHAIN ACTUALLY WORKS
  • Each zone has a key pair. The private key signs the zone's records, producing RRSIG entries.
  • A DNSKEY record publishes the zone's public key so anyone can verify its signatures.
  • A DS (Delegation Signer) record sits in the parent zone and contains a hash of the child zone's public key — this is what lets the parent formally vouch for the child.
  • The chain terminates at the root zone's key, which is the single universally-trusted trust anchor baked into resolver software — verify that one key, and (transitively, via the DS chain) you can trust every signed zone below it.
  • "Authentication, not confidentiality" is the key nuance: DNSSEC stops an attacker from forging a fake answer, but it does nothing to hide what you're looking up — anyone sniffing the network still sees the plaintext query (DoH/DoT, mentioned under slide 11, is the fix for that separate problem).

TLD: Authoritative Servers Slide 10

Top-Level Domain (TLD) servers:

  • responsible for .com, .org, .net, .edu, .aero, .jobs, .museums, and all top-level country domains, e.g.: .cn, .uk, .fr, .ca, .jp
  • Network Solutions: authoritative registry for .com, .net TLD
  • Educause: .edu TLD

Authoritative DNS servers:

  • organization's own DNS server(s), providing authoritative hostname to IP mappings for organization's named hosts
  • can be maintained by organization or service provider
EXPLANATION
  • gTLD vs ccTLD: .com/.org/.net/.edu are "generic" TLDs; .cn/.uk/.jp are "country-code" TLDs (two-letter ISO 3166 codes) — some ccTLDs like .io or .co get repurposed commercially even though they're technically a country's code.
  • Registry vs registrar — a distinction often confused: the registry (e.g. Verisign for .com) operates the actual TLD servers and owns the master database for that TLD; the registrar (e.g. GoDaddy, Namecheap) is the retail front-end that sells domain names to the public and talks to the registry on your behalf. When you "buy a domain," you're buying from a registrar, not the registry.

Local DNS Name Servers Slide 11

  • does not strictly belong to hierarchy
  • each ISP (residential ISP, company, university) has local DNS Server
    • also called "default name server"
    • MacOS: % scutil --dns
    • Windows: >ipconfig /all
  • when host makes DNS query, query is sent to its local DNS server
  • Local DNS server returns reply, answering:
    • From its local cache of recent name-to-address translation pairs (but may be out of date!)
    • acts as proxy, forwards query into hierarchy
EXPLANATION
  • Stub resolver vs recursive resolver: your laptop/phone runs a lightweight stub resolver — it doesn't walk the hierarchy itself; it just forwards every query to a configured recursive resolver (usually your ISP's local DNS server) and trusts whatever answer comes back. The recursive resolver is the one that actually does the walking (or serves from cache).
  • You aren't locked into your ISP's resolver — well-known public alternatives include Google (8.8.8.8), Cloudflare (1.1.1.1), and Quad9 (9.9.9.9).
  • DNS over HTTPS (DoH) / DNS over TLS (DoT) encrypt the query itself between the stub and recursive resolver — this is the piece DNSSEC (slide 9) explicitly does not cover.

DNS Name Resolution: Iterated Query Slide 12

Example: host at engineering.nyu.edu wants IP address for gaia.cs.umass.edu.

  • contacted server replies with name of server to contact
  • "I don't know this name, but ask this server"
EXPLANATION
  • The local DNS server itself walks root → TLD → authoritative (steps 2–7), then relays the final answer back to the requesting host (step 8).
  • Why root/TLD insist on this mode: they handle an enormous fraction of the world's DNS traffic. If they had to do full recursive resolution for every resolver on Earth, their load would explode. By replying with only a referral, they offload the actual walking work onto the (much more numerous, much less loaded) local resolvers — a deliberate load-shedding design choice.

DNS Name Resolution: Recursive Query Slide 13

Example: host at engineering.nyu.edu wants IP address for gaia.cs.umass.edu.

  • puts burden of name resolution on contacted name server
  • heavy load at upper levels of hierarchy?
EXPLANATION
  • In recursive mode, each server says, in effect, "I don't know, let me ask for you" — it queries the next server on the client's behalf and only replies once it has the final answer, rather than handing back a referral.
  • The slide's own rhetorical question — "heavy load at upper levels of hierarchy?" — is exactly why in practice root and TLD servers never actually offer recursion; it's typically only offered between a client and its own local resolver (compare with slide 14).

Iterated vs Recursive Query – Side by Side Slide 14

Iterated QueryRecursive Query

EXPLANATION

Real-world DNS combines both: the client-to-local-resolver leg is recursive (simple for the client — it just gets a final answer), while the local-resolver-to-root/TLD/authoritative leg is iterated (keeps load off the top of the hierarchy). Caching and Updating DNS Records Slide 15

  • Suppose that a host apricot.nyu.edu queries dns.nyu.edu for the IP address for the hostname cnn.com. After an hour later, another NYU host, say, kiwi.nyu.edu, also queries dns.nyu.edu.
  • once (any) name server learns mapping, it caches mapping and immediately returns a cached mapping in response to a query
    • Caching improves response time
    • cache entries timeout (disappear) after some time (TTL)
    • TLD servers typically cached in local name servers
      • thus root name servers not often visited
  • If cnn.com changes its IP address right now, how would you find out that some corner of the internet is still resolving it to the old IP?
  • cached entries may be out-of-date (best-effort name-to-address translation!)
    • if name host changes IP address, may not be known Internet-wide until all TTLs expire!
  • update/notify mechanisms proposed IETF standard
    • RFC 2136
KEY IDEA — TTL
cache entry valid for TTL seconds → discarded → next query re-walks the hierarchy
TTL controls the trade-off: long TTL = cheap/fast but stale; short TTL = fresh but more load.
EXPLANATION
  • Negative caching: resolvers also cache the fact that a name doesn't exist (NXDOMAIN), so repeated typos don't hammer the authoritative server. How long is controlled by the zone's SOA minimum field (see slide 7), not a per-record TTL.
  • Typical TTLs: a static corporate site might use 1 hour–1 day (rarely changes, cheap); a load-balanced/CDN service might use 60–300 sec (may need fast failover).
  • Operational fix for planned IP changes: lower the TTL well in advance → wait for the old (long) TTL to fully drain everywhere → make the change → raise TTL back up. This bounds the worst-case staleness window rather than eliminating it — DNS caching is fundamentally best-effort.
  • Security note (DNS rebinding): because TTLs are attacker-controllable on a domain the attacker owns, a malicious site can serve a very short TTL, then "rebind" the same hostname to an internal/private IP after browser same-origin checks have passed — a known technique for reaching internal network services from a public webpage.

DNS Records Slide 16

DNS: distributed database storing resource records (RR)

RR FORMAT
(name, value, type, ttl)

type=A

  • name is hostname
  • value is IP address
relay1.bar.foo.com, 145.37.93.126, A

type=NS

  • name is domain (e.g., foo.com)
  • value is hostname of authoritative name server for this domain
foo.com, dns.foo.com, NS

type=CNAME

  • name is alias name for some "canonical" (the real) name
  • www.ibm.com is really servereast.backup2.ibm.com
  • value is canonical name
ibm.com, servereast.backup2.ibm.com, CNAME

type=MX

  • value is canonical name of a mailserver associated with alias hostname name
example.com, mail.example.com, MX
EXPLANATION

CNAME is a generic hostname alias; MX specifically tells you where a domain's email should be delivered, and — unlike CNAME — supports multiple entries with priority values, so a fallback mail server can take over automatically if the primary is down. This is why you can't use a CNAME where an MX is required.

DNS Record Types – Extended Reference Slide 17

TypePurposeExample (name, value)

AAAAHostname → IPv6 addresswww.example.com → 2606:2800:220:1:248:...

TXTFree-text data — domain verification, SPF/DKIM anti-spam recordsexample.com → "v=spf1 include:_spf..."

EXPLANATION
  • AAAA is simply the IPv6 counterpart of A — same idea, 128-bit address instead of 32-bit.
  • TXT has no fixed structure at all (it's just free text) — which is exactly why it's reused for two very different real purposes: proving domain ownership (e.g. google-site-verification=…) and publishing email anti-spoofing policies like SPF/DKIM.
  • SOA was already introduced in slide 7's zone-file example — this table simply reconfirms its role as "the header record" every zone must have.
  • Two commonly-tested types not on this slide but worth knowing: PTR (reverse DNS: IP → hostname, used by mail servers to fight spam) and SRV (service discovery: maps a service+protocol+domain to a hostname and port).

DNS Protocol Messages Slide 18

DNS query and reply messages, both have same format:

message header:

  • identification: 16 bit # for query, reply to query uses same #
  • flags:
    • query (0) or reply (1-bit)
    • recursion desired
    • recursion available
    • reply is authoritative
EXPLANATION

The identification field is what lets a resolver match a reply to the query it sent — critical when many queries are in flight at once. The four flag bits listed here reappear directly in slide 20's dig output (as qr, rd, ra, aa) — this slide is the abstract definition, slide 20 is where you actually see them on the wire.

DNS Protocol Messages (continued) Slide 19

DNS query and reply messages, both have same format — same diagram as slide 18, annotated further:

  • name, type fields for a query → the questions section
  • RRs in response to query → the answers section
  • records for authoritative servers → the authority section
  • additional "helpful" info that may be used → the additional info section
  • Each record carries: Type (for example, A, NS, CNAME, and MX), the Value, and the TTL.
EXPLANATION
  • This annotated repeat of slide 18 is making one specific point: every RR in every section (answer, authority, additional) follows the exact same (Type, Value, TTL) shape defined back in slide 16's (name, value, type, ttl) format — the message format and the record format are the same building block, reused everywhere.
  • Transport detail not shown on the slide: DNS runs on port 53, over UDP by default (low overhead, no handshake). Classic messages were capped at 512 bytes over UDP — if a reply would exceed that, the server sets the TC (truncated) flag and the client retries the same query over TCP. Zone transfers (AXFR/IXFR) always use TCP.

Emulating Local DNS Server (Step 1: Ask Root) Slide 21

seed@ubuntu:~$ dig @a.root-servers.net www.example.net

(Only a portion of the reply is shown here)
;; QUESTION SECTION:
;www.example.net.        IN   A

;; AUTHORITY SECTION:
net.  172800  IN  NS  m.gtld-servers.net.
net.  172800  IN  NS  l.gtld-servers.net.
net.  172800  IN  NS  k.gtld-servers.net.

;; ADDITIONAL SECTION:
m.gtld-servers.net.  172800  IN  A  192.55.83.30
l.gtld-servers.net.  172800  IN  A  192.41.162.30
k.gtld-servers.net.  172800  IN  A  192.52.178.30
  • Directly send the query to this server.
  • No answer (the root does not know the answer)
  • Go ask them!
EXPLANATION

This is the iterated-query behavior from slide 12 captured live: the root has no ANSWER SECTION at all — only an AUTHORITY SECTION (a referral to the .net TLD servers) plus an ADDITIONAL SECTION giving their IP addresses directly. That additional-section IP is a glue record — without it, the resolver would need to resolve m.gtld-servers.net to get its IP, but it can't resolve that name without first knowing... its IP. Glue records break this circular dependency.

Inserting records into DNS Slide 23

Example: new startup "Network Utopia"

  • register name networkuptopia.com at DNS registrar (e.g., Network Solutions)
    • provide names, IP addresses of authoritative name server (primary and secondary)
    • registrar inserts NS, A RRs into .com TLD server: 
      (networkutopia.com, dns1.networkutopia.com, NS)
(dns1.networkutopia.com, 212.212.212.1, A)
  • create authoritative server locally with IP address 212.212.212.1
    • type A record for www.networkuptopia.com
    • type MX record for networkutopia.com
EXPLANATION
  • The registrar (retail seller, e.g. Network Solutions) forwards your registration to the registry (the TLD's database operator) via a standard protocol called EPP (Extensible Provisioning Protocol) — this is the "insert NS, A RRs into .com TLD server" step, done on your behalf.
  • Domains are registered for a fixed term and must be renewed; letting one lapse means it becomes available for anyone else to register once a grace period passes.
  • WHOIS is the separate public lookup protocol/database showing who registered a domain and its expiry date.
  • Changing which authoritative servers a domain uses (migrating DNS providers) means updating the NS records at the registrar — this is exactly why such migrations come with "may take up to 48 hours to propagate" warnings: it's bounded by the old NS record's TTL, tying directly back to slide 15's caching discussion.

DNS Request - Wireshark Packet Capture Slide 24

  • Captured packet: Standard query 0x9f7d A www.ietf.org, protocol DNS, sent from the host to its local resolver 10.40.4.44.
  • Header details shown: Flags: 0x0100 Standard query, Questions: 1, Answer RRs: 0, Authority RRs: 0, Additional RRs: 0.
  • Query section: www.ietf.org: type A, class IN.
EXPLANATION

This is a live packet showing exactly the message header format from slides 18–19: an identification (0x9f7d), flags (0x0100), and the four counts — here only Questions is non-zero, confirming this is a query, not a reply (no answers yet). Note the whole thing is one UDP datagram to port 53.

DNS Response - Wireshark Packet Capture Slide 25

  • Same transaction — Flags: 0x8180 Standard query response, No error.
  • Questions: 1, Answer RRs: 1, Authority RRs: 6, Additional RRs: 11.
  • Answers: www.ietf.org: type A, class IN, addr 64.170.98.30
  • Authoritative nameservers: ietf.org: type NS, ns ns1.yyz1.afilias-nst.info, plus ns0.ietf.org, ns1.sea1.afilias-nst.info, ns1.ams1.afilias-nst.info, ns1.mia1.afilias-nst.info.
EXPLANATION

The 0x8180 flags value decodes directly using the table from slide 20: qr=1 (this is a response), rd=1 (recursion was requested), ra=1 (recursion was available), rcode=0 (NOERROR, "success"). The same Transaction ID as slide 24's request is what lets the resolver match this reply to its original query — this is the identification field from slide 18 doing its job in practice.

Questions Slide 27 (1–5)

1. Why can't we just use IP addresses everywhere and skip names entirely?

Names are human-memorable and stable even when the underlying IP changes; DNS exists specifically to bridge "what humans use" and "what routers use."

2. Why isn't DNS just one giant centralized server?

It wouldn't scale — single point of failure, unmanageable traffic volume (Comcast alone: 600B queries/day), distant/slow lookups, and impossible maintenance.

3. Put these in order: TLD server, Authoritative server, Root server.

Root → TLD → Authoritative. Root points to the right TLD, TLD points to the right organization's authoritative server, authoritative server has the actual answer.

4. What's the difference between a domain and a zone?

A domain is the naming subtree (e.g. everything under example.com); a zone is an administrative boundary — who actually manages and maintains the records for a piece of that tree. One domain can be split into many independently-managed zones.

5. Give a practical reason an organization would split its domain into multiple zones.

To delegate control — e.g. a CSE department managing its own cse.pes.edu records without needing central IT to make every change, and so a mistake in one zone doesn't take down the others.

Questions Slide 28 (6–10)

6. In an iterated query, what does a server say when it doesn't know the answer?

"I don't know this name, but ask this server" — it gives a referral and hands the querying party the responsibility. (Slide 12)

7. In a recursive query, who does the extra work of following referrals?

The server that was contacted does it on the client's behalf, rather than sending the client elsewhere. (Slide 13)

8. Which DNS flag in a response tells you whether a server is willing to do recursive resolution for you?

The RA (Recursion Available) flag. Root and TLD servers never set it — by design, they only operate iteratively.

9. What does a TTL control, and what happens right after it hits zero?

How long a resolver may keep serving a cached answer without re-checking. Once it expires, the entry is discarded and the resolver must re-query — walking the hierarchy fresh if needed. (Slide 15)

10. A company changes a server's IP address. Why might some users still reach the old IP for hours afterward?

DNS caching is best-effort — any resolver that already cached the old record keeps serving it until its TTL expires; there's no way to force-flush every cache on the internet at once. (Slide 15)

Questions Slide 29 (11–15)

11. What's the standard operational fix for minimizing disruption during a planned IP change?

Lower the TTL well in advance, wait for the old (long) TTL to fully drain everywhere, make the change, then raise the TTL back — bounding the worst-case staleness window instead of eliminating it.

12. Name the four DNS record types and what each maps.

A: hostname → IPv4 address. NS: domain → authoritative name server. CNAME: alias name → canonical name. MX: domain → mail server.

13. What's the difference between host aliasing (CNAME) and mail server aliasing (MX)?

CNAME points one hostname at another hostname (e.g. www.ibm.com → servereast.backup2.ibm.com); MX specifically tells you where a domain's email should be delivered, and — unlike CNAME — supports priority/fallback servers.

14. What kind of DNS record has no fixed structure, and what are two real uses for it?

TXT — arbitrary free text. Used for domain ownership verification (e.g. google-site-verification=...) and email anti-spoofing policies like SPF/DKIM.

15. What problem does DNSSEC solve that TTL/caching does not?

Authenticity and integrity — DNSSEC lets a resolver verify a response actually came from the real authoritative server (via signed records, chained root → TLD → authoritative), preventing forged/poisoned answers. It says nothing about staleness of a legitimately-changed record — that's still governed by TTL.

Peer-to-peer (P2P) architecture Slide 30

  • no centralized server
  • arbitrary end systems directly communicate
  • peers request service from other peers, provide service in return to other peers
    • self scalability – new peers bring new service capacity, and new service demands
    • Efficient resource sharing
    • Cost-effective, High availability.
    • Load is distributed among peers.
  • peers are intermittently connected and change IP addresses
    • complex management
  • examples: P2P file sharing (BitTorrent), media streaming (Spotify), VoIP (Skype), Blockchain and cryptocurrencies, Video and Content Distribution
EXPLANATION
  • Three flavors of P2P architecture not spelled out on the slide but implied by the examples given:
    • Centralized/hybrid P2P — peers exchange data directly, but a central server still handles indexing/discovery (original Napster).
    • Pure/decentralized P2P — no central server even for discovery; peers find each other via a Distributed Hash Table (DHT) (modern trackerless BitTorrent).
    • Hybrid "supernode" P2P — designated high-bandwidth peers take on extra routing/indexing responsibility for a cluster of ordinary peers (Skype's original design).
  • How BitTorrent (the slide's named example) actually works: a file is split into pieces, each with a hash for integrity; a tracker or DHT tells a new peer who else has the file; rarest-first piece selection keeps every piece well-replicated across the swarm; tit-for-tat choking prioritizes uploading to peers who reciprocate, discouraging free-riding.

Other Application Layer Protocols - FTP Slide 33

  • File Transfer Protocol (FTP) - used to exchange large files on the internet
  • TCP
  • Invoked from the command prompt or some GUI.
  • Allows to update (delete, rename, move, and copy) files at a server.
  • Data connection (Port No. 20) & Control connection (Port No. 21)
EXPLANATION
  • Active vs passive mode (the diagram shows active mode): in active mode the client tells the server which port to connect back to, and the server initiates the data connection — this often fails through firewalls/NAT since the client wasn't expecting an inbound connection. In passive mode (PASV) the server opens a random port and the client connects to it — the client initiates both connections, which plays much better with modern NAT, so it's the default in most modern clients.
  • Common commands over the control connection: USER, PASS, LIST, RETR (download), STOR (upload), QUIT.
  • Security note: plain FTP sends credentials in cleartext; FTPS (FTP over TLS) or SFTP (a subsystem of SSH, unrelated protocol despite the similar name) are the encrypted alternatives used today.

Other Application Layer Protocols - SMTP Slide 34

  • Simple Mail Transfer Protocol - an internet standard for e-mail Transmission.
  • Connections are secured with SSL (Secure Socket Layer).
  • Messages are stored and then forwarded to the destination (relay).
  • SMTP uses a port number 25 of TCP.
EXPLANATION — WHAT AN ACTUAL SMTP SESSION LOOKS LIKE 
C: HELO client.example.com
S: 250 Hello, pleased to meet you
C: MAIL FROM:<bob@example.com>
S: 250 Sender OK
C: RCPT TO:<alice@example.com>
S: 250 Recipient OK
C: DATA
S: 354 Start mail input, end with <CRLF>.<CRLF>
C: Subject: hello ... <message body> ... .
S: 250 Message accepted for delivery
C: QUIT
  • Every response is a 3-digit status code — 2xx success, 3xx continue, 4xx temporary failure, 5xx permanent failure.
  • Note the asymmetry the diagram shows: SMTP sends mail all the way to the recipient's mail server, but the recipient's own client retrieves it using a different protocol — POP3 (downloads and typically removes from server) or IMAP (keeps mail synced on the server, standard for multi-device access).

Other Application Layer Protocols - DHCP Slide 35

  • Dynamic Host Configuration Protocol - assign IP addresses to computers in a network dynamically.
  • IP addresses may change even when computer is in network (DHCP leases).
  • DHCP port number for server is 67 and for the client is 68.
  • A client-server model & based on discovery, offer, request, and ACK.
  • Includes subnet mask, DNS server address, default gateway
EXPLANATION
  • The 4-step sequence is commonly remembered by the acronym DORA — Discover, Offer, Request, ACK — matching exactly the "discovery, offer, request, and ACK" the slide lists.
  • Lease renewal timers, not shown on the slide: T1 (renewal, ≈50% of lease) — client tries to renew directly with the original server. T2 (rebinding, ≈87.5% of lease) — if that failed, client broadcasts to rebind with any DHCP server. If the lease fully expires with no renewal, the client restarts DORA from scratch.
  • DHCP is stateful — the server tracks which addresses are leased to which client (by MAC address) — unlike DNS, which is largely stateless.

Other Application Layer Protocols - SNMP Slide 36

Simple Network Management Protocol - exchange management information between network devices.

Basic components & functionalities

  • SNMP Manager
  • Managed Devices
  • SNMP Agents
  • MIB (Management Information Base)
EXPLANATION
  • Manager = the console (NMS) an admin uses. Managed device = the physical hardware. Agent = software on the device that actually talks SNMP and reports/acts on data. MIB = the structured database of exactly what can be queried or set on that device.
  • Core operations, not named on the slide: GET (manager asks agent for a value), SET (manager changes a config value), TRAP (agent proactively notifies the manager of an event, e.g. link down).
  • Version history: SNMPv1/v2c authenticate with a plaintext "community string" (often left at the default public/private — a classic misconfiguration); SNMPv3 adds real user-based authentication and encryption, and is what's recommended in production today.

Other Application Layer Protocols – Telnet & SSH Slide 37

  • Allows a user to communicate with a remote device.
  • Used mostly by network admin to remotely access and manage devices.
  • Telnet client and server installed – uses TCP port no. 23
  • SSH – uses public key encryption & TCP port 22 by default.

SSH authentication (per the slide's diagram):

  1. Server authentication: Server proves its identity to the client
  2. User authentication: Client proves user's identity to the server
EXPLANATION — WHAT ACTUALLY HAPPENS ON `ssh user@host`
  1. TCP connection on port 22; both sides exchange protocol version strings.
  2. Key exchange (KEX) — client and server negotiate a shared session key (e.g. via Diffie-Hellman) without ever transmitting the key itself.
  3. Server authentication — server presents its host key; client checks it against its known_hosts file (the "authenticity of host can't be established" first-connection prompt).
  4. All further traffic is symmetrically encrypted with the negotiated session key.
  5. User authentication — password, or (more common in production) a public/private key pair, proving possession of the private key without ever sending it.

Telnet vs SSH, the one thing to remember: Telnet sends everything — including your password — in plaintext, trivially sniffable on a shared network. SSH is encrypted end-to-end from the first byte after key exchange, plus cryptographic host identity verification. This is why Telnet is effectively obsolete outside legacy/lab equipment.
