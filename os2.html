Interprocess Communication (IPC)

Processes within a system may be either independent or cooperating. A cooperating process can affect or be affected by the execution of another process, typically by sharing data. To enable this cooperation, processes require Interprocess Communication (IPC) mechanisms.

Reasons for cooperating processes

  1. Information sharing — multiple users or processes need access to shared information (e.g. a shared database)
  2. Computation speed-up — tasks are divided into sub-tasks that execute in parallel on multiple processes
  3. Modularity — the system is divided into separate modules, each running as a separate process
  4. Convenience — allows multiple activities to run concurrently (e.g. editing, printing, and compiling at the same time)

Cooperating vs independent processes

Independent process

  • Cannot affect or be affected by other processes
  • Does not share data with other processes

Cooperating process

  • Can affect or be affected by other processes
  • Requires IPC mechanisms

IPC Models & the Producer–Consumer Problem

There are two fundamental models of Interprocess Communication:

  1. Shared Memory
  2. Message Passing

Producer–Consumer problem

The Producer–Consumer problem is a classical example of cooperating processes. The producer process produces information (data items), and the consumer process consumes the information produced.

Types of buffers

Unbounded buffer

  • No practical limit on buffer size
  • Producer can always produce items
  • Consumer may have to wait if the buffer is empty

Bounded buffer

  • Fixed buffer size
  • Producer must wait if the buffer is full
  • Consumer must wait if the buffer is empty

Bounded-buffer — shared data (shared memory version)

The shared buffer is implemented as a circular array:

#define BUFFER_SIZE 10

typedef struct {
   ...
} item;

item buffer[BUFFER_SIZE];
int in = 0;
int out = 0;
Buffer conditions

Buffer empty → in == out

Buffer full → ((in + 1) % BUFFER_SIZE) == out

Pointer meaning: in points to the next free position; out points to the first full position. This solution can use only BUFFER_SIZE − 1 elements (one slot is always deliberately left empty to distinguish "full" from "empty").

Producer code

item next_produced;

while (true) {
  /* produce an item in next_produced */
  while (((in + 1) % BUFFER_SIZE) == out)
    ; /* do nothing */

  buffer[in] = next_produced;
  in = (in + 1) % BUFFER_SIZE;
}

The producer waits (busy-waiting) if the buffer is full. Busy waiting is used here — inefficient but conceptually simple.

Consumer code

item next_consumed;

while (true) {
  while (in == out)
    ; /* do nothing */

  next_consumed = buffer[out];
  out = (out + 1) % BUFFER_SIZE;
  /* consume the item */
}

The consumer waits if the buffer is empty. Busy waiting is again used.

Interprocess communication — shared memory

  • A region of memory is shared among cooperating processes
  • Communication is controlled by user processes, not by the OS
  • The OS provides only the mechanism, not the synchronization
Key points

Two or more processes share the same memory region — this is the fastest IPC mechanism, since there is no data copying between processes.

Main challenge: synchronization — processes must coordinate access to avoid data inconsistency, using tools such as semaphores, mutex locks, or record locking.

Interprocess Communication — Message Passing

Message passing is another IPC mechanism where processes communicate without shared variables, and the OS provides send and receive operations.

  • send(message)
  • receive(message)

Message size may be fixed or variable. For processes P and Q to communicate: (1) establish a communication link, and (2) exchange messages using send/receive.

Implementation issues in message passing

  • How are communication links established?
  • Can a link be shared by more than two processes?
  • How many links can exist between a pair of processes?
  • What is the capacity of the link?
  • Is message size fixed or variable?
  • Is communication unidirectional or bi-directional?

Implementation of communication links

Physical implementation

  • Shared memory
  • Hardware bus
  • Network

Logical implementation

  • Direct or indirect communication
  • Synchronous or asynchronous communication
  • Automatic or explicit buffering

Direct communication

Processes explicitly name each other.

  • send(P, message) → send message to process P
  • receive(Q, message) → receive message from process Q

Properties: links are established automatically; exactly one link per process pair; usually bi-directional.

Indirect communication

Messages are sent and received via mailboxes (ports). Each mailbox has a unique ID, and processes communicate only if they share a mailbox.

Properties
  • Link established only if processes share a mailbox
  • A link may be associated with multiple processes
  • A process pair may share multiple links
  • Communication can be unidirectional or bi-directional

Mailbox operations

Create a mailbox, send message to mailbox, receive message from mailbox, destroy mailbox.

send(A, message)
receive(A, message)

Mailbox sharing problem

Scenario: processes P₁, P₂, P₃ share mailbox A. P₁ sends a message; P₂ and P₃ are both ready to receive. Possible solutions:

  1. Allow a link to be associated with at most two processes
  2. Allow only one process to execute receive at a time
  3. System selects a receiver arbitrarily and notifies the sender

Message passing — synchronization

Blocking (synchronous)

  • Blocking send — sender waits until message is received
  • Blocking receive — receiver waits until message arrives

Non-blocking (asynchronous)

  • Non-blocking send — sender continues immediately
  • Non-blocking receive — receiver gets message or null
Rendezvous

Both send and receive are blocking — sender and receiver meet at the same time.

Producer–Consumer using message passing

// Producer
message next_produced;
while (true) {
  /* produce item */
  send(next_produced);
}

// Consumer
message next_consumed;
while (true) {
  receive(next_consumed);
  /* consume item */
}
Note

Message passing eliminates shared-memory synchronization issues.

Buffering in message passing

Messages are stored in queues attached to the communication link.

TypeBehaviour
Zero capacityNo messages queued; sender must wait for receiver — also called no buffering (rendezvous)
Bounded capacityQueue size = n messages; sender waits if the queue is full
Unbounded capacityInfinite queue size; sender never waits

IPC System Calls — Pipes

IPC system calls allow multiple processes to communicate and synchronize with each other. UNIX-based operating systems provide several IPC mechanisms such as pipes, FIFOs, message queues, semaphores, and shared memory, each suited for different communication needs.

Pipes

Pipes are the oldest and simplest form of IPC in UNIX systems and are supported by all UNIX variants. A pipe allows data to flow between two processes in a unidirectional manner (half-duplex). Although some modern systems support full-duplex pipes, programs should not rely on this for portability.

A key limitation of pipes is that they can be used only between processes that share a common ancestor. Typically, a pipe is created by a parent process, which then calls fork(), allowing communication between parent and child.

pipe() system call

A pipe is created using the pipe() system call. On success it returns two file descriptors through an array argument:

  • fd[0] → read end of the pipe
  • fd[1] → write end of the pipe

Data written to fd[1] can be read from fd[0]. Internally, the data flows through the kernel buffer, ensuring safe data transfer between processes.

Pipe usage between parent and child

After calling pipe(), the process calls fork() to create a child. Depending on the direction of communication:

Parent → Child

  • Parent closes fd[0] (read end)
  • Child closes fd[1] (write end)

Child → Parent

  • Parent closes fd[1]
  • Child closes fd[0]
Why close unused ends
  • Prevent deadlocks
  • Allow proper detection of end-of-file (EOF)

popen() and pclose()

These functions provide a higher-level interface to pipes using the standard I/O library, simplifying pipe creation, forking, and command execution.

popen() creates a pipe, forks a child process, executes a shell command using exec(), and returns a file pointer instead of a file descriptor. Depending on the mode:

  • "r" → parent reads the output of the command
  • "w" → parent writes input to the command

pclose() closes the stream, waits for the command to terminate, and returns the termination status. This mechanism is commonly used to capture command output or supply input programmatically.

FIFOs (Named Pipes) & Message Queues

FIFOs

FIFOs, also known as named pipes, overcome the major limitation of unnamed pipes by allowing communication between unrelated processes. Unlike pipes, FIFOs exist as special files in the file system.

A FIFO is created using mkfifo() or mkfifoat(). Once created, a FIFO behaves like a regular file and can be accessed using standard file operations: open(), read(), write(), close(), unlink().

Uses of FIFOs

  1. Shell pipelines — allow data transfer between shell commands without using temporary files
  2. Client–Server communication — act as rendezvous points where clients and servers exchange data

Message queues

A message queue is an IPC mechanism where messages are stored as a linked list inside the kernel. Each message queue is identified by a message queue identifier.

Message queues are created or accessed using msgget(). Messages are sent using msgsnd() and received using msgrcv().

Each message consists of:

  • A type field (positive long integer)
  • Message length
  • Actual data

Unlike pipes, messages do not have to be received in FIFO order — instead they can be retrieved based on their type, providing greater flexibility.

Semaphore System Calls

A semaphore is a synchronization tool used to control access to shared resources among multiple processes. Conceptually, a semaphore is a counter that represents the number of available instances of a resource.

When a process wants to access a shared resource:

  • It checks the semaphore value
  • If the value is positive, it decrements the semaphore and proceeds
  • If the value is zero, the process is blocked until the semaphore becomes available

When the process finishes using the resource, it increments the semaphore, and waiting processes are awakened.

To use semaphores, a process must first obtain a semaphore ID using semget(). Semaphore operations are performed using:

  • semop() → atomically performs operations on semaphore sets
  • semctl() → used for control operations such as initialization, deletion, or querying status

Semaphores are crucial for avoiding race conditions and ensuring mutual exclusion.

Linux Domain Sockets

Linux Domain Sockets (also called Unix Domain Sockets, or UDS) are a mechanism for IPC that allows two or more processes running on the same Linux system to communicate efficiently.

Unlike Internet sockets, which use IP addresses and port numbers, Linux Domain Sockets use a file path (such as /tmp/mysocket) as the communication endpoint. Since communication occurs entirely within the operating system kernel, Linux Domain Sockets are faster and more efficient than TCP/IP sockets for local communication.

Socket address family

Linux Domain Sockets use the AF_UNIX (or AF_LOCAL) address family:

socket(AF_UNIX, SOCK_STREAM, 0);
  • AF_UNIX specifies that a Unix Domain Socket is being created
  • SOCK_STREAM specifies a connection-oriented socket
  • 0 selects the default protocol

Socket address structure

The address for a Linux Domain Socket is represented using the sockaddr_un structure:

struct sockaddr_un
{
  sa_family_t sun_family;
  char sun_path[108];
};
  • sun_family: specifies the address family (AF_UNIX)
  • sun_path: specifies the pathname of the socket file (e.g. /tmp/mysocket)

Threads — Overview & Motivation

A thread is the fundamental unit of CPU utilization in a modern operating system. It represents a single sequence of execution within a process. Each thread consists of a thread ID, a program counter, a register set, and a stack. While threads within the same process have their own execution context, they share the process's code section, data section, open files, and signals. Because of this shared environment, threads are lighter and more efficient than processes.

Most modern applications are multithreaded. Instead of performing all tasks sequentially, applications divide work among multiple threads. This improves responsiveness, performance, and resource utilization.

Single-threaded vs multithreaded processes

In a single-threaded process, only one thread of control exists. If that thread blocks due to an I/O operation or long computation, the entire process stops progressing.

In contrast, a multithreaded process contains multiple threads executing concurrently within the same process. If one thread is blocked, other threads can continue executing. This design significantly improves responsiveness and efficiency.

Examples of multithreaded applications

A common example is a web browser. Each browser tab may be managed by separate threads. Some threads handle user input, others load web content, fetch data from the network, play videos, or display animations. Even if one thread is waiting for data from the internet, the browser remains responsive to the user.

Another example is a word processor, which may use separate threads to accept user input, perform spell checking, and perform grammar checking — allowing background tasks to run without interrupting the user's typing.

Multithreaded server architecture

In a multithreaded server, the server process creates a new thread for each client request. This allows the server to handle multiple clients concurrently instead of serving them one at a time — threads simplify server design, reduce response time, and improve throughput.

Process creation vs thread creation

Process creation is considered heavy-weight because it involves creating a new address space, duplicating resources, and high overhead.

Thread creation, on the other hand, is light-weight. Threads share the process address space and most resources, so creating and switching between threads is much faster than processes.

Threads are also extensively used in Remote Procedure Call (RPC) systems and operating-system kernels. Most modern kernels themselves are multithreaded.

Benefits of Multithreading

1. Responsiveness

Multithreading allows an application to remain responsive even if part of it is blocked or performing a lengthy operation. For example, a GUI application can continue responding to user input while another thread performs background computation or I/O.

2. Resource sharing

Threads share the memory and resources of their process. This makes communication between threads easier than communication between processes, which requires IPC mechanisms like shared memory or message passing.

3. Economy

Threads are cheaper to create and manage than processes. Thread switching requires less overhead than process context switching. For example, in Solaris, creating a process is significantly slower than creating a thread.

4. Scalability

Multithreading allows applications to take advantage of multiprocessor and multicore architectures. Different threads can run simultaneously on different cores, improving parallel performance.

Processes vs threads

A process does not share memory by default and has its own file descriptors, filesystem context, and signal handling.

A thread, by default, shares memory, open file descriptors, filesystem context, and signal handling with other threads of the same process. This sharing is what makes threads efficient, but it also introduces synchronization challenges.

Thread Concepts

A thread represents an execution context within a process. It includes all information required for execution, such as its ID, register values, stack, scheduling priority and policy, signal mask, and thread-specific data. Thread-specific data allows each thread to maintain private information without synchronizing access with other threads.

When a thread is created, there is no guarantee which thread will run first — the newly created thread or the calling thread. The new thread inherits the process address space, floating-point environment, and signal mask, but any pending signals are cleared.

Attributes shared by threads

  • Process ID and parent process ID
  • Process group ID and session ID
  • Controlling terminal
  • User and group credentials
  • Open file descriptors
  • Signal dispositions
  • File system information (current working directory, root directory, umask)
  • Resource limits
  • CPU time consumed
  • Nice value

Attributes specific to threads

  • Thread ID
  • Signal mask
  • Thread-specific (private) data
  • errno variable
  • Floating-point environment
  • Stack (local variables and function call information)
  • Register context saved during function calls

These attributes ensure that each thread can execute independently while still sharing the process environment.

Shared vs private thread state

Shared among threads

  • Global variables
  • Heap memory
  • File descriptors
  • Network connections
  • Address space content

Private to each thread — stored in the Thread Control Block (TCB)

  • CPU registers
  • Program counter
  • Execution stack

Execution stack contents: each thread's stack holds function parameters, local variables, temporary data, and return addresses.

Thread states

Thread states are similar to process states: NewReadyRunningWaitingTerminated

Multicore Programming

Earlier in the history of computer design, in response to the need for more computing performance, single-CPU systems evolved into multi-CPU systems. A later, similar trend is to place multiple computing cores on a single processing chip, where each core appears as a separate CPU to the operating system. We refer to such systems as multicore, and multithreaded programming provides a mechanism for more efficient use of these multiple computing cores and improved concurrency.

Concurrency vs parallelism

Concurrency refers to multiple tasks making progress over time. On a single-core system, concurrency is achieved by rapidly switching between tasks using the scheduler.

Parallelism refers to multiple tasks executing at the same time, which is possible only on multicore or multiprocessor systems. Concurrency allows progress, while parallelism provides actual speedup.

Multicore programming challenges

  1. Identifying tasks — examining applications to find areas that can be divided into separate, concurrent tasks. Ideally, tasks are independent of one another and thus can run in parallel on individual cores.
  2. Balance — programmers must ensure that identified tasks perform work of equal value; a task contributing little value may not justify a separate execution core.
  3. Data splitting — the data accessed and manipulated by the tasks must also be divided to run on separate cores.
  4. Data dependency — data accessed by tasks must be examined for dependencies between two or more tasks; when one task depends on data from another, execution must be synchronized.
  5. Testing and debugging — when a program runs in parallel on multiple cores, many different execution paths are possible, making testing and debugging inherently more difficult than for single-threaded applications.

Types of parallelism

Data parallelism

Divides the same data set into subsets and distributes them across multiple cores, performing the same operation on each subset.

Task parallelism

Distributes different tasks (threads) — not data — across multiple computing cores. Each thread performs a unique operation; different threads may operate on the same data or on different data.

As the number of threads increases, CPU architectures provide more support in the form of multiple cores and hardware threads.

User Threads, Kernel Threads & Multithreading Models

User threads are managed by user-level thread libraries without kernel involvement. Common thread libraries include POSIX Pthreads, Windows threads, and Java threads.

Kernel threads are supported directly by the operating system kernel. Almost all modern operating systems, including Linux, Windows, Solaris, and macOS, support kernel threads.

Multithreading models describe how user-level threads (ULTs) are mapped to kernel-level threads (KLTs). Since user threads are managed by thread libraries and kernel threads are managed by the operating system, a mapping mechanism is required to allow user threads to execute on physical CPUs. Different operating systems adopt different mapping models depending on performance, scalability, and implementation complexity. The three primary multithreading models are:

  • Many-to-One
  • One-to-One
  • Many-to-Many (and its Two-Level variant)

Many-to-One model

Multiple user-level threads are mapped to a single kernel thread. Thread management is entirely handled in user space by thread libraries, and the kernel is unaware of multiple threads within the process.

Because all user threads map to one kernel thread, only one thread can execute in kernel mode at any given time. If one thread performs a blocking system call, the entire process blocks, significantly reducing concurrency. Additionally, since only one kernel thread exists, threads cannot run in parallel on multicore systems — execution remains serial even with multiple CPUs available.

Due to these limitations, very few modern systems use this model today.

Examples: Solaris Green Threads, GNU Portable Threads.

One-to-One model

Each user-level thread maps to a separate kernel thread. Whenever a user thread is created, a corresponding kernel thread is also created.

This allows true concurrency because multiple threads can execute in parallel on multicore systems. Blocking of one thread does not affect others, since each has its own kernel thread. However, creating kernel threads involves overhead — therefore, operating systems often limit the number of threads per process to avoid excessive resource consumption.

Examples: Windows, Linux, Solaris 9 and later.

Many-to-Many model

Multiplexes many user threads over many kernel threads — this model combines the benefits of the previous two. The operating system creates a sufficient number of kernel threads, and the thread library schedules user threads onto these kernel threads. This allows:

  • High concurrency
  • Efficient resource usage
  • Parallel execution on multicore systems
  • No blocking of the entire process when one thread blocks

This model is more flexible and scalable than the earlier models.

Examples: Solaris (prior to version 9), Windows with the ThreadFiber package.

Two-Level model

Similar to the many-to-many model but adds one enhancement: it allows a user thread to be bound to a specific kernel thread. This binding is useful when a thread requires guaranteed CPU access or real-time responsiveness — combining the flexibility of many-to-many mapping with the control of one-to-one mapping.

Examples: IRIX, HP-UX, Tru64 UNIX, Solaris 8 and earlier.

Pthreads

Pthreads (POSIX Threads) is a standardized API defined under IEEE 1003.1c for thread creation and synchronization.

Important characteristics
  • It is a specification, not an implementation
  • Defines the behaviour of thread operations
  • Implementation varies by OS

Pthreads is widely used in UNIX systems such as Solaris, Linux, and macOS.

Thread creation — pthread_create()

int pthread_create(
    pthread_t *thread,
    const pthread_attr_t *attr,
    void *(*start_routine)(void *),
    void *arg
);

Parameter explanation

  • thread → handle/ID of thread
  • attr → attribute structure
  • start_routine → function executed by thread
  • arg → data passed to thread
Important note

Passing addresses of local variables is dangerous because the stack frame may disappear. Always pass global variables, heap memory, or main function stack variables.

Thread synchronization — pthread_join()

In multithreaded programs, the main thread often waits for worker threads to complete before exiting.

int pthread_join(pthread_t thread, void **retval);
Key points
  • It is a blocking call
  • Caller sleeps until the target thread terminates
  • Allows retrieval of the thread return value

If threads are neither joined nor detached, they become zombie threads, consuming resources.

Fork-Join pattern

A common multithreading execution model:

  1. Main thread creates worker threads
  2. Worker threads perform tasks
  3. Main thread joins them
  4. Results are collected

Explicit thread termination — pthread_exit()

Threads usually terminate when their start routine finishes. Explicit termination can be done using:

void pthread_exit(void *retval);
  • Terminates only the calling thread
  • If called in main(), the process remains alive until other threads finish
  • Calling exit() instead terminates the entire process immediately

Thread scheduling — PCS vs SCS

Thread scheduling depends on the threading model. In many-to-one and many-to-many systems, the thread library schedules user threads onto CPUs through the kernel — this competition is called Process-Contention Scope (PCS) because scheduling occurs among threads within the same process.

System-Contention Scope (SCS): kernel threads compete globally for CPU time — scheduling occurs across all threads in the system.

PCS vs SCS

PCS → competition within a process. SCS → competition system-wide.

Pthreads allow specifying scheduling scope during thread creation.

Multicore Kernel Concepts — Multiple-Processor Scheduling

Everything discussed for single-CPU scheduling assumed a single processing core — one thread runs at a time. With multiple CPUs we achieve load sharing: multiple threads may run in parallel. But the scheduling problem becomes increasingly complex — there is no single best solution.

Traditionally, the term multiprocessor referred to systems that provided multiple physical processors, each with one single-core CPU. However, the definition has evolved significantly — on modern systems, multiprocessor now applies to: multicore CPUs, multithreaded cores, NUMA systems, and heterogeneous multiprocessing.

Approaches to multiple-processor scheduling

Asymmetric Multiprocessing (AMP)

One processor — the master server — handles all scheduling decisions, I/O processing, and other system activities. All other processors execute user code only.

Simple, because only one core touches the system data structures — far less data sharing is needed. Disadvantage: the master server becomes a potential bottleneck, so overall system performance can drop.

Symmetric Multiprocessing (SMP)

The standard approach for supporting multiprocessors. Each processor is self-scheduling: its own scheduler examines a ready queue and picks a thread to run. No master server — system and user code can run on any core.

Virtually all modern operating systems support SMP — Windows, Linux, macOS, and mobile systems including Android and iOS.

Organization of ready queues

Two possible strategies for organizing threads:

  1. All threads may be in a common ready queue, or
  2. Each processor may keep its own private queue of threads

If we select the common ready queue, we have a possible race condition on the shared ready queue, and must ensure that two separate processors do not choose to schedule the same thread and that threads are not lost from the queue. Locking would be highly contended, since all accesses to the queue would require lock ownership, making the shared queue a likely performance bottleneck.

The per-core option permits each processor to schedule threads from its private run queue and therefore does not suffer from the possible performance problems associated with a shared run queue. Thus, it is the most common approach on systems supporting SMP. Additionally, having private, per-processor run queues may lead to more efficient use of cache memory. There are issues with per-processor run queues — most notably, workloads of varying sizes — but balancing algorithms can be used to equalize workloads among all processors.

Kernel parallelism under SMP

Under SMP the kernel itself runs in parallel — several cores may be executing kernel code at the same instant. Consequences the kernel designer must handle:

  • Shared kernel data structures (ready queues, file tables) can be hit concurrently → race conditions
  • Correctness needs locking; but locks serialise, so heavy locking destroys the parallelism you paid for
  • Highly contended locks turn a shared structure into a bottleneck — exactly the shared-ready-queue problem
  • The practical answer: partition state per core. Private run queues remove the lock from the hot path entirely
  • The kernel then only synchronises for the rarer cross-core operations — for example, migrating a thread during load balancing

Memory Stalls & Chip Multithreading

Traditionally, SMP systems used multiple physical processors to execute several processes in parallel. Modern systems use multicore processors, where multiple computing cores are placed on a single physical chip. Each core maintains its own architectural state and appears to the OS as a logical CPU. Multicore SMP systems are generally faster and more power-efficient than systems with separate physical CPU chips.

Modern processors operate much faster than main memory. When a processor waits for data from memory, a memory stall occurs. A stall can also happen due to a cache miss, when required data is not available in cache. A processor may spend up to 50% of its time waiting for memory.

Memory stall

The thread alternates compute cycles (C) with memory stall cycles (M):

Multithreaded processing cores

Modern processors assign two or more hardware threads to each core. If one thread stalls while waiting for memory, the core can switch to another thread. This improves processor utilization and reduces the effect of memory stalls. Each hardware thread has its own architectural state, such as an instruction pointer and a register set — so the OS views each hardware thread as a logical CPU.

Chip Multithreading (CMT)

CMT allows multiple hardware threads to execute on each physical core. If one hardware thread stalls waiting for memory, the core switches to another thread — the stall cycles get filled.

Example

4 cores × 2 hardware threads = 8 logical CPUs. The OS schedules software threads onto logical CPUs, not onto physical cores.

Intel calls this hyper-threading, also known as simultaneous multithreading (SMT). Contemporary Intel processors such as the i7 support 2 threads per core, while the Oracle SPARC M7 supports 8 threads per core.

Load Balancing

On SMP systems the workload must be kept balanced across all processors to get the benefit of having more than one — otherwise some processors sit idle while others have high workloads. Load balancing attempts to keep the workload evenly distributed across all processors.

There are two approaches to load balancing:

  1. Push migration — a specific task periodically checks the load on each processor. If it finds an imbalance, it evenly distributes the load by moving (pushing) threads from overloaded processors to idle or less-busy ones.
  2. Pull migration — occurs when an idle processor pulls a waiting task from a busy processor.

Push and pull migration can be used together.

Mutual Exclusion & Synchronization

In a multiprogramming operating system, multiple processes execute concurrently. Since processes may be interrupted at any time, their execution may only be partially complete at a given instant. When multiple processes access and manipulate shared data simultaneously, the final outcome may become inconsistent due to uncontrolled interleaving of operations.

To maintain data consistency, operating systems require mechanisms that ensure the orderly execution of cooperating processes. This need gives rise to synchronization techniques and mutual exclusion protocols. A classical example used to illustrate this issue is the Producer–Consumer problem, where both producer and consumer processes share a common buffer and a shared variable called counter, which keeps track of the number of full buffers.

Producer / consumer code (conceptual illustration)

// Producer
while (true) {
  /* produce an item in next_produced */
  while (counter == BUFFER_SIZE)
    ; /* do nothing */
  buffer[in] = next_produced;
  in = (in + 1) % BUFFER_SIZE;
  counter++;
}

// Consumer
while (true) {
  while (counter == 0)
    ; /* do nothing */
  next_consumed = buffer[out];
  out = (out + 1) % BUFFER_SIZE;
  counter--;
}

Race condition

A race condition occurs when multiple processes access shared data concurrently and the final result depends on the order of execution.

Consider how counter++ and counter-- are implemented internally:

counter++ :
  register1 = counter
  register1 = register1 + 1
  counter = register1

counter-- :
  register2 = counter
  register2 = register2 - 1
  counter = register2

Because these operations are not atomic, interleaving may produce incorrect results.

Example interleaving

Initial value: counter = 5

  • Producer reads counter → 5
  • Producer increments → 6
  • Consumer reads counter → 5
  • Consumer decrements → 4
  • Producer writes → counter = 6
  • Consumer writes → counter = 4

Final result becomes 4 instead of 5, demonstrating data inconsistency.

Race conditions can also occur in kernel operations — e.g. suppose processes P₀ and P₁ simultaneously create child processes using fork(). A shared kernel variable next_available_pid stores the next process ID. If both processes access it concurrently without synchronization, the same PID may be assigned to two different processes, leading to system inconsistency.

Critical section problem

To solve race conditions, we define the critical section problem. Consider a system with n processes: P₀, P₁, … Pₙ₋₁. Each process contains a segment of code called the critical section, where shared resources are accessed or modified — e.g. updating shared variables, modifying tables, writing to files.

Key requirement

When one process executes in its critical section, no other process must execute in its critical section.

Structure of a process

do {
  entry section
    critical section
  exit section
    remainder section
} while (true);

Each process follows this structure: Entry section — requests permission to enter the critical section; Critical section — executes shared-resource code; Exit section — releases permission; Remainder section — executes non-critical code.

Requirements for solving the critical-section problem

Any valid solution must satisfy three conditions:

1. Mutual exclusion

If a process is executing in its critical section, no other process can be executing in its critical section at the same time — ensuring exclusive access to shared resources.

2. Progress

If no process is in its critical section and some processes wish to enter, the selection of the next process cannot be postponed indefinitely — the system must not allow indefinite waiting when the critical section is free.

3. Bounded waiting

There must exist a bound on the number of times other processes can enter their critical sections after a process requests entry and before that request is granted — this prevents starvation.

Critical-section handling in operating systems

Preemptive kernel

Allows a process to be preempted while executing in kernel mode. While this improves responsiveness and is suitable for real-time systems, it makes synchronization more complex, especially in SMP architectures.

Non-preemptive kernel

A process runs in kernel mode until it exits, blocks, or voluntarily yields the CPU. Since kernel execution cannot be interrupted, race conditions on kernel data structures are avoided — however, responsiveness may be lower.

Peterson's Solution

Peterson's solution is a classic software-based solution to the critical section problem. It provides an elegant algorithmic approach but works only for two processes.

Assumptions: load and store instructions are atomic; two processes Pi and Pj (j = 1 − i).

Shared variables:

int turn;
boolean flag[2];
  • turn → indicates whose turn it is
  • flag[i] → indicates if process Pi wants to enter

Algorithm for process Pi

do {
  flag[i] = true;
  turn = j;

  while (flag[j] && turn == j)
    ; /* wait */

  /* critical section */

  flag[i] = false;

  /* remainder section */
} while (true);

How Peterson's solution works

  1. Process declares intention using flag[i] = true
  2. Gives turn to the other process
  3. Waits if the other process is interested and has the turn
  4. Enters critical section when safe
  5. Resets flag on exit

This guarantees orderly execution.

Correctness of Peterson's solution

Peterson's algorithm satisfies all three requirements:

Mutual exclusion

A process enters the critical section only if the other process is not interested or it is its turn. Both cannot enter simultaneously.

Progress

If one process is not interested, the other can proceed without delay.

Bounded waiting

The turn variable ensures a process cannot be bypassed indefinitely — thus, starvation is prevented.

Limitation

Peterson's solution assumes atomic load/store instructions and is limited to two processes — it is not reliable on modern architectures that reorder instructions and use caches.

Hardware Support for Synchronization

In concurrent systems, multiple processes execute simultaneously and often share common resources. As discussed earlier, uncontrolled concurrent access leads to race conditions and data inconsistency. Software solutions like Peterson's algorithm provide conceptual understanding, but they are not always practical on modern computer architectures.

Modern processors execute instructions out of order, use caches, and support multiple cores. Because of this complexity, software-only synchronization solutions are not guaranteed to work correctly. Hence, computer hardware provides special atomic instructions to support synchronization efficiently and reliably.

Principles of concurrency

Concurrency introduces unpredictability in execution due to several factors: relative execution speeds of processes are unknown; system interrupts may occur at any time; scheduling policies may vary; context switches may occur unpredictably. Because of these uncertainties, synchronization must rely on mechanisms that guarantee atomicity regardless of timing or scheduling variations.

Disabling interrupts (uniprocessor systems)

In uniprocessor systems, mutual exclusion can be achieved by disabling interrupts. When interrupts are disabled, the currently executing process cannot be preempted, allowing it to complete its critical section safely. However, this approach has major drawbacks:

  • Not suitable for multiprocessor systems
  • Disabling interrupts for long periods reduces system responsiveness
  • Not scalable for modern architectures

Hence, more sophisticated atomic instructions are required. Most hardware synchronization mechanisms are based on the concept of locking: (1) a process requests a lock in the entry section, (2) if the lock is free, it enters the critical section, (3) after execution, it releases the lock in the exit section. Properly designed locking ensures all three critical-section requirements are satisfied.

Atomic hardware instructions

Modern machines provide special instructions that execute atomically, meaning they cannot be interrupted midway. Two important atomic operations are Test-and-Set and Compare-and-Swap. These instructions operate directly on memory words and form the foundation of hardware synchronization.

Test-and-Set instruction

Test-and-Set Lock (TSL) is a hardware instruction used to implement mutual exclusion. It performs two operations atomically: (1) returns the old value of a memory location, (2) sets the memory location to TRUE (locked).

boolean test_and_set(boolean *target) {
  boolean rv = *target;
  *target = TRUE;
  return rv;
}

Solution using test_and_set()

do {
  while (test_and_set(&lock))
    ; /* do nothing */

  /* Critical Section */

  lock = false;

  /* Remainder Section */
} while (true);

If lock is FALSE → process enters the CS; if TRUE → process busy-waits. This ensures mutual exclusion but uses busy waiting.

Compare-and-Swap (CAS) instruction

CAS compares a memory value with an expected value and updates it only if they match.

int compare_and_swap(int *value, int expected, int new_value) {
  int temp = *value;
  if (*value == expected)
    *value = new_value;
  return temp;
}

Solution using compare_and_swap()

do {
  while (compare_and_swap(&lock, 0, 1) != 0)
    ; /* do nothing */

  /* Critical Section */

  lock = 0;

  /* Remainder Section */
} while (true);

Here, 0 = unlocked, 1 = locked. A process enters the CS only when it successfully swaps 0 → 1.

Correctness of the CAS solution

Mutual exclusion → satisfied. Progress → satisfied.

Bounded waiting → not guaranteed. Starvation may still occur.

Bounded waiting using test_and_set

To overcome starvation, an enhanced algorithm introduces waiting queues.

boolean waiting[n];
boolean lock;

// Entry Section
waiting[i] = true;
key = true;
while (waiting[i] && key)
  key = test_and_set(&lock);
waiting[i] = false;

// Exit Section
j = (i + 1) % n;
while ((j != i) && !waiting[j])
  j = (j + 1) % n;

if (j == i)
  lock = false;
else
  waiting[j] = false;

This algorithm ensures mutual exclusion, progress, and bounded waiting — thus, all critical-section requirements are satisfied.

Mutex Locks and Semaphores

Earlier, we studied software solutions (like Peterson's algorithm) and hardware solutions (like test-and-set, compare-and-swap) to the critical section problem. While these solutions are theoretically sound, they are often complex and not directly accessible to application programmers.

To simplify synchronization for programmers, operating system designers provide higher-level software tools. These tools internally use hardware atomic instructions but expose simpler interfaces. The two most fundamental synchronization tools are Mutex Locks and Semaphores.

Mutex locks

A mutex lock (Mutual Exclusion lock) is the simplest synchronization mechanism used to protect critical sections. The idea is straightforward: before entering a critical section, a process must acquire() the lock, and after leaving, it must release() the lock.

A mutex lock is typically implemented using a Boolean variable that indicates whether the lock is available or not. Because these operations must execute without interruption, they are implemented using hardware atomic instructions.

Lock contention

Locks are either contended or uncontended. A lock is contended if a thread blocks while trying to acquire it. If the lock is available when a thread attempts to acquire it, the lock is uncontended.

High contention — a relatively large number of threads attempting to acquire the lock. Low contention — a relatively small number of threads attempting to acquire the lock.

Basic locking structure

while (TRUE) {
  acquire lock
    critical section
  release lock
  remainder section
}

Implementation of acquire() and release()

acquire() {
  while (!available)
    ; /* busy wait */
  available = false;
}

release() {
  available = true;
}

Here, available = true → lock is free; available = false → lock is held. If the lock is unavailable, the process keeps looping until it becomes free.

Spinlocks and busy waiting

Because the waiting process continuously checks the lock variable, this mechanism involves busy waiting. Such locks are called spinlocks because the waiting thread "spins" in a loop. Busy waiting wastes CPU cycles, especially if the waiting time is long — this makes spinlocks inefficient for general systems and particularly problematic in real-time environments.

Advantages of spinlocks
  • No context switch occurs while waiting
  • Context switching itself is time-consuming
  • Efficient when locks are held for very short durations
  • Useful in multiprocessor systems where one thread spins while another executes the critical section on a different CPU

Thus, spinlocks are beneficial in short critical sections but inefficient for long waits.

Conceptual scenario

Consider a university library with 10 reading rooms. Only one student can occupy a room at a time. Students must inform the front desk before entering and after leaving. The front desk maintains the number of available rooms, occupied rooms, and waiting students. When a room becomes free, the desk decides which waiting student gets access — this real-life analogy represents how mutex locks regulate access to limited resources.

Semaphores

Semaphores are more powerful synchronization tools than mutex locks. A semaphore is an integer variable used to control access to shared resources. Unlike mutex locks, semaphores can manage multiple instances of a resource. A semaphore can only be accessed using two atomic operations: wait() (also called P()) and signal() (also called V()).

wait(S) {
  while (S <= 0)
    ; // busy wait
  S--;
}

signal(S) {
  S++;
}

Interpretation: wait() → requests resource; signal() → releases resource; if S <= 0, the process waits.

Types of semaphores

Counting semaphore

  • Value ranges over an unrestricted domain
  • Used when multiple instances of a resource exist
  • Example: printer pool, room allocation

Binary semaphore

  • Value ranges only between 0 and 1
  • Functionally equivalent to a mutex lock
  • Used for mutual exclusion

Process synchronization example

Suppose process P₁ must execute statement S₁ before process P₂ executes S₂. We use a semaphore synch initialized to 0:

P1:
  S1;
  signal(synch);

P2:
  wait(synch);
  S2;

Here, P₂ cannot proceed until P₁ completes S₁.

Semaphore implementation without busy waiting

When implementing semaphores, we must ensure that wait() and signal() themselves execute atomically — otherwise, race conditions may occur inside semaphore operations. To avoid busy waiting, semaphores maintain a waiting queue. Each semaphore contains an integer value and a pointer to the waiting process list:

typedef struct {
  int value;
  struct process *list;
} semaphore;

Two additional operations are introduced: block() → suspends process and places it in the queue; wakeup() → resumes a blocked process.

wait(S) {
  S->value--;
  if (S->value < 0) {
    add process to S->list;
    block();
  }
}

signal(S) {
  S->value++;
  if (S->value >= 0) {
    remove process from list;
    wakeup(process);
  }
}

This eliminates busy waiting and improves CPU utilization.

Problems with semaphores

Deadlock

Deadlock occurs when two or more processes wait indefinitely for events that only each other can trigger.

P0: wait(S); wait(Q);
P1: wait(Q); wait(S);

Both processes hold one semaphore and wait for the other → deadlock.

Starvation

Starvation refers to indefinite blocking, where a process is never removed from the waiting queue. This may occur due to unfair scheduling or priority handling.

Priority inversion

Priority inversion occurs when a low-priority process holds a lock required by a high-priority process, while a medium-priority process preempts the low-priority one — this delays the high-priority process indirectly.

Priority inversion scenario

P₁ → highest priority · P₂ → medium priority · P₃ → lowest priority.

If P₃ holds semaphore S, P₁ waits for S, and P₂ preempts P₃ — then P₂ indirectly blocks P₁.

Priority inheritance protocol

To solve priority inversion, systems use the priority inheritance protocol. When a low-priority process holds a resource needed by a higher-priority process: (1) the low-priority process temporarily inherits the higher priority, (2) intermediate processes cannot preempt it, (3) once the resource is released, priority returns to normal. Priority inheritance boosts P₃'s priority so it can finish and release S.

Classical Problems of Synchronization

Classical synchronization problems are standard problem statements used to demonstrate how synchronization mechanisms such as semaphores, mutex locks, and monitors are applied in real concurrent systems. These problems highlight issues like mutual exclusion, deadlock, starvation, and process coordination. The three most important classical problems are:

  1. Bounded-Buffer (Producer–Consumer) Problem
  2. Readers–Writers Problem
  3. Dining-Philosophers Problem

1. Bounded-buffer problem

The bounded-buffer problem models a system where producers generate data and consumers use that data. The data is stored in a finite buffer consisting of n slots, where each slot can hold exactly one item. Since the buffer is limited, synchronization is required to ensure: producers do not add items when the buffer is full, consumers do not remove items when the buffer is empty, and producers/consumers do not access the buffer simultaneously in conflicting ways.

Semaphores used

  • mutex → initialized to 1; ensures mutual exclusion when accessing the buffer
  • full → initialized to 0; counts number of filled buffer slots
  • empty → initialized to n; counts number of empty buffer slots

Producer process structure

do {
  /* produce item */

  wait(empty);   // ensure empty slot exists
  wait(mutex);   // enter critical section

  /* add item to buffer */

  signal(mutex); // leave critical section
  signal(full);  // increment filled count

} while(true);

The producer first performs wait(empty) to ensure that at least one empty buffer slot is available. It then performs wait(mutex) to gain exclusive access to the buffer. After inserting the item, it releases the mutex lock and signals the full semaphore, indicating that a new item is available for consumption.

Consumer process structure

do {
  wait(full);    // ensure item exists
  wait(mutex);   // enter critical section

  /* remove item from buffer */

  signal(mutex); // leave critical section
  signal(empty); // increment empty count

  /* consume item */

} while(true);

The consumer first checks whether the buffer contains items using wait(full). It then acquires mutual exclusion using wait(mutex) before removing an item. After removal, it releases the mutex and signals empty, indicating that a new empty slot is available.

2. Readers–Writers Problem

The readers–writers problem models access to a shared data resource such as a file or database. There are two types of processes:

  • Readers → only read data
  • Writers → modify data

Problem constraints

  1. Multiple readers can read simultaneously
  2. Only one writer can write at a time
  3. No reader can read while a writer is writing
  4. A writer cannot write if readers are active

Thus, synchronization must allow concurrency among readers but exclusivity for writers.

Shared data structures

  • rw_mutex → controls access to the shared resource (init = 1)
  • mutex → protects the read_count variable (init = 1)
  • read_count → number of active readers (init = 0)

Writer process structure

do {
  wait(rw_mutex);

  /* writing performed */

  signal(rw_mutex);

} while(true);

The writer must acquire exclusive access to the shared resource. It uses rw_mutex to ensure no other reader or writer accesses the data while writing is in progress.

Reader process structure

do {
  wait(mutex);
  read_count++;
  if (read_count == 1)
    wait(rw_mutex);
  signal(mutex);

  /* reading performed */

  wait(mutex);
  read_count--;
  if (read_count == 0)
    signal(rw_mutex);
  signal(mutex);

} while(true);

When a reader arrives, it increments read_count. If it is the first reader, it locks rw_mutex to block writers. Subsequent readers can enter concurrently. When readers finish, they decrement read_count. The last reader releases rw_mutex, allowing writers to proceed.

Readers–writers variations

First variation (reader priority)

Readers are never kept waiting unless a writer already holds the resource.

Second variation (writer priority)

Once a writer requests access, it is given priority to avoid writer starvation.

Both approaches may still lead to starvation of one group. Modern systems solve this using reader–writer locks provided by the kernel.

3. Dining-Philosophers Problem

This classical problem illustrates synchronization and deadlock in resource allocation.

Problem description

Five philosophers sit around a circular table. They alternate between thinking and eating. To eat, a philosopher needs two chopsticks — one on the left, one on the right. Since chopsticks are shared resources, synchronization is required.

Shared data

  • Bowl of rice → shared dataset
  • chopstick[5] → semaphore array initialized to 1

Each chopstick is a binary semaphore.

Basic philosopher algorithm

do {
  wait(chopstick[i]);
  wait(chopstick[(i + 1) % 5]);

  /* eat */

  signal(chopstick[i]);
  signal(chopstick[(i + 1) % 5]);

  /* think */

} while(TRUE);

Problem with this algorithm

If all philosophers pick up their left chopstick simultaneously, each waits for the right chopstick held by their neighbour. This creates a circular wait condition, leading to deadlock.

Deadlock handling solutions

1. Limit number of philosophers

Allow at most 4 philosophers to sit simultaneously. This guarantees at least one philosopher can obtain both chopsticks.

2. Pick both chopsticks atomically

Allow a philosopher to pick up chopsticks only if both are available. This requires a critical section around chopstick acquisition.

3. Asymmetric solution

Change pickup order: odd philosophers → left then right; even philosophers → right then left. This breaks circular wait and prevents deadlock.

Deadlocks — Introduction & System Model

In a multiprogramming environment, multiple processes execute concurrently and compete for a limited number of resources such as CPU time, memory, files, printers, and I/O devices. Since these resources are finite, processes often need to wait until required resources become available.

A deadlock occurs when a set of processes enters a waiting state in which each process is waiting for a resource that is currently held by another process in the same set. Because none of the processes can proceed, the waiting state becomes permanent unless external intervention occurs.

In simple terms

Deadlock = circular waiting for resources with no progress possible.

System model

A system consists of a finite set of resource types: R1, R2, …, Rm. Each resource type may have multiple instances.

Physical resources

  • CPU cycles
  • Memory space
  • Printers
  • Tape drives
  • I/O devices

Logical resources

  • Files
  • Semaphores
  • Mutex locks

Each resource type Ri has Wi instances. For example, if a system has two CPUs, then the CPU resource type has two instances.

Resource usage sequence

Every process uses resources in the following order:

  1. Request — process requests a resource via system calls such as open(), wait(), allocate()
  2. Use — process performs operations using the resource
  3. Release — resource is released via calls such as close(), signal(), free()

Deadlocks occur when processes get stuck between the request and release phases.

Deadlock with physical resources

Example 1 — multiple instances

A system has 3 CD drives. Processes P0, P1, P2 each hold one drive. If P0 requests another drive: no free drives exist, all processes wait — deadlock occurs.

Example 2 — single instances

A system has one printer and one DVD drive. If Pi holds the printer and requests the DVD, and Pj holds the DVD and requests the printer, a circular wait forms → deadlock occurs.

Deadlock with semaphores

Deadlock is not limited to physical resources; it also occurs with logical resources. Example: semaphores S1 = 1, S2 = 1.

P1: wait(S1); wait(S2);
P2: wait(S2); wait(S1);

Each process holds one semaphore and waits for the other → deadlock.

Deadlock characterization — Coffman's conditions

For a deadlock to occur, four necessary conditions must hold simultaneously. These are known as Coffman's Conditions.

1. Mutual exclusion

At least one resource must be non-sharable. Only one process can use it at a time. Examples: printers, tape drives, mutex locks. Sharable resources like read-only files do not cause deadlocks.

2. Hold and wait

A process holding at least one resource is waiting to acquire additional resources held by other processes — this creates dependency chains among processes.

3. No preemption

Resources cannot be forcibly taken from a process. They must be released voluntarily after task completion.

4. Circular wait

A circular chain of waiting processes exists: P0 → waiting for resource held by P1; P1 → waiting for resource held by P2; … ; Pn → waiting for resource held by P0. This cycle locks all processes permanently.

Resource-Allocation Graph (RAG)

Deadlocks can be represented using directed graphs.

Graph components

Vertices (V):

  • Processes → P1, P2, …, Pn (drawn as circles)
  • Resources → R1, R2, …, Rm (drawn as boxes, with a dot per instance)

Edges (E):

  • Request edge: Pi → Rj
  • Assignment edge: Rj → Pi

Cycle interpretation

  • No cycle → no deadlock
  • Cycle + single instance per resource → deadlock
  • Cycle + multiple instances per resource → may or may not be deadlock

Wait-for graph

When each resource has only one instance, the RAG can be simplified by removing resource nodes: edge Pi → Pj means Pi waits for Pj. Deadlock exists if the wait-for graph contains a cycle.

Handling Deadlocks

Operating systems use three major strategies:

  1. Deadlock prevention / avoidance — prevent the system from entering deadlock
  2. Deadlock detection & recovery — allow deadlock, then detect and recover
  3. Ignore deadlocks — the "Ostrich algorithm" — assume deadlocks are rare

Deadlock prevention

Prevention ensures at least one of the four necessary conditions never holds.

Prevent mutual exclusion

Make resources sharable where possible (not feasible for printers, locks, etc.).

Prevent hold and wait

Two approaches: process requests all resources at once before execution, or process requests resources only when holding none. Disadvantages: low utilization, possible starvation.

Prevent no preemption

If a process requests a resource that cannot be allocated, it must release all currently held resources and wait until all can be allocated together.

Prevent circular wait

Assign a numerical ordering to resources. Processes must request resources in increasing (or decreasing) order only — this eliminates circular dependency.

Deadlock detection

Instead of preventing deadlocks, systems may allow them and detect them periodically.

Single instance detection

Use a Resource Allocation Graph with claim edges (future requests). Cycle detection algorithms are applied. Time complexity: O(n²).

Detection with multiple instances

When resources have multiple instances, graph methods are insufficient — matrix-based detection algorithms are used.

Data structures used
  • Available (m vector) — number of available instances
  • Max (n × m matrix) — maximum demand
  • Allocation (n × m matrix) — currently allocated resources
  • Request (n × m matrix) — current pending requests

Deadlock detection algorithm

  1. Initialize: Work = Available; set Finish[i] based on allocation
  2. Find process i such that Finish[i] = false and Request[i] ≤ Work
  3. If found: Work += Allocation[i]; Finish[i] = true; repeat
  4. If any Finish[i] = false → deadlock
Complexity
O(m × n²)

Example of the detection algorithm

Five processes P₀ through P₄; three resource types A (7 instances), B (2 instances), and C (6 instances). Snapshot at time T₀:

ProcessAllocation (A B C)Request (A B C)Available (A B C)
P00 1 00 0 00 0 0
P12 0 02 0 2
P23 0 30 0 0
P32 1 11 0 0
P40 0 20 0 2

A safe (deadlock-free) sequence exists: <P0, P2, P3, P1, P4>.

Deadlock avoidance

Avoidance requires prior knowledge of process resource requirements. The OS dynamically examines allocation states before granting requests to ensure the system never enters an unsafe state.

Safe state

A system is safe if there exists a safe sequence <P1, P2, …, Pn> such that each process can obtain its required resources in order and complete execution.

Safe vs unsafe vs deadlock
  • Safe state → no deadlock
  • Unsafe state → possibility of deadlock
  • Deadlock state → already deadlocked

Goal: never enter an unsafe state.

Resource-Allocation Graph avoidance

Adds claim edges representing future requests. A request is granted only if converting claim → assignment does not form a cycle.

Banker's algorithm

The most famous deadlock avoidance algorithm — named after a banker allocating loans safely. Each process declares its maximum resource needs in advance.

Data structures

  • Available
  • Max
  • Allocation
  • Need = Max − Allocation

Each row represents a process vector.

Safety algorithm

  1. Work = Available
  2. Finish[i] = false
  3. Find i where Need[i] ≤ Work
  4. Work += Allocation[i]
  5. Mark Finish[i] = true
  6. Repeat

If all Finish = true → safe state.

Resource request algorithm

When Pi requests resources:

  1. Check Request ≤ Need
  2. Check Request ≤ Available
  3. Temporarily allocate resources
  4. Run the safety algorithm
  5. If safe → grant
  6. Else → rollback and wait

Signals & Signal Handling

A signal is a software mechanism used in UNIX and UNIX-like operating systems to notify a process that a particular event has occurred. Signals serve as a form of software interrupt, allowing the operating system or other processes to communicate asynchronously with a running process.

Signals may arise due to events generated internally by a process or externally by the operating system, hardware, or other processes. Regardless of their source, all signals follow the same general lifecycle:

  1. A signal is generated due to some event
  2. The signal is delivered to a process
  3. The process must handle the signal

This model ensures that processes can respond to exceptional conditions, user actions, or system events in a controlled manner.

Synchronous and asynchronous signals

Synchronous signals

Generated as a direct result of the execution of a process itself — the process performs an illegal or exceptional operation, which immediately triggers the signal (e.g. illegal memory access, division by zero). Since these signals arise from the process's own execution, they are always delivered to the same process that caused the event.

Asynchronous signals

Originate from events external to the running process, such as user input, timers, or other processes (e.g. terminating a process using Ctrl+C, timer expiration events). Such signals are typically sent from one process to another, or from the OS to a process.

Signal handlers

Once a signal is delivered, the receiving process must respond. This response is performed by a signal handler, a function designed to process the signal. There are two types of signal handlers:

1. Default signal handler

Every signal has a predefined default action defined by the kernel. If the process does not specify any custom handling behaviour, this default handler executes automatically. Default actions may include terminating the process, ignoring the signal, stopping the process, or continuing a paused process. For example, an illegal memory access usually results in immediate program termination.

2. User-defined signal handler

Processes may override the default behaviour by defining their own signal handling function, allowing customized responses such as saving program state, cleaning up resources, logging errors, or graceful shutdown. User-defined handlers are registered using system calls like signal() or sigaction() in UNIX systems.

Signal handling in single-threaded programs

In single-threaded programs, signal handling is straightforward. Since the process contains only one thread of execution, any signal delivered to the process is automatically handled by that single thread — there is no ambiguity in delivery, and the handler executes within that thread's context.

Signal handling in multithreaded programs

Signal handling becomes more complex in multithreaded environments because a process may contain multiple threads executing concurrently. When a signal is generated, the system must decide which thread should handle it. Several delivery strategies are possible:

  1. Deliver the signal to the thread to which the signal applies
  2. Deliver the signal to every thread in the process
  3. Deliver the signal to selected threads
  4. Assign a specific thread to handle all signals

The chosen method depends on the signal type and system design.

Delivery rules for signals

The signal delivery method depends heavily on whether the signal is synchronous or asynchronous:

  • Synchronous signals must be delivered to the thread that caused the exception. For example, a division-by-zero error must be handled by the offending thread itself.
  • Asynchronous signals may be delivered to one or more threads, depending on system policy. For example, a termination signal like Ctrl+C may be delivered to all threads of the process.

UNIX signal delivery functions

kill(pid_t pid, int signal)

Here, pid → target process ID; signal → signal number. This function does not necessarily terminate a process — it simply sends the specified signal, whose action depends on its handler.

Thread-specific signal delivery

In multithreaded UNIX systems, threads can control which signals they accept or block. If a thread blocks a signal, it will not handle that signal — instead, the signal may be delivered to another thread that is not blocking it. Since signals need to be handled only once, the system typically delivers the signal to the first eligible thread.

POSIX provides a function to send signals to specific threads:

pthread_kill(pthread_t tid, int signal)

This allows fine-grained signal delivery control within multithreaded applications.

Signals in Windows systems

Unlike UNIX, Windows does not provide native signal support. Instead, Windows uses a mechanism called Asynchronous Procedure Calls (APCs) to emulate signal-like behaviour. An APC allows a thread to specify a function that will be executed when a particular event occurs. This mechanism is conceptually similar to asynchronous signals in UNIX but differs in implementation.

Key characteristics
  • Delivered to a specific thread
  • Used for event notifications
  • More structured than UNIX signals

Thus, APCs serve as Windows' alternative to signal handling.

Signals in Linux

In Linux systems, signals are treated as software interrupts used to notify processes about asynchronous events. Several standard Linux signals include:

SignalMeaning
SIGINTGenerated when user presses Ctrl+C. Terminates the program.
SIGALRMGenerated when a timer set by the alarm() function expires.
SIGABRTGenerated when a process calls the abort() function.
SIGSTOPPauses a process; it can be resumed later.
SIGCONTResumes a previously stopped process.
SIGSEGVIndicates a segmentation fault due to illegal memory access.
SIGKILLImmediately terminates a process; cannot be caught or ignored.

These signals enable Linux to manage process execution, debugging, and termination efficiently.
