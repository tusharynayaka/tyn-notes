Introduction to Operating Systems

Operating systems form the backbone of modern computing. Every application, from a calculator to complex AI software, relies on the OS to interact with hardware. Without one, every developer would need to write hardware-specific code, which would make software development impractical.

Need for an operating system

If no OS existed, application developers would need to interact directly with the CPU, memory, disk, and I/O devices — requiring detailed knowledge of hardware architecture, device protocols, and low-level instructions.

The operating system abstracts hardware complexity and provides a standardized interface, letting developers focus on solving problems rather than managing hardware.

Definition

An operating system is a program that acts as an intermediary between the user and computer hardware. It provides a user-friendly environment in which users can easily develop and execute programs.

Without an operating system

  • Hardware knowledge would be mandatory for programming
  • Software portability would be extremely limited
  • Resource conflicts would be difficult to manage

Genesis of operating systems

Early computers had no operating system — programs were loaded manually and only one program could run at a time. As hardware grew more powerful and users demanded multitasking, operating systems evolved to manage resources efficiently and provide better usability.

Operating system goals

  • Execute user programs and make solving user problems easier
  • Make the computer system convenient to use
  • Use hardware efficiently
  • Manage system resources: memory, processor(s), and I/O devices

An effective OS balances user convenience with efficient hardware utilization.

Why study operating systems?

Although only a small percentage of computer professionals actually design or modify operating systems, almost all software runs on top of one. Understanding OS fundamentals leads to writing efficient programs, developing secure applications, debugging performance issues, and understanding resource behaviour such as memory usage and CPU scheduling.

Four Components of a Computer System

An abstract view of a computer system separates it into four major components, each layered on top of the one below it.

1. Hardware

Provides the basic computing resources: CPU, main memory, and I/O devices.

2. Operating system

Controls and coordinates the use of hardware among various applications and users.

3. Application programs

Define how system resources are used to solve user problems — word processors, compilers, web browsers, database systems, video games.

4. Users

Can be people, machines, or other computers.

What operating systems do — user view vs system view

From the user's perspective

  • Desire convenience
  • Want ease of use
  • Expect good performance
  • Do not care much about resource utilization

From the system's perspective

  • Especially in shared systems (mainframes, minicomputers)
  • Must ensure fair resource allocation
  • Must maximize utilization of CPU time, memory, I/O devices
  • No single user should monopolize resources

What operating systems do — across environments

  • Dedicated systems (workstations): have dedicated resources but still rely on shared servers (file, print, compute servers)
  • Handheld devices: resource-constrained, optimized for battery life and usability
  • Embedded systems: often have little or no user interface — automobiles, medical devices, home appliances

Operating systems are designed to balance usability and resource efficiency based on the system type.

System view — two major roles

1. Resource allocator

  • Manages all system resources
  • Resolves conflicting resource requests
  • Ensures fairness and efficiency

2. Control program

  • Controls execution of programs
  • Prevents errors
  • Prevents improper use of the computer
Defining the OS

The fundamental goal of a computer system is to execute user programs and solve user problems. The operating system combines resource allocation and control mechanisms into a single piece of software.

The kernel

  • The core part of the OS
  • The only program running at all times

Everything else is either a system program (ships with the OS) or an application program.

Computer System Organization & Interrupts

A computer system consists of one or more CPUs, device controllers, shared main memory, and a common system bus. The CPU and device controllers can execute concurrently, competing for memory cycles — a memory controller synchronizes access to shared memory.

Modern systems support parallelism, concurrency, and high-speed I/O operations. Key points of operation:

  • CPU and I/O devices execute concurrently
  • Each device controller manages a specific device
  • A device controller contains a local buffer and registers for control actions
  • Data transfer flows: device → controller buffer → main memory

After completing an operation, the device controller signals the CPU by generating an interrupt.

Booting the system

  • The first program executed is the bootstrap program, stored in ROM or EEPROM (also called firmware)
  • Functions: initializes CPU registers, initializes memory, initializes device controllers, and loads the OS kernel into memory

After booting, the first user-level process created is init, which waits for events and starts system services.

Interrupts

An operating system is interrupt-driven. An interrupt transfers control to an Interrupt Service Routine (ISR) using an interrupt vector that contains the addresses of service routines; the CPU state (program counter, registers) is saved before servicing the interrupt.

A trap or exception is a software-generated interrupt caused by errors or user requests (system calls).

Steps in interrupt handling

  1. Save current CPU state
  2. Identify interrupt type
  3. Execute the appropriate interrupt service routine
  4. Restore CPU state
  5. Resume execution

Interrupts can be identified by polling or by vectored interrupt systems.

Interrupt timeline

While a single process performs output: the CPU executes the user process, issues an I/O request, and the device begins transferring while the CPU keeps running other work; when the transfer completes, an I/O interrupt is raised, processed, and the user process resumes. Interrupt-processing time and I/O transfer time both vary from request to request.

Types of interrupts

Hardware interrupt

Generated by devices — keyboard, disk, network.

Software interrupt

Also called an exception or trap. Caused by errors (e.g. division by zero) or requests for OS services (system calls).

The OS also handles problems such as infinite loops, unauthorized memory access, and processes interfering with each other.

Storage Structure & Storage Hierarchy

Main memory

  • The only large storage medium directly accessible by the CPU
  • Implemented as Random Access Memory (RAM), using DRAM
  • Typically volatile

Other memory types include ROM and EEPROM (used in smartphones to store factory-installed programs).

Program execution model — fetch, decode, execute

Typical instruction execution follows the fetch–decode–execute cycle, repeating until program termination. This model is known as the Von Neumann architecture.

Secondary storage

An extension of main memory: non-volatile and large capacity.

  • Hard disks — platters, tracks, sectors; managed by a disk controller
  • Solid State Drives (SSD) — faster, non-volatile
  • Flash memory — used in cameras, PDAs

Storage hierarchy

Storage systems are organized by speed, cost, and volatility — smaller and faster storage sits nearer the CPU, while larger, slower, and cheaper storage sits further away.

Caching

Caching is a fundamental principle used at many levels — hardware, operating system, and software.

  • Frequently used data is copied to faster storage
  • The cache is checked first
  • If data is not present, it is fetched from slower storage

Challenges: cache size, replacement policy, and cache management.

I/O Structure & Direct Memory Access

Storage is treated as an I/O device. A large portion of OS code manages I/O, focusing on reliability and performance. Components involved: CPUs, multiple device controllers, and a common system bus — each device controller has a device driver and a uniform interface to the kernel.

I/O operation flow

  • Device controller maintains a local buffer
  • Transfers data between the device and memory
  • CPU resumes execution after an I/O-completion interrupt

Two models exist: the CPU can either wait for I/O completion, or continue execution while I/O proceeds.

Direct Memory Access (DMA)

Used for high-speed I/O devices to reduce CPU overhead.

  • Data is transferred directly between the device and main memory
  • CPU involvement is minimized
  • Only one interrupt is generated per block transfer (instead of one per byte)

This improves performance significantly compared to interrupt-per-byte I/O.

Computer-System Architecture

Most systems use a single general-purpose processor to execute user programs, alongside special-purpose processors that are device-specific (disk controller, keyboard controller, graphics controller). These run a limited, fixed instruction set, are built directly into hardware, and are managed and monitored by the OS.

Example — disk controller microprocessor

Receives a sequence of disk requests from the CPU, maintains its own queue, implements its own disk-scheduling algorithm, and reduces overhead on the main CPU by handling disk operations independently.

Multiprocessor systems

Also called parallel systems or tightly-coupled systems. Advantages:

  1. Increased throughput — more processors complete more tasks in less time
  2. Economy of scale — sharing peripherals, memory, and power supplies reduces overall system cost
  3. Increased reliability — failure of one processor does not halt the system completely, known as graceful degradation or fault tolerance

Asymmetric vs Symmetric Multiprocessing

Asymmetric Multiprocessing (AMP)

  • Each processor is assigned a specific task
  • One processor may act as the master, others as workers
  • Less flexible

Symmetric Multiprocessing (SMP)

  • All processors are equal peers — no master–slave relationship
  • Each processor performs all tasks and has its own registers and private cache
  • All processors share the same physical memory
  • Most modern operating systems use SMP

Multi-core design

A recent trend in CPU design places multiple processing cores on a single chip, each executing its own instructions independently.

  • Faster on-chip communication compared to inter-chip communication
  • Lower power consumption
  • Better performance per watt
  • More efficient than multiple single-core processors

Blade Servers & Clustered Systems

Blade servers

A modern server architecture where multiple processor boards, I/O boards, and network boards are housed in a single chassis. Each blade boots independently and runs its own operating system. Some blade servers are also multiprocessor systems — essentially multiple independent multiprocessor systems in one enclosure.

Clustered systems

Consist of multiple independent systems working together. Key characteristics: usually share storage using a Storage-Area Network (SAN), provide high availability, and can continue operation even if one system fails.

Types of clustering

  • Asymmetric clustering — one machine is in hot-standby mode and takes over if the primary machine fails
  • Symmetric clustering — multiple nodes run applications simultaneously and monitor each other

High-Performance Computing (HPC) clusters

Used for scientific and compute-intensive tasks; applications must support parallel execution and often use a Distributed Lock Manager (DLM) to prevent data conflicts.

Operating-System Structure & Operations

Multiprogramming

Essential for system efficiency — a single user cannot keep the CPU and I/O devices busy at all times, and without multiprogramming the CPU would be idle during I/O operations.

  • The OS organizes multiple jobs (code + data)
  • A subset of jobs is kept in main memory
  • One job is selected using job scheduling
  • When a job waits (e.g. for I/O), the OS switches to another job

This ensures the CPU is always utilized.

Multitasking (time sharing)

A logical extension of multiprogramming.

  • The CPU switches between jobs very frequently
  • Users can interact with programs while they run
  • Enables interactive computing, with response time typically under one second

Each executing program is called a process. If multiple processes are ready, CPU scheduling decides which runs; if memory is insufficient, swapping moves processes in and out; virtual memory allows execution even if a process is not fully in memory.

Dual-mode and multimode operation

Dual-mode operation protects the operating system by distinguishing between two modes.

ModeMode bitDescription
User mode1User programs execute with limited privileges
Kernel mode0OS executes with full access to hardware

Privileged instructions can only be executed in kernel mode, preventing misuse of system resources. A system call switches the mode from user to kernel. Modern CPUs also support multi-mode operation, such as a Virtual Machine Manager (VMM) mode for virtual machines.

Transition from user mode to kernel mode

When an interrupt occurs, or a trap/system call is issued, the hardware automatically switches from user mode to kernel mode. After the request is handled, control returns to user mode and the user program resumes execution safely.

Timer

The timer prevents a process from running indefinitely or hogging CPU resources.

  • Interrupts the system after a fixed or variable interval
  • Typical ranges: fixed at 1/60 second, variable from 1 ms to 1 second

Implementation

  • Fixed-rate clock + counter
  • OS sets the counter (a privileged instruction)
  • Counter decrements on each clock tick
  • When the counter reaches zero, an interrupt occurs

Uses of the timer: enforces CPU time limits, enables preemptive scheduling, and prevents infinite loops.

Operating-System Services

An operating system provides an environment for the execution of programs, and offers services to both users and programs to make the system easier, safer, and more efficient to use.

User-oriented services

1. User interface (UI)

  • Command-Line Interface (CLI) — uses command interpreters (shells) to accept text commands
  • Graphical User Interface (GUI) — uses windows, icons, menus, and mouse interactions
  • Batch interface — commands executed in batches with no user interaction

2. Program execution

The OS must be able to load a program into memory, run it, and terminate it — normally (successful completion) or abnormally (error condition) — ensuring smooth execution and cleanup.

3. I/O operations

A running program may require input/output operations such as reading from a file, writing to a file, or accessing I/O devices (keyboard, printer, disk). The OS provides uniform access, hiding hardware complexities.

File-system related services

4. File-system manipulation

The file system is one of the most important OS components. Programs may need to read/write files, create and delete files and directories, search for files, list file information, and manage permissions. The OS ensures data integrity and controlled access.

5. Communications

Processes may need to exchange information on the same computer or across different computers over a network, via:

  • Shared memory
  • Message passing, where packets are moved by the OS

Essential for multiprogramming and distributed systems.

Error-detection services

6. Error detection

The OS must constantly monitor for errors in the CPU, memory, I/O devices, and user programs. For each type of error the OS takes corrective action to ensure system consistency and correctness. Debugging facilities help programmers and users identify issues efficiently.

System-oriented services

7. Resource allocation

When multiple users or jobs run concurrently, the OS must allocate resources fairly and efficiently — CPU cycles, main memory, file storage, and I/O devices. Scheduling and allocation policies determine how resources are shared.

8. Accounting

The OS keeps track of which users use the system, how much of each resource is used, and the type of resources consumed. Useful for system tuning, usage analysis, and billing in shared or cloud environments.

9. Protection and security

  • Protection — ensures processes do not interfere with each other and controls access to system resources
  • Security — protects the system from external attacks, requires user authentication, and prevents unauthorized access to devices and data

System Calls

System calls provide the interface between a program and the operating system. They allow programs to request services from the OS, are usually written as high-level language routines, and are internally implemented in assembly or low-level code.

Types of system calls

  1. Process control — create, terminate, load, execute processes
  2. File manipulation — read, write, create, delete files
  3. Device manipulation — request and release devices; read/write device data
  4. Information maintenance — get/set system and process information
  5. Communications — message passing, shared memory operations
  6. Protection — control access permissions, set user privileges
Example — a printf() call in C
  1. User program calls printf()
  2. The C library intercepts the call
  3. The C library invokes the system call write()
  4. The OS performs the write operation
  5. The return value is passed back to the user program

This shows how user-level functions interact with kernel services.

Process Creation & Termination

The operating system must provide mechanisms for both process creation and process termination.

Process creation

  • A parent process can create child processes
  • Child processes may create further processes, forming a process tree
  • Each process is identified by a Process ID (PID)

Resource sharing options

  • Parent and child share all resources
  • Child shares a subset of the parent's resources
  • Parent and child share no resources

Execution options

  • Parent and child execute concurrently
  • Parent waits until the child terminates

Process creation using fork()

  • fork() creates a new process — the child is a duplicate of the parent, and its address space is copied
  • To run a different program, exec() is used, which replaces the process's memory with a new program

UNIX example: fork() creates the child process, exec() loads a new program into it.

Process termination

A process terminates when it executes its last statement or calls the exit() system call.

  • A status value is returned from child to parent
  • The parent retrieves this status using wait()
  • The OS deallocates all process resources

Parent terminating a child

A parent may terminate a child using abort() if the child exceeds allocated resources, the task assigned to the child is no longer needed, or the parent itself is terminating.

Cascading termination

Some operating systems do not allow a child to exist without a parent — if the parent terminates, all children terminate too. This is called cascading termination, initiated by the operating system.

Zombie and orphan processes

Zombie process

The child has terminated but the parent has not yet called wait().

Orphan process

The parent terminates before the child; the child is adopted by init / a system process.

These are handled using process tables and system calls like wait().

System Calls for Process Management

System calls provide the mechanism through which a process requests services related to process creation, execution, synchronization, and termination.

Process identifiers (PID)

  • Every process is assigned a unique, non-negative integer PID
  • The PID is the only universally known identifier that uniquely identifies a process, and is often embedded into other identifiers for uniqueness

PID reuse: although PIDs are unique at any instant, they are reused after processes terminate. UNIX systems delay PID reuse so newly created processes don't get recently used PIDs, avoiding confusion.

vfork() system call

vfork() creates a new process without copying the parent's address space, assuming the child will immediately call exec() or exit().

  • Child temporarily shares the parent's address space
  • Guarantees that the child runs first
  • Parent is suspended until the child calls exec() or exit()

Return values match fork() (child → 0, parent → child's PID, error → -1). vfork() is faster than fork() but must be used carefully.

exit() — process termination

A process can terminate normally by:

  1. Returning from main()
  2. Calling exit()
  3. Calling _exit() or _Exit()
  4. Returning from the start routine of the last thread
  5. Calling pthread_exit() from the last thread

Abnormal termination can occur by calling abort(), receiving certain signals, or the last thread responding to a cancellation request.

Regardless of termination type, the kernel closes all open file descriptors and releases all memory used by the process.

wait() and waitpid()

These system calls let a parent process synchronize with its child processes. A call to wait() or waitpid() can:

  1. Block — if all child processes are still running
  2. Return immediately — if a child has already terminated and is waiting
  3. Return an error — if the process has no children

If called after receiving SIGCHLD, wait() returns immediately. Return values: PID of child on success, 0 if state hasn't changed, -1 on failure.

waitid() allows finer control over which child process to wait for, using separate arguments instead of combining PID and process group (returns 0 on success, -1 on error).

exec() family of system calls

int execl(const char *pathname, const char *arg0, ...);
int execv(const char *pathname, char *const argv[]);
int execle(const char *pathname, const char *arg0, ...
           /* (char *)0, char *const envp[] */);
int execve(const char *pathname, char *const argv[], char *const envp[]);

When a process calls an exec() function, the current process image is completely replaced and the new program starts execution at its main() function.

Important
  • PID does not change
  • No new process is created
  • Text, data, heap, and stack are all replaced

Return value: -1 on error; does not return at all on success.

getpid() and getppid()

  • getpid() → returns the PID of the calling process
  • getppid() → returns the PID of the parent process

If the original parent has terminated, the process is re-parented — the parent PID changes to the new parent (usually init / a system process).

Race conditions

A race condition occurs when multiple processes access shared data and the final result depends on the order of execution.

After fork(), parent and child execute concurrently and it is unpredictable which one runs first — logic that depends on execution order can fail.

Waiting and polling

  • To wait for a child → use wait()
  • To wait for a parent → a polling loop may be used
Problem with polling

Polling wastes CPU time — the process wakes periodically just to check a condition.

Solution: use signaling mechanisms instead of polling. Signals avoid race conditions and CPU wastage.

Life Cycle of an I/O Request

An I/O-bound process frequently performs input/output operations such as reading from disk or writing to devices. This cycle repeats continuously for I/O-bound workloads.

  1. Process requests an I/O operation (read/write)
  2. OS moves the process to the waiting state
  3. CPU is allocated to another ready process
  4. Device controller performs the I/O operation
  5. After completion, the device sends an interrupt
  6. OS interrupt handler executes
  7. Process is moved back to the ready state
  8. Scheduler assigns the CPU again
  9. Process resumes execution
  10. Process soon issues another I/O request

CPU Scheduling — Basic Concepts

In a system with a single CPU core, only one process can execute at a time; all others must wait until the CPU becomes free. Multiprogramming's main objective is to keep the CPU busy at all times and maximize CPU utilization — several processes are kept in main memory, and when one process must wait (usually for I/O), the OS takes the CPU away from it and assigns the CPU to another ready process. On a multicore system, the same idea extends to each core independently, improving overall throughput.

Alternating sequence of CPU and I/O bursts

Process execution consists of an alternating sequence of CPU bursts (executing instructions) and I/O bursts (waiting for I/O completion). Maximum CPU utilization is achieved when CPU bursts of one process overlap with I/O bursts of another.

CPU scheduling algorithms focus mainly on the distribution of CPU burst times. I/O-bound processes have many short CPU bursts; CPU-bound processes have few long CPU bursts. This distribution matters when designing, evaluating, and comparing scheduling algorithms.

CPU scheduler & ready queue

The CPU scheduler (short-term scheduler) selects a process from the ready queue and allocates the CPU to it. The ready queue may be organized as a FIFO queue, a priority queue, a tree, or an unordered linked list. Each entry in the queue is a Process Control Block (PCB).

Preemptive vs non-preemptive scheduling

CPU scheduling decisions can occur when a process:

  1. Switches from running → waiting (non-preemptive)
  2. Switches from running → ready (preemptive)
  3. Switches from waiting → ready (preemptive)
  4. Terminates (non-preemptive)
Issues in preemptive scheduling

Shared-data access must be handled carefully, preemption while executing in kernel mode must be considered, and interrupts may occur during critical OS operations.

Examples: Windows 3.x is non-preemptive; Windows 95 onward and Macintosh OS use preemptive scheduling.

Problems with preemptive scheduling — race conditions

Can occur when one process is preempted while updating shared data and another process accesses inconsistent data. Preemptive kernels use mutex locks and other synchronization mechanisms to solve this. Most modern operating systems are fully preemptive, even in kernel mode.

The dispatcher

The dispatcher is a module that gives control of the CPU to the process selected by the short-term scheduler. It performs a context switch, switches the CPU to user mode, and jumps to the correct location in the user program.

Dispatch latency — the time taken to stop one process and start another — is an important performance metric.

Scheduling criteria

  1. CPU utilization — percentage of time the CPU is busy
  2. Throughput — number of processes completed per unit time
  3. Turnaround time — time from submission to completion of a process
  4. Waiting time — total time a process spends waiting in the ready queue
  5. Response time — time from request submission to first response; important in time-sharing systems
Optimization criteria

Maximize: CPU utilization, throughput.   Minimize: turnaround time, waiting time, response time.

Different scheduling algorithms optimize different criteria based on system goals.

Scheduling Algorithms — FCFS & SJF

Scheduling algorithms decide which process gets the CPU and for how long.

First-Come, First-Served (FCFS)

The simplest CPU scheduling algorithm.

  • Processes are executed in the order they arrive
  • Uses a FIFO queue
  • Non-preemptive — once the CPU is allocated, the process runs until completion or an I/O wait

Drawbacks of FCFS — the convoy effect

Short processes get stuck behind a long process — e.g. one CPU-bound process ahead of many I/O-bound processes. FCFS is non-preemptive, so a process can occupy the CPU for a long time: a poor choice for time-sharing systems, and unfair when responsiveness is important.

Shortest-Job-First (SJF) scheduling

SJF associates each process with the length of its next CPU burst.

Scheduling rule

The process with the shortest CPU burst is scheduled next.

Key properties

  • An optimal scheduling algorithm — produces the minimum average waiting time
  • Can be non-preemptive (SJF) or preemptive (Shortest-Remaining-Time-First)
Main challenge

The exact length of the next CPU burst is not known in advance — it must be predicted.

Determining the length of the next CPU burst

Since the actual burst time is unknown, the OS predicts it using exponential averaging.

Exponential averaging
τₙ₊₁ = α·tₙ + (1 − α)·τₙ

τₙ₊₁ = predicted next CPU burst · tₙ = actual last CPU burst · τₙ = previous prediction · α = weighting factor, 0 ≤ α ≤ 1. α controls the importance of recent history — commonly α = 0.5.

The preemptive version of SJF is called Shortest-Remaining-Time-First (SRTF).

Numerical example — exponential averaging

Given T₁ = 10, α = 0.5, previous CPU bursts: 8, 7, 4, 16 (SJF is non-preemptive, so order becomes 4, 7, 8, 16):

  • T₂ = 0.5 × 4 + 0.5 × 10 = 7
  • T₃ = 0.5 × 7 + 0.5 × 7 = 7
  • T₄ = 0.5 × 8 + 0.5 × 7 = 7.5
  • T₅ = 0.5 × 16 + 0.5 × 7.5 = 11.8

Result: predicted 5th CPU burst = 11.8

Priority Scheduling & Round Robin

Priority scheduling

A priority number (integer) is associated with each process.

Scheduling rule

The CPU is allocated to the process with the highest priority. In preemptive mode the waiting time for the highest-priority process is always zero; in non-preemptive mode it may not be zero.

Types

  • Preemptive priority scheduling — a running process can be preempted if a higher-priority process arrives
  • Non-preemptive priority scheduling — a running process continues until it finishes or blocks

Relation to SJF: SJF is a special case of priority scheduling, where priority = the inverse of the predicted next CPU burst time.

Problem — starvation

Low-priority processes may never get CPU time; this occurs when high-priority processes continuously arrive.

Solution — aging

Gradually increase the priority of a process as it waits, ensuring that every process eventually executes.

Round-Robin (RR) scheduling

Designed specifically for time-sharing systems.

Key characteristics

  • Similar to FCFS, but with preemption added
  • Uses a fixed time unit called a time quantum or time slice, typically 10–100 ms
  • The ready queue is treated as a circular queue

Each process gets the CPU for at most one time quantum; if it does not finish within the quantum, it is preempted and placed at the end of the ready queue.

Round-Robin performance

If n = number of processes in the ready queue and q = time quantum, then each process gets 1/n of the CPU time, the CPU is allocated in chunks of at most q time units, and a process waits no longer than (n − 1) × q time units for its next turn.

Example

5 processes, time quantum = 20 ms → each process gets 20 ms every 100 ms.

Effect of time-quantum size

Very large quantum

RR behaves like FCFS — no effective preemption.

Very small quantum

Too many context switches, high overhead, reduced CPU efficiency.

RR performance depends heavily on the time-quantum size.

Example — effect of time quantum (burst time = 10 units)

QuantumEffect
12Process completes in one quantum — no context-switch overhead
6Process needs 2 quanta — one context switch
1Process needs 10 quanta — 9 context switches, execution slows significantly

Practical considerations

  • Modern systems typically use a time quantum of 10–100 ms
  • Context-switch time is usually under 10 microseconds
  • Hence context-switch overhead is a small fraction of the quantum
Turnaround time vs time quantum — rule of thumb

80% of CPU bursts should be shorter than the time quantum — this balances responsiveness, context-switch overhead, and CPU utilization.

Multilevel Queue & Multilevel Feedback Queue Scheduling

Multilevel queue scheduling

The ready queue is partitioned into multiple separate queues, based on the type of process — e.g. a foreground queue for interactive processes and a background queue for batch processes.

  • Each process is permanently assigned to one queue
  • Each queue has its own scheduling algorithm — foreground → Round Robin, background → FCFS

CPU scheduling between queues

Scheduling must also be done between the queues, not just within a queue.

  1. Fixed priority scheduling — the foreground queue has higher priority than the background queue; all foreground processes execute before background processes, which can lead to starvation of background processes
  2. Time-slice scheduling between queues — each queue gets a percentage of CPU time, e.g. 80% CPU time → foreground (RR), 20% CPU time → background (FCFS)

Priority behaviour

Each queue has absolute priority over lower-priority queues — a process in a lower queue cannot execute unless all higher-priority queues are empty. If a higher-priority process arrives, the currently running lower-priority process is preempted.

Multilevel Feedback Queue (MLFQ) scheduling

Unlike multilevel queue scheduling, MLFQ allows processes to move between queues. It supports aging, preventing starvation by gradually moving processes to higher-priority queues.

Parameters defining an MLFQ scheduler

  1. Number of queues
  2. Scheduling algorithm for each queue
  3. Method used to upgrade a process
  4. Method used to demote a process
  5. Method used to determine which queue a process enters when it needs CPU service

Example — three queues

QueueAlgorithm
Q₀Round Robin, time quantum = 8 ms
Q₁Round Robin, time quantum = 16 ms
Q₂FCFS

Execution rules

  1. A new process enters Q₀ and receives 8 ms
  2. If not completed, it is moved to Q₁ and receives 16 ms
  3. If still not completed, it is moved to Q₂ (FCFS)

Queue priority & preemption rules

  • The scheduler always executes processes in Q₀ first
  • Q₁ is considered only when Q₀ is empty
  • Q₂ is considered only when both Q₀ and Q₁ are empty
  • A process arriving in Q₀ preempts processes in Q₁ and Q₂
  • A process arriving in Q₁ preempts processes in Q₂

This ensures responsiveness for interactive processes.

Multiple-Processor Scheduling

When multiple CPUs are available, load sharing becomes possible, but scheduling becomes more complex.

Asymmetric Multiprocessing (AMP)

One processor (the master) handles scheduling decisions, I/O processing, and system activities; other processors execute only user code.

Advantages: simple design, and only one processor accesses system data structures — meaning less synchronization overhead.

Symmetric Multiprocessing (SMP)

Each processor is self-scheduling. Processes may be in a common ready queue, or in separate per-processor queues. All modern operating systems support SMP.

Processor affinity

When a process runs on a processor, its data gets loaded into that processor's cache. Migrating the process to another processor invalidates the old cache and requires cache repopulation — this is expensive. To reduce this cost, the OS tries to keep a process on the same processor.

Soft affinity

The OS attempts to keep a process on the same processor, but migration is still possible.

Hard affinity

The OS allows a process to specify which processors it may run on, implemented using system calls.

Load balancing

In SMP systems, load must be evenly distributed across processors — this is mainly needed when each processor has its own ready queue. Goal: ensure all processors are utilized effectively.

Load-balancing techniques

  • Push migration — a periodic task checks processor loads and moves processes from overloaded processors to idle or lightly loaded ones
  • Pull migration — an idle processor pulls a process from a busy processor

Push and pull migration can be used together.

Bash Shell, Variables & Control Flow

What is a shell?

A shell is the Linux command-line interpreter. It provides an interface between the user and the kernel — it reads user commands and executes them. Commands may be built-in shell commands, external programs, scripts, or user-defined applications.

Example

Typing ls — the shell interprets the command and asks the kernel to execute the ls program.

Shell command syntax

command [arg1] [arg2] ... [argn]

Items in [ ] are optional; commands may run with or without arguments.

Command processing

  1. The shell reads the entire line after Enter is pressed
  2. The shell parses the input into command name, options, and filenames
  3. The shell searches for the command — in the specified path (e.g. ./mycommand), or in directories listed in the $PATH environment variable
  4. If the syntax is correct, the kernel executes the command

Various shells

bashBourne Again Shell — the most popular shell; default in most Linux distributions; developed by GNU

Check the current shell with: echo $SHELL

Environment variables vs shell variables

Environment variables

Defined for the current shell, inherited by child processes, and used to pass information to spawned programs.

Shell variables

Exist only in the current shell, are not inherited by child shells, and are used for temporary data (counters, paths).

Naming convention: usually written in uppercase letters. View all environment variables with env or printenv.

Shell basics

Child shell behaviour: when a new shell is spawned, shell variables from the parent are not available (only exported/environment variables are).

Setting environment variables at login

Edit the .profile file in $HOME and add export commands, e.g. export PATH=$PATH:/my/custom/path — this ensures variables are set automatically on login.

Shell control flow — if statement

Shell scripts support conditional execution.

if [ -f filename ]
then
  echo "File exists"
else
  echo "File does not exist"
fi

Concept to remember: if evaluates a condition and executes commands accordingly.

Shell control flow — loops

Shell supports looping constructs such as for, while, and until. A nested loop is a loop inside another loop, used for multi-level iteration.

#!/bin/bash
for i in {1..5}
do
  echo "i = $i"
done
#!/bin/bash
for i in {1..5}
do
  for j in {1..3}
  do
    echo "i=$i and j=$j"
  done
done

Used to control loop execution flow.

  • break — exits the loop immediately
  • continue — skips the current iteration and moves to the next one

  then

cron

What is cron?

cron is a daemon (background service) — the daemon itself is called crond. It runs continuously after system boot and executes scheduled tasks automatically.

cron functionality

  • Cron reads instructions from crontab (cron tables)
  • Each user can have their own crontab
  • Jobs are scheduled using a specific syntax
  • Used for backups, log cleanup, periodic monitoring, and automation

Checking & managing cron jobs

# List scheduled cron jobs
crontab -l

# Edit crontab — add, edit, or delete cron jobs
crontab -e

Cron runs automatically at system boot on most systems; you can also check cron's status and start the service if it is not running.

cron syntax

Cron job format
minute  hour  day  month  weekday  command
ScheduleScheduled value
5 0 * 8 *At 00:05, in August
5 4 * * 6At 04:05, on Saturday
0 22 * * 1-5At 22:00, every weekday Monday through Friday

cron example — run a program every minute

# crontab -e
* * * * * /bin/bash $HOME/OS/hello.exe &> $HOME/OS/cron_output.log

# crontab -l
# m h  dom mon dow   command
*/1 * * * * /bin/bash $HOME/OS/hello.exe &> $HOME/OS/cron_output.log

Executed jobs are recorded in the system log (/var/log/syslog), showing each run of crond invoking the command at the scheduled minute.
