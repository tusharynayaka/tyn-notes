A single-page reference covering the principles of network applications (client-server vs. peer-to-peer, sockets, transport service requirements), the Web via HTTP and HTTPS (persistent connections, cookies, caching, HTTP/2–3, TLS), and fully worked delay and throughput problems — expanded from the lecture slides with explanations.

Application Layer: Overview & Example Apps

The application layer is where network software actually lives. Our goals in studying it are twofold: understand the conceptual and implementation aspects of application-layer protocols (transport-layer service models, the client-server paradigm, the peer-to-peer paradigm), and learn about real protocols by examining popular ones — chiefly HTTP.

Some network apps

The application layer hosts almost everything a user actually interacts with on the internet:

  • social networking (TikTok, Facebook, Instagram, X, WeChat)
  • Web
  • text messaging
  • e-mail (Gmail, Yahoo Mail)
  • multi-user network games
  • streaming stored video (YouTube, Hulu, Netflix)
  • P2P file sharing
  • voice over IP
  • real-time video conferencing (Skype, Hangouts)
  • Internet search
  • remote login
  • generative AI (chatbots, text-to-image/video)
  • …

Creating a network app

Writing a network application means writing programs that: (1) run on different end systems, and (2) communicate over the network — e.g. web server software communicates with browser software.

Key insight

There is no need to write software for network-core devices. Routers and switches in the core do not run user applications — only end systems (hosts) do. Confining applications to end systems is precisely what allows for rapid application development and propagation: a new app can be deployed just by installing it on end systems, without touching the core.

Client-Server Paradigm & Peer-to-Peer Architecture

Two broad architectures describe how network applications organize their communicating end systems.

Client-server paradigm

Server

  • always-on host
  • permanent IP address
  • often housed in data centers, for scaling

Clients

  • contact and communicate with the server
  • may be intermittently connected
  • may have dynamic IP addresses
  • do not communicate directly with each other

Examples: HTTP, IMAP, FTP.

Peer-to-peer (P2P) architecture

  • no always-on server
  • arbitrary end systems communicate directly with each other
  • peers request service from other peers and provide service in return to other peers
Self scalability

New peers bring new service capacity as well as new service demand — unlike a fixed server whose capacity is bounded, a P2P system's total capacity grows as its user base grows.

Peers are intermittently connected and change IP addresses, which makes management complex. Example: P2P file sharing (BitTorrent).

Processes communicating

A process is a program running within a host. Two processes within the same host communicate using inter-process communication, a mechanism defined by the operating system. Processes in different hosts communicate by exchanging messages.

Client vs server process

Client process: the process that initiates the communication.

Server process: the process that waits to be contacted.

Note: applications built with a P2P architecture still have client processes and server processes — a peer plays the client role when it initiates a request and the server role when it responds to one.

Sockets & Addressing Processes

Sockets

A process sends and receives messages to and from its socket. The socket is analogous to a door: the sending process shoves the message out the door and relies on the transport infrastructure on the other side of the door to deliver the message to the socket at the receiving process. Two sockets are involved in any exchange — one on each side.

Addressing processes

To receive messages, a process must have an identifier. Every host device has a unique 32-bit IP address — but does the IP address of the host on which a process runs suffice to identify the process itself?

No

Many processes can be running on the same host, so the IP address alone is not enough. The identifier must include both the IP address and a port number associated with the process on that host.

Example port numbers: HTTP server → port 80; mail server → port 25. To send an HTTP message to a web server at gaia.cs.umass.edu: IP address 128.119.245.12, port number 80.

What an Application-Layer Protocol Defines

An application-layer protocol specifies exactly how the processes within an application communicate with one another. It defines:

  • Types of messages exchanged — e.g. request, response
  • Message syntax — what fields appear in messages, and how those fields are delineated
  • Message semantics — the meaning of the information contained in each field
  • Rules for when and how processes send and respond to messages

Open vs proprietary protocols

Open protocols

Defined in RFCs; everyone has access to the protocol definition. This allows for interoperability. Examples: HTTP, SMTP.

Proprietary protocols

Not openly published. Example: Skype.

What Transport Service Does an App Need?

When designing an application, four transport-service dimensions matter:

Data integrity

Some apps (file transfer, web transactions) require 100% reliable data transfer. Others (audio) can tolerate some loss.

Throughput

Some apps (multimedia) require a minimum amount of throughput to be "effective." Other, "elastic" apps make use of whatever throughput they get.

Timing

Some apps (Internet telephony, interactive games) require low delay to be "effective."

Security

Encryption, data integrity, and related guarantees.

TCP service

  • flow control: sender won't overwhelm receiver

Web, HTTP and HTTPS: Overview

First, a quick review of the Web: a web page consists of objects, each of which can be stored on different web servers. An object can be an HTML file, a JPEG image, a Java applet, an audio file, and so on. A web page consists of a base HTML file which includes several referenced objects, each addressable by a URL.

Example: www.someschool.edu/someDept/pic.gif — www.someschool.edu is the host name, /someDept/pic.gif is the path name. If a web page contains HTML text plus 5 JPEG images, the page has 6 objects in total: the base HTML file plus the 5 images.

HTTP: hypertext transfer protocol

HTTP is the Web's application-layer protocol, defined in RFC 1945 and RFC 2616. It follows a client/server model:

  • client: the browser that requests, receives (using the HTTP protocol), and "displays" web objects
  • server: the web server that sends (using the HTTP protocol) objects in response to requests

HTTP uses TCP

  1. client initiates a TCP connection (creates a socket) to the server, port 80
  2. server accepts the TCP connection from the client
  3. HTTP messages (application-layer protocol messages) are exchanged between the browser (HTTP client) and the web server (HTTP server)
  4. TCP connection is closed

HTTP is "stateless"

The server maintains no information about past client requests.

Aside: why statelessness is a deliberate design choice

Protocols that maintain "state" are complex! Past history (state) must be maintained, and if the server or client crashes, their views of "state" may become inconsistent and must be reconciled.

With HTTP being stateless: there is no need for client/server to track the "state" of a multi-step exchange, all HTTP requests are independent of each other, and there is no need for client/server to "recover" from a partially-completed-but-never-completely-completed transaction.

HTTP Connections: Persistent vs Non-Persistent

Non-persistent HTTP

  1. TCP connection opened
  2. at most one object sent over the TCP connection
  3. TCP connection closed

Downloading multiple objects required multiple connections.

Persistent HTTP

TCP connection opened to a server; multiple objects can be sent over a single TCP connection between the client and that server; the TCP connection is closed only afterward.

Non-persistent HTTP: example walkthrough

User enters URL www.someSchool.edu/someDepartment/home.index (a base HTML file containing text plus references to 10 JPEG images):

  1. HTTP client initiates a TCP connection to the HTTP server (process) at www.someSchool.edu on port 80
  2. HTTP server at that host, waiting for a TCP connection at port 80, "accepts" the connection and notifies the client
  3. HTTP client sends an HTTP request message (containing the URL) into the TCP connection socket — the message indicates that the client wants the object someDepartment/home.index
  4. HTTP server receives the request message, forms a response message containing the requested object, and sends the message into its socket
  5. HTTP server closes the TCP connection
  6. HTTP client receives the response message containing the HTML file and displays it; parsing the HTML file, it finds 10 referenced JPEG objects
  7. Steps 1–5 are repeated for each of the 10 JPEG objects

Non-persistent HTTP: response time

RTT (round-trip time) is the time for a small packet to travel from client to server and back. Per object, the HTTP response time requires: one RTT to initiate the TCP connection, one RTT for the HTTP request and the first few bytes of the HTTP response to return, plus the object/file transmission time.

Non-persistent HTTP response time
2·RTT + file transmission time

Persistent HTTP (HTTP/1.1)

Non-persistent HTTP issues: requires 2 RTTs per object; OS overhead for each TCP connection (TCP buffers and variables must be allocated); browsers often open multiple parallel TCP connections to fetch referenced objects in parallel, to compensate.

Persistent HTTP (HTTP/1.1) fixes this: the server leaves the connection open after sending a response; subsequent HTTP messages between the same client/server are sent over the still-open connection; the client sends requests as soon as it encounters a referenced object. This brings response time down to as little as one RTT for all the referenced objects (cutting response time roughly in half compared to sequential non-persistent connections).

Connection management in HTTP/1.x

Three connection-management patterns exist in practice: short-lived connections (a fresh TCP establish/close for every object — the non-persistent model), a persistent connection (one TCP connection reused sequentially for each request/response), and HTTP pipelining (multiple requests fired back-to-back over one persistent connection, without waiting for each response before sending the next request).

WorkedComparing non-persistent, persistent, and pipelined HTTP

A webpage consists of: 1 HTML file + 6 images. Assume: one RTT = 80 ms, and object transmission time is negligible.

(a) Non-persistent HTTP. Each object requires 1 RTT to establish a TCP connection + 1 RTT for the HTTP request and the beginning of the response = 2 RTT per object. There are 7 objects (1 HTML + 6 images):

7 × 2RTT = 14 RTT = 14 × 80 ms = 1120 ms = 1.12 s

(b) Persistent HTTP, without pipelining. The TCP connection is established only once (1 RTT). Then: 1 RTT to request/receive the base HTML file, and 6 RTT to request/receive the 6 images sequentially (1 RTT per image, since the client waits for each response before requesting the next).

1 RTT (TCP) + 1 RTT (HTML) + 6 RTT (images) = 8 RTT = 8 × 80 ms = 640 ms = 0.64 s

(c) Persistent HTTP with pipelining. The client opens a single TCP connection and sends multiple HTTP requests back-to-back without waiting for each response. After the TCP connection (1 RTT) and the HTML file (1 RTT), the client parses the HTML, discovers all 6 images, and requests all of them together in a single batch — needing only about 1 more RTT for all of them.

1 RTT (TCP) + 1 RTT (HTML) + 1 RTT (all 6 images) = 3 RTT = 3 × 80 ms = 240 ms

HTTP Request & Response Messages

There are two types of HTTP messages: request and response. Both are ASCII (human-readable).

HTTP request message

GET /index.html HTTP/1.1\r\n
Host: www-net.cs.umass.edu\r\n
User-Agent: Firefox/3.6.10\r\n
Accept: text/html,application/xhtml+xml\r\n
Accept-Language: en-us,en;q=0.5\r\n
Accept-Encoding: gzip,deflate\r\n
Accept-Charset: ISO-8859-1,utf-8;q=0.7\r\n
Keep-Alive: 115\r\n
Connection: keep-alive\r\n
\r\n

The first line is the request line (containing the method — GET, POST, HEAD — plus the URL and version). The lines that follow are header lines. A carriage-return/line-feed (\r\n) at the start of a line, on its own, indicates the end of the header lines.

HTTP request message: general format

method sp URL sp version cr lf

request line

header field name : value cr lf

header lines (repeated), then a blank cr lf

entity body

HTTP specifications: RFC 1945, RFC 2616, RFC 7540.

Other HTTP request methods

POST method

A web page often includes form input. User input is sent from the client to the server in the entity body of the HTTP POST request message.

HEAD method

Requests only the headers that would be returned if the specified URL were requested with an HTTP GET method — no body.

GET method (for sending data to server)

Include user data in the URL field of the HTTP GET request message, following a ?:

www.somesite.com/animalsearch?monkeys&banana

PUT method

Uploads a new file (object) to the server, completely replacing the file that exists at the specified URL with the content in the entity body.

HTTP response message

HTTP/1.1 200 OK\r\n
Date: Sun, 26 Sep 2010 20:09:20 GMT\r\n
Server: Apache/2.0.52 (CentOS)\r\n
Last-Modified: Tue, 30 Oct 2007 17:00:02 GMT\r\n
ETag: "17dc6-a5c-bf716880"\r\n
Accept-Ranges: bytes\r\n
Content-Length: 2652\r\n
Keep-Alive: timeout=10, max=100\r\n
Connection: Keep-Alive\r\n
Content-Type: text/html; charset=ISO-8859-1\r\n
\r\n
data data data data data ...

The first line is the status line (protocol, status code, status phrase); it's followed by header lines, a blank line, and the data (e.g. the requested HTML file).

HTTP response status codes

The status code appears in the 1st line of a server-to-client response message. Some sample codes:

  • 200 OK — request succeeded, the requested object appears later in this message
  • 301 Moved Permanently — requested object has moved; new location specified later in this message (in the Location: field)
  • 400 Bad Request — request message not understood by the server
  • 404 Not Found — requested document not found on this server
  • 505 HTTP Version Not Supported

Cookies & Maintaining User/Server State

A website/HTTP/Internet cookie is a piece of data from a specific website, stored on a user's computer, that allows sites to keep track of users — e.g. remembering a language selection. You've likely seen the consent banners ("We value your privacy… Accept All / Reject All") that are the visible face of cookie usage.

Recall: HTTP GET/response interaction is stateless

There is no notion of multi-step exchanges of HTTP messages needed to complete a Web "transaction": there's no need for client/server to track the "state" of a multi-step exchange, all HTTP requests are independent of each other, and there's no need for client/server to "recover" from a partially-completed-but-never-completely-completed transaction.

Contrast: a stateful protocol

In a stateful protocol, a client might lock a data record X, update it twice, then unlock it — expecting either both changes to X or none at all. Question: what happens if the network connection or the client crashes midway through such a sequence? Answering that requires the protocol to track state, which is exactly the complexity HTTP avoids by design.

Cookies: how they work

Web sites and client browsers use cookies to maintain some state between transactions, built from four components:

  1. a cookie header line of the HTTP response message
  2. a cookie header line in the next HTTP request message
  3. a cookie file kept on the user's host, managed by the user's browser
  4. a back-end database at the web site

Example: Susan uses a browser on her laptop and visits a specific e-commerce site for the first time. When the initial HTTP request arrives at the site, the site creates a unique ID (the "cookie") and an entry in its backend database for that ID. Subsequent HTTP requests from Susan to this site will contain the cookie ID value, allowing the site to "identify" Susan.

What cookies can be used for

  • track a user's browsing history
  • remembering login details (authorization)
  • track visitor count
  • shopping carts
  • recommendations
  • save coupon codes
Aside — cookies and privacy

Cookies permit sites to learn a lot about you on their site. Third-party cookies (tracking cookies) allow a common identity (cookie value) to be tracked across multiple web sites; browsers now disable or restrict these by default.

Sites use first-party cookies to track user behavior on a given website, and third-party cookies to track user behavior across multiple websites — without the user ever choosing to visit the tracker site directly!

Worked example: how third-party ad tracking actually happens

Suppose loading a nytimes.com sports page triggers a request to an ad exchange, AdX.com, to fetch an ad. The base HTML from nytimes.com sets a first-party cookie (1634) since that's the site the user chose to visit. The embedded request to AdX.com — made because the page told the browser to fetch an ad from there — causes AdX to set its own third-party cookie (7493), even though the user never chose to visit AdX.com.

A day later, the user visits an unrelated site, socks.com, which also happens to embed an AdX.com ad slot. The browser's request to AdX.com carries the same third-party cookie (7493) from before — because it's the same cookie jar, scoped to AdX.com regardless of which "first-party" page embedded it. AdX now has two data points tied to cookie 7493: this user visited NY Times sports, and this user visited socks.com. AdX can now return a targeted ad for socks back on the NY Times page, since it recognizes the same visitor across both unrelated sites.

The mechanism in one sentence

AdX tracks the user's web browsing over every site that happens to embed an AdX ad, and can return targeted ads based on that cross-site browsing history — all driven purely by the third-party cookie being resent on every request to the same ad-server domain.

Web Caches (Proxy Servers) & Conditional GET

Goal: satisfy a client's request without involving the origin server at all.

The user configures their browser to point to a web cache. The browser then sends all HTTP requests to the cache: if the requested object is in the cache, the cache returns the object directly to the client; else the cache requests the object from the origin server, caches the received object, and then returns it to the client.

A web cache acts as both client and server: it is a server to the original requesting client, and a client to the origin server. Typically the cache is installed by an ISP (university, company, or residential ISP). The origin server tells the cache about an object's allowable caching behaviour via response headers:

Cache-Control: max-age=<seconds>
Cache-Control: no-cache

Why web caching?

  • reduces response time for the client's request (speed) — the cache is physically closer to the client
  • reduces traffic on an institution's access link (saves bandwidth)
  • the internet is dense with caches, which enables "poor" content providers to more effectively deliver content
  • privacy — surfing the internet somewhat more anonymously
  • activity logging

WorkedCaching example — the access-link bottleneck

Scenario: access link rate = 1.54 Mbps; RTT from the institutional router to the origin servers = 2 sec; web object size = 100K bits; average request rate from browsers to origin servers = 15/sec (average data rate to browsers = 1.50 Mbps).

LAN utilization
(15 req/sec) × (100 Kbits/req) / (1 Gbps) = 0.0015
Access-link utilization
(15 req/sec) × (100 Kbits/req) / (1.54 Mbps) = 0.974 ≈ 0.97

End-to-end delay = Internet delay + access-link delay + LAN delay = 2 sec + minutes + microseconds.

Problem

Large delays occur at high utilization! An access link running near 97% utilization means queuing delay explodes (this follows the same intuition as M/M/1-style queuing: as utilization → 1, queuing delay → ∞).

Option A — buy a faster access link: upgrade 1.54 Mbps → 154 Mbps. Access-link utilization drops from .97 to .0097, and end-to-end delay drops from "minutes" to milliseconds. Cost: a much faster access link is expensive.

Option B — install a web cache (cheap!): suppose the cache hit rate is 0.4 (40% of requests are satisfied at the cache, 60% still go to the origin). Then only 60% of requests use the access link:

Data rate over access link
0.6 × 1.50 Mbps = 0.9 Mbps → utilization = 0.9 / 1.54 = 0.58
Average end-to-end delay
0.6 × (delay from origin servers) + 0.4 × (delay when satisfied at cache)
= 0.6 (2.01) + 0.4 (~msecs) ≈ 1.2 sec

Conclusion: installing a cache gives a lower average end-to-end delay than upgrading to a 154 Mbps link — and it's far cheaper.

Conditional GET — browser caching

Goal: don't re-send an object if the cache already has an up-to-date cached version — this avoids the object transmission delay and lowers link utilization.

The cache specifies the date of its cached copy in the HTTP request:

If-modified-since: <date>

The server's response contains no object at all if the cached copy is already up-to-date:

HTTP/1.0 304 Not Modified

If the object was modified after that date, the server instead responds normally with HTTP/1.0 200 OK and the full <data>.

HTTP/2 and HTTP/3

Key goal across both: decreased delay in multi-object HTTP requests.

HTTP/1.1's approach and its limits

HTTP/1.1 introduced multiple, pipelined GETs over a single TCP connection. The server responds in-order (FCFS: first-come-first-served scheduling) to GET requests. Two consequences follow:

  • with FCFS, a small object may have to wait for transmission behind a large object — this is head-of-line (HOL) blocking
  • loss recovery (retransmitting lost TCP segments) stalls the transmission of every object queued behind the lost segment

HTTP/2 [RFC 7540, 2015]

HTTP/2 increases flexibility at the server in how it sends objects to the client:

  • methods, status codes, and most header fields are unchanged from HTTP/1.1
  • transmission order of requested objects is based on client-specified object priority (not necessarily FCFS)
  • the server can push unrequested objects to the client
  • objects are divided into frames, and frames are scheduled to mitigate HOL blocking

From HTTP/2 to HTTP/3

HTTP/2 still runs over a single TCP connection, which means:

  • recovery from packet loss still stalls all object transmissions on that connection
  • as in HTTP/1.1, browsers have an incentive to open multiple parallel TCP connections to reduce stalling and increase overall throughput
  • there is no security built into the TCP connection itself
HTTP/3

HTTP/3 adds security and per-object error- and congestion-control (finer-grained pipelining) by running over UDP instead of TCP, via the QUIC transport protocol.

HTTPS & Transport Layer Security (TLS)

HTTPS is HTTP with encryption — all communication between browser and server is encrypted (bi-directionally). The "S" stands for "Secure," i.e. HTTP over a Secure Socket Layer. HTTPS uses TLS (formerly SSL) to encrypt ordinary HTTP requests and responses. Attackers monitoring the wire can't read the data crossing it, and the client can verify it is really talking to the server it thinks it's talking to.

Concretely: HTTP + TLS = HTTPS. HTTPS uses port 443 for data communication (versus port 80 for plain HTTP).

Public/private-key cryptography

HTTPS is based on public/private-key cryptography: the public key is used for encryption, while the secret private key is required for decryption. Any message encrypted with Bob's public key can be decrypted only with Bob's private key.

Asymmetric encryption

Uses two different keys — a public key for encryption and a secret private key for decryption.

Symmetric encryption

Uses the same secret key for both encryption and decryption — much faster, and used for the bulk of TLS-protected traffic once a shared key has been agreed.

An SSL/TLS certificate is a web server's digital certificate, issued by a third-party Certificate Authority (CA). It creates an encrypted connection and establishes trust. A certificate (technically an X.509 certificate) contains: the domain name (e.g. bank.com), the server's public key, issuer information (CA details), an expiration date, and a CA digital signature (an encrypted hash created by a trusted CA's private key).

Transport Layer Security (TLS) protocol

TLS is a widely deployed security protocol above the transport layer, supported by almost all browsers and web servers via https (port 443). It provides three guarantees:

  • confidentiality — via symmetric encryption (encrypts data so eavesdroppers can't read it)
  • integrity — via cryptographic hashing (ensures data isn't altered or corrupted in transit)
  • authentication — via public-key cryptography (verifies the client is actually talking to the genuine server, not an impostor)

History: from SSL to TLS 1.3

  • SSL (Secure Sockets Layer): created by Netscape in the mid-1990s
  • SSL 1.0: never released publicly, due to major flaws
  • SSL 2.0 & 3.0: released in 1995 and 1996, but later broken by critical vulnerabilities
  • TLS (Transport Layer Security): created by the IETF starting in 1999 as SSL's official standard successor
  • TLS 1.0 & 1.1: released in 1999 and 2006 — now deprecated
  • TLS 1.2 & 1.3: the only secure, actively used standards on the web today
"SSL certificate" is a naming fossil

A digital certificate (technically an X.509 certificate) does not care about protocol versions — it works identically whether the server ultimately speaks TLS 1.2, TLS 1.3, or legacy SSL. The term "SSL Certificate" persists purely because of roughly 30 years of marketing and consumer familiarity; modern security tools and browsers actually run on TLS, not SSL.

What actually changed under the hood (SSL → modern TLS)

Handshake & performance

SSL handshake: required multiple back-and-forth round trips (2-RTT). Connection setup was slow, creating noticeable lag for users. TLS handshake: streamlined the negotiation — TLS 1.3 cuts handshake latency in half by allowing key-exchange parameters to be sent in the very first message (1-RTT).

Security & cryptography

Weak cryptography excised: SSL allowed insecure encryption algorithms like RC4 stream ciphers, RSA key transport, and MD5 hashing, all of which attackers could break relatively easily. TLS removed these in favor of authenticated encryption (AEAD) such as AES-GCM and ChaCha20.

Mandatory forward secrecy: under SSL, if an attacker recorded encrypted web traffic and later stole the server's private key — even years afterward — they could retroactively decrypt all that past traffic. Modern TLS forces the use of temporary session keys (Ephemeral Diffie-Hellman), so a stolen server key can't decrypt previously recorded sessions.

How TLS authentication works

  1. Certificate presentation: the server sends its digital certificate, containing its public key and the CA's signature
  2. CA trust verification: the browser checks the digital signature against its built-in database of trusted Root Certificate Authorities (e.g. DigiCert, Let's Encrypt)
  3. Proof of ownership (CertificateVerify): to prove the server isn't an attacker replaying a stolen public certificate, the server signs a unique handshake message using its secret private key
  4. Public-key verification: the browser decrypts that signature using the public key from the certificate — if it decrypts successfully, the server is proven to hold the matching private key, confirming its identity

TLS 1.3 handshake: 1-RTT

  1. Client hello: the client guesses a key-agreement protocol and its parameters, and indicates which cipher suites it supports
  2. Server hello: the server chooses the key-agreement protocol/parameters, the cipher suite, and sends its server-signed certificate
  3. Client: checks the server certificate, generates the shared key, and can now make an application request (e.g. an HTTPS GET)
"Cipher suite"

A set of distinct cryptographic algorithms bundled together to secure a network connection — used for key generation, encryption, MAC (Message Authentication Code), and digital signatures.

In older versions (TLS 1.2 and SSL), the server sent its certificate out in plain text — anyone monitoring your Wi-Fi network could see exactly which website's certificate was being sent down to your computer. In TLS 1.3, the browser and server establish a temporary secret key before the certificate is sent, so the certificate itself is encrypted — an eavesdropper on public Wi-Fi can no longer read it as it travels across the wire.

TLS 1.3 handshake: 0-RTT (session resumption)

For returning visitors, TLS 1.3 introduces a 0-RTT (Zero Round-Trip Time) mode: the initial hello message itself contains encrypted application data, "resuming" an earlier connection between client and server. That application data is encrypted using a "resumption master secret" saved from the earlier connection — uses a Pre-Shared Key (PSK), letting the browser send encrypted HTTP requests (like GET /home) in the very first packet, eliminating handshake latency entirely.

Caution — replay attacks

0-RTT data is vulnerable to replay attacks, since an attacker who captures the first packet can resend it. It may be acceptable for idempotent requests like an HTTP GET, but is risky for client requests that modify server state (e.g. a payment).

Delay & Throughput: Solved Problems

These worked problems apply the core delay and throughput formulas from the network-layer/transport toolbox to concrete numeric scenarios. Recall the four components of nodal delay:

Nodal delay
dnodal = dproc + dqueue + dtrans + dprop

processing delay + queuing delay + transmission delay + propagation delay

Transmission delay

dtrans = L / R

L = packet size (bits), R = transmission rate (bps) — the time to push all bits of the packet onto the link

Propagation delay

dprop = m / s

m = distance (meters), s = propagation speed (m/s) — the time for a bit to physically travel down the link

Ignoring processing and queuing delays, the end-to-end (one-hop) delay is simply:

End-to-end delay
dend-to-end = L/R + m/s

Delay Problems — Q1 to Q5

Q1Transmission delay of a packet

Suppose the packet length is 4000 bits, and the link transmission rate along the link from the first router to the second is 10 MBps. What is the transmission delay?

L = 4000 bits; transmission rate R = 10 MBps = 10 × 8 × 106 bps = 80 Mbps.

dtrans = L/R = 4000 / (10 × 8 × 106) = 0.00005 s = 50 microseconds

Q2Network transfer vs courier delivery

There are two ways to send 10 TB of data from Bengaluru to Chennai: a dedicated link transmitting at 100 Mbps, or a special courier option with delivery in one day. Which would you prefer?

Convert total data to bits: 10 TB = 10 × 1012 × 8 bits = 8×1013 bits.

Transmission time = 10×1012×8 / (100×106) = 800,000 s / 86,400 ≈ 9.3 days

With the special courier option, the data would arrive in a single day. Hence the courier option would be preferred for speedy delivery — this is the classic "never underestimate the bandwidth of a truck full of hard drives" scenario.

Q3Distance from propagation speed and delay

An optical fiber cable transfers packets at 70% of the speed of light, arriving in 10 microseconds. What distance did the packet traverse?

Speed of propagation = 70% of 3×108 m/s = 0.7 × 3×108 = 2.1×108 m/s.

Distance = speed × time = 2.1×108 × 10×10-6 = 2100 m = 2.1 km

Q4Solving for transmission delay given a delay ratio

The time taken by a packet to travel across a link is 1000 times the time taken for the packet to be inserted into the link. Assuming no queuing/processing delay, what is the transmission delay if the link connects an end-to-end distance of 2 km, with a total delay of 3 microseconds?

Given: distance = 2 km, total delay = 3 µs; propagation delay = 1000 × transmission delay. End-to-end delay = transmission delay + propagation delay:

3 µs = TD + 1000 TD = 1001 TD

Solving: transmission delay ≈ 2.997 ns ≈ 3 ns.

Q5Solving for processing delay given the other three components

Data traveling in Alice's network of 2 computers takes a one-hop transmission delay of 0.003 ms to go from one computer to the other. If the queuing delay is 1 microsecond and the distance between the two systems is 3 km, find the time taken by Alice's router for bit-level error checking and processing, given a total nodal delay of 0.04 ms.

Setup
dnodal = dproc + dqueue + dtrans + dprop
0.04×10-3 = dproc + 0.001×10-3 + 0.003×10-3 + 3000/(3×108)

Solving: dproc = (0.04 − 0.01 − 0.001 − 0.003) × 10-3 = 0.026 ms.

Throughput Problems — Q6 to Q8

Q6Actual throughput given network efficiency

Hosts Alice and Bob are connected via a router. The bandwidth of each link between Alice and the router is 15 Mbps. If the efficiency of data transfer in the entire network is 80%, what is the actual throughput of the network?

Ideal throughput = min{15, 15} = 15 Mbps. Efficiency = (amount of data transferred per second) / (amount of data that could be transferred per second) = 80/100 × 15.

Throughput = 12 Mbps

Q7Maximum throughput under circuit switching

Consider a 10 Mbps link being shared by 7 users. What is the maximum throughput per user if the network uses circuit switching?

In circuit switching, the link bandwidth is divided equally among all users:

Throughput per user = 10/7 Mbps ≈ 1.43 Mbps

Note the throughput per user is nearly equal to a fixed, guaranteed slice — regardless of whether other users are actively sending data — which is the defining trade-off of circuit switching versus packet switching's statistical multiplexing.

Q8Time to push a packet onto the network

Alice and Bob are connected via a router. The bandwidth of each link between the router and Bob is 20 Mbps. If the network allows the actual transmission of data at 20 Mbps, what is the time taken for a packet of size 1000 bits to enter the network?

Transmission delay
L/R = 1000 / (20×106) = 5×10-5 s = 50 microseconds

Q9Full derivation — propagation vs transmission delay (multi-part)

Two hosts A and B are connected by a single link of rate R bps, separated by m meters, with propagation speed s meters/sec. Host A sends a packet of size L bits to Host B.

(a) Propagation delay: dprop = m/s.

(b) Transmission delay (time to push all L bits onto the link): dtrans = L/R.

(c) Ignoring processing and queuing delays, the end-to-end delay:

dend-to-end = L/R + m/s

(d) If Host A begins transmitting at t = 0, at time t = dtrans the sender has just finished transmitting the last bit — so the last bit is just leaving Host A (at the beginning of the link).

(e) If dprop > dtrans: at t = dtrans, the first bit is still in the link and has not yet reached Host B.

(f) If dprop < dtrans: the first bit reached Host B earlier — at t = dtrans, the first bit has already arrived at Host B.

(g) Given s = 2.5×108 m/s, L = 1500 bytes, R = 10 Mbps, find the distance m so that dprop equals dtrans.

L = 1500 bytes = 1500×8 = 12,000 bits; R = 10 Mbps = 10×106 bps.

dtrans = 12000 / (10×106) = 1.2×10-3 s = 0.0012 s
Set m/s = 0.0012 ⟹ m = s × 0.0012 = 2.5×108 × 0.0012

m = 3×105 meters = 300,000 meters = 300 km.

Bandwidth-Delay Product — Q10

Bandwidth-delay product
R × dprop

Interpretation: the maximum number of bits that can be "in transit" (in the link) at any given time — the pipe's raw capacity, independent of how much data you actually have to send.

Q10 (part 1)Bandwidth-delay product with R = 5 Mbps

Hosts A and B are 20,000 km apart, connected by a direct link of R = 5 Mbps, with propagation speed 2.5×108 m/s.

Bandwidth-delay product: distance = 20,000 km = 2×107 m.

dprop = m/s = 2×107 / 2.5×108 = 0.08 s
R × dprop = (5×106)(0.08) = 400,000 bits

Sending an 800,000-bit file continuously: since the file size (800,000 bits) is larger than the bandwidth-delay product (400,000 bits), the maximum number of bits "in flight" is capped at 400,000 bits (the pipe's own capacity) — the rest of the file simply hasn't been sent yet at any given instant.

Width of one bit in the link: time per bit = 1/R = 1/(5×106) = 2×10-7 s.

Bit width = s × (1/R) = 2.5×108 × 2×10-7 = 50 meters

A football field is about 100 meters, so a single bit here occupies about half a football field of physical fiber.

Q10 (part 2)Same scenario with R = 1 Gbps

(a) Bandwidth-delay product: dprop = m/s = 2×107 / 2.5×108 = 0.08 s (unchanged, since distance and propagation speed didn't change).

R × dprop = (109)(0.08) = 8×107 bits = 80,000,000 bits (80 Mb)

(b) Sending an 800,000-bit file: since the bandwidth-delay product (80,000,000 bits) is now much larger than the file size (800,000 bits), the maximum bits in the link at any given time is capped by the file size itself: 800,000 bits — the whole file fits in the pipe simultaneously with room to spare.

(c) Width of one bit: width = s/R = 2.5×108 / 109 = 0.25 meters (25 cm) — a much shorter bit than at 5 Mbps, since the faster link pushes bits out more quickly, compressing each one's physical footprint on the wire.

Applied Scenarios — Q11 to Q14

Q11Can an ISP deliver on its latency promise?

An ISP offers a 10 Mbps connection and promises less than 5 ms of end-to-end delay for online gaming, provided the other players are also customers no more than 10,000 km away. Assume an idle network, propagation speed 2.5×108 m/s, no processing/queuing delay, and 100 KB of data generated per second. Can the ISP deliver?

R = 10 Mbps = 10×106 bps; distance m = 10,000 km = 107 m; s = 2.5×108 m/s; data rate = 100 KB/s = 100,000 × 8 = 800,000 bits/sec.

Propagation delay
dprop = m/s = 107 / 2.5×108 = 0.04 s = 40 ms
Transmission delay (per second of data)
dtrans = 800,000 / (10×106) = 0.08 s = 80 ms
Total nodal delay
dtotal = dprop + dtrans = 40 + 80 = 120 ms

Promised delay: < 5 ms. Actual delay: ≈ 120 ms. The ISP cannot deliver on their promise — the sheer volume of data being generated (800 Kbps worth of gaming traffic pushed through a 10 Mbps pipe) dominates the delay budget, dwarfing the already-modest 40 ms propagation delay across 10,000 km.

Q12Finding the transmission speed that synchronizes two packets

Two hosts are 5,000 km apart. Two 4 MB packets must be sent from one host to the other. Queuing delay at the host is 10 ms and the propagation speed is 2.5×108 m/s. Find the transmission speed at the source such that it finishes transmitting the second packet exactly when the first packet arrives at the destination.

Distance m = 5×106 m; packet size = 4 MB = 4×106 bytes = 32×106 bits (using 4×106×8).

Propagation delay
dprop = 5×106 / 2.5×108 = 0.02 s = 20 ms

When does the first packet arrive? It must (1) wait 10 ms in queue, (2) be transmitted for dtrans, and (3) propagate for 20 ms:

tarrive,1 = 10 + dtrans + 20 = 30 + dtrans (ms)

When does the second packet finish transmitting? It waits 10 ms in queue, then the first packet is transmitted (dtrans), then the second is transmitted (another dtrans):

tfinish,2 = 10 + 2dtrans (ms)

Setting these equal (finish transmitting packet 2 = arrival of packet 1):

10 + 2dtrans = 30 + dtrans ⟹ dtrans = 20 ms

Transmission rate: dtrans = L/R ⟹ 0.02 = 32×106/R ⟹ R = 32×106/0.02 = 1.6×109 bps = 1.6 Gbps.

Q13Network transfer vs. driving — which dominates the delay?

100 TB of data is to be transferred between Bengaluru (Host A) and Chennai (Host B), 350 km apart. Transmission speed at Host A = 1 Gbps; propagation speed of the dedicated link = 2×108 m/s. Compare transferring over the link versus driving to Chennai and back (one-way drive = 7 hours). Which delay component dominates?

Data size = 100 TB = 100×2?... using decimal TB: 100×1012×8 = 8×1014 bits.

Transmission time
dtrans = 8×1014 / 109 = 8×105 s = 800,000 s ≈ 222 hours ≈ 9.25 days
Propagation delay
dprop = 350×103 / 2×108 = 0.00175 s = 1.75 ms

— negligible compared to days

Round-trip driving time = 7 + 7 = 14 hours, vastly faster than 9.25 days of network transfer.

Verdict

Driving is much faster. The dominant component is the transmission delay — while propagation delay is a mere 1.75 ms, the time required to push 100 TB through a 1 Gbps "pipe" is so massive that it accounts for roughly 99.99% of the total time. This is the classic "sneakernet"/truck-full-of-hard-drives result: for very large bulk transfers, physical transport of storage media can beat even fast dedicated links.

Q14Lossy high-bandwidth vs lossless lower-bandwidth channel

There are two paths to transmit 100 packets, each 16 MB, from host A to host B: a lossy channel with 50% loss probability at 20 Gbps, and a lossless channel at 10 Gbps. Both channels have a propagation speed of 2×108 m/s and a queuing delay of 10 ms per packet at the host. Assume all lost packets are retransmitted with no additional overhead. Which path is better?

Packet size = 16 MB = 16×8×106 = 128 Mbits.

Path 1 — lossless (10 Gbps)

Transmission delay per packet
dtrans = 128×106 / (10×109) = 0.0128 s = 12.8 ms

Total delay per packet = 10 + 12.8 = 22.8 ms. For 100 packets:

100 × 22.8 ms = 2280 ms = 2.28 seconds

Path 2 — lossy (20 Gbps, 50% loss)

Expected transmissions per packet under 50% loss (geometric retry): 1/(1 − 0.5) = 2. So the total number of transmissions needed: 100 × 2 = 200.

Transmission delay per packet
128×106 / (20×109) = 0.0064 s = 6.4 ms

Total per transmission attempt = 10 + 6.4 = 16.4 ms. For 200 transmission attempts:

200 × 16.4 ms = 3280 ms = 3.28 seconds

Conclusion: even though the lossy link has double the bandwidth, the 50% retransmission rate doubles the number of transmissions needed and, combined with the per-attempt queuing delay, increases total delay significantly. The lossless channel is better for this workload — 2.28 s versus 3.28 s.
