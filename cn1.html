UE25CS243A — COMPUTER NETWORKS · UNIT 1

Unit 1: Internet Foundations, Performance & the Application Layer

Everything up to (but not including) DNS: what the Internet is made of, how packets are delayed and switched, the layered reference model and the devices that live at each layer, and the application layer's founding principles through HTTP/HTTPS — with every worked problem and formula collected at the end.

1. Introduction to Computer Networks and the Internet

A computer network is two or more devices connected together to communicate and share data or resources. The Internet is a massive "network of networks," interconnecting billions of computing devices globally. It can be described from two angles: what it's physically built from, and what it does for the software running on top of it.

1.1 The "nuts and bolts" view

  • End systems (hosts): traditional devices (PCs, workstations, servers) and Internet "things" (smartphones, appliances, traffic-control systems) running network applications, sitting at the Internet's edge.
  • Packet switches: routers and switches that forward packets (discrete chunks of data) across the network infrastructure.
  • Communication links: the physical media connecting components — fiber optics, copper, radio, or satellite. A link's transmission rate is formally called bandwidth.
  • Networks: a localized collection of devices, routers and links managed by a single organization — home networks, enterprise networks, mobile networks, and national/global ISPs.
  • Protocols: the operational rules governing all communication. A protocol defines the format and order of messages exchanged among entities, and the actions taken on transmission or receipt (e.g. TCP, IP, HTTP, Ethernet). Internet standards are formalized in RFCs by the IETF.

1.2 The service view

Two ways to describe the same Internet

Infrastructure for applications: the Internet provides the foundation needed to support high-level services — the Web, streaming video, multimedia teleconferencing, email, distributed systems.

Programming interface: the network offers a distinct programming interface to distributed applications, using logical "hooks" (sockets) that let sending and receiving applications connect to and reliably use the Internet transport service — analogous to a postal service.

2. The Network Edge

The network edge is populated exclusively by end systems (hosts), broadly categorized into clients and servers. In modern architectures, servers are predominantly housed in massive, centralized data centers with high-bandwidth links (tens to hundreds of Gbps) connecting hundreds to thousands of servers.

2.1 Access networks

Access networks are the physical connections linking an end system to the first router (the "edge router") on the path to any distant end system. They're evaluated on transmission rate (bps) and whether access is shared or dedicated.

Home access

Wired Ethernet (up to 1 Gbps), WiFi access points (54–450 Mbps), and a router/firewall/NAT device, connecting to a headend or central office via fiber or coax.

Enterprise networks

A robust mix of wired and wireless tech: institutional mail/web servers through Ethernet switches (100 Mbps–10 Gbps) and institutional routers to the broader Internet.

WLANs

Within/around a building (~100 ft), using 802.11b/g/n (WiFi), up to 100s of Mbps.

Wide-area cellular

Provided by mobile operators over tens of km, using 4G/5G, tens of Mbps.

2.2 Physical media

Physical media are the actual links through which bits propagate between a transmitter and receiver pair.

Guided media (signal confined to a solid medium)

  • Twisted pair (TP): two insulated copper wires (unshielded/shielded). Cat 5 → 100 Mbps–1 Gbps Ethernet; Cat 6 → 10 Gbps.
  • Coaxial cable: two concentric copper conductors; bidirectional, broadband — multiple frequency channels at once, hundreds of Mbps per channel.
  • Fiber optic cable: glass fibers carrying light pulses (one pulse = one bit). High-speed point-to-point (tens–hundreds of Gbps), immune to electromagnetic noise, very low error rates, fewer repeaters needed.

Unguided media

Signals propagate freely through the electromagnetic spectrum with no physical wire — half-duplex, and vulnerable to reflection, obstruction and interference. Includes terrestrial microwave (up to 45 Mbps), WLANs, wide-area cellular, and satellite microwave (large propagation delay, ~280 ms end-to-end).

3. The Network Core

The network core is the intricate mesh of interconnected routers that transports data across the global infrastructure.

3.1 Packet switching vs. circuit switching

Packet switching

Application-layer messages are split into packets, forwarded router-to-router. Routers use store-and-forward: the whole packet must arrive before it's sent onward. Efficient for "bursty" traffic and needs no call setup — but is prone to congestion, delay and loss from buffer overflow.

Circuit switching

End-to-end resources are strictly reserved for the call's duration (classic telephony). Guarantees circuit-like performance, but wastes idle capacity when unused. Relies on FDM (distinct frequency bands per user) or TDM (periodic time frames/slots).

3.2 Routing vs. forwarding

  • Routing: a global, network-wide process using routing algorithms to determine the optimal source-to-destination path.
  • Forwarding: a local, router-specific action — moving an arriving packet from an input link to the correct output link, per the local forwarding table and the packet header.

3.3 Internet structure and hierarchy

Connecting millions of access ISPs directly (an O(N²) mesh) doesn't scale, so the Internet is a hierarchical network of networks: access networks connect to local/regional ISPs, which connect to a small number of well-connected Tier-1 commercial ISPs (Level 3, Sprint, AT&T, NTT) providing national/international coverage. Tier-1 networks peer directly or via Internet Exchange Points (IXPs). Major content providers (Google, Facebook) run private global networks connecting their data centers directly to the Internet — often bypassing regional and Tier-1 ISPs to optimize delivery.

4. Delay, Loss & Throughput — Theory

Network performance is evaluated through delay, loss, and throughput.

4.1 The four components of nodal delay

Total nodal delay
dnodal = dproc + dqueue + dtrans + dprop
  • Processing delay (dproc): time to check for bit errors and determine the output link — typically well under a microsecond.
  • Queuing delay (dqueue): time waiting in the output buffer for transmission — highly variable, depends on router congestion. It's the only one of the four that varies once a route is fixed.
  • Transmission delay (dtrans = L/R): time to push all of a packet's L bits onto the link at rate R.
  • Propagation delay (dprop = d/s): time for a bit to travel the physical distance d at propagation speed s (≈ 2×108–3×108 m/s depending on medium). Independent of packet length or transmission rate.

4.2 Traffic intensity and queuing delay

Traffic intensity
I = L·a / R

L = packet length, a = average packet arrival rate, R = link bandwidth.

  • I ≈ 0 → negligible average queuing delay.
  • I → 1 → queuing delay escalates rapidly.
  • I > 1 → arrival rate exceeds service rate; average delay → ∞. Systems must be engineered so I ≤ 1.
Queuing delay (for I < 1)
Queuing delay = I·L / [R(1 − I)]
Packet loss

A queue (buffer) ahead of a link has finite capacity. Packets that arrive when the buffer is full are irreversibly dropped.

Throughput & Bottleneck Links

Throughput is the rate (bits/time) at which bits are successfully transferred from sender to receiver — measured instantaneously or averaged over time. End-to-end throughput is strictly capped by the bottleneck link: the link on the path with the lowest transmission capacity.

Throughput along a path
Throughput = min(R1, R2, …, RN)

the minimum capacity across every link on the path.

Worked micro-example

10 server–client connections share a backbone hop of R = 300 Mbps (30 Mbps/connection if split evenly). Server links Rs = 50 Mbps, client links Rc = 90 Mbps. Max throughput per connection = min(50, 90, 30) = 30 Mbps — the shared middle link is the bottleneck.

Solved Problems — Delay & Bandwidth-Delay Product

Q1Transmission delay

Packet length L = 4000 bits; transmission rate R = 10 MBps = 10×8×106 = 80 Mbps.

dtrans = L/R = 4000 / (80×106) = 50 microseconds

Q2Network transfer vs. courier — 10 TB Bengaluru → Chennai

Dedicated link at 100 Mbps vs. a courier delivering in one day.

10×1012×8 / (100×106) = 800,000 s ≈ 9.3 days

The courier (1 day) wins decisively — never underestimate the bandwidth of a truck full of hard drives.

Q3Distance from propagation speed and delay

A fiber link runs at 70% of the speed of light and a bit arrives in 10 µs.

s = 0.7 × 3×108 = 2.1×108 m/s
Distance = s × t = 2.1×108 × 10×10-6 = 2100 m

Q4Solving for processing delay given the other three

dtrans = 0.003 ms, dqueue = 1 µs, distance = 3 km, dnodal = 0.04 ms.

0.04×10-3 = dproc + 0.001×10-3 + 0.003×10-3 + 3000/(3×108)
dproc = (0.04 − 0.01 − 0.001 − 0.003) × 10-3 = 0.026 ms

Q5Queuing delay from traffic intensity

R = 1,700,000 bps, L = 1000 bits, a = 31 packets/s.

I = L·a/R = 1000×31 / 1,700,000 ≈ 0.0182
Queuing delay = I(L/R)(1−I) × 1000 ≈ 0.0105 ms

Q6Bandwidth-delay product — how many bits fit "in the pipe"?

Hosts A, B are 20,000 km apart, link R = 5 Mbps, s = 2.5×108 m/s.

Bandwidth-delay product
R × dprop
dprop = 2×107 / 2.5×108 = 0.08 s
R × dprop = 5×106 × 0.08 = 400,000 bits

Sending an 800,000-bit file continuously: since the file (800,000 bits) exceeds the bandwidth-delay product (400,000 bits), only 400,000 bits can be in flight at once — the pipe's own capacity caps it. At R = 1 Gbps instead, the product becomes 80,000,000 bits — now far larger than the file, so the entire 800,000-bit file fits in the pipe at once.

Q7Can an ISP deliver on a latency promise?

ISP promises <5 ms end-to-end delay for gaming at R = 10 Mbps, distance ≤10,000 km, s = 2.5×108 m/s, 100 KB/s of game data, no processing/queuing delay.

dprop = 107/2.5×108 = 0.04 s = 40 ms
dtrans = (100,000×8) / (10×106) = 0.08 s = 80 ms
Total = 40 + 80 = 120 ms

The ISP cannot deliver — actual delay (120 ms) is far beyond the promised 5 ms; the data volume being pushed through the pipe dominates, dwarfing the 40 ms propagation term.

Q8Lossy high-bandwidth vs. lossless lower-bandwidth channel

100 packets × 16 MB (128 Mbits each). Lossy: 20 Gbps, 50% loss. Lossless: 10 Gbps. Queuing delay = 10 ms/packet at the host; propagation identical on both.

Lossless (10 Gbps)
dtrans = 128×106/10×109 = 12.8 ms; per packet total = 22.8 ms
100 × 22.8 ms = 2.28 s
Lossy (20 Gbps, 50% loss)
Expected transmissions/packet = 1/(1−0.5) = 2 → 200 total transmissions
dtrans = 128×106/20×109 = 6.4 ms; per attempt total = 16.4 ms
200 × 16.4 ms = 3.28 s

Even with double the bandwidth, 50% retransmission doubles the number of transmissions needed — the lossless channel wins (2.28 s vs. 3.28 s).

Q9Actual throughput given efficiency

Each link between Alice, Bob and the router is 15 Mbps; network efficiency is 80%.

Ideal throughput = min(15,15) = 15 Mbps
Actual throughput = 0.80 × 15 = 12 Mbps

Q10Maximum throughput under circuit switching

A 10 Mbps link is shared by 7 users under circuit switching, which divides bandwidth equally regardless of activity.

Throughput/user = 10/7 ≈ 1.43 Mbps

Q11Bottleneck-link throughput across a multi-hop path

Host A → Host B across three links: R1 = 10 Mbps, R2 = 5 Mbps, R3 = 30 Mbps, no other traffic.

Throughput = min(10, 5, 30) = 5 Mbps

Q12Four client–server pairs sharing a middle hop

Shared middle link R = 200 Mbps (fairly divided across 4 pairs); server links Rs = 70 Mbps; client links Rc = 90 Mbps.

5. Protocol Layers & Encapsulation

Given the immense complexity of network infrastructure, systems are organized into layered reference models. Layering gives explicit structure and modularizes components — easing maintenance, since changes within one layer stay transparent to the rest of the system.

5.1 The TCP/IP and OSI models

  • Application: supports network applications; unit = Message.
  • Presentation (OSI only): lets applications interpret data meaning — encryption, compression, machine-specific conventions. In TCP/IP this is left to the application developer.
  • Session (OSI only): synchronization, checkpointing, recovery of data exchange.
  • Transport: process-to-process data transfer (TCP, UDP); unit = Segment.
  • Network: routes datagrams from source host to destination host (IP, routing protocols); unit = Datagram.
  • Data Link: transfers data between neighboring elements across a physical link (Ethernet, WiFi); unit = Frame.
  • Physical: transmits raw bits "on the wire."
Encapsulation

As a message descends the stack at the source, each layer appends its own header to the payload: message M gets a transport header Ht to become a segment; the network layer adds Hn to form a datagram; the link layer adds Hl to form a frame. Decapsulation reverses this, header by header, on arrival.

Taxonomy of Network Devices

Network components operate at specific layers, which dictates their functionality and "intelligence" within the architecture.

Physical layer devices

  • Repeater: regenerates, amplifies and reconstructs incoming signals to extend transmission length before attenuation degrades them.
  • Hub: connects multiple units on a LAN by blindly broadcasting incoming data to every port — a single collision domain, shared bandwidth, half-duplex, no address filtering.
  • Modem: connects a computer to the Internet by modulating digital signals into analog waveforms for transmission, and demodulating incoming analog back into digital.

Data link layer devices

  • NIC: a physical card/chip holding a MAC address; handles connectivity, data conversion, error detection.
  • Bridge: a 2-port device joining segments; reduces congestion by filtering traffic via MAC addresses, forwarding based on learned address mappings.
  • Switch: an intelligent, multiport bridge — learns and stores MAC addresses, routes data straight to the intended port. Enables full-duplex, dedicated bandwidth, multiple isolated collision domains, and eliminates broadcast domains.

Higher-layer devices

  • Router (network layer): connects disparate networks, routes packets by logical IP address, builds dynamic routing tables via routing algorithms; also performs NAT (private ↔ public IP translation).
  • Gateway (all layers): a portal between networks with entirely different configurations — a protocol converter, uni- or bi-directional, translating across any OSI layer.
  • Firewall (transport/application layer): monitors incoming/outgoing traffic and applies security rules to permit or block streams.
  • Access Point (AP): a Layer-2 device bridging wireless clients onto the wired LAN — functionally a "wireless hub/bridge."
  • Wireless LAN Controller (WLC): centrally manages many APs across an office/campus — handles roaming and channel planning.
  • L3 Switch: combines a Switch (Layer 2) + Router (Layer 3) in one box — the modern default in campus and data-center networks.

6. Application Layer Principles

The core objective of network application development is to write software that runs on disparate end systems and communicates over the network infrastructure. Because network-core components (routers, switches) operate only at lower layers and never run application software, this decoupling enables rapid application development and deployment — a new app just installs on end systems, without touching the core.

6.1 Client-server vs. peer-to-peer

Client-server paradigm

The server is an always-on host with a permanent IP address, often housed in data centers for scale. Clients initiate contact, may be intermittently connected, may have dynamic IPs, and do not communicate directly with each other. Examples: HTTP, IMAP, FTP.

Peer-to-peer (P2P)

No always-on server; arbitrary end systems ("peers") communicate directly, each acting as both client and server in turn. Self-scalable: new peers add capacity as well as demand. Management is complex due to intermittent connectivity and changing IPs. Example: BitTorrent.

A process is a program running within a host. Processes on the same host use OS-defined inter-process communication; processes on different hosts communicate by exchanging messages. The client process initiates contact; the server process waits to be contacted — even in P2P apps, a peer plays the client role when initiating and the server role when responding.

6.2 Sockets & addressing processes

A process sends/receives messages through its socket — the "door" through which the application shoves a message out, trusting the transport infrastructure on the other side to deliver it to the receiving socket. Everything above the socket is the application developer's responsibility; everything below it is the OS's.

Why an IP address alone isn't enough

Many processes can run on the same host, so an identifier needs both the host's 32-bit IP address and a port number for the specific process (e.g. HTTP server → port 80, mail server → port 25).

What an application-layer protocol defines: the types of messages exchanged (request, response), the message syntax (fields and delineation), the message semantics (field meanings), and the rules for when/how processes send and respond. Protocols are open (defined in RFCs, enabling interoperability — HTTP, SMTP) or proprietary (not openly published — e.g. Skype).

Transport Service Requirements & TCP vs. UDP

Four dimensions matter when an application chooses what it needs from the transport layer:

Data integrity

HTTP, FTP, SMTP need 100% reliable transfer. Real-time audio/video can tolerate some loss.

Throughput

"Bandwidth-sensitive" apps (video conferencing) need a guaranteed minimum. "Elastic" apps (email, file transfer) use whatever's available.

Timing

VoIP and interactive games need low delay (tens of ms) to stay effective.

Security

Encryption and data-integrity guarantees against interception or tampering.

TCP vs. UDP

TCP (connection-oriented)

  • reliable transport between processes
  • flow control: sender won't overwhelm receiver
  • congestion control: throttles the sender when the network is overloaded
  • requires an explicit setup (handshake)
  • does not provide: timing, minimum throughput, security

UDP (connectionless)

  • unreliable, best-effort data transfer
  • no connection setup
  • no flow control, no congestion control
  • no reliability, timing, throughput or security guarantees

7. The Web and HTTP

A web page consists of objects (an HTML file, JPEG image, Java applet, audio file, …), each addressable by a URL — e.g. www.someschool.edu/someDept/pic.gif, where www.someschool.edu is the host name and /someDept/pic.gif the path name. A page with 1 HTML file + 5 images has 6 objects total.

HTTP (Hypertext Transfer Protocol, RFC 1945 / RFC 2616) is the Web's application-layer protocol. It's a client/server model: the browser (client) requests, receives and displays objects; the server sends objects in response. HTTP uses TCP: the client opens a TCP connection (socket) to the server on port 80, the server accepts it, HTTP messages are exchanged, then the TCP connection closes.

HTTP is "stateless"

The server keeps no memory of past client requests.

Why statelessness is deliberate

Stateful protocols are complex: history must be maintained, and if server or client crashes, their views of "state" can become inconsistent and must be reconciled. HTTP's statelessness means no tracking of multi-step exchanges, all requests are independent, and there's no need to "recover" a partially-completed transaction.

Non-persistent vs. persistent HTTP

Non-persistent HTTP

Open a TCP connection → send at most one object → close the connection. Multiple objects need multiple connections. Each object costs 2 RTT (one for TCP setup, one for request + first bytes of response) plus transmission time.

Persistent HTTP (HTTP/1.1)

The server leaves the connection open after responding; later requests to the same client/server reuse it. The client can send requests as soon as it discovers referenced objects, cutting response time to as little as 1 RTT for all objects.

Non-persistent HTTP response time (per object)
2·RTT + file transmission time

Three connection-management patterns in practice: short-lived connections (fresh TCP per object — non-persistent), a single persistent connection reused sequentially, and HTTP pipelining (multiple requests fired back-to-back over one persistent connection, without waiting for each response).

HTTP Request & Response Messages

Both request and response messages are plain ASCII text.

Request message

A request line (method, space, URL, space, version, CRLF), followed by header lines, a blank CRLF, and an optional entity body.

GET

Requests an object; can also send data appended to the URL after a ? (e.g. ?monkeys&banana).

POST

Sends form/user input to the server in the entity body.

HEAD

Requests only the headers a GET would return — no body.

PUT

Uploads a file, completely replacing whatever exists at that URL with the entity body's content.

Response message

A status line (protocol, status code, status phrase), header lines (Date, Server, Content-Length, …), a blank line, then the data payload.

Status codes

  • 200 OK — request succeeded; object follows.
  • 301 Moved Permanently — object moved; new location in the Location: header.
  • 400 Bad Request — server didn't understand the request.
  • 404 Not Found — object doesn't exist on this server.
  • 505 HTTP Version Not Supported.

Cookies & Maintaining State

Since HTTP is stateless by design, the Web uses cookies to simulate persistence across multi-step transactions, built from four components:

  1. a Set-cookie: header line in the server's HTTP response
  2. a Cookie: header line the browser injects into subsequent requests
  3. a cookie file kept on the user's host, managed by the browser
  4. a back-end database at the website that maps the ID back to user context

Uses: shopping carts, login/authorization, tracking visitor counts and browsing history, recommendations, coupon codes.

First-party vs. third-party cookies

First-party cookies track behavior on the site the user actually chose to visit. Third-party cookies (typically set by ad networks embedded across many sites) let a single identity be tracked across multiple unrelated websites — even though the user never directly visited the tracker's own domain. Modern browsers restrict third-party cookies by default.

Web Caches (Proxy Servers) & Conditional GET

Goal: satisfy a client's request without the origin server being involved at all. The browser is configured to send all HTTP requests to a cache: on a cache hit the cache returns the object directly; on a cache miss it requests the object from the origin, caches it, then returns it. A web cache acts as both server (to the client) and client (to the origin) at once — typically installed by an ISP.

Why cache: reduces client response time (physically closer), reduces access-link traffic, lets under-resourced content providers deliver content more effectively, improves privacy (more anonymous browsing), and enables activity logging.

WorkedCaching vs. upgrading the access link

LAN = 1 Gbps; access link = 1.54 Mbps; RTT to origin = 2 s; object size = 100 Kbits; request rate = 15/s.

Without caching
Access-link utilization = (15 × 100 Kbits) / 1.54 Mbps ≈ 0.97

At ~97% utilization, queuing delay explodes — end-to-end delay stretches into minutes.

Option A — upgrade the link to 154 Mbps: utilization drops to 0.0097; delay drops to milliseconds — but a much faster link is expensive.

Option B — add a cache with a 40% hit rate (60% of requests still hit the origin):

Access-link utilization = 0.6 × 1.50 / 1.54 ≈ 0.58
Avg end-to-end delay = 0.6 × 2.01 s + 0.4 × (~0 ms) ≈ 1.2 s

Conclusion: a cheap cache beats an expensive faster link for lowering average delay.

Conditional GET

Goal: avoid re-sending an object the cache already has up to date. The cache sends If-modified-since: <date>; if the object is unchanged, the server replies with an empty HTTP/1.0 304 Not Modified — otherwise a normal 200 OK with the full data.

HTTP/2 and HTTP/3

Shared goal: decrease delay in multi-object HTTP requests.

HTTP/1.1's pipelined GETs are served in-order (FCFS). This causes head-of-line (HOL) blocking: a small object can get stuck behind a large one, and loss recovery (retransmitting a lost segment) stalls every object queued behind it.

HTTP/2 [RFC 7540, 2015]

  • methods, status codes and most headers are unchanged from HTTP/1.1
  • transmission order follows client-specified priority, not strict FCFS
  • the server can push unrequested objects
  • objects are split into frames, scheduled to mitigate HOL blocking
HTTP/2's remaining limit

It still runs over a single TCP connection, so packet-loss recovery still stalls every object on that connection — and there's no built-in security in TCP itself.

HTTP/3

Runs over UDP via QUIC instead of TCP, adding mandatory security plus per-object error- and congestion-control (finer-grained "pipelining") — a lost packet on one stream no longer stalls unrelated streams.

HTTPS & Transport Layer Security (TLS)

HTTPS is HTTP with encryption — bi-directional, over port 443 (vs. 80 for plain HTTP). It uses TLS (formerly SSL) to encrypt requests/responses, so eavesdroppers on the wire can't read the traffic, and the client can verify it's really talking to the server it thinks it is.

Public/private-key cryptography

Asymmetric encryption

Two different keys: a public key for encryption, a secret private key for decryption. Only the matching private key can decrypt what the public key encrypted.

Symmetric encryption

The same secret key encrypts and decrypts — much faster, used for the bulk of TLS traffic once a shared key is agreed.

An SSL/TLS (X.509) certificate, issued by a Certificate Authority (CA), contains: the domain name, the server's public key, issuer/CA info, an expiration date, and a CA digital signature.

Three guarantees TLS provides

  • Confidentiality — symmetric encryption keeps eavesdroppers out.
  • Integrity — cryptographic hashing detects tampering/corruption.
  • Authentication — public-key cryptography verifies the server's identity.

History: SSL → TLS 1.3

  • SSL — created by Netscape, mid-1990s; 1.0 never released (major flaws); 2.0/3.0 released 1995/1996, later broken.
  • TLS — IETF's official successor from 1999. TLS 1.0/1.1 (1999/2006) are deprecated; TLS 1.2 and 1.3 are the only actively-used secure standards today.
"SSL Certificate" is a naming fossil

A digital certificate works the same regardless of whether the server ultimately speaks TLS 1.2, 1.3, or legacy SSL. The term persists from ~30 years of marketing; modern tools actually run TLS, not SSL.

What changed from SSL to modern TLS

Handshake & performance: SSL needed multiple round trips (2-RTT); TLS 1.3 cuts this to 1-RTT by sending key-exchange parameters in the very first message.

Cryptography: weak algorithms (RC4, RSA key transport, MD5) were dropped in favor of authenticated encryption (AES-GCM, ChaCha20).

Forward secrecy: TLS mandates ephemeral Diffie-Hellman session keys, so a stolen server key can't retroactively decrypt previously recorded traffic.

How TLS authentication works

  1. Certificate presentation: server sends its certificate (public key + CA signature).
  2. CA trust verification: browser checks the signature against its trusted root CA list.
  3. Proof of ownership: server signs a unique handshake message with its private key, proving it isn't replaying a stolen certificate.
  4. Public-key verification: browser decrypts that signature with the certificate's public key — success confirms the server holds the matching private key.

TLS 1.3 handshakes: 1-RTT and 0-RTT

1-RTT (new connection): Client Hello (proposed key-agreement params + supported cipher suites) → Server Hello (chosen params, cipher suite, signed certificate) → client verifies, derives the shared key, and can immediately issue an HTTPS GET.

In TLS 1.2/SSL the certificate was sent in plain text — visible to anyone monitoring the network. In TLS 1.3, a temporary secret key is established before the certificate is sent, so it travels encrypted.

0-RTT (session resumption)

Returning clients holding a Pre-Shared Key (PSK) can send encrypted application data in the very first packet, eliminating handshake latency — but 0-RTT data is vulnerable to replay attacks, so it's only safe for idempotent requests (a GET), not state-changing ones (a payment).

Delay

Total nodal delay
dnodal = dproc + dqueue + dtrans + dprop
Transmission delay
dtrans = L / R

L = packet length (bits), R = transmission rate (bps)

Propagation delay
dprop = d / s

d = distance (m), s = propagation speed (m/s)

End-to-end delay (ignoring proc/queue)
dend-to-end = L/R + d/s
Traffic intensity
I = L·a / R

must keep I ≤ 1; a = average packet arrival rate

Queuing delay (I < 1)
Queuing delay = I·L / [R(1 − I)]

Throughput

End-to-end throughput
Throughput = min(R1, R2, …, RN)

capped by the bottleneck link

Bandwidth-delay product
R × dprop

max bits "in flight" in the link at once

HTTP timing

Non-persistent HTTP response time (per object)
2·RTT + file transmission time
Quick reference: RTTs for N objects (1 base file + N−1 referenced objects)

Non-persistent: 2N RTT

Persistent, no pipelining: N + 1 RTT (1 for TCP setup, 1 per object sequentially)

Persistent + pipelining: ≈ 3 RTT (1 TCP setup + 1 base file + 1 batched round for all referenced objects)
