01Functions

A function packages a sequence of code so it can be invoked repeatedly with different inputs. Before we can talk about data structures, we need to be completely comfortable with how functions work in C — especially how arguments are passed, because almost every trick used later (linked lists, stacks) depends on pointers moving data in and out of functions correctly.

Why do we use functions?

Mathematically, a function is a special kind of relation: it associates a sequence of arguments with a single result. In mathematics, applying the same function to the same arguments always gives the same result — this is called a pure function. It doesn't depend on the day, the mood of the caller, or anything else external.

In programming, a function is a named block of code. When it is called (or invoked) with arguments, that code executes and hands a result back to the caller — the code that made the call — from the callee — the function that was called.

We use functions for five main reasons:

  • Divide and conquer — break a complex problem into smaller, manageable parts and solve each separately.
  • Sharing — commonly needed solutions can be grouped into a library, so nobody reinvents the wheel.
  • Maintenance — logic used in many places lives in one function; a fix or update happens in exactly one place.
  • Reliability — library functions are usually well-tested, flexible and efficient; we trust them more than ad-hoc code we just wrote.
  • Reuse — a function can be called again and again without rewriting its body.

Anatomy of a function definition

returntype fnname(<list of parameters with type>)
{
    <statements>
    return <expr>;
}

Every function has a return type. Even if nothing meaningful is returned, the type must be stated explicitly as void — the compiler needs to know, ahead of time, how much temporary space to reserve for the result, and whether it needs to cast the return expression to match.

The parameter list is a comma-separated list of typed variables. Function names follow ordinary identifier rules. Even a function that takes no parameters at all must still have parentheses — void f4() is a function with zero parameters, not an error.

Key ideaParameters are ordinary variables that exist only for the duration of one call. When the function is invoked, an activation record (also called a stack frame) is created to hold the parameters, local variables, temporaries, the return address, and space for the return value. When the function returns, this entire frame is popped and destroyed — there is no concept of a Python-style closure here.
int f1(int x) { return x * x; }
int f2(int x, int y) { return x + y; }
double f3(int x) { return sqrt(x); }
void f4() { printf("f4 says hello\n"); }

int main()
{
    int a = 25, b = 10, res;
    res = f1(a);           // square of a
    res = f1(11);          // square of a literal
    res = f1(11 + a);      // square of an expression
    res = f2(a, b);        // a + b
    printf("sqrt : %lf\n", f3(25.0));
    f4();
}

The function call, step by step

A call looks like fnname(arguments…). Arguments are always expressions. When a call is made, this sequence of events happens:

  1. An activation record is created (return address, parameters, locals, temporaries, return-value slot).
  2. The arguments are evaluated — the order in which multiple arguments are evaluated is undefined in C. So a = 10; f(a++, a); could legally produce either f(10, 10) or f(10, 11). Never write code that depends on argument evaluation order.
  3. Arguments are copied into the corresponding parameters.
  4. Control transfers to the callee.
  5. The function body runs.
  6. On a return statement (or falling off the end), control returns to the caller.
  7. If there was a return expr;, the expression's value is computed and copied into the temporary return slot. If the function is void, this step and the next are simply skipped.
  8. The caller picks up that value — a function call is itself an expression.

Declaration vs. definition

Can we call a function before it's defined, or one defined in a different file? Only if the compiler has already been told the number, types and order of the arguments, and the return type. By default the compiler assumes a missing return type is int — but it cannot check anything about the call unless it already knows the function's shape.

We supply that shape with a declaration (also called a prototype or signature — a term that entered C from C++):

int f2(int x, int y);  // declaration — no body
Interface vs. implementationThe declaration is the interface: it tells a caller what the function expects, but nothing about how it works internally. Because of this separation, the person implementing the function can rewrite its body freely — the caller is never affected, as long as the interface itself doesn't change.

Parameter passing & pointers

C passes arguments by value: the argument is copied into the parameter, and there is no copying back. Changing the parameter can never change the corresponding argument — this is guaranteed and is not something you can work around by "trying harder."

void foo(int x);
int a = 10;
foo(a);
printf("a : %d\n", a); // still 10 — foo cannot touch a

If the argument's type doesn't exactly match the parameter's type, it is converted (e.g. a double silently truncated to int) — but again, this conversion never changes the original variable.

So how do we let a function change a caller's variable? We pass a pointer to it instead. The parameter becomes a pointer; dereferencing that pointer gives us an l-value referring to the original variable, so assigning through it does change the caller's data. This is exactly why scanf needs &variable.

void what(int* q) { int temp = 100; *q = temp; }

int a = 10;
int *p = &a;
what(p);
printf("a : %d\n", a); // 100 — changed via the pointer
Common trapPassing a pointer lets you change what it points to — it does not let you change the pointer variable itself in the caller. 
void bar(int* q) { int temp = 100; q = &temp; } // only changes the local copy q

int a = 10;
int *p = &a;
bar(p);   // a and p in the caller are unaffected
To change a pointer itself from inside a function, you must pass a pointer to a pointer (int**).

Return mechanism & dangling pointers

A return always goes through a temporary: the return expression is evaluated, cast to the function's declared return type if needed, and copied into a temporary slot that the caller then reads. A C function returns exactly one value — but that value can be a pointer.

int* one(int* x) { return x; }
int c = 1000;
int *p = one(&c);
printf("%d\n", *p); // 1000 — perfectly fine, c still exists
Danger — dangling pointer 
int* two() { int x = 111; return &x; } // x is LOCAL!
p = two();
printf("%d\n", *p); // undefined behaviour
x lives in two()'s stack frame, which is destroyed the instant the function returns. The returned pointer p now points to memory that no longer logically exists — a dangling pointer: the pointer still "works" as a value, but the location it refers to is gone. Dereferencing it is undefined behaviour — it might crash, might silently return garbage, or might appear to work by pure luck. Never return the address of a local variable.

Interface vs. implementation — a worked example

Suppose we need to check whether a number is a palindrome. We only need to know the signature:

int is_palindrome(int n);

Client code can use it immediately without knowing (or caring) how it's implemented:

int n; scanf("%d", &n);
if(is_palindrome(n))
    printf("%d is a palindrome\n", n);
else
    printf("%d is not a palindrome\n", n);

The implementor is free to write the reversal logic inline or delegate to a helper rev() function — the client is never affected either way. This split is formalised in C using header files: declarations (the interface) live in a .h file shared by both client and server code; definitions (the implementation) live in a .c file the client never needs to see.

Multiple files and the make tool

A typical modular project has a server file (implementation), a client file (usage) and a header (interface) — e.g. server.c, client.c, server.h. Each .c file is compiled separately and then linked into a single executable. Every time you edit a file, you must remember to recompile — which gets tedious and error-prone as a project grows.

The make tool automates exactly two ideas: (1) which files a target depends on, and (2) which command(s) to run when those dependencies change.

a.out : client.o server.o
    gcc client.o server.o

client.o : client.c server.h
    gcc -c client.c

server.o : server.c server.h
    gcc -c server.c

Run with make -f mymakefile.mk. Each block has a target on the left of :, its source dependencies on the right, and an indented (tab-prefixed) command below that runs only if a dependency is newer than the target.

02Recursion

Recursion expresses the solution to a problem in terms of a smaller instance of the same problem, plus one or more simple "escape hatch" cases that stop the recursion.

What is recursion?

A function that calls itself — directly, or indirectly through another function — is recursive. We can use recursion as an alternative to a loop. Every correct recursive function needs:

  • A base case (also called the escape hatch) — a simple case solved directly, without further recursion.
  • A recursive case — the problem expressed in terms of a smaller version of itself, guaranteed to progress toward the base case.
Tracing tipWhen a function makes recursive calls at more than one place in its body, mark each call site with a number so you always know exactly where execution should resume once a nested call returns.

Example — counting set bits

This function counts the number of 1s in the binary representation of a number. If n is odd, its last bit is 1, so we count it and recurse on n / 2. If it's even, the last bit is 0, so we just recurse on n / 2. If n is 0, there's nothing left to count.

int what(int n)
{
    if(n == 0)          return 0;                     // base case
    else if(n % 2)     return 1 + what(n / 2);       // odd: count this bit
    else              return what(n / 2);           // even: skip this bit
}

Tracing what(25): 25 is 11001 in binary, i.e. three 1-bits. The calls unfold as what(25) → 1+what(12) → 1+what(6) → 1+what(3) → 1+what(1) → 1+what(0), which returns 0, then unwinds back up adding 1 three times, giving 3.

Example — fast exponentiation

What does this function compute?

int what(int a, int n)
{
    if(n == 0)      return 1;
    else if(n % 2) return a * what(a * a, n / 2);
    else          return what(a * a, n / 2);
}

It computes an using the classic "fast power" idea: if n is even, square the base and halve the exponent (an = (a²)n/2); if n is odd, do the same but multiply one extra factor of a back in. This runs in O(log n) multiplications instead of the naive O(n).

Aliasing surprise — GCD via pointers

This function computes the greatest common divisor of the two values pointed to by p and q, and then divides each argument by that GCD in place:

void what(int *p, int *q)
{
    int m = *p, n = *q;
    while(m != n) { if(m > n) m -= n; else n -= m; }
    *p /= m; *q /= n;
}

int a = 25, b = 15;
what(&a, &b);           // a becomes 5, b becomes 3 — as expected
what(&a, &a);           // !! surprising !!
printf("%d\n", a);

The second call passes the address of a for both parameters — p and q now point to the exact same memory. This is called aliasing. Since a already equals itself, m == n immediately (both become the current value of a, say 5), so the loop body never runs. Then *p /= m divides a by 5, making a become 1. But then *q /= n runs — and q is also a, which is now 1, while n is still the old value 5 — so a becomes 1 / 5 = 0. Aliasing silently corrupted the result. This is a powerful lesson: when two pointer parameters can refer to the same object, code that looks correct for distinct variables can misbehave.

03Arrays

An array is a fixed-size, homogeneous, contiguous block of storage accessed by an integer index. It resembles a Python list, but with important restrictions that come from C's low-level, no-safety-net philosophy.

Array — characteristics

  • Has a fixed number of elements, all of the same type (homogeneous).
  • Size is fixed at creation — either a compile-time constant, or (in C99) a runtime value via a Variable Length Array (VLA).
  • An array can never grow or shrink.
  • Elements are selected by a zero-based integer index (or subscript).
  • Supports random access: the time to access any element is the same, regardless of its position.
  • At compile time, the compiler knows everything about the array (its size, its type). At runtime, the array "degenerates" into a plain pointer — the size information is simply not stored anywhere.
  • Out-of-bounds access is never checked. Checking would need extra memory (to store the size at runtime) and extra time on every access — a cost C refuses to impose on every program just to protect careless code. C's philosophy: the programmer gets what he deserves.
  • Because an array degenerates to a constant pointer, arrays cannot be assigned to one another — they are not assignment-compatible.
Undefined behaviourint a[5]; a[5] = 1; compiles without warning but writes past the array's end. Nothing stops it, nothing guarantees a crash — the program may run "fine" for a while and fail unpredictably later.

Declaration & initialization

int a[] = {10, 20, 30, 40, 50};  // compiler counts 5 elements
int b[5];                       // 5 uninitialized elements (local scope)
int c[5] = {11, 22};             // remaining 3 elements become 0

When an initializer list is shorter than the declared size, C fills the rest with zero — but it will never silently make the array bigger than declared.

Traversal — four equivalent styles

Given int a[] = {10,20,30,40,50}; int n = 5;, here are increasingly pointer-flavoured ways to walk it — all produce identical output.

a) Plain indexing

for(int i=0; i<n; ++i)
    printf("%d ", a[i]);

b) Pointer standing in for the array

int *p = a;
for(int i=0; i<n; ++i)
    printf("%d ", p[i]);

c) Pointer arithmetic

int *p = a;
for(int i=0; i<n; ++i)
    printf("%d ", *(p + i));

d) Incrementing the pointer

int *p = a;
for(int i=0; i<n; ++i)
    printf("%d ", *p++);

Only three pointer operations are legal in C: adding an integer to a pointer, subtracting an integer from a pointer, and subtracting two pointers into the same array. Nothing else — a pointer must never be treated as if it were an ordinary integer.

Why version (d) can't use the array name*a++ would try to increment a itself — but an array name is a constant pointer, so a++ is a compile error. Only a genuine pointer variable like p can be incremented. Also note the difference between (*p)++ (increments the value at p, yielding the old value there) and *p++ (increments p itself, dereferencing the old address).

Passing arrays to functions

When an array is passed as an argument, the parameter always becomes a pointer — it is never actually an array, and there is no way to recover the number of elements from just the pointer. int x[] and int *x as a parameter mean exactly the same thing.

Because the size is lost, we must communicate it separately, using one of three conventions:

  1. Pass the array and its size explicitly.
  2. Pass a pointer to the beginning and a pointer to the end.
  3. Use a sentinel — a special logical value marking the end (like C strings using '\0').
void read_array(int x[], int n)
{
    for(int i=0; i<n; ++i) scanf("%d", x++);  // &x[i], x+i, x++ all equivalent
}
void disp_array(int *x, int n)
{
    for(int i=0; i<n; ++i) printf("%d ", *x++);
}

Multidimensional arrays

Since arrays are homogeneous and elements can themselves be arrays, we get multidimensional arrays. A matrix is naturally an array of arrays — a two-dimensional array.

int a[5][4]; // conceptually 5 rows, 4 columns

Conceptually this looks like a grid, but the compiler lays it out as one long, linear, contiguous strip of memory in row-major order — row 0's four elements, then row 1's four elements, and so on. At runtime, the array degenerates to a pointer to its first row.

A 2×3 array is really one flat run of 6 integers; the "rows and columns" are just a way of computing offsets into it.

The row-major address formula

Without knowing the number of columns per row, it is impossible to locate an element inside a linear block. This is exactly why the row count is required in a 2D array's type.

Row-major address formula Address(A[i][j]) = Base_Address + ( (i × columns_per_row) + j ) × size_of_element

Worked example: int a[2][3] = {{66,90,86},{23,44,11}}; with base address 2000 and sizeof(int) = 4:

address(a[1][2]) = 2000 + ((1 * 3) + 2) * 4 = 2000 + 20 = 2020

Which matches the value 11 in the diagram above.

Two-dimensional arrays can also be initialized row by row, partially (missing elements default to 0), or as one flat, comma-separated sequence — int c[3][2] = {11,22,33,44,55,66}; is identical to {{11,22},{33,44},{55,66}}. A 2D array is always rectangular: int a[][3] = {{11,22,100},{33,44}}; gives 2 rows (counted from the outer braces) of 3 columns each — 6 integers total, with the missing trailing values zero-filled.

Because the array name is a pointer to its first row, indexing decomposes as pointer arithmetic: a[3][2] is exactly the same value as *(*(a + 3) + 2). We can also declare a "pointer to an array of 4 ints" directly: int (*p)[4] = a; p[3][2] works identically.

Passing 2D arrays to functions

The parameter becomes a pointer to a row, and the number of columns must be known to compute row offsets — so it cannot be omitted:

void foo(int x[][4]);      // OK — column count required
void foo(int (*x)[4]);     // OK — same thing, explicit pointer form
void foo(int x[5][4]);     // OK — first dimension is ignored anyway

void foo(int x[][]);       // ✗ illegal — column count missing
void foo(int x[5][]);      // ✗ illegal — same problem

To make a routine work for any matrix size (not just a hard-coded number of columns), C99 lets you forward-declare the size parameters before the array parameter, separated by ;:

void disp_matrix(int rowsize; int colsize; int x[rowsize][colsize], int rowsize, int colsize);

Whatever comes after the rightmost ; is the real parameter list; what precedes it just tells the compiler that rowsize and colsize will appear later. Note that colsize must match the array's actual physical layout, not just whatever logical portion of it your program chooses to use.

04Structures

Think of a backpack: laptop, books, pens, a water bottle — all different types of things, but easier to carry (and refer to) together under one name. A structure does exactly this for related, possibly non-homogeneous, data.

Structures — the basics

struct student
{
    int rnum;
    char name[20];
    int marks;
};

This declares a type — struct student — with three named fields (or members): rnum, name, and marks. The declaration fixes the binary layout — field order and total size — but creates no variable, and therefore uses no memory by itself. Note the required trailing ; — it signals that no variables were declared right after the closing brace (though they legally could have been).

struct student s1;
strcpy(s1.name, "abc");
s1.marks = 78;
s1.rnum = 56;

struct student *p = &s1;
p->marks;      // preferred: p is already "dereferenced" conceptually
(*p).marks;    // equivalent — parentheses needed because of operator precedence

Characteristics of a structure:

  • One or more components, generally heterogeneous, each with a name (unlike an array, whose components are found by computed index).
  • Every field's offset is fixed at compile time — a structure, like an array, supports random access: reaching any field costs the same regardless of its position.
  • Total size depends on the implementation, but is at least the sum of its members' sizes (see padding, next section).
  • A structure variable stands for the whole structure — it does not degenerate to a pointer the way an array does.
  • Structures are assignment-compatible: t2 = t1; triggers a memberwise copy, and this works even if a member is itself an array.

Layout, padding & alignment

struct test1 { char j; int i; };

If char is 1 byte and int is 4 bytes, is sizeof(struct test1) exactly 5? Not necessarily — it depends on the implementation. Every type has an alignment requirement (a byte boundary, word boundary, etc.) that lets the CPU access it efficiently. To keep i aligned, the compiler may insert unused filler bytes — called padding — between j and i. So this structure might report size 8 (time-efficient, word-aligned) or size 5 (space-efficient, no padding).

AnalogyIt's like note-taking: starting a new topic on a fresh page (padding) makes it easier to find later but wastes paper; cramming it onto the same page (no padding) saves paper but makes scanning slower. Neither choice is "wrong" — it's a trade-off.

The compiler directive #pragma pack(1) forces byte-boundary alignment (no padding at all). Pragmas are compiler directives and are not portable — not every compiler supports them the same way.

Initializing structures

struct student s1;                       // uninitialized — fields hold junk
struct student s2 = {23, "pes", 99};       // order must match field order
struct student s3 = {23, "pes"};            // partial — remaining field(s) become 0
struct student s5 = {.name="pes", .marks=45}; // designated initialization, by field name

Copying & comparing structures

struct test1 { int i; char ch; };
struct test1 t1 = {23, 'w'};
struct test1 t2 = t1;   // memberwise copy: t2.i=23, t2.ch='w'
t1.i = 189;         // t2.i is completely unaffected

C provides no operator to compare two structures directly (no t1 == t2). You must compare field by field: if(t1.i==t2.i && t1.ch==t2.ch).

Watch outIf a field is itself a pointer, a memberwise copy only copies the pointer value — both copies now point to the same target, creating aliasing. See "Structures holding heap pointers" below.

Passing & returning structures

A structure argument is passed by value — a full copy is made, so changes made inside the function never reach the caller's original:

void f1(struct test t) { strcpy(t.a, "pqrstuv"); } // t.a change is local only

To let a function modify the caller's structure, pass a pointer:

void f2(struct test* p) { strcpy(p->a, "pqr"); }
f2(&t1); // t1.a is now "pqr"

When you want to pass a structure efficiently but guarantee it won't be modified, pass a pointer to a constant structure:

void f3(const struct test* p) { printf("%s\n", p->a); } // writes through p are compile errors
Best practicePassing a structure by value is generally considered bad practice: it costs more memory, more copy time, and causes subtle problems if any member is a pointer. Prefer pointers — const-qualified when you don't intend to modify.

A function can also return a structure by value (copied into a temporary, then assigned to a variable in the caller) or a pointer to one — but if returning a pointer, it must point to something that outlives the function call (never a local variable — same dangling-pointer trap as before).

typedef — naming a type

When a client writes int a;, they don't need to know how an int is stored — just what operations are legal on it. We'd like the same for structures: give the type one clean name, and by convention, discourage the user from poking at its internals directly (so the implementation can later change — say to an array, or a structure of structures — without breaking client code).

typedef struct student student_t;  // creates a type NAME
student_t s1;                    // creates a VARIABLE of that type

05Dynamic Memory Management

So far, every variable has been created on entering a block and destroyed on leaving it — we had no control over the timing. Dynamic memory lets a program request memory whenever it needs it, and release it whenever it's done, independent of any function's block structure.

Before we begin: pointer refresher

A variable in a block is created (given an address) as soon as the block is entered, but is not initialized by default. If the variable is a pointer, dereferencing it before assigning it a valid address is undefined behaviour — the program may not crash, but reading through garbage as if it were an address is dangerous.

int *p; int a = 10; p = &a;
int **pp = &p;

printf("%p\n", &pp);  // address of a variable whose type is int**
printf("%p\n", pp);   // value of pp — an address, of type int*
printf("%p\n", *pp);  // value of p — an address, of type int
printf("%d\n", **pp); // value of a

The memory region managed dynamically is called the heap.

malloc & free

FunctionWhat it does
malloc(size)Allocates size bytes on the heap; returns a generic void* (cast to the type you need); returns NULL on failure.
free(ptr)Returns previously-allocated memory back to the heap manager.
calloc(n, size)Allocates memory for n elements of size bytes each, and zero-initializes every byte.
realloc(ptr, size)Resizes a previously allocated block, copying old values into the new location if it moves.
int *p = (int*)malloc(sizeof(int));  // don't hard-code "4 bytes" — use sizeof
*p = 20;
free(p);
BookkeepingYou never tell free how many bytes to release — so how does it know? When malloc allocates memory, it secretly stores the block's size somewhere alongside it — this hidden accounting is called bookkeeping (or housekeeping). free looks this up using the pointer value you give it, regardless of which variable name holds that value.
int *p = (int*)malloc(sizeof(int) * 4); // "array on the heap"
p[0] = 11; *(p + 1) = 22;
free(p);         // releases the whole 4-int block at once
free(p + 1);     // ✗ TERRIBLE — p+1 was never returned by malloc; no bookkeeping there

Calling free on a pointer not pointing to a heap block returned by malloc/calloc/realloc, or freeing the same pointer twice, are both undefined behaviour.

int *p = (int*)malloc(sizeof(int));
*p = 20;
int *q = p;   // q is an alias of p
free(q);      // perfectly valid — free cares about the pointer VALUE, not the variable name

Garbage, leaks & dangling pointers

These two failure modes are opposites, and it's important to keep them distinct:

TermDefinition
Garbage / Memory leakA location exists on the heap, but you have no access to it any more (every pointer that referenced it has been overwritten or gone out of scope).
Dangling pointerYou still have access (a pointer variable with a value) but the location it points to no longer exists (it was freed, or was a local variable whose stack frame is gone).
// Garbage / memory leak
p = (int*)malloc(sizeof(int)); *p = 30;
p = (int*)malloc(sizeof(int));  // the first block is now unreachable — leaked!
// Dangling pointer
int *p = (int*)malloc(sizeof(int)); *p = 30;
int *q = p;
free(q);
printf("%d\n", *p); // p is now dangling — dereferencing is undefined behaviour
Important distinctionA dangling pointer, by itself, is not dangerous — the pointer variable is just holding an address, which is harmless. Dereferencing it is what's dangerous. Also: dangling pointers can happen anywhere (heap or stack), but a memory leak can only happen on the heap — a leaked stack variable is automatically reclaimed when its block exits.

Unlike Python (which uses reference-count based garbage collection), C has no garbage collector — automatic reclamation costs time and space that C's design philosophy refuses to spend by default. Keeping memory clean is entirely the programmer's responsibility.

calloc & realloc

int *p = (int*)calloc(4, sizeof(int)); // 4 ints, all zeroed — calloc gives no choice of initial value besides 0
int *q = (int*)realloc(p, 10000); // resize the block p points to
  • Size can be increased or decreased.
  • The pointer returned by realloc may differ from the original — the block may physically move.
  • On growth, existing values are copied forward; new locations are left uninitialized.
  • On shrinkage, only values that fit in the new, smaller size are kept — the rest are lost.

Self-referential structures

struct A { int c; struct A *p; }; // perfectly legal

struct Z { int c; struct Z z; };  // ✗ compile error — infinite size!

A structure directly containing a field of its own type (struct Z) is a compile-time error — the compiler can never finish computing its size, since that size depends on itself. But a structure containing a pointer to its own type is perfectly fine, because every pointer has a fixed, known size regardless of what it points to. This is called a self-referential structure, and it is the foundation of every linked structure we build next (linked lists, stacks, trees).

struct A one;
one.c = 10;
one.p = &one;  // points to itself!
printf("%d %d %d\n", one.c, one.p->c, one.p->p->c); // 10 10 10 — one.p and one.p.p are the same object

Structures holding heap pointers

When a structure contains a pointer field and gets copied (by assignment or passing), the pointer field is copied as a value — both structures end up pointing at the same heap block. This creates several classic scenarios:

CaseWhat happens
1. Pointer to a local variablex.p = &z; y = x; — both x.p and y.p alias z. Changing z through either pointer affects both.
2. Both point to the same heap block, then one is freedy = x; (both point to the same malloc'd int); freeing through either makes both dangling.
3. After copy, reassign y's pointer to a fresh blockThe aliasing is broken — x.p and y.p now point to two independent locations. Safe.
4. After copy, reassign x's pointer insteadSame outcome as case 3 — aliasing broken, both safe.
5. Pointer set to NULL after useThe heap block becomes unreachable — garbage, hence a memory leak (the pointer itself is fine — it's just NULL now — but the block it used to hold is lost).

06The Concept of Type & Abstract Data Types

Before building actual data structures, it helps to be precise about what a "type" even is, and why we want to invent our own.

The concept of a type

We naturally classify things around us — "sportsman", "musician" — grouping items that share behaviour. This idea traces back to Mathematics' concept of a set: natural numbers, extended to integers, then rationals, then reals, then complex numbers — each extension driven by an operation that wasn't "closed" in the smaller set.

A type in a programming language captures this same idea:

  • It specifies what values are legal.
  • It specifies what operations we can perform on those values.
  • It does not say how those operations are carried out internally.
  • It lets us treat every value of that type uniformly (adding two integers works the same regardless of their specific values).

In C, a variable's type is fixed at declaration and can never change; type-checking happens at compile time. Python is the opposite: type is attached to the value, not the variable, and can change dynamically.

Abstract Data Types (ADTs)

Can a language support every possible real-world "type"? No — the set of possible things is unbounded. Instead, a good language gives us a way to define our own types. This is exactly what an Abstract Data Type (ADT) is:

  • Like a built-in type, it exposes a small set of operations.
  • It specifies what those operations do, never how.
  • The interface is fixed ("sacred") once decided; the implementation underneath can be freely changed.
  • Both the user and the implementor depend only on the interface — never on each other's code. This is called inversion of dependency: if A depends on B directly, any change to B forces a change to A; but if both A and B depend only on something stable (the interface), changing one never breaks the other.
Car analogyYou can drive almost any car once you've learned to drive one — the interface (steering wheel, pedals) never changes, even though the implementation underneath (mechanical vs. hydraulic brakes, manual vs. power steering) varies wildly. Imagine if pressing the brake sometimes accelerated the car instead — an interface, once agreed upon, simply cannot change.

A Data Structure, in this course's terms, is:

  • An interface.
  • With a number of elements arranged in a particular way to support a few operations efficiently.
  • Constrained by time and space trade-offs — there's rarely a single "correct" arrangement, only ones better suited to a particular use (like tumblers or books arranged for either compact storage or easy access — neither is objectively "wrong").

List — as an ADT

A list is a data structure with:

  • Zero or more components.
  • Each element has an ordinal position (unlike a Python set, which has no notion of position).
  • No random access — only sequential access, one element after another.
  • Insertion/deletion at a known position needs only a handful of pointer operations — no shifting, unlike an array.

Interface: create, destroy, insert, delete, … Implementation choices: an array, or a linked list.

07Linked Lists

A linked list is the classic implementation of the List ADT, built directly on top of self-referential structures and dynamic memory.

Building a linked list

struct node { int key_; struct node *next_; };
typedef struct node node_t;

next_ is a pointer to the same type of structure — a self-referential structure, exactly as introduced earlier. We build a three-node list one malloc call at a time:

node_t *p;
p = (node_t*)malloc(sizeof(node_t));
p->key_ = 20;

p->next_ = (node_t*)malloc(sizeof(node_t));
p->next_->key_ = 40;

p->next_->next_ = (node_t*)malloc(sizeof(node_t));
p->next_->next_->key_ = 60;
p->next_->next_->next_ = NULL;  // terminator — marks the end of the list

Each node holds a key and a pointer to the next node; the final node's pointer is NULL, marking the list's end.

Traversing & freeing a list

void disp(node_t* q)
{
    while(q != NULL) { printf("%d ", q->key_); q = q->next_; }
}
The single most important statement in data structures q = q -> next_;

We can't do q++ to move along the list — nodes are scattered wherever malloc happened to place them, not laid out contiguously like an array. Instead we follow the explicit link stored inside the current node.

void freelist(node_t* q)
{
    node_t* r;
    while(q != NULL) { r = q->next_; free(q); q = r; }
}
Order mattersYou must save q->next_ into r before calling free(q) — once a node is freed, reading its next_ field is undefined behaviour. This "save the link before you cut it" pattern recurs throughout data structures. Also note: never write plain free(p) where p is the head — that would free only the first node and strand the rest of the list as unreachable garbage.

Ordered insertion — the four cases

An ordered list keeps nodes sorted (non-decreasing key order, say). Insertion has to consider four distinct situations:

  1. Empty list — the new node simply becomes the head.
  2. Insert in the middle — the new node's key falls between two existing nodes.
  3. Insert at the end — the new key is larger than everything currently in the list.
  4. Insert at the beginning — the new key is smaller than the current head's key.
if(ptr_list->head == NULL)
{
    ptr_list->head = temp;
    temp->next_ = NULL;    // case 1: empty list
}

For a non-empty list, we need two pointers walking together — a lagging prev and a leading pres — because a singly-linked list only lets us move forward. If we only tracked pres and moved past the correct insertion point, there would be no way to "go back":

node_t* prev = NULL;
node_t* pres = ptr_list->head;
while(pres != NULL && pres->key_ < temp->key_)
{
    prev = pres;
    pres = pres->next_;
}
// after the loop: temp is inserted between prev and pres

Once the loop ends, prev and pres straddle the correct insertion point (either could be NULL, covering the beginning/end cases naturally), and the new node's links are rewired around them.

08Stacks

A stack is a data structure where every operation happens at exactly one end — the "top". Like a spring-loaded stack of plates in a cafeteria: you can only add or remove from the top.

Stack — interface (LIFO)

The stack ADT is Last-In, First-Out (LIFO). Its interface, independent of implementation, is:

FunctionPurpose
void init_stack(stack_t*)Initialize an empty stack.
void deinit_stack(stack_t*)Remove all elements, returning the stack to empty.
void push(stack_t*, T val)Add an element at the top.
T pop(stack_t*)Remove and return the top element.
int is_empty(stack_t*)True if there is nothing to pop.
int is_full(stack_t*)True if there is no room left to push (array version only, in practice).

Crucially, using a stack never requires knowing how it's implemented — exactly the interface/implementation split from Chapter 6.

Last-In, First-Out: the most recently pushed element is always the first one popped.

Array implementation

#define MAXSIZE 5
struct stack { char key_[MAXSIZE]; int top_; };
typedef struct stack stack_t;

The design decision: top_ tracks the index of the last element added (not the next free slot). This single decision shapes every function:

  • init_stack sets top_ = -1 — a deliberately invalid array index, meaning "empty."
  • is_empty just checks top_ == -1.
  • is_full checks whether top_ has reached MAXSIZE - 1.
  • push increments top_ first, checks for fullness, then stores the value.
  • pop checks for emptiness first, then reads the value at top_ and decrements it.

Linked-list implementation

struct node { char key_; struct node* next_; };
typedef struct node node_t;
struct stack { node_t* top_; };
typedef struct stack stack_t;

The interface (the six function signatures) is identical to the array version — clients don't need to change a single line of their own code, at most a recompile.

  • init_stack sets top_ = NULL.
  • push creates a new node, links its next_ to the current top, then moves top_ to point at the new node — in that order.
  • pop: (1) save the key, (2) save the top node's address, (3) advance top_ to the next node, (4) free the saved old node, (5) return the saved key.
  • is_empty checks top_ == NULL.
  • is_full is trickier — there's no fixed capacity, so we try a trial malloc: if it fails, the stack is (heap-)full; either way, we must immediately free that trial allocation to avoid a leak.
The power of an ADTThe client code that uses push/pop is completely unaware whether the stack underneath is an array or a linked list. That is the entire point of separating interface from implementation.

Application — well-formed parentheses

Is ((5 + 6) * (7 + 8)) well-formed? Ignoring everything except the brackets: (()) — matched. But )( or ())()) are not — matching counts of ( and ) is necessary but not sufficient; order matters too (a closing bracket must never appear before its matching opener).

Algorithm For each character: '(' → push a placeholder. ')' → if the stack is empty, invalid; otherwise pop. At the end, the string is valid only if the stack is empty and we never hit an empty-stack pop. 
int is_valid = 1; char ch, *s = str;
while(is_valid && (ch = *s++) != '\0')
{
    if(ch == '(')      push(&mystack, 'x');
    else if(ch == ')')
    {
        if(!is_empty(&mystack)) pop(&mystack);
        else is_valid = 0;
    }
}
if(is_valid && is_empty(&mystack)) printf("Well formed expression\n");
else printf("not well formed expression\n");

Application — mixed bracket types

What about (){}[], ([{}])? A single placeholder is no longer enough — ([)] must be rejected even though brackets are individually balanced. The trick: push the matching closing bracket for whatever opener you see, so that when a closer arrives you can directly compare it against what's on top of the stack.

if(ch == '(')      push(&mystack, ')');
else if(ch == '[') push(&mystack, ']');
else if(ch == '{') push(&mystack, '}');
else if(ch==')'||ch==']'||ch=='}')
{
    if(!is_empty(&mystack)) { if(ch != pop(&mystack)) is_valid = 0; }
    else is_valid = 0;
}

Application — evaluating postfix expressions

Ordinary arithmetic uses infix notation — the operator sits between its operands (4 * 5 + 6) — which forces us to deal with precedence, associativity, and nested parentheses (BODMAS). A postfix expression puts the operator after its operands (4 5 * 6 +), so every operator can be evaluated the instant it's seen — no precedence rules, no parentheses, and every operator is uniformly left-associative.

InfixPostfix
3 + 43 4 +
4 * 5 + 64 5 * 6 +
4 + 5 * 64 5 6 * +
5 * 6 + 7 * 85 6 * 7 8 * +

Each operator pops exactly as many operands as it needs, computes, and pushes the result back — the final value left on the stack is the answer.

Algorithm — evaluate postfix (assumes whitespace-separated tokens) Scan left to right. Digit → accumulate a multi-digit number. Operator → pop two operands (val1 = top, val2 = next), apply val2 OP val1 (note the order!), push the result. At the end, exactly one value remains on the stack — the answer. 
while((ch = *s++) != '\0')
{
    if(ch=='+'||ch=='-'||ch=='*'||ch=='/')
    {
        val1 = pop(&mystack);
        val2 = pop(&mystack);
        switch(ch)
        {
            case '+': push(&mystack, val2 + val1); break;
            case '-': push(&mystack, val2 - val1); break;
            case '*': push(&mystack, val2 * val1); break;
            case '/': push(&mystack, val2 / val1); break;
        }
    }
    else if(ch >= '0' && ch <= '9') { is_num = 1; val = val*10 + ch - '0'; }
    else if(ch == ' ' && is_num) { push(&mystack, val); val = 0; is_num = 0; }
}
printf("result : %d\n", pop(&mystack));
Order matters for non-commutative operatorsBecause val1 is popped first (it was pushed last, i.e. it's the right operand), subtraction and division must compute val2 OP val1, not val1 OP val2 — reversing this silently breaks any expression using - or /.

Application — infix → postfix conversion

To convert, we use a stack of operators (not operands). The core rule: output operands immediately; hold operators on the stack until something of lower-or-equal precedence forces them out.

Example — 4 * 5 + 6: output 4; push *; output 5; see + (lower precedence than the * on the stack) → pop * to output, push +; output 6; drain stack → pop +. Result: 4 5 * 6 +.

Example — 4 + 5 * 6: output 4; push +; output 5; see * (higher precedence than + on the stack) → just push * (don't pop +); output 6; drain stack, popping in LIFO order: * then +. Result: 4 5 6 * +.

Handling parentheses — 3 * (4 + 5) * 6: a ( is given an artificially very high precedence while it's still in the input string (so it always gets pushed and never gets popped by an ordinary operator), but once it's sitting on the stack it's treated as having very low precedence (so it never blocks anything else from being pushed on top of it). On seeing ), pop and output everything down to (and including) the matching (, which is then discarded (not output).

Algorithm — infix to postfix '(' → push. ')' → pop to output until '(' is popped and discarded. Operand → output directly. Operator → if stack empty, push; else pop-and-output while the stack's top has ≥ precedence (for equal precedence, this correctly enforces left-associativity), then push. At the end, drain the whole stack to output. 
while((ch = *s++) != '\0')
{
    if(ch == ')')
    {
        while((ch1 = pop(&mystack)) != '(') { *p++ = ' '; *p++ = ch1; }
    }
    else if(ch=='('||ch=='+'||ch=='-'||ch=='*'||ch=='/')
    {
        if(is_empty(&mystack)) push(&mystack, ch);
        else
        {
            while(!is_empty(&mystack) && prec_in_str(ch) < prec_in_stack(peek(&mystack)))
            { *p++ = ' '; *p++ = pop(&mystack); }
            push(&mystack, ch);
        }
    }
    else { *p++ = ch; }  // operand — straight to output
}
while(!is_empty(&mystack)) { *p++ = ' '; *p++ = pop(&mystack); }
*p = '\0';

More applications of stacks

Beyond bracket-matching and expression evaluation, stacks appear throughout computing whenever "undo the most recent step" or "remember where to come back to" is needed:

  • Depth-first search of a graph.
  • Backtracking algorithms.
  • Branch and bound search.
  • Simulating recursive function calls — which is fitting, since a function's own call stack is, quite literally, a stack.

More formally: the languages that can be recognized using a stack (in addition to a simple state machine) are called context-free languages, recognized by a push-down automaton — and essentially every programming language's grammar (nested blocks, nested expressions) falls into this category. You'll study this formally later in your curriculum.

09Multilists & Skiplists

Two extensions to the plain linked list, aimed at two different goals: skip lists trade a little extra memory for much faster search; multilists let a single physical node participate in more than one logical relationship at once.

Skip lists

Motivation: imagine traveling from Bangalore to a small village between Srirangapatna and Mysore. A shuttle bus stopping at every village takes forever. Better: take an express bus straight to Mysore (or Srirangapatna), then a short local hop to the village. A skip list applies exactly this idea to a sorted linked list.

In an ordinary sorted list, searching for a value near the end still requires walking past almost every node — in the worst case, the number of comparisons is proportional to the list's length.

Jump 10→40→70 on the express level; 100 overshoots, so drop to level 0 at 70 and walk 70→80→90. Only a handful of steps instead of nine.

Structure: a skip list layers multiple linked lists on top of one another. Level 0 contains every element; each level above contains progressively fewer (conventionally, roughly half as many as the level below), acting as an "express lane" over the level beneath it.

Searching: start at the top level. Move forward while the next node's key is still less than the target. When the next node would overshoot the target, drop down one level at the current node and continue. Repeat until you reach level 0, where the element is either found or confirmed absent.

Each node stores forward pointers only for the levels it actually participates in — a level-0-only node has just one pointer; a node present in every level needs one pointer per level. Insertion and deletion follow the same top-down, level-by-level logic used for searching.

ApplicationsIn-memory ordered data needing fast insert/search/delete; concurrent data structures (operations at different levels can proceed with less contention than a balanced tree); priority-ordered event queues. Skip lists are often used as a simpler alternative to balanced binary search trees.

Note: implementing a skip list is explicitly stated as outside this course's syllabus — understanding the concept and the search trace is what matters here.

Multilists

A multilist is literally a "list of lists" — the same physical node can be part of more than one logical list simultaneously, letting one piece of data serve multiple relationships without duplication.

Motivating example — sparse matrices. A 10,000 × 10,000 matrix (common in image processing, finite-element/finite-difference methods, large electrical networks) would need 100 million storage cells if stored naively — yet the vast majority of entries are typically zero. Storing only the non-zero values (each tagged with its row and column) saves huge amounts of memory, but then how do you efficiently walk an entire row, or an entire column, for operations like matrix addition or multiplication?

Solution: give every non-zero element two link fields — one threading it into its row's list, and another threading it into its column's list. Each non-zero value therefore lives in two lists simultaneously, using only one physical node.

Each non-zero cell (row, col, value) is one node reachable from both its row's list and its column's list.

Another example — one physical node, multiple logical views. Consider students and the courses they take. We could maintain two separate structures — "courses per student" and "students per course" — but that duplicates data, doubles memory use, and risks the two copies going out of sync if only one is updated. A multilist instead stores each (student, course) relationship as a single node, reachable by traversing either "student-wise" or "course-wise," so there is exactly one place to update and no risk of the two views disagreeing.

Applications of multilistsSparse matrices · graph representations · social network relationships · systems needing multiple simultaneous "views" over the same underlying data (such as different indexes into the same files).
Salient pointWhy it matters
Represents multiple relations with one nodeAvoids storing the same logical data twice.
Avoids duplicationNo wasted memory for redundant copies.
Avoids multiple updatesOne update keeps every "view" consistent — no synchronization bugs.
Costs complexityPointer management, and insertion/deletion logic, become noticeably more intricate than a single plain list.
