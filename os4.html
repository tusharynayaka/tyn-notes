File Management, Storage Management & Security

Files, attributes, operations and access methods; directories and reading them; driver development and flash drives; mounting, sharing and protection; file-system and directory implementation; allocation methods; free-space management; efficiency and performance; mass storage, disk structure, scheduling and management; RAID; OS security, program and network threats; the access matrix, access control and revocation; and the shell tools awk and sed.

File concept & attributes

A file system is the part of the operating system that stores data on secondary storage, organises it efficiently, and provides access and protection mechanisms. Physical storage is a collection of raw disk blocks; the file system presents a logical view in which users deal with named files rather than block numbers.

A file is a named, logical unit of related information stored on secondary storage. It is the smallest logical unit an OS writes to disk: data must be placed in a file, and a file must be opened before it can be read or written. A file may contain text, a program, an image, audio, video or numeric data, and it can be viewed as:

  • A sequence of bytes — the simplest model, used by UNIX and Windows.
  • A sequence of records — fixed or variable length, used by databases and mainframe systems.
  • A structured object whose meaning is defined by the user or the program that created it.

File attributes

Every file carries metadata stored in its directory entry or control block. Typical attributes are:

Attribute Meaning
Name Human-readable identifier, unique within its directory.
Identifier Unique internal tag (often a number) used by the file system.
Type Kind of file — text, binary, executable, directory, device, and so on.
Location Pointer to the device and blocks holding the file's contents.
Size Current size, and often a maximum allowed size.
Protection Who may read, write, execute or delete the file.
Time / date / user Creation, last modification, last access, and owner identity.

File types and extensions

An operating system may recognise file types explicitly (for example, by a type field) or rely on a name–extension convention. Extensions help both the user and the OS infer the intended content and the program that should open it.

Extension File type Typical use
.c, .java, .pySourceHuman-written program text
.o, .objObjectCompiled but not yet linked code
.exe, .outExecutableReady-to-run binary
.sh, .batBatch / shellSequence of commands
.txt, .md, .pdfText / documentReadable content
.jpg, .png, .mp3, .mp4MultimediaImages, audio, video
.zip, .tar, .gzArchiveCompressed or bundled files
.so, .dllLibraryShared code loaded at run time

On UNIX-like systems the kernel itself does not usually care about the extension; the type is determined by the file's metadata and contents. The extension is a convention for applications and users. On other systems (notably Windows) the extension is bound to an application and determines how the file is opened.

UNIX file types

UNIX represents every object in the file-system namespace as a file with a type:

  • Regular file — ordinary data or program text.
  • Directory — a file whose contents are directory entries.
  • Character special — a device accessed byte by byte (keyboard, serial port, terminal).
  • Block special — a device accessed in blocks (disk, SSD, USB drive).
  • FIFO (named pipe) — a one-way inter-process communication channel with a name in the file system.
  • Socket — an endpoint for network or local inter-process communication.
  • Symbolic link — a file containing the path of another file.

File structure

Internally a file may be organised in several ways:

  • None / byte stream — an unstructured sequence of bytes; the program imposes meaning.
  • Simple records — lines, fixed-length records, or variable-length records with a length field.
  • Complex structures — formatted documents, relocatable object files, indexed databases.

Complex structures can be simulated on a byte-stream file by inserting control characters or headers, which is how most modern systems keep the kernel simple while letting applications define richer formats.

File operations & locking

A file is an abstract data type. The operating system provides a fixed set of operations on it, and every higher-level library call eventually reduces to these primitives.

Basic operations

Operation Purpose
CreateAllocate a directory entry and an FCB; set initial attributes.
OpenLocate the FCB, check permissions, load metadata into memory, return a handle.
ReadCopy data from the current file position into a user buffer and advance the pointer.
WriteCopy data from a user buffer to the file at the current position, extending it if needed.
Reposition (seek)Move the read/write pointer without transferring data (lseek).
DeleteRemove the directory entry and release the file's blocks.
TruncateErase the contents but keep the file and its attributes; size becomes zero.
CloseRelease the open-file entry and flush buffers; the handle becomes invalid.

The open-file table

Opening a file is expensive: the directory must be searched and the FCB read from disk. The OS therefore caches information about open files. Two levels are typical:

  • A system-wide open-file table — one entry per open file, holding the FCB, disk location and open count.
  • A per-process open-file table — one entry per open in each process, holding a pointer to the system entry and the process's own file pointer and access mode.

Each open entry records the file pointer (current read/write offset), file-open count (how many processes have it open), the disk location, and the access rights granted at open time. The open count lets the OS remove the system-wide entry only when the last process closes the file.

Why the open count matters

If two processes open the same file, the system-wide entry is shared but each process needs its own file pointer. Closing one process's handle must not destroy the shared entry, because the other process is still using it. The open count is decremented on each close and the entry is freed only at zero.

File locking

Locking coordinates concurrent access, much like reader–writer locks:

  • Shared lock — several processes may hold it simultaneously and read; equivalent to a reader lock.
  • Exclusive lock — only one process may hold it and write; equivalent to a writer lock.

Enforcement comes in two flavours:

Mandatory locking Advisory locking
The OS enforces the lock: an incompatible access is denied. The OS only records the lock; processes must voluntarily check it.
Used by Windows and some UNIX configurations. Traditional UNIX behaviour (flock, fcntl).

File descriptors and handles

UNIX returns a small integer file descriptor from open(); Windows returns a handle. Both index the per-process table. Descriptors 0, 1 and 2 are conventionally standard input, standard output and standard error, so a program can redirect its I/O simply by changing table entries.

Access methods

An access method determines how a file's bytes or records are located and read. The choice affects both the file-system implementation and the allocation method that can be used.

Sequential access

Data is processed in order, from the beginning to the end. The system keeps a current-position pointer and supports:

  • read next — return the next record and advance the pointer.
  • write next — append the next record and advance the pointer.
  • reset — return to the beginning (or seek to a position).

This is the natural mode for text files, logs, streams and magnetic tape. It is efficient because the next block is usually adjacent or already in the read-ahead buffer.

Direct (relative) access

The file is treated as a sequence of fixed-length logical blocks, numbered from 0. The operations are read n, write n and position to n, where n is a relative block number — an index from the start of the file, not an absolute disk address. The OS translates n into a physical block using the file's allocation information.

Relative block addressing
physical block = file start + n   (contiguous allocation)
The relative number hides the file's actual placement, so the OS is free to relocate the file. Direct access is essential for databases and indexed files.

Sequential access can be simulated on a direct-access file by keeping a current position and reading cp, cp+1, cp+2, …. The reverse simulation — direct access on a purely sequential medium such as tape — is impractical, because reaching block n requires passing every earlier block.

Other access methods

  • Indexed access — an index maps keys to block addresses, allowing a record to be found without scanning. A file may have multiple indexes (for different keys).
  • Direct access by key — a hash function computes the block from the key.
Method Typical medium / use Strength
SequentialTape, logs, textSimple, fast when access is in order
DirectDisk, databasesAny block reachable quickly
IndexedLarge databases, ISAMFast lookup by key

Directory structure

A directory is a collection of entries, each describing a file: its name, its identifier or inode number, and often its type, size and location. Both the directory structure and the file contents reside on disk. The directory is the map that lets the OS translate a human-readable name into a file control block.

Objectives of directory organisation

EfficiencyLocate a file quickly, without scanning the whole disk.
NamingLet different users use the same name, and let one file have several names.
GroupingOrganise files logically by project, type or owner.

Operations on a directory

  • Search for a file by name.
  • Create a file and add its entry.
  • Delete a file and remove its entry.
  • List the directory contents.
  • Rename a file.
  • Traverse the file system, for example to back it up or compute its size.

Paths and the working directory

An absolute path starts at the root and lists every component, for example /mail/prog/main.c. A relative path starts at the current working directory, for example prog/main.c when the working directory is /mail. The working directory removes the need to repeat long prefixes, and . and .. refer to the current and parent directories.

Partitions, volumes and file systems

  • A disk is divided into partitions (also called minidisks or slices).
  • A partition formatted with a file system and given a name is a volume.
  • A volume may be raw (no file system) or hold one of many file-system types.
  • Volumes may be combined or protected with RAID.
  • Each volume tracks its own file-system information in a device directory or volume table of contents.

Directory organisations

Single-level directory

One directory contains every file for every user.

  • Simple — one table to search and maintain.
  • Naming conflict — two users cannot both have project.c.
  • No grouping — all files are mixed together.

Two-level directory

Each user gets a separate directory, with a master directory (or user-file directory) above them.

  • Solves naming conflicts: each user has an independent namespace.
  • Searching is efficient: only the user's own directory is scanned.
  • Path names take the form /user/file.
  • Still no grouping within a user's files.

Tree-structured directory

The most common organisation. A root directory contains subdirectories, which contain further subdirectories or files, forming a tree.

  • Every file has a unique path from the root.
  • Supports grouping and a current working directory.
  • Absolute and relative paths both work.
  • Files cannot be shared directly between branches; a link is needed.

Acyclic graph directory

A tree extended with links, so a file or subdirectory can appear in more than one place. Sharing is convenient, but a file may have several paths and several names.

  • Hard link — a second directory entry pointing to the same inode; the file exists until the last link is removed.
  • Symbolic (soft) link — a small file containing the path of the target.
  • Reference count — the inode counts how many links point to it, preventing premature deletion.
  • Dangling pointer — a link whose target has been deleted. Symbolic links can dangle; reference counting and careful deletion avoid it.

General graph directory

If links may point to directories, cycles become possible. Cycles complicate traversal (the same directory may be visited forever) and storage reclamation (a reference count may never reach zero). Solutions include:

  • Forbid links to directories, keeping the graph acyclic.
  • Allow them but detect cycles during traversal.
  • Use garbage collection to find unreachable blocks when reference counts are unreliable.
Choosing an organisation

Single-level is only adequate for a single user. Two-level adds per-user isolation. Tree adds grouping and is the default on modern systems. Acyclic and general graphs add sharing at the cost of link management, dangling references and possible cycles.

Reading directories & file attributes

Applications rarely read raw directory blocks. The C library provides a portable interface that hides the on-disk directory format and works on ext4, XFS, FAT and network file systems alike.

Directory streams

Call Purpose
opendir(path)Open a directory and return a DIR * stream, or NULL on error.
readdir(dirp)Return a pointer to the next struct dirent, or NULL at the end.
rewinddir(dirp)Restart the stream at the first entry.
closedir(dirp)Close the stream and release its resources.

struct dirent typically contains the entry's inode number (d_ino), its record length (d_reclen), its type (d_type) and its name (d_name). The type may be DT_REG, DT_DIR, DT_LNK, DT_CHR, DT_BLK, DT_FIFO or DT_SOCK.

The . and .. entries

Every directory contains an entry for itself (.) and for its parent (..). A program that walks a tree must skip them, or it will loop forever. They are real directory entries, not special cases in the kernel.

Retrieving attributes

readdir gives names and inode numbers, but not sizes, permissions or timestamps. Those come from the stat family:

Call Behaviour
stat(path, &st)Follow symbolic links and report the target's attributes.
lstat(path, &st)Do not follow links; report the link itself.
fstat(fd, &st)Report attributes of an already-open file descriptor.

struct stat includes the file type and permission bits (st_mode), inode number (st_ino), number of hard links (st_nlink), owner and group IDs (st_uid, st_gid), size in bytes (st_size), allocated blocks (st_blocks), and access, modification and change times (st_atime, st_mtime, st_ctime).

Listing a directory with attributes 
#include <dirent.h>
#include <sys/stat.h>
#include <stdio.h>

int main(void) {
    DIR *d = opendir(".");
    struct dirent *e;
    struct stat st;

    while ((e = readdir(d)) != NULL) {
        if (stat(e->d_name, &st) == -1) continue;
        printf("%10ld  %s\n", (long)st.st_size, e->d_name);
    }
    closedir(d);
    return 0;
}

opendir opens the stream, readdir returns one entry at a time, and stat fills in the metadata. closedir releases the stream.

For a directory, st_size is the size of the directory file itself, not the total size of the files it contains. Computing a tree's total size requires recursive traversal.

Mounting & file sharing

Mounting

Before a file system can be used it must be mounted: attached to a directory of an already-visible file system. The attachment directory is the mount point. A USB drive, a second partition or a remote export is not accessible until it is mounted somewhere.

  1. The system already has a root file system.
  2. The new file system exists independently on its device.
  3. The OS checks its superblock and type.
  4. The new file system is attached at the mount point; its root becomes the mount point's contents.
  5. Paths that pass through the mount point now resolve into the new file system.

Mounting does not copy data. It installs a translation in the mount table so that path lookup crosses from one file system into another transparently.

File sharing and identity

Multi-user systems need controlled sharing: collaboration, efficient use of resources and avoidance of duplicate copies. Protection is built on identity:

  • User ID (UID) — identifies each user; permissions can be per user.
  • Group ID (GID) — identifies a group of users; permissions can be per group.
  • Every file records an owner (its creator) and a group.

Remote file systems

Distributed systems let files be shared across machines. Sharing may be:

  • Manual — files are transferred with FTP or a similar tool.
  • Automatic — a distributed file system makes remote files appear local.
  • Web-based — files are served over HTTP.

In the client–server model, the server stores the files and the client requests access. The client can mount a remote export so that it looks like a local directory. Standard calls such as open, read and write are translated into network operations.

Protocol Environment
NFS (Network File System)UNIX / Linux
CIFS / SMBWindows (and others via Samba)

Distributed naming services — LDAP, DNS, NIS and Active Directory — provide unified lookup of users, hosts and resources. Challenges include authentication across machines, network delay, and the complexity of managing distributed identities.

Remote identity is the hard part

A server must decide whether a request really comes from the user it claims. Trusting the client's assertion is insecure; strong authentication, Kerberos tickets or signed requests are needed. This is why remote file systems are more complex than local ones even when the file operations look identical.

File protection

Protection controls who may perform which operation on a file. The owner should be able to decide both what can be done and by whom.

Types of access

  • Read (R) — view the contents.
  • Write (W) — modify or overwrite the contents.
  • Execute (X) — run the file as a program.
  • Append — add data at the end without changing existing data.
  • Delete — remove the file.
  • List — read a directory's entries.

UNIX permission classes and bits

UNIX divides users into three classes: owner (user), group and others (public). Each class has three bits, read, write and execute, giving nine permission bits.

Permission encoding
r = 4 (100)2    w = 2 (010)2    x = 1 (001)2
mode = owner×64 + group×8 + others
Each digit is the sum of the bits granted. 7 = rwx, 6 = rw−, 5 = r−x, 4 = r−−, 1 = −−x, 0 = −−−.
Worked example

Owner: read + write + execute = 4 + 2 + 1 = 7 (111).

Group: read + write = 4 + 2 = 6 (110).

Others: execute only = 1 (001).

Combined mode: 761. The command chmod 761 game applies it.

Commands

Command Effect
chmod 761 gameSet owner rwx, group rw, others x.
chmod u+x gameAdd execute for the owner symbolically.
chgrp G gameAttach group G to the file.
chown alice gameChange the owner (privileged).

Access control lists

The nine-bit scheme is compact but coarse: it cannot grant rights to two different groups, or to one specific user. An access control list (ACL) stores, per file, a list of (user or group, rights) pairs. It is more expressive but longer, and lookup is a linear scan unless indexed. Modern Linux supports POSIX ACLs alongside the traditional bits; Windows uses ACLs as its primary mechanism.

The minimum privilege idea

Each process should run with only the rights it needs. A text editor does not need permission to modify the kernel, and a backup tool does not need permission to delete files. Limiting rights limits the damage a compromised program can do.

Driver development

A device driver is a specialised software component that lets the operating system communicate with and control a hardware device. It is a translator: the OS issues generic requests such as “read block 42”, and the driver converts them into the device-specific command sequence the hardware understands. This keeps device details out of the kernel core and lets one OS support thousands of devices.

Classes of driver

Class Data transfer Examples
Character device driver One character or byte at a time; often stream-oriented. Keyboard, mouse, serial port, terminal.
Block device driver Fixed-size blocks; supports random access and caching. Hard disk, SSD, USB drive.
Network device driver Packets rather than a byte stream or blocks. Ethernet card, Wi-Fi adapter.

How a driver handles a request

  1. Application request — a program calls read(), write() or ioctl().
  2. System call — the C library traps into the kernel.
  3. Kernel processing — the kernel identifies the device, checks permissions, and selects the driver.
  4. Driver translation — the driver builds the device-specific command, programs the controller, and starts the transfer.
  5. Hardware operation — the device performs the I/O, often by DMA.
  6. Interrupt / response — the device raises an interrupt when done; the driver's handler acknowledges it, checks status, and wakes the waiting process.

Driver development in Linux

Most Linux drivers are kernel code written in C against the kernel's internal APIs. A driver may be built into the kernel image or compiled as a loadable kernel module and inserted at run time with insmod or modprobe. Modules keep the base kernel small and let drivers be updated without rebuilding everything.

  1. Device identification — understand the hardware, its registers, its interrupt line and its bus interface.
  2. Driver implementation — write the probe, remove, read, write and interrupt routines using kernel APIs.
  3. Registration — register the driver with the kernel (character/block device numbers, file_operations, bus driver structures).
  4. Device communication — implement open, read, write, ioctl and close, handling blocking, DMA and error paths.
  5. Testing and debugging — exercise the driver with real hardware, check for races, leaks and interrupt-handling bugs. Kernel bugs can crash the whole machine, so testing is careful and often done in a virtual machine.
Kernel mode has no safety net

A user-space bug kills a process; a kernel-driver bug can corrupt memory, deadlock the scheduler or panic the system. Drivers must validate every pointer and length supplied by user space, must not sleep in interrupt context, and must release locks on every path.

Flash drives

Flash memory is non-volatile: it retains data without power. It is used in USB drives, SSDs, memory cards and phones. With no moving parts it is faster and far more shock-resistant than a magnetic disk, but it has two awkward properties: it cannot be overwritten in place, and each cell wears out after a limited number of erase cycles.

NAND organisation

Most flash storage uses NAND memory, organised hierarchically:

  • Page — the smallest unit for read and write. A typical page is 2–16 KiB.
  • Block — a collection of pages (often 128–256); the smallest unit for erase.
  • Chip — many blocks, plus a controller that manages them.
The asymmetry that shapes flash
read / write → page level
erase → block level
If a block has 256 pages, any page can be written, but the whole block must be erased before its pages can be rewritten. A single-page update therefore cannot be done in place.

NAND cell types

Type Bits per cell Character
SLC1Fast, reliable, highest endurance; expensive.
MLC2Higher capacity, moderate endurance.
TLC3High capacity, widely used in consumer SSDs.
QLC4Very high capacity, lower endurance and speed.

Flash management techniques

  1. Flash Translation Layer (FTL) — maps the logical block addresses the OS uses to physical page locations in flash. The mapping is indirect, so a logical block can move without the OS noticing. The FTL also handles bad blocks and power-loss recovery.
  2. Wear levelling — distributes erases across all blocks so that no block wears out early. Dynamic levelling moves only hot data; static levelling also relocates cold data periodically.
  3. Garbage collection — finds blocks containing obsolete pages, copies the still-valid pages elsewhere, erases the block, and returns it to the free pool. This is why a flash write can be slower than a read.
  4. Bad-block management — detects blocks that fail during manufacture or use, marks them, and remaps their logical addresses to spare blocks.
  5. TRIM — the OS tells the device which blocks are no longer in use, so garbage collection can skip copying dead data. TRIM improves both speed and endurance.

How the OS sees a flash device

The OS treats an SSD or USB drive as a block device. The file system issues logical block reads and writes; the block driver forwards them to the device; the FTL translates them into physical page operations. The OS does not need to know about pages, blocks or wear.

Why an update is not an overwrite

A block holds 256 pages and page 10 must be updated. Flash cannot rewrite page 10 in place. The FTL writes the new version to a free page (say page 200 of another block), updates its mapping so logical page 10 now points there, and marks the old copy invalid. The old block cannot be reused until every valid page in it has been moved out and the whole block is erased. Garbage collection performs that move; wear levelling chooses which block to erase next.

File-system implementation

Users see system calls such as open, read and write. The file system must translate each into block-level operations on a device, while keeping metadata consistent and access fast. It does this with a layered design and with structures kept both on disk and in memory.

Layered file system

Layer Responsibility
Device drivers and interrupt handlers Talk to the hardware; issue commands and service interrupts.
Basic file system Issues generic block commands (“retrieve block 123”), manages buffers and caches.
File-organisation module Translates logical block numbers to physical block numbers; manages free space and allocation.
Logical file system Manages metadata: directories, file control blocks, protection and name resolution.

The layering gives modularity, easier debugging and flexibility: a new device driver or a new on-disk format can be added without rewriting the layers above or below.

File control block (FCB)

Every file has an FCB, a record describing it. It contains the file's name (or a pointer to it), ownership, permissions, size, dates, and the location of its data blocks. In UNIX the FCB is the inode; in NTFS the information is stored in the Master File Table (MFT). The directory entry maps a name to an FCB.

On-disk structures

  • Boot control block — the information needed to boot an OS from this volume; usually the first block. Present only if the volume contains an OS.
  • Volume control block (superblock) — describes the whole file system: total blocks, free blocks, block size, free-block pointers or bitmap, and the location of the inode table. In NTFS this role is played by the MFT.
  • Directory structure — organises files; stores names and inode numbers (or MFT records).
  • Per-file FCB — the inode: size, permissions, dates, block pointers, link count.

In-memory structures

  • Mount table — which file systems are mounted, where, and of what type.
  • System-wide open-file table — a copy of each open FCB and its open count.
  • Per-process open-file table — file descriptors, file pointers and access modes.
  • Buffers and caches — recently read blocks and directory data.
Following an open and a read

Open: search the directory for the name → load the FCB into memory → check permissions → create a system-wide entry (or increment its count) → create a per-process entry → return a file descriptor.

Read: use the file pointer to compute the logical block → ask the file-organisation module for the physical block → check the buffer cache → if absent, ask the basic file system to read the block → copy the requested bytes to the user buffer → advance the file pointer.

Virtual File System (VFS)

A virtual file system provides one system-call interface for many different file-system types — ext4, XFS, FAT, NFS, procfs and so on. The VFS defines generic operations and dispatches each request to the implementation that owns the file. It is object-oriented in spirit: a vnode represents a file and holds either an inode (local file system) or network information (remote file system).

  1. The application calls the standard API.
  2. The request enters the VFS.
  3. The VFS determines the file-system type from the mount and the path.
  4. The VFS calls that file system's implementation.
  5. The result returns through the same interface.

VFS supports multiple file systems, gives a uniform interface, simplifies development and enables network file systems without changing applications.

Directory implementation

A directory is itself a file, but its contents are entries rather than user data. The implementation must support lookup by name, insertion, deletion and listing. Two classic structures dominate.

Linear list

The directory is an array or linked list of entries, each holding a name and a pointer to the FCB or inode.

  • Lookup — a linear search comparing names; O(n).
  • Insert — append, or reuse a deleted slot.
  • Delete — mark the slot free or compact the list.
  • List — walk the list in order.

It is simple and compact for small directories. It becomes slow for large ones, and deletion leaves holes unless the list is compacted. Caching the directory in memory and using a linked list of variable-size entries are common refinements.

Hash table

A hash function maps the file name to a bucket; the bucket holds a chain of entries whose names hash to the same value. Lookup, insertion and deletion are O(1) on average.

Hash directory
bucket = h(name) mod B
B is the number of buckets. Collisions are resolved by chaining (or open addressing). A good hash spreads names evenly; a poor one creates long chains and loses the advantage.
  • Strength — fast name lookup even with thousands of files.
  • Weakness — collisions; resizing/rehashing when the directory grows; listing the directory in order requires sorting.
Structure Lookup Insert / delete Ordered listing Best for
Linear listO(n)O(1) at end / O(n) searchNaturalSmall directories
Hash tableO(1) averageO(1) averageRequires sortingLarge directories
Real systems

ext4 uses a hash tree (htree) for large directories, which behaves like a B-tree over hashed names. NTFS stores directory entries in a B+ tree keyed by name. Both keep lookup logarithmic or better while supporting ordered enumeration and growth.

Allocation methods

Files are stored in disk blocks. The allocation method decides which blocks belong to a file and how their addresses are recorded. It affects access speed, fragmentation, growth and metadata size.

Contiguous allocation

Each file occupies a run of adjacent blocks. The directory stores the starting block and the length (number of blocks).

Contiguous address mapping
block = start + ⌊ offset / block_size ⌋
displacement = offset mod block_size
  • Advantages — excellent performance; both sequential and direct access are trivial; only two numbers of metadata; minimal seek movement.
  • Disadvantages — external fragmentation; the file size must be known in advance (or the file must be moved to grow); finding a large enough hole is hard; compaction is expensive and may require downtime.

Linked allocation

Each block contains the file's data plus a pointer to the next block; the last block has a null pointer. The directory stores only the first and last block.

  • Advantages — no external fragmentation; files grow easily; no compaction; any free block can be used.
  • Disadvantages — pointer overhead in every block; only sequential access is efficient, because block n requires following n links; a lost pointer breaks the rest of the file.

Clustering allocates groups of blocks rather than single blocks. This reduces the number of pointers and seeks, at the cost of internal fragmentation in the last cluster.

File Allocation Table (FAT)

FAT is linked allocation with the pointers moved out of the data blocks into a table at the start of the volume. Each entry corresponds to one block and holds the index of the next block (or an end-of-file/free marker). The directory stores the first block; the chain is followed through the FAT.

  • Faster than in-block linked allocation, because the FAT can be cached in memory, so following a chain needs no disk reads.
  • Simpler recovery — a damaged data block does not destroy the chain.
  • Cost — the FAT itself can be large: one entry per block. On a 1 TiB volume with 4 KiB blocks there are 268 million entries.

Indexed allocation

Each file has an index block containing the addresses of all its data blocks. The directory points to the index block.

  • Advantages — supports direct access; no external fragmentation; the index can be cached; the metadata for a file is in one place.
  • Disadvantages — every file needs a whole index block, which wastes space for tiny files; a single index block limits the maximum file size.

Handling large files

  1. Linked index blocks — the index blocks themselves form a chain. Simple, but direct access to a late block still requires walking the chain.
  2. Multilevel indexing — a first-level index points to second-level index blocks, which point to data. This scales to very large files, but small files pay for unused levels.
  3. Combined scheme — the inode holds a few direct pointers, one single-indirect, one double-indirect and one triple-indirect pointer. Small files use only direct pointers; large files use the indirect tree. This is the UNIX inode design.
UNIX inode capacity
max blocks = D + P + P² + P³
D = number of direct pointers, P = pointers per block. With 12 direct pointers and 256 pointers per 1 KiB block (4-byte addresses), the inode can address 12 + 256 + 65,536 + 16,777,216 blocks.

Free-space management

The file system must know which blocks are free. It maintains a free-space list. Creating a file removes blocks from the list; deleting a file returns them. Efficient tracking keeps allocation fast and avoids wasting space.

Bit vector (bitmap)

One bit per block: 1 means free, 0 means allocated (the convention can be reversed, but must be consistent).

Bitmap size
bitmap bytes = (number of blocks) / 8
For 1 TiB with 4 KiB blocks: 268,435,456 blocks → about 32 MiB of bitmap. That is small enough to keep in memory, which makes allocation fast.
  • Advantages — simple; finding the first free block is a bit scan; finding a run of n contiguous free blocks is possible with word operations.
  • Disadvantages — the bitmap itself consumes memory; on very large volumes it may not fit, and then it must be paged.

Linked list

All free blocks are linked: each free block stores a pointer to the next free block, and the OS keeps a pointer to the first.

  • Advantages — no extra space beyond the free blocks themselves; simple.
  • Disadvantages — traversal requires disk I/O and is slow; finding a large contiguous run is difficult.

Grouping

A refinement of the linked list: the first free block stores the addresses of n free blocks, and the last of those addresses points to the next group. The OS can allocate n blocks after one read instead of following n links.

Counting

Because free space often occurs in contiguous runs, store a list of (start block, count) pairs. A run of 10 blocks starting at 5 is one entry: (5, 10). This is compact when the disk is lightly fragmented. The list is often kept in a balanced tree so that a run of a required length can be found quickly.

Efficiency & performance

What makes a file system efficient

  • Allocation method — contiguous is fastest but fragments; indexed is flexible; linked is simple but slow.
  • Directory structure — hashing or trees keep lookup fast as directories grow.
  • Metadata allocation — pre-allocating inodes or blocks reduces fragmentation and allocation cost; dynamic allocation saves space.
  • Data structures — fixed-size entries are simpler and faster; variable-size entries save space but complicate updates.
  • Block size — larger blocks mean fewer I/Os and less metadata, but more internal fragmentation; smaller blocks mean less waste but more overhead.

Buffer cache

A buffer cache is a region of main memory holding recently used disk blocks. Reads hit the cache instead of the disk; writes are buffered and written later. It exploits locality of reference: a block just used is likely to be used again.

Page cache and unified virtual memory

Modern systems cache file data as pages in the same virtual-memory system used for process memory. This is a page cache. Linux, Windows and Solaris use a unified buffer cache, where file data and process pages share one cache.

Double caching

If a separate buffer cache and page cache both hold the same file data, memory is wasted and data must be copied twice. A unified cache avoids duplicate copies, reduces memory pressure and simplifies consistency.

Read-ahead and free-behind

  • Read-ahead — when a block is requested, fetch the next few blocks as well. Sequential readers then find their data already in memory. Requesting page 5 may load pages 5, 6 and 7.
  • Free-behind — discard a page as soon as it has been read, because a sequential stream will not need it again. This keeps the cache from being polluted by a single large sequential read.

Other performance techniques

  • Delayed writes — batch small writes into one larger disk transfer.
  • Journaling — write metadata changes to a log before applying them, so a crash can be recovered by replaying or discarding the log.
  • Clustering and extents — allocate contiguous runs to reduce seeks and metadata.
  • Block placement — keep a file's blocks near each other and near its metadata to reduce seek time.
  • Consistent caching policy — decide whether writes are write-through (safe, slow) or write-back (fast, risk of loss on power failure).

Mass-storage structure

Mass storage is secondary storage: non-volatile devices that hold data permanently and at much larger scale than RAM. The OS must understand their physical structure because that structure determines access time, scheduling and reliability.

Magnetic hard disk (HDD)

  • Platters — one or more circular disks, typically 1.8 to 3.5 inches, coated with magnetic material.
  • Surfaces — each platter has two recording surfaces.
  • Tracks — concentric circles on a surface.
  • Sectors — subdivisions of a track; the smallest addressable unit (historically 512 bytes, now commonly 4 KiB).
  • Cylinder — the set of tracks at the same radius across all platters.
  • Disk arm and heads — one head per surface, all moving together; only one head reads or writes at a time.

The arm moves radially to the desired cylinder, then the platter rotates until the desired sector passes under the head. These two mechanical motions dominate disk latency.

Removable and optical media

  • CD, DVD and Blu-ray — optical, removable, lower capacity than modern HDDs.
  • USB flash drives — solid-state, removable, no moving parts.

Solid-state drives (SSD)

  • Non-volatile NAND flash; no moving parts.
  • No seek time and no rotational latency, so random access is dramatically faster.
  • Lower power, silent, more shock-resistant.
  • More expensive per byte; limited write/erase endurance; capacity historically lower.
  • Attached through PCIe/NVMe rather than a slow legacy bus, to avoid the interface becoming the bottleneck.

Magnetic tape

  • Very large capacity at low cost per byte.
  • Strictly sequential access; random access is roughly a thousand times slower than disk.
  • Used for backup, archival and bulk transfer, not for interactive file systems.

Disk attachment

Disks connect through I/O buses and controllers:

  • Host controller — on the motherboard; talks to the bus.
  • Disk controller — inside the drive; executes commands and reports status.

Addressing

A modern disk is addressed by logical block address (LBA): a flat integer for each sector. The drive's controller maps the LBA to cylinder, head and sector, hiding the geometry from the OS. This is why the OS can treat very different devices — HDD, SSD, RAID volume — through the same block interface.

Disk structure & access time

Disk performance is the sum of mechanical and electronic delays. The OS can influence some of them through scheduling and placement, but not the rotation speed or the transfer rate.

Components of access time

Disk access time
Taccess = Tseek + Trotation + Ttransfer
Trotation,avg = 1 / (2 × RPM/60) = 30 / RPM seconds
Ttransfer = bytes / transfer_rate
Seek moves the arm; rotation waits for the sector; transfer moves the data. On average the rotational wait is half a revolution.
  • Seek time — time to move the head to the target track. It grows with seek distance, though not linearly; short seeks cost less than long ones.
  • Rotational latency — time for the target sector to rotate under the head; average half a rotation.
  • Transfer time — time to read or write the requested bytes once the head is positioned.
Worked example

A disk spins at 7,200 RPM. Average rotational latency = 30 / 7200 s = 4.17 ms. If the average seek is 8 ms and the transfer of 4 KiB at 150 MB/s takes about 0.027 ms, then

T ≈ 8 + 4.17 + 0.027 ≈ 12.2 ms.

Because seek and rotation dominate, scheduling seeks well matters far more than shaving the transfer time.

Disk bandwidth

Bandwidth
bandwidth = total bytes transferred / total time
Scheduling that reduces total head movement increases effective bandwidth, because more of the elapsed time is spent transferring rather than seeking.

Reliability: head crash

The head flies on a microscopic cushion of air. A shock, a particle or a landing can make it touch the surface — a head crash. The magnetic coating is damaged and the data under the head is usually unrecoverable. This is why disks are sealed, parked when powered down, and protected by redundancy such as RAID.

Rotational latency and the OS

Rotational latency is hard for the OS to optimise because the disk hides the physical sector layout behind logical block addresses. Modern drives therefore reorder requests internally in the controller. The OS may send a batch of requests and let the drive choose the best order, rather than micro-managing every seek.

Disk scheduling

When many I/O requests are queued, the order in which they are served determines total head movement, and therefore throughput and average waiting time. The goal is to minimise seek time and maximise bandwidth, while avoiding starvation.

Each request names an operation (read/write), a disk address, a memory address and a sector count. The OS keeps a queue; scheduling only matters when the queue has more than one request.

Running example

Request queue: 98, 183, 37, 122, 14, 124, 65, 67. Initial head position: 53. Disk range: 0–199. All totals below are in cylinders of head movement.

FCFS — First-Come, First-Served

Serve requests in arrival order. It is fair and trivial, but the head sweeps back and forth across the disk with no regard for proximity.

53 → 98 → 183 → 37 → 122 → 14 → 124 → 65 → 67

Movement: 45 + 85 + 146 + 85 + 108 + 110 + 59 + 2 = 640 cylinders.

FCFS has no starvation, but poor throughput because of large, unnecessary seeks.

SSTF — Shortest Seek Time First

Always serve the request closest to the current head position. This is the disk analogue of shortest-job-first.

53 → 65 → 67 → 37 → 14 → 98 → 122 → 124 → 183

Movement: 12 + 2 + 30 + 23 + 84 + 24 + 2 + 59 = 236 cylinders.

Much better than FCFS, but far-away requests can starve if near requests keep arriving.

SCAN — the elevator algorithm

The head moves in one direction, serving every request it passes, then reverses at the end of the disk and serves the requests on the way back. Like an elevator.

Starting at 53 and moving toward 0:

53 → 37 → 14 → 0 → 65 → 67 → 98 → 122 → 124 → 183

Movement: 16 + 23 + 14 + 65 + 2 + 31 + 24 + 2 + 59 = 236 cylinders.

SCAN reduces starvation and gives more uniform wait times than SSTF. Requests just behind the reversal point wait longest.

C-SCAN — circular SCAN

The head serves requests in one direction only. On reaching the end it jumps back to the other end without serving anything, then sweeps forward again. The disk is treated as circular, so waiting time is more uniform.

Starting at 53 and moving upward:

53 → 65 → 67 → 98 → 122 → 124 → 183 → 199 → 0 → 14 → 37

Movement: 12 + 2 + 31 + 24 + 2 + 59 + 16 + 199 + 14 + 23 = 382 cylinders.

The return jump adds movement but equalises service. It is fairer than SCAN for requests near the ends.

LOOK and C-LOOK

SCAN and C-SCAN travel all the way to the physical end of the disk even when no request lies there. LOOK stops at the last request in the current direction and reverses; C-LOOK jumps only from the last request back to the first request, not to the physical end.

LOOK (toward 0): 53 → 37 → 14 → 65 → 67 → 98 → 122 → 124 → 183

Movement: 16 + 23 + 51 + 2 + 31 + 24 + 2 + 59 = 208 cylinders.

C-LOOK (upward): 53 → 65 → 67 → 98 → 122 → 124 → 183 → 14 → 37

Movement: 12 + 2 + 31 + 24 + 2 + 59 + 169 + 23 = 322 cylinders.

Algorithm Movement Starvation Character

Choosing an algorithm

  • SSTF is simple and efficient for light, random loads, but risks starvation.
  • SCAN and C-SCAN behave well under heavy load and are fairer.
  • LOOK and C-LOOK avoid unnecessary travel and are usually the best practical choices for HDDs.
  • On SSDs, seek time is irrelevant; the scheduler should simply avoid starving requests and keep the device queue full. The FTL reorders internally anyway.
  • Request pattern, file allocation and disk structure all affect the real result.
OS versus controller scheduling

The OS may batch requests and send them to the disk controller, which reorders them using its own knowledge of physical geometry. This two-level arrangement lets the OS enforce fairness and priority while the controller optimises seek and rotational latency.

Disk management

Before a disk can hold files it must be formatted, partitioned and given a file system. The OS also has to boot from it, handle defective blocks, and provide swap space for virtual memory.

Low-level (physical) formatting

The drive is divided into sectors, each with a header, a data area and a trailer. The header identifies the sector; the trailer holds an error-correcting code (ECC). The controller uses the ECC to detect and often correct small read errors. Low-level formatting is usually done at manufacture; modern drives also perform internal defect management.

Partitioning

The disk is divided into partitions (minidisks, slices). The OS records their start, length and type in a partition table (MBR or GPT). Each partition can hold a different file system or be used raw. A partition with a file system is a volume.

Logical formatting

Logical formatting creates the file system inside a partition. It writes:

  • The boot block (or boot control block), containing code to load the OS.
  • The superblock / volume control block: block size, total and free blocks, inode table location, free-space structures.
  • An empty root directory and the initial metadata structures.

Some systems reserve space for efficiency or reliability — for example, ext4 reserves a percentage of blocks for the root user so that a full disk can still be repaired.

Boot blocks

A boot block is a small program that the firmware loads and executes. It in turn loads the boot loader or the kernel. A disk may have a master boot record and per-partition boot blocks; the active one is selected by the firmware or the boot manager. The boot block must fit in a single sector and must know enough about the file system to find the kernel image.

Bad blocks

Disks develop defective sectors. Two strategies handle them:

  • Sector sparing (forwarding) — the controller maintains a list of bad sectors and remaps each to a spare sector. The OS never sees the defect; logical addressing continues to work.
  • Sector slipping — the controller shifts subsequent sectors by one position to skip the bad one, preserving the logical order. This is used when spare sectors are not available or when the defect is discovered during low-level formatting.

File systems may also mark bad blocks and avoid allocating them, and recovery tools can scan for and relocate them. Backups and RAID are the real defence: a block that fails silently can otherwise corrupt a file.

Swap space

Swap space holds pages evicted from memory. It may be a dedicated raw partition (fast, no file-system overhead) or a file in an existing file system (flexible, easier to resize). Raw partitions avoid double buffering and metadata, so they are faster; swap files are easier to manage and can share a disk with data.

  • Swap is usually sized at one to two times RAM, though the right size depends on workload.
  • Anonymous pages (heap, stack) go to swap; clean file-backed pages can simply be re-read from their file and need no swap copy.
  • Mobile systems often use compressed memory or no swap at all, to avoid flash wear and latency.
Formatting destroys data

Low-level formatting, repartitioning and logical formatting all replace metadata and can make existing data unreachable. A file system must be unmounted and backed up before any of these operations. "Quick format" usually rewrites metadata only, which is why old data may still be recoverable.

RAID structure

RAID (Redundant Array of Independent Disks) combines several smaller disks into one logical unit to improve performance, capacity and reliability. A single large disk is expensive and is a single point of failure; many small disks are cheaper, can be accessed in parallel, and can carry redundant data so that one failure does not lose everything.

Striping and mirroring

  • Striping — split a file's blocks across disks. Block i goes to disk i mod n, so different blocks can be read in parallel and long transfers use all disks. Striping alone gives no redundancy: any disk failure loses data.
  • Mirroring — keep an exact copy on a second disk. Reads can be served from either copy in parallel; writes must go to both, so write performance is lower and storage cost doubles. Recovery is simple and fast.

Reliability metrics

Mean times
MTTFsystem = MTTFdisk / N
MTTDLmirrored = MTTF2 / (2 × MTTR)
N disks fail N times as often as one. MTTF is mean time to failure, MTTR is mean time to repair, MTTDL is mean time to data loss. The mirrored formula assumes independent failures and that a second failure during repair causes data loss.
Worked example

One disk has MTTF = 100,000 hours. An array of 100 disks has MTTFsystem = 100,000 / 100 = 1,000 hours — about 42 days. Adding disks makes the array less reliable unless redundancy is added.

For a mirrored pair with MTTF = 100,000 hours and MTTR = 10 hours: MTTDL = 100,000² / (2 × 10) = 1010 / 20 = 5 × 108 hours, which is about 57,000 years. Mirroring changes the exponent, which is why it is so effective.

Level by level

  • RAID 0 — pure striping. Maximum capacity and speed, no protection. Any disk failure loses the array. Useful only for scratch or cache data.
  • RAID 1 — mirroring. Full redundancy, fast reads, slower writes, 50% capacity. The most expensive per usable byte but the simplest to recover.
  • RAID 2 — bit-level striping with Hamming ECC across extra disks. It needs many disks and is not used in practice; modern drives already provide ECC internally.
  • RAID 3 — bit/byte striping with one dedicated parity disk. Every I/O involves all disks, so it suits large sequential transfers but not many small random requests.
  • RAID 4 — block striping with a dedicated parity disk. Reads can be parallel, but every write must update the single parity disk, which becomes a bottleneck.
  • RAID 5 — block striping with distributed parity. Parity blocks are spread across all disks, removing the single parity bottleneck. It tolerates one disk failure and is the most widely used level for general storage. A write requires read-modify-write of data and parity, so write performance is lower than RAID 0 or 1.
  • RAID 6 — two independent parity blocks (P and Q), tolerating two simultaneous failures. This matters during the long rebuild of a large RAID 5 array. Writes are slower and two disks' worth of capacity is lost.
  • RAID 10 — mirror pairs, then stripe across the pairs (RAID 1+0). High performance, high reliability, fast rebuild, but 50% capacity overhead.

RAID 0+1 versus RAID 1+0

In RAID 0+1 a single disk failure makes its entire stripe inaccessible, and the mirror must serve everything until repair. In RAID 1+0 a single disk failure affects only its own mirror pair, and the surviving copy continues; the array can often tolerate multiple failures as long as they are in different pairs. RAID 1+0 is therefore preferred for critical systems.

Parity and advanced concepts

  • Parity — an XOR of the data blocks. If one block is lost, XORing the survivors reconstructs it. This is why RAID 5/6 need only one or two extra disks rather than a full mirror.
  • P + Q — two independent parity functions used by RAID 6 so that two losses can be reconstructed.
  • NVRAM / battery-backed cache — buffers writes so that parity updates can be batched and survive power loss, improving RAID write performance.
  • Hot spare — an idle disk that automatically replaces a failed one, shortening the vulnerable rebuild window.

The security problem

Protection is the set of mechanisms that control which users and processes may access which resources. Security is broader: it is the defence of the system and its data against misuse, whether the attacker is outside the machine or a legitimate user inside it. A system is secure when its resources are used and accessed only as intended, in every circumstance.

Perfect security is impossible, so the practical goal is to make an attack cost more than it is worth. Security is therefore a balance of prevention, detection, recovery and cost.

What is at risk

  • Programs and processes.
  • Files and stored data.
  • Memory and CPU time.
  • Network bandwidth and services.
  • User accounts and credentials.

A breach can cause unauthorised access, data theft or disclosure, modification or destruction, misuse of resources, or disruption of service.

Five types of security violation

Violation Meaning Example
Breach of confidentiality Unauthorised reading or disclosure of data. An attacker reads customer records or stored passwords.
Breach of integrity Unauthorised modification of data. A student changes marks in a database.
Breach of availability Unauthorised destruction or disruption of resources. An attacker deletes important files.
Theft of service Unauthorised use of system resources. Using someone else's server to run one's own programs.
Denial of service Preventing legitimate users from accessing a service. Flooding a web server so genuine users cannot reach it.
CIA

The first three — confidentiality, integrity and availability — are the classic "CIA triad" and are the three basic goals a secure system tries to protect. Theft of service and denial of service are attacks on availability and on resource accounting rather than on data itself.

Protection versus security

Protection is internal and mechanism-oriented: it enforces the access rules the OS has been given. Security is external and policy-oriented: it decides whether those rules are adequate, whether identities are trustworthy, and whether the system can resist attacks that bypass the rules. A file permission check is protection; preventing an attacker from impersonating the file's owner is security.

Program threats

Program threats come from malicious or compromised programs. Because a program runs with the privileges of the user who started it, a misbehaving program can do anything that user can do: read data, modify files, escalate privileges, execute code or disrupt the system.

Malware

Malware (malicious software) is software designed to exploit, disable, damage or gain unauthorised access to a system. It may appear to be a legitimate program. Trojan horses, spyware, ransomware, viruses and worms are all forms of malware.

Trojan horse

A program that appears to perform a useful function but secretly performs a malicious one. It runs with the user's privileges, so it can access everything the user can. A free game that also copies the user's files or installs other malware is a typical example.

Spyware

Software that secretly collects information about the user or system — browsing activity, behaviour, credentials, files, system details — and sends it to a remote party without consent.

Ransomware

Malware that encrypts the victim's files and demands payment for the decryption key. It attacks availability: the data still exists but cannot be read. Regular offline backups are the most effective defence, because the victim can restore without paying.

Code injection and buffer overflow

Code injection is the insertion or execution of unauthorised code through a program, usually because input is not validated. A classic route is a buffer overflow: data longer than a fixed-size buffer overwrites adjacent memory, potentially including a return address, so a carefully crafted input redirects execution.

void read_name(char *input) {
    char name[8];        /* fixed-size buffer */
    strcpy(name, input); /* no length check */
}

If input is longer than seven characters plus the terminator, the extra bytes spill past name and overwrite neighbouring memory. The remedy is to validate lengths and use bounded functions such as strncpy, strlcpy or fgets, and to never trust input from outside the program.

Viruses

A virus is a fragment of code embedded in a legitimate program or file. It replicates by infecting other programs and usually needs the user to run the infected program or open the infected file. It can modify or destroy files, corrupt programs and crash the system.

Worms

A worm is a self-replicating program that spreads across systems, typically over a network, without needing a host program. It exploits network or software vulnerabilities, consumes bandwidth and CPU, and may install further malware.

Trap door / back door

A hidden entry point that bypasses normal authentication. It may be left intentionally during development for testing, or inserted maliciously. If it survives into production, anyone who discovers it can log in without the normal procedure.

Principle of least privilege

Every user and program should have only the minimum privileges needed for its task, limited in scope (which resources) and time (how long). A backup program needs to read files, not delete them; administrator rights should be granted only for the duration of the administrative task. Least privilege limits the damage a compromised program can do.

System & network threats

Attacks can target the system as a whole — its services, resources and operating environment — or the network over which machines communicate. Networked systems are exposed to attacks launched from anywhere.

System threats

Their goals are to make resources unavailable, consume CPU, memory or storage, gain access, exploit service weaknesses, or disrupt operation.

Denial of service (DoS)

A DoS attack makes a service unavailable to legitimate users by exhausting its resources: CPU, memory, bandwidth, connection slots. The attacker does not steal data; the goal is to overwhelm. A flood of connection requests can consume every slot so that genuine users cannot connect. When the flood comes from many machines, it is a distributed denial of service (DDoS) and is much harder to stop.

Port scanning

A systematic probe of network ports to discover which services are listening. Port 80/443 suggests a web server, port 22 an SSH server. The scan itself is not an attack; it is reconnaissance that tells an attacker where to aim. Administrators use the same technique to audit their own systems and close unnecessary ports.

Network threats

  • IP spoofing — forging the source address of packets so they appear to come from a trusted host, or so the real sender is hidden.
  • Man-in-the-middle (MITM) — the attacker positions between two parties and can read or modify their traffic while each believes it is talking directly to the other.
  • Packet sniffing — capturing and analysing packets on the network. Unencrypted credentials and data are directly readable.

Access matrix

The access matrix is a protection model that states exactly who may do what. It relates two kinds of entity:

  • Domains — subjects: users, processes or protection contexts. They form the rows.
  • Objects — resources: files, printers, memory segments, devices. They form the columns.
  • Cells — the access rights that a domain holds on an object, such as read (r), write (w), execute (x), print or delete.
Domain F1 F2 F3 Printer
D1readread
D2print
D3readexecute

An empty cell means no access. D2 can only print; it cannot read or write any file. D4 has D1's rights plus write on F1 and F3.

How the OS uses the matrix

When a process in domain Di requests operation op on object Oj, the OS looks at cell (Di, Oj) and allows the operation only if op is listed. The OS also decides which domain a process runs in and what rights that domain has.

Domain switching

A process may need to change domain — for example, a user process enters a privileged service. To model this, domains are also treated as objects, so they appear as columns. Switching from Di to Dj requires the switch right in cell (Di, Dj).

Rights that modify the matrix

  • Copy — the holder may duplicate the right and grant it to another domain.
  • Owner — full control over the object; the owner may add or remove rights.
  • Control — the holder may change the rights of a domain object.

Implementing the matrix

A full matrix is large and mostly empty, so it is never stored densely. Three standard implementations exist:

Global table

One table stores every non-empty triple <domain, object, rights>. The OS searches it on each access.

  • Strength — simple and compact when few rights exist.
  • Weakness — grows large; lookup is slow; grouping similar rights is hard.

Access control list (ACL)

Each object keeps a list of (domain, rights) pairs. This is the matrix stored by columns. It answers: who can access this object, and what can they do?

Access control & RBAC

Access control decides who may access a resource and what they may do with it. The OS applies protection mechanisms to files, devices and other objects, and rights may be attached to users, domains or roles.

If the request is permitted, the subject uses the object; otherwise it is denied and may be logged. The check must happen on every access, not only at open time, unless the open-time check is sufficient for the whole session.

Role-based access control (RBAC)

In RBAC, permissions are assigned to roles, not directly to users. A role represents a job or function. Users are assigned one or more roles, and inherit the permissions those roles carry.

RBAC chain
Users → Roles → Permissions → Objects
A user's effective rights are the union of the permissions of all roles assigned to them.
University example

The role Faculty may read and write the files holding course marks. The role Student may read only its own results. A new faculty member is granted the Faculty role; every permission follows automatically. When the person leaves, removing the role withdraws all permissions at once, with no need to edit each file.

Why RBAC helps

  • Simpler administration — permissions are managed per role, not per user.
  • Consistency — everyone with the same role gets the same rights.
  • Least privilege — each role carries only what its job requires.
  • Auditability — roles make it clear who is supposed to have which access.
Roles versus groups

A group is a collection of users; a role is a collection of permissions. A user can be placed in a group without changing what the group may do, while a role is defined by what it may do. RBAC usually combines both: roles are assigned to users, and roles are authorised on objects.

Revocation of access rights

Revocation is the removal of access rights that were previously granted. Access requirements change: a user changes role, leaves a project, no longer needs a resource, or a resource becomes more sensitive. A dynamic protection system must be able to withdraw rights, not only grant them.

Example: before revocation, D1 has read and write on F1. After revoking write, D1 has read only.

When revocation is needed

  • A user's role or responsibility changes.
  • A user no longer needs access.
  • A resource becomes more restricted.
  • Temporary access expires.
  • An administrator withdraws a permission.

Dimensions of revocation

Pair Meaning
Immediate vs delayed Rights are removed at once, or after a specified time or condition.
Selective vs general Remove from one user/domain, or from everyone holding that right.
Partial vs total Remove some rights while keeping others, or remove all access to the object.
Temporary vs permanent Remove for a period or until a condition, or remove permanently.
Examples

Immediate and selective — an employee leaves; their access to all files is removed at once while everyone else keeps theirs.

Delayed and temporary — a guest may access a project folder until the end of the week, then access is withdrawn automatically.

Partial — write is removed from a file but read remains.

General and total — a file becomes confidential, so every domain except the owner loses all rights.

Revocation with ACLs and capabilities

With an ACL, all information about an object is in one place, so revocation is straightforward: find the domain's entry and delete or modify it. The change takes effect for every future access.

With a capability list, rights are held by domains and can be copied or passed on. Revoking one capability may require finding every copy scattered across the system. Special techniques are needed.

Revocation techniques for capabilities

  1. Reacquisition — capabilities have a limited validity. When one expires, the domain must request it again; if the right has been revoked, the request is refused. Simple, but access persists until the next renewal.
  2. Back-pointers — the system keeps a list of pointers to every copy of a capability. Revocation follows the list and removes or invalidates each copy. Flexible but costly to maintain.
  3. Indirection — capabilities point to entries in a global table rather than directly to the object. Deleting or invalidating an entry revokes every capability that goes through it. Efficient and centralised.
  4. Keys — each capability carries a key; changing or invalidating the key makes old capabilities unusable. Simple, but key management must be careful.

awk & sed

awk and sed are UNIX text-processing tools. They are used from the shell and in pipelines to filter, extract, transform and report on text without opening an interactive editor.

awk — pattern-directed data processing

awk reads input line by line, splits each line into fields, and executes an action when a pattern matches. It is effectively a small programming language, well suited to tables and columnar data.

awk program shape
awk 'pattern { action }' file
If the pattern is omitted, the action runs for every line. If the action is omitted, the default action is to print the line.

Fields and records

  • Record — one input line by default.
  • Field — a whitespace-separated column; $1 is the first, $2 the second, and $0 the whole line.
  • NR — number of records read so far (line number across all files).
  • NF — number of fields in the current record.
  • FS — input field separator (default whitespace); OFS — output field separator.

Common examples

# print the first and fourth columns
awk '{print $1, $4}' employee.txt

# print lines containing "manager"
awk '/manager/ {print}' employee.txt

# count lines (NR at END)
awk 'END {print NR}' employee.txt

# print the last field of every line
awk '{print $NF}' file.txt

# use a comma as the field separator
awk -F, '{print $2}' data.csv

# sum a column and print a total
awk '{sum += $3} END {print sum}' marks.txt

BEGIN runs before any input is read; END runs after all input is processed. They are used for initialisation and for totals or summaries. Conditions can be written before the action, for example $3 > 50 {print $1}, or inside it with an if.

sed — stream editing

sed (stream editor) edits text as a stream, line by line, in a single pass. It is ideal in pipelines because it reads standard input and writes standard output without modifying the original file unless asked.

sed program shape
sed 'command' file
s/old/new/[g]   substitute
Without g, only the first occurrence on each line is replaced. The -n option suppresses automatic printing, so only explicit p commands print.

Common sed commands

-iEdit the file in place (GNU sed).
# replace hello with world (first occurrence per line)
sed 's/hello/world/' file.txt

# replace every occurrence
sed 's/hello/world/g' file.txt

# delete line 2
sed '2d' file.txt

# print only line 2
sed -n '2p' file.txt

# delete lines 4 to 6
sed '4,6d' file.txt

# edit the file in place (a backup is wise)
sed -i.bak 's/old/new/g' file.txt

When to use which

Use awk when the data is structured into columns and you need to compute, filter or summarise. Use sed when you need a simple, fast line-oriented edit such as a global substitution or deletion. They compose well: sed can normalise text before awk extracts fields, and both can sit in the middle of a pipeline.
