Microarchitecture

How the MIPS instruction set is actually built: architectural state and performance analysis, the single-cycle datapath and its control, the multicycle processor with its finite-state controller, and the five-stage pipeline with forwarding, stalls, flushes and its own performance equation.

Architecture versus Microarchitecture

Architecture is the programmer's view: the instruction set specification plus the architectural state that a program can observe. In MIPS that state is the program counter (PC), the 32 registers, and memory. Microarchitecture is how that state and instruction set are realized in hardware. One architecture can have many microarchitectures: the same MIPS binary can run on a single-cycle, a multicycle, or a pipelined implementation, and each will have a different cost and performance.

PROCESSOR = DATAPATH + CONTROL

The datapath is the collection of functional blocks that hold and transform data: PC, instruction memory, register file, ALU, data memory and multiplexers. The control unit reads the instruction and decides which datapath elements act in each cycle by asserting control signals.

The MIPS subset used in this unit

To keep the datapath readable, the designs implement a representative subset: R-type instructions (and, or, add, sub, slt), memory instructions (lw, sw), and the branch beq. The multicycle design adds addi and j. Every idea generalizes to the full instruction set; the subset merely removes instructions that would add multiplexers without adding a new concept.

Design always balances three constraints: cost (area and manufacturing), power (energy per operation and cooling), and performance (execution time). The fastest design is not automatically the best design if it is too large, too hot, or too expensive.

Performance Analysis

Program execution time is the product of three quantities: how many instructions the program executes, how many cycles each instruction takes on average, and how long one cycle lasts.

THE PERFORMANCE EQUATION
Execution Time = IC × CPI × Tc
IC = instruction count    CPI = cycles per instruction    Tc = clock period
Tc = 1 / f, where f is the clock frequency. IPC = instructions per cycle = 1 / CPI.

The instruction count is fixed by the program and the compiler. CPI is a property of the microarchitecture and the instruction mix. The clock period is set by the critical path through the datapath plus register overhead. Improving any one factor helps, but the factors interact: a design that shortens the clock may raise CPI, and a design that lowers CPI may lengthen the clock. The right comparison is always the product.

SPEEDUP
Speedup = Told / Tnew = (IC × CPI × Tc)old / (IC × CPI × Tc)new
With the same program and instruction count, speedup is the ratio of CPI × Tc products.

Amdahl's law limits the benefit of optimizing only one part of a system. If a fraction f of the work is sped up by a factor S, the overall speedup is bounded by the unchanged remainder:

AMDAHL'S LAW
Speedup = 1 / [(1 − f) + f / S]
Even an infinite speedup of the optimized part leaves 1/(1 − f) as the maximum overall speedup.

Worked comparison

Suppose a program executes 100 billion instructions. A single-cycle processor has CPI = 1 and a 925 ps clock, so:

SINGLE-CYCLE EXECUTION TIME
T = 100 × 109 × 1 × 925 × 10−12 s = 92.5 s

A multicycle processor has a much shorter 325 ps clock but needs an average of 4.12 cycles per instruction, so:

MULTICYCLE EXECUTION TIME
T = 100 × 109 × 4.12 × 325 × 10−12 s = 133.9 s

The multicycle design has the faster clock yet the slower program, because the extra cycles outweigh the shorter period. This is the central lesson of performance analysis: never judge a processor by clock frequency alone. A pipelined design tries to keep CPI near 1 and the clock short, which is why it wins when hazards are controlled.

BENCHMARKS AND MIX

Real programs do not execute each instruction equally often. A benchmark's instruction mix (percentage of loads, stores, branches, jumps, R-type operations) determines the average CPI. Multicycle CPI is a weighted average of the cycles required by each instruction class.

State Elements and Timing

A processor is built from a handful of state elements and combinational blocks. The PC is a 32-bit register whose output addresses the instruction memory. The register file has two read ports and one write port. The ALU performs arithmetic and logic and produces a Zero flag. Data memory is read or written under control signals. Multiplexers select among alternative sources.

ElementInputsOutputsControl
PCPC' (next address)PC (current address)Clock; PCWrite enable
Instruction memoryAddress32-bit instructionNone (read-only)
Register fileA1, A2, A3, WD3RD1, RD2WE3 (write enable), clock

Registers are edge-triggered. On a rising clock edge a register captures its input; the output then becomes valid after a small clock-to-Q delay tpcq. The combinational logic that follows must settle before the next edge, leaving a setup time tsetup before the edge. The minimum clock period for a path is therefore:

GENERAL PATH TIMING
Tc ≥ tpcq + tcombinational + tsetup
The critical path is the slowest such path in the design. Every other path has slack.

Single-Cycle Datapath

In a single-cycle processor, every instruction completes in exactly one clock cycle. All the functional units needed by an instruction are placed in the datapath and connected by multiplexers; the control unit selects the path for the current instruction. The design is conceptually simple, but the clock must be long enough for the slowest instruction, and hardware cannot be reused across cycles.

Step 1: fetch the instruction

The PC holds the address of the instruction to execute. Its output drives the address input of the instruction memory, which reads out the 32-bit instruction. At the same time the PC's next value is computed: normally PC + 4, or the branch target when a branch is taken. A multiplexer controlled by PCSrc chooses between them.

Step 2: read the source registers

The instruction fields rs (bits 25:21) and rt (bits 20:16) address the register file. The two read ports produce RD1 and RD2. For lw, rs is the base-address register; for an R-type instruction, both rs and rt are ALU sources.

Step 3: sign-extend the immediate

The 16-bit immediate (bits 15:0) is sign-extended to 32 bits to form SignImm. Memory offsets and branch displacements may be negative, so the sign bit must be replicated into the upper 16 bits.

Step 4: compute the address or ALU result

Source A of the ALU normally comes from RD1. Source B is selected by ALUSrc: it is either RD2 (for R-type operations) or SignImm (for lw, sw, addi). For a load or store, the ALU adds the base and offset to produce the memory address. For an R-type instruction, it performs the requested operation. The ALU also produces a Zero flag indicating whether the result is zero.

Step 5: access memory and write back

For lw, the ALU result addresses data memory, and the read data is written back to the register file through the MemtoReg multiplexer. For sw, the value from RD2 is written to memory and no register write occurs. For an R-type instruction, the ALU result is written to rd. For beq, the ALU subtracts the two registers; if Zero is asserted and Branch is enabled, PCSrc selects the branch target.

PC→ Instruction memory→ Register file→ ALU→ Data memory→ Register write-back
The load path is the longest: instruction fetch, register read, ALU, data memory, register setup.

The branch target is computed by shifting SignImm left by two (converting a word offset to a byte offset) and adding it to PC + 4. A separate adder is used for this so that the main ALU remains free for the comparison. The result feeds the PCSrc multiplexer.

The branch path in detail

For beq, the two source registers are read in the same way as for an R-type instruction. The main ALU subtracts them and asserts Zero when they are equal. In parallel, the sign-extended immediate is shifted left by two and added to PC + 4 to form the branch target. The final PC input is selected by PCSrc = Branch AND Zero: if the instruction is a branch and the values are equal, the target is taken; otherwise the sequential PC + 4 is used. The branch does not write a register or access data memory.

Extending the datapath: addi and j

addi needs no new datapath hardware. It uses the same immediate path as lw, but writes the ALU result to rt instead of writing memory data. Its control signals are RegWrite = 1, RegDst = 0, ALUSrc = 1, Branch = 0, MemRead = 0, MemWrite = 0, MemtoReg = 0, and ALUOp = 00 (add).

j does need one extra multiplexer. The jump target is formed from the upper four bits of PC + 4, the 26-bit instruction field, and two zero bits. A Jump control signal selects this target at the PC input:

Single-Cycle Performance and Limitations

The clock period must cover the longest path through the datapath. For a load, the path is: PC clock-to-Q → instruction memory → register file read → ALU → data memory → write-back multiplexer → register file setup. This gives:

SINGLE-CYCLE CRITICAL PATH
Tc = tpcq_PC + 2tmem + tRFread + tALU + tmux + tRFsetup
The factor 2 is for instruction memory plus data memory. The load path is slower than an R-type path because it includes the data memory.

Substituting the timing values:

NUMERICAL
Tc = 30 + 2(250) + 150 + 200 + 25 + 20 = 925 ps
fmax = 1 / 925 ps ≈ 1.08 GHz

With CPI = 1, a program of 100 billion instructions takes 100 × 109 × 925 ps = 92.5 s. This is the baseline against which the other designs are measured.

Why single-cycle is not the final answer

  • Every instruction pays for the slowest one. A simple R-type operation could finish much sooner than a load, but it must wait for the full 925 ps clock.
  • Hardware is duplicated. Separate instruction and data memories, a separate branch adder, and many multiplexers are needed because everything happens in one cycle.
  • No resource reuse. The ALU and memory sit idle for parts of the cycle, yet cannot be used by another instruction.
  • CPI is fixed at 1, so the only way to improve performance is to shorten the critical path — which is difficult once the load path dominates.

The multicycle design attacks the first and third problems by breaking the instruction into steps and reusing hardware. The pipelined design attacks all of them by overlapping instructions while keeping each stage short.

Multicycle Datapath

The single-cycle processor uses a separate adder, memory and multiplexer for every instruction because everything must happen in one clock. A multicycle processor takes the opposite approach: it breaks each instruction into a sequence of shorter steps and reuses the same functional units in different cycles. The clock can then be much shorter, because no step has to traverse the entire load path.

Additional state elements

Reusing hardware requires registers to hold intermediate values between steps:

  • IR — the instruction register, holding the fetched instruction for the whole instruction.
  • A and B — latches for the two register-file outputs, so the values survive while the ALU is reused.
  • ALUOut — holds an ALU result (a memory address or an arithmetic result) for the next cycle.
  • PC, instruction/data memory, register file and one ALU — shared across all steps.

Because the same memory serves instructions and data, an IorD multiplexer selects whether the memory address comes from the PC (instruction fetch) or from ALUOut (data access). The register file's write address is selected by RegDst, and its write data by MemtoReg.

The five canonical steps

StepActionReused units
1. FetchIR ← Memory[PC]; PC ← PC + 4PC, memory, ALU
2. Decode / register readA ← rs; B ← rt; compute branch target in ALUOutRegister file, ALU
3. Execute / addressALUOut ← A + SignImm (load/store) or A op B (R-type) or A − B (branch)ALU
4. MemoryLoad: read Memory[ALUOut]; store: write B to Memory[ALUOut]Memory
5. Write-backRegister ← memory data or ALUOutRegister file

Not every instruction uses all five steps. A branch finishes after the execute step, a store finishes after the memory step, and only a load needs the final write-back. This is the source of the varying CPI: the hardware is shared, but different instructions consume different numbers of cycles.

Multicycle Control: The Finite-State Machine

In a multicycle processor the control unit cannot be a simple truth table of the opcode, because the same opcode requires different control signals in different cycles. The control must remember where it is in the instruction. It is therefore a finite-state machine (FSM): a state register plus combinational next-state and output logic. The FSM enters S0 on reset and returns to S0 at the end of every instruction.

Notice the elegance of S1: it always reads the registers and computes the branch target in parallel, because every instruction might need either. The opcode then selects the next state: S2 for memory instructions, S6 for R-type arithmetic, S8 for a branch. Decoding does not itself need control signals beyond the register read; the FSM simply spends one cycle letting the register file and ALU settle.

For beq the ALU is used twice: in S1 it adds PC to the shifted immediate and stores the branch target in ALUOut; in S8 it subtracts the two source registers to set the Zero flag. PCSrc = 1 then chooses ALUOut as the next PC only when Branch and Zero are both asserted. Reusing one ALU for two different jobs is the essence of the multicycle trade-off.

Multicycle Performance

Because the datapath is reused, the critical path is no longer the full load path. The longest step is either the ALU operation plus a multiplexer or a memory access, whichever is slower. The clock period is:

MULTICYCLE CRITICAL PATH
Tc = tpcq + tmux + max(tALU + tmux, tmem) + tsetup
One ALU, one memory, and the registers that separate steps; the max chooses the slower of the ALU and memory paths.
NUMERICAL
Tc = 30 + 25 + max(200 + 25, 250) + 20 = 325 ps
fmax = 1 / 325 ps ≈ 3.08 GHz

The clock is almost three times faster than the single-cycle 925 ps. But each instruction now takes several cycles, so average CPI must be computed from the instruction mix. Using the SPECINT2000 mix (25% loads, 10% stores, 11% branches, 2% jumps, 52% R-type):

AVERAGE CPI
CPI = (0.11 + 0.02)(3) + (0.52 + 0.10)(4) + (0.25)(5)
CPI = 0.39 + 2.48 + 1.25 = 4.12
Branches and jumps take 3 cycles; R-type and stores take 4; loads take 5.

For 100 billion instructions the execution time is:

MULTICYCLE EXECUTION TIME
T = 100 × 109 × 4.12 × 325 × 10−12 s = 133.9 s

This is slower than the single-cycle 92.5 s, even though the clock is much faster. The reason is that CPI grew from 1 to 4.12, and 4.12 × 325 ps = 1339 ps per instruction, compared with 925 ps for the single-cycle design. The multicycle processor wins on hardware cost and clock frequency, but loses on this particular mix because it pays several cycles of sequencing overhead for every instruction.

WHY BUILD IT THEN?

The multicycle design uses far less hardware (one ALU, one memory, no duplicated adders) and is the natural stepping stone to a pipeline. Its variable cycle count also matches instructions of different complexity. The performance comparison depends on the instruction mix and on how much the single-cycle clock is penalized by its slowest path.

Pipelined Datapath

A pipelined processor takes the multicycle idea one step further: instead of one instruction using the whole datapath for several cycles, several instructions occupy different stages at the same time. The datapath is divided into five stages separated by pipeline registers, so each stage works on a different instruction in every cycle. The result is one instruction completed per cycle after the pipeline fills, while each individual instruction still takes five cycles.

The five stages

Pipeline registers

Four register banks separate the stages and carry both data and control from one stage to the next:

IF→ IF/ID→ ID→ ID/EX→ EX→ EX/MEM→ MEM→ MEM/WB→ WB
Each register bank is clocked; it holds the results of one stage for use by the next.

The IF/ID register holds the fetched instruction and PC + 4. ID/EX holds the register values, the sign-extended immediate, the register numbers and the control signals. EX/MEM holds the ALU result, the store data and the destination register. MEM/WB holds the memory read data or ALU result plus the destination register. Control signals are generated in ID and travel down the pipeline with their instruction, so each stage knows what to do without re-decoding the opcode.

After the first instruction fills the pipeline, one instruction finishes every cycle. The latency of one instruction is five cycles, but the throughput is one instruction per cycle. This is the same distinction as the cookie example: pipelining improves throughput without shortening the time one task spends in the system.

Control in the pipeline

The control unit is similar to the single-cycle control, but its outputs are latched into the pipeline registers and used in the stage where they are needed. RegWrite is needed in WB, MemRead/MemWrite in MEM, ALUSrc/ALUOp in EX, and RegDst in WB. Carrying control bits alongside data is simpler and faster than decoding the instruction again in every stage.

A crucial detail is the register file write/read timing: the register file writes on the first half of the clock and reads on the second half. This allows an instruction to read a register written by an instruction in WB in the same cycle, reducing the need for forwarding in the simplest cases.

Pipeline Hazards

Pipelining assumes that instructions can execute independently, but real programs violate that assumption. A hazard is any condition that prevents the next instruction from executing in its scheduled cycle. The pipeline must stall (insert a bubble), forward data, or flush wrong instructions. Every such event raises the effective CPI above the ideal 1.

Structural hazards

A structural hazard occurs when two instructions need the same hardware resource in the same cycle. A single memory used for both instruction fetch and data access would conflict when a load is in MEM while another instruction is in IF. MIPS avoids this with separate instruction and data memories (or separate ports). The register file also needs enough ports: two reads and one write per cycle.

Data hazards

A data hazard occurs when an instruction needs a value that an earlier instruction has not yet written. The classic read-after-write (RAW) case is:

add $s0, $s1, $s2   # produces $s0 in EX/MEM
sub $t0, $s0, $s3   # needs $s0 in EX, one cycle later

Without help, the subtract would read the old $s0 in ID before the add has reached WB. Two techniques fix this:

  • Forwarding (bypassing): route the result directly from the EX/MEM or MEM/WB pipeline register to the ALU input of the dependent instruction. The value exists in the pipeline even though it has not been written to the register file.
  • Stalling: freeze the dependent instruction in ID and insert a bubble into EX until the value is available in the register file.

Forwarding handles most ALU-to-ALU dependencies with no penalty. A load-use hazard is the important exception: the loaded value is only available after MEM, so an instruction immediately using the loaded register cannot get it in time even with forwarding. The pipeline stalls one cycle:

lw  $s0, 0($t0)    # value available at end of MEM
add $t1, $s0, $s2  # needs it in EX, one cycle too early -> stall 1 cycle

The hazard unit compares the destination register of the instruction in EX/MEM and MEM/WB with the source registers of the instruction in ID/EX, and asserts the forwarding mux selects. It detects a load-use hazard when the instruction in ID/EX is a load and its destination matches a source of the instruction about to enter EX; it then stalls the PC and IF/ID and clears the control signals in ID/EX.

Forwarding priority matters when two older instructions both write the same register: the youngest producer must win. The usual conditions are: forward from EX/MEM if EX/MEM.RegWrite is set, EX/MEM.rd ≠ 0, and EX/MEM.rd matches either source of the instruction in EX; otherwise forward from MEM/WB under the analogous conditions. Register 0 is excluded because it must always read as zero. The forwarding multiplexers sit directly before the ALU inputs, so the dependent instruction receives the value in the same cycle it needs it.

Control hazards

A control hazard occurs because the processor does not know the outcome of a branch until the branch is evaluated. By then it has already fetched the next sequential instruction, which may be wrong. The responses are:

  • Flush: discard the wrongly fetched instructions by clearing their control signals (turning them into bubbles).
  • Move the decision earlier: evaluate the branch in ID rather than EX, so fewer wrong instructions are fetched.
  • Predict: guess taken or not-taken and fetch along the predicted path; flush only on a misprediction.
  • Delayed branch: define the instruction after the branch as always executed (the delay slot), so it does useful work regardless of the outcome.

A taken branch typically costs one or more cycles of lost work. The exact penalty depends on how many stages are flushed and when the branch is resolved. Jumps are similar but their target is known earlier.

HARDWARE SUMMARY

Forwarding muxes sit at the ALU inputs; the hazard detection unit controls PCWrite, IF/ID write, and the ID/EX control clear; the flush logic clears control bits for wrong-path instructions. These are the price of overlapping execution, and they are why real pipelines rarely achieve CPI exactly 1.

Pipelined Performance

The pipeline clock is set by the slowest stage, not by the sum of all stages. If the slowest stage (including register clock-to-Q and setup) takes 250 ps, then:

PIPELINE CLOCK AND THROUGHPUT
Tc = max(stage delays) = 250 ps
Throughput = 1 / Tc = 1 / 250 ps = 4 × 109 instructions/s
In general Tc = tpcq + max(combinational stage delay) + tsetup; the 250 ps figure already represents the limiting stage with that overhead.

One instruction still spends five stages in the pipeline, so its latency is:

PIPELINE LATENCY (ONE INSTRUCTION)
Latency = k × Tc = 5 × 250 ps = 1250 ps
Latency is longer than the single-cycle 925 ps, but throughput is far higher because five instructions overlap.

Ideal speedup of a k-stage pipeline is k, but unbalanced stages, register overhead and hazards reduce it.

Where the ideal is lost

  • Unbalanced stages: the clock is set by the slowest stage; faster stages sit idle, so the effective speedup is less than the number of stages.
  • Pipeline register overhead: tpcq and tsetup are paid in every stage, so splitting a path into more stages has diminishing returns.
  • Hazards: data stalls, load-use stalls and branch flushes insert bubbles. If the average number of stall cycles per instruction is s, then CPI = 1 + s and execution time becomes IC × (1 + s) × Tc.
  • Fill and drain: at the start and end of a program the pipeline is not full, so very short programs see less benefit.

The pipeline is nevertheless the dominant organization in modern processors because it keeps CPI close to 1 while allowing a short clock. Deeper pipelines raise the clock further but increase hazard penalties and the cost of a misprediction; this is one of the central trade-offs in processor design.

Comparing the Three Processors

All three designs implement the same architecture and the same instruction set. They differ only in how the datapath is scheduled, which changes CPI, clock period, hardware cost and control complexity.

The single-cycle design is the conceptual baseline: every instruction follows the same long path. The multicycle design trades CPI for a shorter clock and much less hardware. The pipelined design recovers CPI while keeping the short clock, at the cost of forwarding, stalls, flushes and a more complex control path. In practice, real processors combine pipelining with multiple issue, caches, branch prediction and speculation—but the performance equation and the hazard trade-offs remain the same.

THE ONE-SENTENCE SUMMARY

Performance is IC × CPI × Tc; the single-cycle design minimizes CPI at the cost of Tc, the multicycle design minimizes Tc at the cost of CPI, and the pipeline tries to minimize both while paying for hazards.
