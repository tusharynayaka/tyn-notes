Memory Management

Hardware and control structures, address translation, dynamic loading and linking, memory-mapped files, swapping, fragmentation, segmentation, paging, page-table structures, the TLB and effective access time, virtual memory, demand paging, copy-on-write, page replacement, frame allocation, thrashing, NUMA and memory locality, and the clock algorithm.

Background & basic hardware

Main memory is a large array of bytes, each with its own unique address. The CPU uses these addresses to fetch instructions and operands and to store results. From the point of view of the memory unit, all it sees is a continuous stream of addresses; it has no idea which instruction generated an address or whether the address belongs to code, data, a stack frame, or a page table.

What happens when an instruction executes

  1. Fetch — the CPU fetches the next instruction from memory using the program counter.
  2. Decode — the instruction is decoded to determine the operation, the addressing mode, and the operands required.
  3. Operand fetch — operands are read from registers or from memory.
  4. Execute — the operation is performed by the ALU or control unit.
  5. Store result — the result is written back to a register or to memory.

A single high-level statement can expand into many such instruction cycles, and each memory reference inside those cycles is an address that must be translated and protected.

Storage the CPU can access directly

Before a program can execute it must be brought from disk into main memory and placed in the ready queue. The CPU can directly access only two levels of storage:

  • CPU registers — accessible within one clock cycle or less; no memory bus transaction is required.
  • Main memory (RAM) — accessed over the memory bus and may take many CPU cycles, during which the CPU can stall.

To bridge this speed gap, a cache is placed between the CPU registers and main memory. The cache holds recently used instructions and data, and it operates without explicit operating-system control. Cache is a performance optimisation; it does not remove the need for protection or address translation.

Why protection is required

Because the CPU talks to memory directly, one process must not be able to read or overwrite the operating system or another process. Protection therefore has to be enforced by hardware mechanisms — the operating system alone cannot intervene between every CPU memory reference. The base and limit registers, paging protection bits, and the valid–invalid bit are examples of such hardware support.

Uniprogramming & multiprogramming

Uniprogramming

In early systems only one program occupied memory at a time. The program was loaded at a fixed physical location and had complete control of the machine.

  • The program always runs at the same location in physical memory.
  • No other program is present, so no protection mechanism is needed between processes.
  • The program can access any physical address, including the operating system's memory.
  • The system creates the illusion that the program owns the whole machine.

The major drawback is wasted CPU time: while the single program waits for an I/O operation, the CPU sits idle, because there is no other program to run.

Multiprogramming

Modern systems keep several processes in memory at the same time. While one process waits for I/O, the CPU can execute another. This raises CPU utilisation and throughput but creates two protection problems:

  1. Protect the operating system from user processes.
  2. Protect processes from each other.

Both must be solved in hardware. A user process runs in user mode; the operating system runs in kernel mode. Only privileged instructions executed in kernel mode may change the protection registers or the page tables.

UniprogrammingOne process, fixed location, no isolation, CPU idle during I/O.
MultiprogrammingMany processes, dynamic placement, hardware isolation, higher CPU utilisation.
Degree of multiprogramming

The number of processes kept in memory at once. Raising it improves CPU utilisation up to a point; raising it too far, without enough frames per process, causes thrashing (covered later).

Base & limit protection

The simplest hardware protection scheme uses two registers per process: a base register and a limit register. Together they define the legal physical memory range of the process.

  • Base register — the smallest legal physical address the process may use. It is also called the relocation register.
  • Limit register — the size of the allowed region, not the largest address. The largest legal address is base + limit − 1.
Protection check
0 ≤ logical address < limit
physical address = base + logical address
If the logical address is ≥ the limit, the hardware raises a trap; the access is never sent to memory.

How a reference is checked

  1. The CPU generates a logical address.
  2. Hardware compares it with the limit register.
  3. If it is outside the range, a trap transfers control to the operating system, which normally terminates the offending process.
  4. If it is inside the range, the base value is added and the resulting physical address is placed on the memory bus.
Worked example

Suppose base = 300040 and limit = 120900. The legal physical range is 300040 to 420939. A logical address of 0 maps to 300040; a logical address of 120899 maps to 420939. A logical address of 120900 is rejected even though it is only one past the last legal byte.

The base and limit registers are loaded by the operating system as part of the context switch, using privileged instructions. A user program cannot change them, otherwise it could grant itself access to another process's memory. This scheme protects the OS, other processes, and other users' data.

Key point

Base-and-limit gives contiguous protection: one process occupies one contiguous range. It does not by itself allow a process to be scattered over non-adjacent frames — that requires paging or segmentation.

Address binding & the MMU

Programs are stored on disk as binary executable files and loaded into memory before execution. A process does not necessarily start at address 0; it can be placed anywhere in physical memory. Address binding is the process of mapping one address space to another — deciding which physical address corresponds to each instruction and data item.

Three kinds of addresses

  • Symbolic addresses — names used in source code, such as variables, labels and functions.
  • Relocatable addresses — offsets generated by the compiler relative to the start of the program or module, for example “14 bytes from the start of this module”.
  • Absolute addresses — the actual physical memory addresses used by the memory hardware.

The compiler, assembler, linker and loader convert symbolic addresses into relocatable addresses and finally into absolute addresses.

The three binding stages

Stage When binding happens Code produced / requirement
Compile time The final memory location is known before compilation. Absolute code. If the starting address later changes, the program must be recompiled.
Load time The location is not known at compile time; binding occurs when the program is loaded. Relocatable code. The loader fixes the final addresses.
Execution time The process may move while it runs, so binding is delayed until run time. Requires hardware support — a Memory Management Unit (MMU) or base/limit registers.
Comparison

Compile-time binding is fastest but inflexible. Load-time binding allows relocation at load but not afterwards. Execution-time binding is the most flexible and is what modern multiprogrammed systems use, because processes can be moved, swapped or paged at any time.

Multistep processing of a user program

  1. The source program is written in a high-level language or assembly.
  2. The compiler or assembler produces object code with relocatable addresses.
  3. The linker combines object modules and required library routines, resolving external references.
  4. The loader places the resulting load module into memory and performs load-time relocation if needed.
  5. Execution begins; at run time the MMU translates each logical address into a physical address.

The Memory Management Unit (MMU)

The MMU is the hardware that translates logical addresses generated by the CPU into physical addresses used by the memory unit. In the simplest relocation scheme it adds the value of a relocation register to every logical address:

Dynamic relocation
physical address = logical address + relocation register
The relocation register holds the starting physical address of the process. The translation is performed at run time for every reference.
Worked example

If the relocation register is 14,000 and the CPU generates logical address 346, the MMU produces 14,000 + 346 = 14,346. The program itself only ever sees address 346, so it can be loaded anywhere without recompilation.

Logical versus physical address space

Logical (virtual) address Physical address
Generated by the CPU during execution. The actual address in main memory.
Used by the process; the process's view of memory. Used by the memory hardware and the memory bus.
Translated by the MMU. Obtained after translation; never seen by the user program.

With compile-time and load-time binding the logical and physical addresses are identical, because the final address is fixed before execution. With execution-time binding they differ, and every reference must be translated at run time.

Common exam trap

“Logical address” and “virtual address” are synonyms. “Physical address” is what the memory chip sees. A process never generates a physical address directly.

Dynamic loading, dynamic linking & shared libraries

Dynamic loading

Dynamic loading delays bringing a routine into memory until it is actually called. The main program is loaded first; a routine is loaded only on its first invocation. If the routine is never called, it is never loaded.

  • Saves memory when large modules are rarely used — for example an export, print or help feature.
  • No special operating-system support is strictly required: the program itself can implement the loading using a relocatable linking loader.
  • The first call is slower because the routine must be located and loaded; later calls are normal.

Static linking

Static linking combines system libraries with the program during compilation or loading. The resulting executable contains its own copy of every library routine it uses.

  • Advantage: the executable is self-contained and does not depend on library versions at run time.
  • Disadvantage: each program carries a private copy of the library code, wasting disk space and memory when many programs use the same library.

Dynamic linking

Dynamic linking postpones linking of library references until execution time. Instead of embedding the full library, the executable contains a small piece of code called a stub for each library routine.

  1. The stub locates the required library routine in memory (loading the library if necessary).
  2. It replaces itself with the address of that routine.
  3. It transfers control to the library routine.

After the first call, later calls go directly to the resolved routine. The library code is shared: one physical copy is mapped into the address space of every process that uses it.

Executable before first call          After resolution
+----------------------+              +----------------------+
| call printf  ------> | stub         | call printf  ------> | library code
+----------------------+              +----------------------+

Shared libraries and position-independent code

Shared libraries are compiled as position-independent code (PIC) so that they can be loaded at any virtual address and mapped into different processes without modification. This is essential because two processes may map the same physical library page at different virtual addresses.

  • Linux/UNIX: shared objects .so, managed by the dynamic linker (ld-linux.so) and the program interpreter recorded in the ELF header.
  • Windows: dynamic-link libraries .dll, loaded by the Windows loader.

Dynamic linking in Linux — sequence

  1. The executable contains a small statically linked routine and a list of required shared libraries.
  2. When the program starts, the dynamic linker loads the required libraries into the process's address space.
  3. It resolves references to functions and variables, using relocation tables and the global offset table (GOT) / procedure linkage table (PLT).
  4. Lazy binding may resolve a function only on its first call; eager binding resolves everything at load time.
Aspect Static linking Dynamic linking
When libraries are combined Compile or load time Execution time (or first call)
Library copy Private copy in each executable One shared copy in memory
Executable size Larger Smaller
Startup No resolution overhead Extra dynamic-linker work at startup
Library update Relink the program Replace the shared library (subject to ABI compatibility)
Failure mode Self-contained Missing or incompatible library prevents startup
Dynamic loading vs dynamic linking

Dynamic loading is about when a routine is brought into memory. Dynamic linking is about when library references are resolved. A dynamically linked program may still load all its libraries at startup; a dynamically loaded routine may come from a statically linked module.

Memory-mapped files & mmap()

Normally a process reads a file with open(), read(), write() and close(). Every access is a system call, and data is copied between the kernel buffer and the user buffer. Memory mapping replaces this with ordinary memory accesses: part of the process's virtual address space is logically associated with the file.

Definition

Memory mapping a file associates a region of a process's virtual address space with a file (or shared-memory object), so that the file contents can be accessed through normal loads and stores instead of explicit read()/write() calls.

How it works

  1. The process calls mmap(); the OS reserves a virtual-address range and records the file, offset and protection in the process's mapping structures.
  2. The entire file is not loaded. On the first access to a mapped page, a page fault occurs and the OS reads the corresponding file block into a physical page.
  3. Subsequent accesses to that page are normal memory references — no system call.
  4. Modified pages are written back to the file lazily, when memory pressure requires eviction or when the mapping is flushed/closed.
  5. munmap() removes the mapping.

The mmap() interface

void *mmap(void *addr, size_t length, int prot,
           int flags, int fd, off_t offset);
Parameter Meaning
addr Preferred starting virtual address; NULL lets the kernel choose.
length Number of bytes to map.
prot Memory protection: PROT_READ, PROT_WRITE, PROT_EXEC, PROT_NONE.
flags Mapping type: MAP_SHARED or MAP_PRIVATE (plus options such as MAP_ANONYMOUS, MAP_FIXED).
fd File descriptor of the file to map.
offset Starting offset inside the file; must be a multiple of the page size.

Protection flags

  • PROT_READ — pages may be read.
  • PROT_WRITE — pages may be written.
  • PROT_EXEC — pages may contain executable code.
  • PROT_NONE — no access; useful as a guard region.

Flags are combined with bitwise OR, e.g. PROT_READ | PROT_WRITE.

Mapping flags

  • MAP_SHARED — changes are shared with other mappings of the same region and may be written back to the file.
  • MAP_PRIVATE — private copy-on-write mapping; changes are not written back to the file.

Use MAP_SHARED for IPC or file update, and MAP_PRIVATE for read-mostly or speculative work.

Complete example

#include <sys/mman.h>
#include <sys/stat.h>
#include <fcntl.h>
#include <unistd.h>
#include <stdio.h>

int main(void) {
    int fd = open("student.txt", O_RDONLY);
    struct stat sb;
    fstat(fd, &sb);

    char *p = mmap(NULL, sb.st_size, PROT_READ,
                   MAP_PRIVATE, fd, 0);
    if (p == MAP_FAILED) { /* handle error */ }

    /* Access the file as ordinary memory */
    for (off_t i = 0; i < sb.st_size; i++)
        putchar(p[i]);

    munmap(p, sb.st_size);
    close(fd);
    return 0;
}
Why MAP_PRIVATE here

The program only reads the file. A private mapping means that if it did write, the file would not be modified; the kernel would create a private copy of the touched page. O_RDONLY plus PROT_READ is sufficient and safer.

Sharing and copy-on-write

If two processes map the same file with MAP_SHARED, their virtual mappings can point to the same physical pages. A write by one process becomes visible to the other through the shared physical page (subject to the file's write-back semantics). This is an efficient way to implement shared memory.

With MAP_PRIVATE, the initial pages are shared read-only. When a process writes a page, the kernel creates a private copy for that process — this is copy-on-write. The other process keeps the original page.

Sharing rule
same file + MAP_SHARED → same physical page → visible updates
same file + MAP_PRIVATE → COW on write → private updates
Sharing memory does not synchronise access. Processes still need mutexes, semaphores or other mutual-exclusion mechanisms to avoid race conditions.

Memory-mapped files on Windows

Windows exposes the same idea through file mapping. The sequence is:

  1. CreateFile opens the file.
  2. CreateFileMapping creates a file-mapping object — a kernel object that describes the file (or a page-file-backed region) and its protection. The file itself is not yet mapped into the process.
  3. MapViewOfFile maps a view — a range of the object — into the process's virtual address space and returns a pointer to it.
  4. The process reads and writes the view as ordinary memory.
  5. UnmapViewOfFile removes the view; the mapping object is closed when its last handle is closed.

A mapping object can have several views, and several processes can open the same named mapping object. Shared views see the same physical pages; a copy-on-write view (PAGE_WRITECOPY) gives each process private changes, exactly like MAP_PRIVATE on POSIX systems. A named mapping object is therefore also a convenient shared-memory IPC mechanism.

Memory-mapped files versus ordinary file I/O

Normal file access Memory-mapped file
Uses read() and write(). Uses normal memory loads and stores.
Explicit system call per access. One mmap() sets up the whole region.
Data passes through a kernel buffer; extra copy to user memory. The process maps file pages directly; no per-access kernel-to-user copy.
Good for simple sequential I/O. Good for repeated, random or large-file access.
Predictable behaviour for small files. Page faults and address-space consumption are the costs.

Advantages

  • Faster access: file data is reached through memory addresses.
  • Reduced system-call overhead: no read()/write() per access.
  • Efficient random access to any part of the file.
  • Efficient handling of large files through demand paging — only touched pages are loaded.
  • Supports sharing: several processes can map the same file.
  • Supports copy-on-write and can implement shared-memory IPC.

Limitations

  • Synchronisation is still required when several processes modify shared data.
  • Accessing a non-resident page causes a page fault, which is expensive.
  • The mapping consumes part of the process's virtual address space.
  • For very small or one-pass sequential accesses, ordinary I/O may be simpler and just as fast.
  • File size and mapping constraints must be managed carefully; changing the file size while it is mapped can raise SIGBUS.

munmap()

When the mapping is no longer needed, the process calls munmap(addr, length). The mapping is removed; dirty shared pages are written back according to the mapping semantics. Closing the file descriptor does not remove an existing mapping.

Memory-mapped file vs shared memory

A memory-mapped file is backed by a file on disk: the file persists after the processes exit. Shared memory is a region shared between processes, often implemented using a memory mapping of a file or an anonymous shared object. Every shared-memory mapping is a memory mapping, but not every memory-mapped file is intended for IPC.

Swapping

Swapping moves an entire process temporarily out of main memory to secondary storage and later brings it back so it can continue execution. It lets the system run more processes than physical memory could otherwise hold.

Backing store

The secondary storage used for swapped processes is called the backing store. It must be large enough to hold copies of the memory images of all swapped-out processes and must allow direct access to those images — a disk, not a tape.

Roll-out, roll-in

A common variant used with priority scheduling is roll-out, roll-in: a low-priority process is swapped out so that a higher-priority process can be loaded and executed. When the higher-priority process finishes, the lower-priority process may be rolled back in.

Schematic view

  1. When memory becomes full, inactive processes are swapped out.
  2. This frees memory for active processes.
  3. A swapped-out process that becomes ready must be swapped back in before it can run.

This permits oversubscription: the total memory demanded by all processes can exceed the installed physical memory. Idle or blocked processes are the best candidates for swapping.

Context-switch time with swapping

Normally a context switch saves one process's state and loads another's. If the next process is not in memory, the switch is preceded by a swap-in, which adds disk transfer time.

Swap time
swap time = process size ÷ disk transfer rate
total overhead = swap-out time + swap-in time
Worked example

Process size = 100 MB, disk transfer rate = 50 MB/s.

Swap-out = 100 ÷ 50 = 2 s; swap-in = 2 s; total = 4 s added to the context switch. For a 3 GB process: 3000 ÷ 50 = 60 s each way, or about 120 s for a full swap-out plus swap-in. Swapping large processes is therefore extremely slow.

Limitations of swapping

Pending I/O problem

A process waiting for I/O cannot simply be swapped out. The device may still be transferring data directly into or out of that process's memory. If the memory is reassigned, the device could overwrite another process's data.

Two solutions are used:

  • Never swap out a process with pending I/O.
  • Use double buffering: transfer the data first into kernel buffers, then copy it to process memory after the process is resident again. This adds overhead.

Performance overhead

Disk access is orders of magnitude slower than memory access. Swapping entire processes causes large latency spikes and heavy disk traffic. For this reason, standard whole-process swapping is rarely used in modern general-purpose operating systems.

Swapping in modern systems

Linux uses demand paging rather than whole-process swapping. It moves individual 4 KB pages (or groups of pages) to a swap area, not entire processes. This reduces the amount of data transferred and lets the system keep the resident parts of every process in memory.

  • Swap space is usually a dedicated partition or swap file.
  • Only pages that are not currently needed are written out.
  • Mobile systems often avoid disk swapping entirely; they may reclaim read-only code pages and reload them from storage, or use compressed memory.
Exam wording

Swapping moves processes; demand paging moves pages. Both use a backing store, but paging gives finer control and much lower transfer cost per decision.

Contiguous memory allocation

In contiguous allocation each process occupies a single continuous block of physical memory. This is the simplest placement policy and gives fast address translation: a logical address plus a base gives the physical address.

Memory layout

Memory is normally divided into two regions:

  • Operating-system region — usually in low memory; contains the interrupt vector, kernel code, and kernel data structures.
  • User-process region — in high memory; holds the processes.

Interrupt vector

The interrupt vector is a table of addresses of interrupt service routines (ISRs). On the classic x86 real-mode layout it occupies the first 1024 bytes of memory:

  • 256 interrupt vectors.
  • 4 bytes per vector (segment:offset).
  • Address range 000000H – 0003FFH.

Relocation and limit registers

Contiguous allocation uses the same base/limit protection as before:

  • Relocation (base) register — starting physical address of the process.
  • Limit register — maximum logical address range the process may use.

When the scheduler selects a process, the dispatcher loads these registers during the context switch. The MMU then translates every logical address dynamically.

Translation
physical address = relocation register + logical address
valid only if logical address < limit

Fixed partitioning

Memory is divided into partitions of fixed size at system start-up. Each partition holds exactly one process.

  • The degree of multiprogramming is limited by the number of partitions.
  • A process smaller than its partition wastes the difference — internal fragmentation.
  • A process larger than every partition cannot run at all.
  • Used in early systems such as IBM OS/360.

Variable partitioning

Partitions are created dynamically to match process size. The OS maintains a table of allocated partitions and free partitions, called holes.

  • A hole is a contiguous block of available memory.
  • When a process arrives, a hole large enough is selected and split.
  • When a process terminates, its partition becomes free and is merged with adjacent holes if possible.

Variable partitioning has no internal fragmentation (the allocation exactly matches the request), but it produces external fragmentation as holes accumulate.

Before:  [ OS ][ P1 ][ free ][ P2 ][ free ][ P3 ]
After P2 exits:  [ OS ][ P1 ][ free ][ free ][ free ][ P3 ]
                              └──── coalesced hole ────┘

Partitioning & fit strategies

When several holes can satisfy a request, the operating system must choose one. The three classical strategies are first-fit, best-fit and worst-fit.

Strategy Rule Advantage Disadvantage
First-fit Allocate the first hole that is large enough. Fast; stops searching early. Tends to fragment the beginning of memory.
Best-fit Allocate the smallest hole that is large enough. Leaves the smallest leftover hole. Must search the entire list; creates many tiny unusable holes.
Worst-fit Allocate the largest hole. Leaves a large remainder that may be useful. Must search the entire list; generally worst utilisation.

In practice, first-fit and best-fit usually outperform worst-fit in both speed and storage utilisation.

Worked example

Holes in address order: 100, 500, 200, 300, 600 KB. Request: 212 KB.

  • First-fit: skip 100; allocate from 500 → remainder 288 KB.
  • Best-fit: candidates 500, 300, 600; choose 300 → remainder 88 KB.
  • Worst-fit: choose 600 → remainder 388 KB.

The buddy system

Linux avoids a simple first-fit/best-fit free list for its physical page allocator and uses the buddy allocator. Blocks are always powers of two — 4 KB, 8 KB, 16 KB, 32 KB, 64 KB and so on.

  1. A request is rounded up to the next power of two.
  2. If no block of that size is free, a larger block is split into two “buddies”.
  3. One buddy is returned; the other is split again if necessary.
  4. When a block is freed, the allocator checks whether its buddy is also free and merges them.

Splitting and merging are fast, and the scheme limits external fragmentation. Its cost is internal fragmentation: a 21 KB request is satisfied by a 32 KB block, wasting 11 KB.

Why partitioning matters

All three fit strategies attack the same problem: choosing among holes without knowing the future sequence of requests. No online strategy is optimal for every workload; the goal is acceptable utilisation with low search cost.

Fragmentation & compaction

Internal fragmentation

Internal fragmentation is unused space inside an allocated block, because the block is larger than the request.

Example

A process requests 400 KB but receives a 512 KB fixed partition. The 112 KB difference is internal fragmentation: it belongs to the process's partition but cannot be used by anyone else.

Paging also causes internal fragmentation in the last page: a 10 KB process with 4 KB pages gets three pages (12 KB), wasting 2 KB.

External fragmentation

External fragmentation occurs when enough total free memory exists but it is split into non-contiguous holes, so no single hole can satisfy a large request.

Example

Free memory consists of holes of 100 KB, 80 KB and 60 KB — 240 KB in total. A request for 200 KB fails, even though 240 KB is free, because no hole is large enough.

The 50-percent rule

Statistical analysis of first-fit allocation shows that, for every N blocks allocated, about 0.5N blocks are lost to fragmentation. Equivalently, roughly one third of memory may be unusable.

50-percent rule
fragmented blocks ≈ 0.5 × allocated blocks
usable ≈ 2/3 of memory · fragmented ≈ 1/3
This is a statistical expectation for first-fit, not a guarantee for a particular workload.

Compaction

Compaction reduces external fragmentation by rearranging memory contents so that all free blocks merge into one large block at one end.

  1. Move allocated blocks toward one end of memory.
  2. Update every affected base/relocation value.
  3. The remaining free space becomes one contiguous hole.

Requirements and costs:

  • Requires dynamic relocation — execution-time binding — because processes are moved after they have started.
  • Copies large amounts of memory, consuming CPU time.
  • May require stopping or freezing processes during the move.
  • Not possible with compile-time or load-time binding, since addresses cannot be changed.

Because of these costs, compaction is rarely used as a routine technique in modern systems; paging solves external fragmentation more cleanly.

Segmentation

Segmentation is a memory-management scheme that supports the user's logical view of a program. Instead of treating memory as one linear array of bytes, it divides a program into variable-sized logical units called segments.

What is a segment?

A segment corresponds to a meaningful program structure, with its own name and length. Typical segments include:

  • the main program;
  • procedures, functions, methods and objects;
  • local and global variables;
  • the stack;
  • arrays and the symbol table;
  • shared libraries and common blocks.

Programmers think in these units, so segmentation matches the programmer's view much better than a flat byte array. Segments may vary in size and may be placed anywhere in physical memory; they do not need to be contiguous.

Logical address

Segmented address
<segment number s, offset d>
The segment number identifies the segment; the offset identifies a byte inside it.

Segment table

The hardware uses a segment table to translate a segmented address. Each entry contains:

  • Segment base — starting physical address of the segment.
  • Segment limit — length of the segment.
  • Protection bits (read, write, execute) in real implementations.

Two registers support the table:

  • STBR (segment-table base register) — points to the table in memory.
  • STLR (segment-table length register) — number of segments in the table.
Translation and bounds check
s < STLR
d < segment limit
physical address = segment base + d
If either check fails, the hardware raises a trap — a segmentation fault.

Hardware translation steps

  1. The CPU generates <s, d>.
  2. s is used as an index into the segment table. If s ≥ STLR, trap.
  3. The entry's base and limit are fetched.
  4. d is compared with the limit. If d ≥ limit, trap (segmentation fault).
  5. Otherwise the physical address is base + d.

Worked example

Segment Base Limit
0219600
1230014

31327580
4195296
  • (0, 430) → 430 < 600 → 219 + 430 = 649.
  • (1, 10) → 10 < 14 → 2300 + 10 = 2310.
  • (2, 500) → 500 > 100 → segmentation fault.
  • (3, 400) → 400 < 580 → 1327 + 400 = 1727.
  • (4, 112) → 112 > 96 → illegal address.
Check the limit first

Do not compute base + offset before the limit check. The offset is a logical displacement; if it is outside the segment, the sum is meaningless and must never reach memory.

Sharing segments

Two processes can share a segment by pointing their segment-table entries to the same base address. This is used for shared libraries, shared data structures and interprocess communication. Because the same physical memory is referenced, sharing is efficient and requires no copying.

Protection

Each segment can carry its own protection bits. A code segment can be execute-only or read/execute, a data segment read/write, and a shared library read/execute. This gives fine-grained protection that matches the logical structure of the program.

Disadvantage: external fragmentation

Segments are variable-sized, so free memory becomes scattered as segments are created and destroyed. Even when total free memory is sufficient, a new segment may not fit because no single hole is large enough. This is external fragmentation — the main reason paging was developed.

Segmentation with paging

Real processors (notably Intel x86) combine both ideas: a logical address is first segmented, then each segment is paged. Segmentation provides the logical view and protection; paging eliminates external fragmentation and allows the segment to be scattered in physical memory.

Paging

Paging permits a process's physical address space to be non-contiguous. It divides logical memory into fixed-size pages and physical memory into fixed-size frames of the same size. Any page can be loaded into any free frame.

Basic method

  • Physical memory is divided into frames; logical memory into pages.
  • Page size = frame size; the size is determined by the hardware, typically 4 KB (also 8 KB, 2 MB, 1 GB).
  • The OS divides each program into pages and finds a free frame for each page.
  • A page table per process maps page numbers to frame numbers.

If a program has N pages, the OS must find N free frames. The pages need not be adjacent, and their order in physical memory is irrelevant.

Pages and frames
number of pages = logical address space ÷ page size
number of frames = physical memory ÷ frame size

On Linux the page size can be checked with getconf PAGESIZE. Typical values are 4096 bytes (4 KB), 8192 bytes, 2 MB and 1 GB (huge pages).

Non-contiguous mapping

Consecutive logical pages do not have to occupy consecutive physical frames. For example:

Logical pagePhysical frame
05
12
27
31

The page table records this mapping. The offset inside the page is copied unchanged, because pages and frames are the same size.

Paging hardware

The MMU performs translation using the page table. The page table itself is stored in main memory; the page-table base register (PTBR) points to its start, and the page-table length register (PTLR) gives its size.

Page-table entries

A page-table entry typically contains:

  • the frame number;
  • a valid–invalid bit — is the page resident / part of the address space?
  • protection bits — read, write, execute;
  • a dirty (modify) bit — has the page been written?
  • a reference (use) bit — has the page been accessed recently?

Worked example (m = 4, n = 2)

Let the logical address space be 24 = 16 bytes and the page size 22 = 4 bytes. Then there are 4 logical pages and 2 offset bits. Physical memory is 32 bytes, so there are 32 ÷ 4 = 8 frames.

Suppose page 3 maps to frame 1. Logical address 13 is binary 1101:

  • page number = 11 = 3;
  • offset = 01 = 1;
  • frame base = 1 × 4 = 4;
  • physical address = 4 + 1 = 5, binary 0101.

The offset bits are unchanged; only the page-number bits are replaced by the frame number.

Free frames

The OS maintains a list of free frames. Before a process is loaded, frames are marked free. As pages are allocated, the page table is updated and the frames are removed from the free list. When a process terminates, its frames return to the free list.

Page-table management

Each process has its own page table. The table serves two purposes: address translation and memory protection. On a context switch the dispatcher must load the new process's page-table base (and possibly flush or tag the TLB), which adds to context-switch cost.

Fragmentation in paging

Paging eliminates external fragmentation because every free frame is the same size and can hold any page. It can still cause internal fragmentation in the last page.

Example

Page size = 4 KB, process size = 10 KB. The process needs 3 pages = 12 KB. The last page is only 2 KB full, so 2 KB is wasted internally.

Shared pages

Paging makes sharing easy: map the same physical frame into the page tables of several processes. Shared code must be reentrant — it must not modify itself, and it should be read-only so that all processes see the same instructions.

Sharing calculation

40 users run the same editor with 150 KB of code and 50 KB of private data.

  • Without sharing: (150 + 50) × 40 = 8000 KB.
  • With shared code: 150 + (50 × 40) = 2150 KB.

Advantages

  • Eliminates external fragmentation.
  • Allows non-contiguous allocation and efficient use of free frames.
  • Simplifies allocation: any free frame will do.
  • Supports virtual memory, sharing, and protection.
  • Makes swapping/page replacement practical because the unit is small and fixed.

Disadvantages

  • The page table consumes additional memory.
  • Address translation adds overhead — at least one extra memory access without a TLB.
  • Internal fragmentation in the last page.
  • Context switching must manage page tables and TLB state.
  • Page-table size can become very large for sparse 64-bit address spaces.

Address translation & address bits

In paging, the logical address generated by the CPU is split into a page number and an offset. The page number indexes the page table; the resulting frame number is combined with the unchanged offset to form the physical address.

Paged address
logical address = page number p | page offset d
physical address = frame number f | page offset d

Bit layout

If the logical address space is 2m bytes and the page size is 2n bytes:

  • the high-order m − n bits are the page number;
  • the low-order n bits are the offset;
  • the number of pages is 2m−n;
  • the physical address needs f + n bits, where f is the number of frame number bits.
Useful counts
page-table entries = 2m−n
page-table size = entries × entry size
frames = physical memory ÷ 2n
Example 1 — 16-bit address, 4 KB pages

4 KB = 212, so offset = 12 bits and page number = 16 − 12 = 4 bits. The logical address has 16 bits: pppp oooooooooooo.

Example 2 — 32-bit address, 4 KB pages, 4-byte entries

Offset = 12 bits; page number = 20 bits. Number of pages = 220 ≈ 1,048,576. Page-table size = 220 × 4 bytes = 4 MB for a single process. With 2 GB of physical memory, frames = 231 ÷ 212 = 219 = 524,288 frames.

Example 3 — offset extraction

Page size = 4 KB, logical address = 16,385. Divide by 4096: 16,385 = 4 × 4096 + 1. So page number = 4 and offset = 1.

Example 4 — 64 pages of 1024 words, 32 frames

Logical: 64 × 1024 = 65,536 = 216 → 16-bit logical address. Page number = 6 bits, offset = 10 bits. Physical: 32 × 1024 = 32,768 = 215 → 15-bit physical address. Frame number = 5 bits, offset = 10 bits.

Rule of thumb

Only the page-number bits change. The offset is never translated, because the page and the frame have exactly the same size. This is why paging is sometimes called a “page-number replacement” scheme.

Structure of the page table

The page table is consulted on every memory reference, so its organisation has a direct effect on performance and memory overhead. Several structures are used.

1. Page table in registers

The page table can be implemented as a set of dedicated registers, one per entry. Translation is extremely fast, but the approach is practical only for very small tables. A modern process may have millions of pages, so registers cannot hold the whole table.

2. Page table in main memory

Most systems store the table in main memory. The PTBR points to its base and the PTLR gives its length. This introduces the two-memory-access problem:

  1. one access to the page table to obtain the frame number;
  2. one access to the actual data or instruction.

Every logical reference therefore becomes two physical memory accesses, roughly doubling memory latency. The TLB is the standard solution.

3. Hierarchical (multi-level) page tables

A single-level table for a large sparse address space wastes memory: most entries are unused, yet the table must cover the whole virtual range. Hierarchical paging splits the page number into several indices.

Two-level paging (32-bit, 4 KB pages)
p1 (10 bits) | p2 (10 bits) | offset (12 bits)
p1 indexes the outer table; p2 indexes an inner table; the offset addresses a byte inside the page.
  • Each outer entry points to an inner page table.
  • Inner tables are allocated only for address ranges that are actually used.
  • For a process using one small region, the cost can be one outer table (4 KB) plus one inner table (4 KB) instead of a 4 MB flat table.
  • A TLB miss now requires more memory accesses: one per level plus the data access.

Modern systems use three, four or five levels. x86-64 Linux normally uses 4-level paging for 48-bit virtual addresses (9 + 9 + 9 + 9 + 12 bits), with optional 5-level paging for 57-bit addresses (9 + 9 + 9 + 9 + 9 + 12).

Trade-off

More levels save page-table memory for sparse address spaces but increase the number of memory accesses on a TLB miss. The TLB hides this cost for the common case.

4. Hashed page tables

Hashed page tables are used for very large address spaces, especially 64-bit systems. The virtual page number is hashed into a hash table. Each bucket entry contains:

  • the virtual page number;
  • the mapped frame number;
  • a pointer to the next entry in the same bucket (collision chain).

The hash narrows the search to one bucket or a short chain, instead of walking a huge table. A clustered hash table stores several consecutive page mappings in one entry, which helps when pages are accessed sequentially.

5. Inverted page tables

An inverted page table stores one entry per physical frame, not one per virtual page. Each entry contains:

  • the virtual address (or virtual page number) currently mapped there;
  • the process identifier (PID/ASID);
  • the frame number and protection bits.
Advantages Disadvantages
Table size depends on physical memory, not virtual address space. Searching for a virtual page can be slow; hashing is used to speed it up.
One table for the whole system, not one per process. Sharing is harder: one physical frame has only one entry, so multiple virtual mappings to the same frame need extra structures.
Attractive for very large virtual address spaces. A context switch may require changing the PID associated with entries.

6. Huge pages

Modern Linux supports huge pages of 2 MB and 1 GB in addition to the standard 4 KB page. One TLB entry then covers a much larger region, increasing TLB reach and reducing TLB misses for large working sets. The trade-off is greater internal fragmentation and less flexible allocation.

TLB & effective access time

The Translation Lookaside Buffer

The TLB is a small, fast, associative hardware cache of recent page-table entries. It is consulted before the page table in memory, so a translation that hits in the TLB avoids the extra memory access entirely.

  • Typically 64 to 1024 entries.
  • Implemented with associative (content-addressable) memory: all entries are compared in parallel.
  • Stores page number → frame number, plus protection and validity information.
  • Some entries may be wired down — permanently resident for critical kernel code.

Address-space identifiers (ASIDs)

Without ASIDs, the TLB must be flushed on every context switch, because the same virtual page number in a different process maps to a different frame. Flushing discards useful translations and slows the switch.

An ASID is stored with each TLB entry and identifies the process (or address space) it belongs to. Entries for several processes can then coexist, and a context switch only needs to change the current ASID.

TLB hit and TLB miss

Hit

  1. The page number matches a TLB entry.
  2. The frame number is available immediately.
  3. The physical address is formed with the offset.
  4. No page-table memory access is needed.

Miss

  1. The page number is not in the TLB.
  2. The page table in memory is accessed.
  3. The frame number is retrieved (and protection checked).
  4. The mapping is inserted into the TLB, possibly evicting an entry using LRU or FIFO.
  5. The physical address is formed and the access continues.

Effective access time (EAT)

Let:

  • h = TLB hit ratio (fraction of references found in the TLB);
  • t = TLB lookup time;
  • m = main-memory access time.
General EAT with a TLB
EAT = h(t + m) + (1 − h)(t + 2m)
= t + m + (1 − h)m
On a hit: TLB lookup plus one memory access. On a miss: TLB lookup, page-table access, then data access.

When the TLB lookup time is small enough to ignore, or is included in the memory access time, the formula simplifies to:

Simplified EAT
EAT = h × m + (1 − h) × 2m
= m(2 − h)
Worked example 1 — hit ratio 80%

Memory access time = 10 ns, TLB lookup ignored.

EAT = 0.80 × 10 + 0.20 × 20 = 8 + 4 = 12 ns. This is a 20% slowdown compared with a direct memory access.

Worked example 2 — hit ratio 99%

EAT = 0.99 × 10 + 0.01 × 20 = 9.9 + 0.2 = 10.1 ns — only about 1% slowdown. A high hit ratio makes the page table almost invisible.

Worked example 3 — TLB lookup included

TLB access = 10 ns, memory access = 100 ns, hit ratio = 95%.

Hit: 10 + 100 = 110 ns. Miss: 10 + 100 (page table) + 100 (data) = 210 ns.
EAT = 0.95 × 110 + 0.05 × 210 = 104.5 + 10.5 = 115 ns.

At 100% hit, EAT = 110 ns; at 0% hit, EAT = 210 ns.

Worked example 4 — two-level paging

TLB access = 20 ns, memory access = 100 ns, hit ratio = 98%. A miss requires two page-table accesses plus the data access.

Hit: 20 + 100 = 120 ns. Miss: 20 + 100 + 100 + 100 = 320 ns.
EAT = 0.98 × 120 + 0.02 × 320 = 117.6 + 6.4 = 124 ns.

General rule for L levels

On a TLB miss with an L-level page table, the cost is t + L×m + m: one memory access per level plus the final data access. On a hit it is t + m.

Memory protection in paging

Protection bits in each page-table entry specify read, write and execute permission. The valid–invalid bit has two related uses:

  • Valid — the page is part of the process's logical address space and is resident.
  • Invalid — the page is outside the address space (a protection fault) or not currently resident (a page fault, handled by demand paging).

Writing to a read-only page, or accessing an address outside the process's space, traps to the OS. Demand paging deliberately marks non-resident pages invalid so that the first access triggers the loader.

Shared pages and reentrant code

Page tables can map the same frame into multiple processes. Shared code must be reentrant: it must not modify itself and should be mapped read-only. Each process still needs its own private data pages. This is how shared libraries save memory.

Virtual memory & demand paging

Virtual memory is a memory-management technique that lets a process execute even when its entire program is not resident in physical memory. Only the parts that are actually needed at a given moment are kept in RAM; the rest remain on secondary storage. The logical address space can therefore be much larger than the installed physical memory.

A process does not use all of its code at once. Error-handling routes, debugging code, rarely called modules and large data structures may never be touched during a run. Loading them wastes precious frames. Virtual memory makes loading partial and lazy, and in doing so it gives four practical benefits:

  • Programs are no longer constrained by the amount of RAM.
  • Each process occupies fewer frames, so more processes fit in memory.
  • CPU utilisation and throughput rise because more work is ready to run.
  • Pages can be shared between processes — the basis of shared libraries and shared memory.

Logical versus physical memory

Virtual memory cleanly separates two ideas that were previously the same thing:

Logical (virtual) memory Physical memory
The view seen by the process. It starts at address 0 and extends to a maximum determined by the architecture. The actual RAM installed in the machine, divided into fixed-size frames.
Contiguous and private to the process. Shared by all processes and managed by the OS.

The MMU translates logical addresses into physical addresses on every reference. Virtual memory is implemented in practice by demand paging; demand segmentation is the older alternative and is rarely used today.

The virtual address space

A process's virtual address space is conventionally laid out with the heap growing upward and the stack growing downward. The gap between them is unused, which lets both regions expand dynamically as the program allocates memory or recurses. Virtual memory also tolerates a sparse address space: large unused regions (holes) cost nothing because they are simply never mapped to frames.

Sharing through virtual memory

Because page tables map virtual pages to arbitrary frames, the same physical frame can appear in several address spaces. A shared library is loaded once and mapped read-only into every process that uses it. The same mechanism implements shared memory for inter-process communication: each process maps the same frames at a (possibly different) virtual address.

Demand paging

Demand paging loads a page only when it is referenced, rather than loading the whole process at startup. The component that brings pages in is the pager; a lazy swapper avoids swapping a page until it is actually needed. The benefits are lower memory use, less disk I/O at startup, faster program start, and support for more concurrent users.

When the CPU references a page, exactly one of two things happens:

  1. Page is resident — the valid bit is set, translation proceeds, and execution continues normally.
  2. Page is not resident — the valid bit is clear, the hardware traps to the OS, and a page fault is raised. The program itself needs no modification; the OS handles the situation transparently.

The valid–invalid bit

Each page-table entry carries a valid–invalid bit. In a pure paging system without virtual memory, the bit distinguishes pages inside the address space from pages outside it. With demand paging the same bit is reused: v means the page is resident, i means it is not currently in memory. Initially every entry may be marked invalid, and entries become valid as pages are faulted in.

Pure demand paging

In the extreme case the process starts with no pages in memory. The first instruction immediately faults, and pages are loaded one by one as execution touches them. The initial burst of faults is costly, but once the working set is resident, locality of reference keeps the fault rate low.

Locality of reference

Demand paging works because programs do not access memory uniformly. They exhibit locality of reference:

  • Temporal locality — a location used recently is likely to be used again soon (loops, counters, hot variables).
  • Spatial locality — locations near a recently used address are likely to be used soon (contiguous instructions, arrays, records).

Locality is why a small number of frames can serve a large program, and it underpins caching, paging and the working-set model.

Instruction restart

A fault can occur in the middle of an instruction, after some operands have already been fetched. To resume correctly the OS must be able to restart the instruction from a clean state. It saves the CPU registers, the program counter and the process state, loads the missing page, restores the state, and re-executes the instruction. The faulting instruction must therefore be restartable: it must not have produced a visible side effect before the fault.

Performance of demand paging

Let p be the probability that a memory reference causes a page fault (0 ≤ p ≤ 1). The effective access time blends the fast resident case with the very slow fault case.

Effective access time — demand paging
EAT = (1 − p) × memory access time + p × page-fault service time
p = 0 means no faults; p = 1 means every access faults. Because the service time is milliseconds while the access time is nanoseconds, even a tiny p dominates the result.
Worked example

Memory access time = 200 ns; page-fault service time = 8 ms = 8,000,000 ns.

EAT = (1 − p)(200) + p(8,000,000) = 200 + p(7,999,800) ns.

For p = 0.001 (one fault per thousand accesses): EAT = 200 + 0.001 × 7,999,800 = 8,200 ns.

That is roughly 41× slower than an unfaulted access. To keep slowdown near 10%, the fault rate must be on the order of 0.0000025 — which is why demand paging is only viable with strong locality.

Swap space and modern demand paging

Swap space is a reserved area of disk used to hold pages that do not fit in RAM. It is typically sized at one to two times RAM and is faster than ordinary file-system storage because it is allocated in raw blocks without file metadata.

Modern systems go further:

  • Pages are demand-paged directly from executable files, so clean code pages need no swap copy.
  • Anonymous pages (heap and stack) use swap or compressed memory.
  • Read-only pages are reclaimed first when memory runs low, since they can be re-read from the file.
  • Mobile systems often avoid swapping entirely and simply reload code pages from flash when needed.

Page-fault handling

A page fault occurs when the CPU references a page that is not currently in main memory. The hardware cannot complete the translation, so it traps to the operating system. The OS must validate the reference, bring the page in, update the tables, and restart the instruction.

Step-by-step service routine

  1. The MMU finds the page-table entry invalid and raises a page-fault trap. The faulting address is saved in a register (on x86, CR2).
  2. The OS checks whether the reference is legal. An address outside the process's address space, or a write to a read-only page, is a protection violation — the process is sent SIGSEGV and terminated.
  3. If the reference is legal but the page is not resident, the OS locates the page on disk. For a file-backed page this means finding its offset in the executable or mapped file; for an anonymous page it means finding its slot in swap.
  4. The OS looks for a free frame on the free-frame list.
  5. If no frame is free, a page-replacement algorithm selects a victim. If the victim is dirty, it is written back to disk first.
  6. The required page is read from disk into the chosen frame (a DMA transfer; the process is blocked and another process may run).
  7. The page table is updated: the frame number is written and the valid bit is set to v.
  8. The instruction is restarted from the saved state. This time translation succeeds and execution continues.

Major and minor faults

Major (hard) fault Minor (soft) fault
The page is not in memory at all and must be read from disk or swap. The page is in memory but is not yet mapped into this process's page table, or a reclaimed frame can simply be reassigned.
Very slow — involves a storage access. Fast — no storage I/O required.

Kernel page reaper and the OOM killer

To keep memory available, the kernel defines minimum and maximum free-memory thresholds. When free memory drops below the minimum, a reaper reclaims pages (clean file pages first, then dirty ones) until the maximum is reached again. If memory becomes critically low and reclaim cannot keep up, Linux invokes the Out-of-Memory (OOM) killer, which selects and terminates a process to recover memory.

What the hardware must provide

  • A valid bit (or present bit) per page-table entry.
  • A protection field (read / write / execute) so illegal accesses are distinguished from missing pages.
  • A dirty bit recording whether the page has been modified.
  • A reference bit recording whether the page has been used recently.
  • A faulting-address register so the OS knows which page caused the trap.

Copy-on-write

Copy-on-write (COW) is an optimisation used when a process is created with fork(). A naive fork() copies every page of the parent's address space, which is expensive and often wasted: the child frequently calls exec() immediately, or only touches a few pages. COW avoids the copy until a page is actually written.

How it works

  1. After fork(), parent and child share the same physical frames.
  2. Every shared page is marked read-only in both page tables, and a COW flag is recorded.
  3. When either process reads a page, nothing happens — the shared frame is used directly.
  4. When either process writes a page, the write-protection fault traps to the OS.
  5. The OS allocates a new frame, copies the page's contents into it, and maps the new frame writable into the faulting process's table. The other process keeps the original frame.
  6. Only that one page has been duplicated; all untouched pages remain shared.

Advantages and costs

Fast creationfork() returns almost immediately, because pages are not copied.
Low memory useShared pages are stored once until modified.
Fewer allocationsOnly pages actually written are duplicated.
Fault overheadEach first write costs a protection fault plus a page copy.

COW is also used by mmap(MAP_PRIVATE): a private file mapping starts shared and read-only, and modifications trigger per-page copies so the underlying file is never changed. The same idea appears in snapshotting file systems.

Page replacement

When a page fault occurs and memory is full, the OS must evict an existing page to make room. This is page replacement. Two separate decisions are involved:

  1. Frame allocation — how many frames each process receives.
  2. Page replacement — which page to evict when a process needs a new frame.

The goal of both is the same: minimise the page-fault rate, because every fault costs a disk access and stalls the process.

The replacement procedure

  1. Locate the required page on disk.
  2. Find a free frame. If one exists, use it.
  3. If no frame is free, select a victim using the replacement algorithm.
  4. If the victim is dirty, write it back to disk; if clean, discard it.
  5. Read the new page into the freed frame.
  6. Update the page tables and restart the faulting instruction.

Dirty bit (modify bit)

Each page-table entry has a dirty bit set by hardware whenever the page is written. On eviction:

  • Dirty = 1 — the page differs from its disk copy, so it must be written back before the frame is reused.
  • Dirty = 0 — the page is identical to its disk copy (or was loaded read-only), so it can simply be dropped.

Checking the dirty bit roughly halves the I/O cost of replacement, because clean pages — including all pure code pages — need no write-back.

Reference string

Algorithms are compared using a reference string: the sequence of page numbers a process accesses. Only page numbers matter, not full addresses, and a repeated access to the resident page causes no fault. The fault count depends on both the algorithm and the number of frames. The standard string used below is:

7, 0, 1, 2, 0, 3, 0, 4, 2, 3, 0, 3, 0, 3, 2, 1, 2, 0, 1, 7, 0, 1

FIFO, optimal & LRU

FIFO — First-In, First-Out

The oldest page in memory is evicted. FIFO is trivial to implement: keep the pages in a queue and evict the head. Its weakness is that it ignores usage — a page that has been resident a long time but is used constantly is still evicted first.

Belady's anomaly

FIFO can sometimes produce more faults when given more frames. With the string 1, 2, 3, 4, 1, 2, 5, 1, 2, 3, 4, 5:

  • 3 frames → 9 faults
  • 4 frames → 10 faults

Optimal and LRU never suffer Belady's anomaly: they are stack algorithms, so the set of pages in memory with n frames is always a subset of the set with n+1 frames.

OPT — optimal replacement

Replace the page that will not be used for the longest time in the future. OPT produces the minimum possible fault count, but it requires knowledge of the future reference string, so it is unimplementable. It is used only as a benchmark against which real algorithms are measured.

Implementing LRU

Exact LRU requires a total order on page usage. Two common hardware-assisted approaches are:

  • Counters / timestamps — every page-table entry has a time-of-use field; the CPU clock is copied in on each reference, and the smallest timestamp is evicted. This needs a search of the table on every replacement.
  • Stack — keep a doubly linked stack of page numbers; move a page to the top when referenced. The bottom is the LRU page. Updating the stack on every memory reference is expensive and normally needs hardware support.

Because both are costly, real systems approximate LRU with the reference bit and the clock algorithm.

Clock (second-chance) replacement

The clock algorithm — also called second chance — is a cheap approximation of LRU. Exact LRU needs the full order of use; clock needs only a single reference bit (R bit) per frame. Frames are arranged in a circular list, and a pointer called the clock hand sweeps around it like a clock hand.

Data per frame

  • The page number currently in the frame.
  • The reference bit — set to 1 by hardware whenever the page is accessed.

A newly loaded page has its reference bit set to 1, because loading it was itself caused by an access. Any later access also sets the bit to 1.

Working principle

  1. When a page is accessed, hardware sets its reference bit to 1.
  2. On a page fault with no free frame, the hand examines the current page.
  3. If the reference bit is 0, the page is evicted and the new page takes its place.
  4. If the reference bit is 1, the bit is reset to 0 — the page gets a second chance — and the hand advances to the next frame.
  5. The scan repeats until a page with bit 0 is found.

Multiple scansMay sweep several times before finding R = 0.
Degrades to FIFOIf every reference bit is 1, behaviour matches FIFO.

Enhancements

  • Enhanced second chance — use the pair (reference bit, dirty bit) and prefer evicting (0,0) over (0,1) over (1,0) over (1,1). This avoids writing back pages unnecessarily.
  • N-bit aging — shift the reference bit into a counter periodically, producing a crude usage history and a better LRU approximation.

Allocation of frames

Frame allocation decides how many physical frames each process receives. It is the other half of the replacement problem: even a perfect replacement algorithm performs badly if a process has too few frames. Physical memory is finite, so the OS must divide it efficiently to reduce faults, improve CPU utilisation and raise throughput.

For example, if a system has 128 frames and the OS occupies 35, the remaining 93 frames form the free-frame list. A fault takes a frame from this list; once it is exhausted, a replacement algorithm must free a frame.

Minimum number of frames

Every process needs a minimum number of frames, determined by the instruction set architecture, because a single instruction may touch several pages:

  • A simple memory-reference instruction needs 2 frames — one for the instruction, one for the data.
  • With indirect addressing, at least 3 frames are needed — instruction, indirect word, and final data.
  • Complex instructions (string moves, cross-page operands) may need more.

If fewer frames than this minimum are allocated, the instruction can never complete: it faults, evicts a page it still needs, and faults again forever. The maximum is bounded only by available physical memory.

Equal allocation

Every process receives the same number of frames, regardless of size.

Equal allocation
frames per process = ⌊ m / n ⌋
m = total available frames, n = number of processes. Leftover frames form a free-frame buffer.

With 93 frames and 5 processes: 93 ÷ 5 = 18 frames each, with 3 left over. It is simple and fair, but it ignores process size: small processes waste frames while large processes fault heavily.

Proportional allocation

Frames are distributed in proportion to process size.

Proportional allocation
ai ≈ (si / S) × m
si = size of process i, S = sum of all process sizes, m = total frames. Round down, then distribute leftovers.
Worked example

Two processes of 10 and 127 pages share 62 frames. S = 137.

P1: (10/137) × 62 ≈ 4.52 → 4 frames.

P2: (127/137) × 62 ≈ 57.47 → 57 frames.

Total 61, leaving 1 frame as buffer. The large process now has enough frames to hold its working set, so its fault rate drops sharply.

Global versus local allocation

Global allocation Local allocation
A process may replace any frame in memory, including frames belonging to other processes. A process may replace only pages from its own allocated set of frames.
The number of frames per process changes dynamically. The number of frames per process is fixed.
Better utilisation and throughput; more flexible. Predictable, stable performance; processes do not interfere.
A process's performance depends on others' memory behaviour; thrashing can spread. Unused frames of one process cannot help another, lowering efficiency.
Allocation and replacement are coupled

The allocation policy determines which frames a process owns; the replacement policy determines which page within the allowed set is evicted. Global replacement effectively makes allocation dynamic, while local replacement fixes it. The choice directly affects whether thrashing can propagate between processes.

Thrashing & working set

Thrashing is a condition in which a process spends more time servicing page faults than executing instructions. It happens when a process does not have enough frames to hold its working set — the pages it is actively using. Pages are swapped in and out continuously, and useful work almost stops.

How thrashing develops

  1. The process references a page that is not in memory.
  2. A page fault occurs.
  3. The OS evicts an existing page to load the required one.
  4. The evicted page is needed again shortly afterward.
  5. Another fault occurs, evicting the page just loaded.
  6. The cycle repeats; the process makes no progress.
Illustration

A process needs 8 pages but is given only 4 frames. It loads page 5, replacing page 2. Soon it needs page 2 again, faults, and replaces page 5. Then page 5 is needed again, and so on. The same few frames are recycled endlessly and the CPU sits idle waiting for disk.

Causes

  • Insufficient frames — fewer frames than the working set requires.
  • High degree of multiprogramming — too many processes competing for the same frames; each gets too few.
  • Global replacement — a thrashing process steals frames from others, so thrashing spreads through the system.
  • Runaway fault rate — each fault increases disk I/O, which slows every process, which causes more faults.

Effects

  • Very high page-fault rate and heavy disk activity.
  • CPU utilisation collapses even though processes are runnable.
  • Throughput and effective access time degrade severely.
The thrashing feedback loop

Low CPU utilisation caused by thrashing looks, to the scheduler, like an idle machine. The OS responds by admitting more processes, which lowers the frames per process further and makes thrashing worse. Breaking this loop requires either reducing the degree of multiprogramming or allocating frames based on measured need.

The locality model

During execution a process moves through a sequence of localities — a function and its locals, a loop and its data, a module. If enough frames are available to hold the current locality, faults are rare. If not, the process thrashes. The locality model explains why allocation must be based on active pages, not total program size.

Working-set model

The working set is the set of pages referenced in the most recent Δ page references (the working-set window). Its size, WSSi, estimates the frames process i needs right now.

Working-set condition
D = Σ WSSi
if D > m → thrashing is imminent
D is total demand, m is total frames. If demand exceeds supply, the OS must suspend or swap out one or more processes.

The OS tracks each process's working set and admits a new process only if enough frames remain for its expected working set. When D exceeds m, a process is suspended and its frames are redistributed.

Page-fault frequency (PFF)

PFF controls thrashing directly by measuring each process's fault rate and comparing it with two thresholds:

Fault rate Action
Above the upper limit The process needs more frames — allocate additional frames.
Below the lower limit The process has excess frames — reclaim some for others.
High, but no free frames Suspend a process and give its frames to processes with higher demand.

Preventing thrashing

  1. Allocate enough frames to hold each process's working set.
  2. Use the locality model to estimate active memory requirements.
  3. Apply the working-set model to allocate frames dynamically.
  4. Control the fault rate with PFF.
  5. Reduce the degree of multiprogramming when demand exceeds supply.
  6. Prefer local replacement so one process cannot drag others down.

NUMA & memory locality

NUMA (Non-Uniform Memory Access) is a shared-memory multiprocessor architecture in which each processor has its own local memory. All processors can still address the complete shared memory space — there is a single system image — but access time depends on where the memory lives. Local access is fast; remote access through the interconnect is slower. This is what makes access non-uniform.

Compared with UMA (uniform memory access), where every CPU contends for one shared bus and one memory pool, NUMA reduces contention and increases aggregate bandwidth, and it scales to far more CPUs. The price is higher latency for remote references and greater hardware and software complexity.

Architecture

A NUMA system is built from nodes. Each node contains:

  • One or more CPU cores.
  • A local memory controller.
  • Local RAM.
  • High-speed interconnect links to the other nodes.

Components

Component Role
Processors Execute instructions; can reach local and remote memory, but local is significantly faster.
Local memory Directly attached to a processor; lowest latency and highest bandwidth; preferred for hot data.
Remote memory Memory owned by another node; reached through the interconnect with higher latency.
High-speed interconnect Connects nodes so processors can access remote memory and communicate.
Memory controller Manages transfers between a processor and its memory; typically one per node.
Operating system Schedules processes and allocates memory; a NUMA-aware OS keeps a process near its data.

NUMA-aware allocation

The OS tries to allocate frames as close as possible to the CPU executing the process. Two techniques matter:

  • First-touch placement — a page is allocated on the node of the CPU that first faults it in. A process that initialises its own data therefore gets local memory.
  • Migration and affinity — the scheduler keeps a process on its home node, and may migrate pages or processes if the balance drifts.
Why locality matters more on NUMA

On UMA, every miss costs the same. On NUMA, a cache miss that goes to remote memory can cost several times a local miss. Placing data and the threads that use it on the same node is therefore a first-order performance concern, not a micro-optimisation.

Memory locality

Memory locality is the tendency of a program to access the same locations, or nearby locations, repeatedly over a short period. It is the principle behind the entire memory hierarchy — registers, cache, RAM and virtual memory — and it is what makes demand paging and caching effective.

Temporal locality

If a location is accessed now, it is likely to be accessed again soon. Loops, counters and hot variables exhibit this. Keeping them in cache or in a local frame avoids repeated slow accesses.

Spatial locality

If a location is accessed, nearby locations are likely to be accessed soon. Instructions and array elements are stored contiguously, so fetching a cache line or a whole page amortises the cost over many accesses.

How locality improves performance

  1. Reduces memory access time — needed data is close to the CPU, in cache or local memory.
  2. Raises cache hit rate — repeated and nearby accesses keep data resident in cache.
  3. Reduces cache misses — fewer trips to main memory.
  4. Improves paging efficiency — only frequently used pages need to be resident, so faults are rarer.
  5. Speeds up execution overall — the CPU spends more time computing and less time waiting.

NUMA advantages and disadvantages

PerformanceLocal memory gives low latency and high bandwidth per node.
ScalabilityMore nodes and CPUs can be added than a UMA bus allows.
Less contentionEach node mostly uses its own memory, reducing shared-bus pressure.
ComplexityRequires specialised hardware and NUMA-aware OS support.
CostMore expensive than UMA due to interconnect and controllers.
VariabilityShared-memory workloads can perform worse than on UMA.
