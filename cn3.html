Unit 3: Transport Layer Congestion Control, QUIC, Network Layer, IP, SDN & Data Centers

TCP congestion control (Tahoe, Reno, CUBIC), QUIC and HTTP/3, then the network layer: forwarding and routing, inside a router, IPv4 format, fragmentation, addressing, NAT, SDN with OpenFlow and P4, data center networking and multicast.

1. Principles of Congestion Control

1.1 Why it matters — the 1986 collapse

In October 1986 the link between Lawrence Berkeley Lab and UC Berkeley, only 400 m apart, fell from 32 kbps to 40 bps — a drop of roughly 800×, with all hardware healthy. Every sender kept retransmitting into a router queue that was already full, so the link spent almost all its capacity carrying duplicate copies and starved new data. Van Jacobson's congestion-control algorithms (1988), the base of modern TCP, were written to fix exactly this.

Diagnostic case — 9 PM hostel, Netflix buffering

Is it flow control or congestion control? Almost certainly congestion control: hundreds of students share the hostel Wi-Fi AP, aggregation switches and ISP uplink, so router buffers fill (long queueing delay) and overflow (loss). A flow-control problem would mean the Netflix server is overrunning your device's receive buffer (rwnd).

How to tell from where you sit: (1) CPU/RAM/disk idle in Task Manager → receiver is not the bottleneck; (2) ping/traceroute to the gateway and 8.8.8.8 shows RTT spikes and loss → queueing/overflow in the network; (3) roommates are slow too, or your own phone hotspot fixes it on the same device → network congestion.

1.2 Congestion vs. flow control

Informal definition of congestion: "too many sources sending too much data too fast for the network to handle." It shows up in two ways: long delays (queueing in router buffers) and packet loss (buffer overflow). It is a top-10 problem in networking.

1.3 Causes and costs of congestion — three scenarios

Notation: λin = original data rate from the application; λ'in = offered load (original + retransmitted data) into the network, so λ'in ≥ λin; λout = throughput delivered to the receiving application. All links have capacity R.

Scenario 1 — two senders, one router, infinite buffers

  • No drops, so no retransmissions. Two connections share one outgoing link of capacity R, so each can get at most R/2.
  • For λin between 0 and R/2: λout = λin. Above R/2, throughput is capped at R/2.
  • As λin → R/2 the average queue grows without bound and the delay → ∞.
Cost #1

Even with zero loss, large queueing delays appear as the arrival rate approaches link capacity.

Scenario 2 — two senders, one router, finite buffers, reliable transfer

  • 2a — perfect knowledge of free buffer: sender transmits only when a buffer slot is free. No loss, no retransmission, λ'in = λin, λout reaches R/2.
  • 2b — retransmit only when known lost: packets are dropped at a full buffer and resent. At offered load λ'in = R/2, only λout = R/3 is original data; the other R/6 is retransmissions.
  • 2c — realistic, premature timeouts: delay is large, the timer fires before the packet is lost, and the sender sends a duplicate. Both copies reach the receiver, which discards one. If every packet is forwarded twice, λout falls to R/4 as λ'in → R/2.
Costs #2

(a) Retransmissions are needed to compensate for buffer-overflow drops. (b) Unneeded retransmissions make the bottleneck link carry multiple copies of the same packet, wasting bandwidth and lowering the maximum throughput.

Scenario 3 — four senders, multi-hop paths, timeout/retransmit

  • Hosts A, B, C, D, routers R1–R4, finite buffers, every link capacity R. The A→C flow (R1→R2) and B→D flow (R2→R3) compete for the same output buffer at R2.
  • Small λ'in: overflow is rare, throughput grows roughly linearly with offered load.
  • Large λ'in: A→C traffic reaching R2 has already crossed R1→R2 so it is bounded (≤ R, in fact ≤ R/2 because R1 is shared). B→D traffic enters R2 directly from B, so its offered load (with aggressive retransmissions) can grow without limit. Every free slot at R2 is filled by a B→D packet, so A→C packets are dropped and A→C end-to-end throughput → 0. By symmetry every two-hop flow starves.
Cost #3

When a packet is dropped downstream, all the upstream transmission capacity and buffering already spent on it was wasted. Throughput peaks and then collapses toward zero as offered load keeps rising.

2. Approaches to Congestion Control & ECN

2.1 Two architectures

End-to-end

The network layer gives no explicit feedback. End systems infer congestion from observed behaviour: packet loss (timeout or 3 duplicate ACKs) and rising RTT. This is the traditional TCP approach.

Network-assisted

Routers give explicit feedback — a single congestion bit, or an explicit maximum sending rate. Examples: TCP ECN, ATM ABR, DECbit, IBM SNA.

Two ways to deliver network-assisted feedback

  • A — Choke packet: the congested router sends a control packet straight back to the sender ("I am congested, slow down").
  • B — Mark and echo (more common): the router marks a header field of a forward data packet; the receiver notifies the sender in its ACK. This takes a full RTT.

2.2 ECN — Explicit Congestion Notification

RFC 3168 (originally RFC 2481, 1999). Lets a router signal incipient congestion before the buffer overflows, so no packet is destroyed.

1. Router sets CE (11) in IP ToS→ 2. Receiver sets ECE in next ACK→ 3. Sender halves cwnd, sets CWR

  1. Router: when the queue passes a threshold it sets the CE (Congestion Experienced) codepoint, two bits 11 in the IP ToS/DiffServ field. The packet is still delivered.
  2. Receiver: sees CE and sets the ECE (ECN-Echo) flag in the TCP header of its next ACK.
  3. Sender: on an ACK with ECE it halves cwnd (as if 3 dup ACKs) and sets the CWR (Congestion Window Reduced) flag in the next data segment so the receiver stops echoing ECE.
  4. Deployment: router, sender and receiver must all support ECN — why a 1999 mechanism took almost two decades to deploy.

Trade-off: congestion is signalled with zero drops, but feedback still costs a full RTT and routers must be modified — the reason original TCP chose end-to-end inference.

3. TCP Congestion Control — Window, Rate & Principles

Each TCP connection has a send buffer, a receive buffer and state such as LastByteSent, LastByteAcked and the receiver's rwnd. For congestion control the sender adds a variable, the congestion window cwnd, adjusted dynamically from observed congestion.

In-flight data limit
LastByteSent − LastByteAcked ≤ min(cwnd, rwnd)

When rwnd is huge this reduces to LastByteSent − LastByteAcked ≤ cwnd.

Approximate TCP sending rate
Rate ≈ cwnd / RTT bytes/sec

At the start of each RTT the sender sends cwnd bytes and waits one RTT for the ACKs. Changing cwnd changes the rate.

3.1 The rate dilemma and self-clocking

Send too fast → congestion collapse. Send too slowly → bandwidth wasted. TCP wants a high rate that does not congest the network.

Self-clocking: TCP uses arriving ACKs to trigger cwnd increases. Slow ACKs (high delay or low bandwidth path) → cwnd grows slowly; fast ACKs → cwnd grows quickly.

3.2 Three guiding principles

  1. A lost segment implies congestion (timeout or 3 duplicate ACKs) → decrease the rate.
  2. An acknowledged segment means the network is delivering → increase the rate.
  3. Bandwidth probing: keep increasing on ACKs until loss, back off, then probe again in case available bandwidth changed.

The classic algorithm has three components: Slow Start, Congestion Avoidance, Fast Recovery.

4. AIMD — Additive Increase, Multiplicative Decrease

Ignoring the initial slow-start ramp, TCP increases its rate linearly until loss, then cuts it multiplicatively.

AIMD rules
Additive increase: cwnd ← cwnd + 1 MSS per RTT
Per ACK in CA: cwnd ← cwnd + MSS × (MSS / cwnd)
Multiplicative decrease: cwnd ← cwnd / 2 (Reno, 3 dup ACKs)
  • Additive increase: +1 MSS per RTT until loss. In practice the sender adds MSS × (MSS/cwnd) bytes on every new ACK instead of waiting for an RTT.
  • Multiplicative decrease: 3 dup ACKs → Reno cwnd/2, Tahoe → 1 MSS. Timeout → both Tahoe and Reno set cwnd = 1 MSS.
  • Sawtooth: climbing by +1 MSS/RTT and halving on loss draws the saw-tooth that visualises bandwidth probing.
  • Why AIMD: Kelly (1998) and Srikant (2012) showed AIMD, run as a distributed asynchronous algorithm, optimises flow rates network-wide with good stability and fairness.
Key exam rule

The only difference between Tahoe and Reno is the response to 3 duplicate ACKs. On a timeout they behave identically.

5. TCP Slow Start

Starting at 1 MSS and growing +1 MSS/RTT would take far too many round trips to reach available capacity, so a new connection starts in Slow Start and grows exponentially.

  • Initial window (textbook): cwnd = 1 MSS, initial rate MSS/RTT.
  • Doubling each RTT: 1 → 2 → 4 → 8 MSS …
  • Per-ACK implementation: cwnd ← cwnd + 1 MSS for every new ACK. One segment ACKed → 2; those two ACKed → +2 → 4; and so on. No RTT timer needed.
  • Real practice: RFC 6928 (2013) raised the initial window to IW = 10 MSS (≈ 14 KB), enough for a small page in the first RTT. A Wireshark capture shows ten segments in the first flight.
Slow start growth
cwnd after n RTTs = 2n × initial cwnd

Round r (starting at 1 in round 1) has cwnd = 2r−1 MSS until it reaches ssthresh.

Three ways slow start ends

  1. Timeout: ssthresh = cwnd/2, cwnd = 1 MSS, restart slow start.
  2. cwnd ≥ ssthresh: switch to Congestion Avoidance (linear growth).
  3. 3 duplicate ACKs: Fast Retransmit, then Fast Recovery.

6. Loss Detection, Fast Retransmit/Recovery & the Reno FSM

6.1 Why timeout and 3 dup ACKs are treated differently

  • Timeout = severe congestion (not even enough later segments arrived to generate duplicate ACKs). Tahoe and Reno both: ssthresh = cwnd/2, cwnd = 1 MSS, slow start up to ssthresh, then linear.
  • 3 duplicate ACKs = the network is still delivering (at least 3 segments after the lost one reached the receiver). Reno: halve cwnd, Fast Recovery, linear growth. Tahoe: cwnd = 1 MSS regardless.
  • Fast Retransmit: retransmit the missing segment on the third duplicate ACK without waiting for the timer.

Each of the 3 duplicate ACKs proves one segment has left the network and sits in the receiver's buffer. The sender adds 3 MSS to replace those 3 segments in flight so the pipe stays full. Method for any TCP numerical

Step-by-step recipe
  1. Write cwnd per round: double each round in slow start (or +1 per ACK), +1 per round in congestion avoidance.
  2. Switch to linear the round cwnd reaches ssthresh (cap the doubling at ssthresh — e.g. ssthresh 8: 1, 2, 4, 8, then 9).
  3. On loss: ssthresh = cwnd/2 of the value just before loss.
  4. Timeout or Tahoe 3-dup → cwnd = 1 and slow start again. Reno 3-dup → cwnd = ssthresh and linear.
  5. If the question gives sizes in KB, convert to MSS first; time = number of RTTs × RTT. Cap cwnd at rwnd if one is given.

Quick worked patterns

  • cwnd = 12, 3 dup ACKs: ssthresh = 6; Tahoe cwnd = 1; Reno cwnd = 6 (after deflation, 9 during recovery).
  • cwnd = 20, timeout: ssthresh = 10, cwnd = 1, then 1, 2, 4, 8, 10 (capped), 11 …
  • Time to return to a window W after timeout (cwnd = W): ssthresh = W/2; slow start to W/2 takes log₂(W/2 ÷ initial) RTTs, then (W − W/2)/MSS RTTs of linear growth.
  • Reaching ssthresh from 1 MSS: n doublings = log₂(ssthresh in MSS) RTTs (e.g. 64 MSS → 6 RTTs).

8. TCP CUBIC

8.1 Reno's problem on long fat networks

+1 MSS/RTT was fine in 1990 at a few Mbps; on fast long-delay links it is glacial.

  • Example 1: 10 Gbps path with 100 ms RTT and 1500 B segments → BDP = 10 Gbps × 0.1 s = 1 Gbit = 125 MB ≈ 83,333 segments. A loss halves the window (≈ 41,666 segments lost); climbing back at +1 per 100 ms takes ≈ 41,666 RTTs (over an hour; over 2 hours for the whole 83,000).
  • Example 2: to sustain 10 Gbps at 100 ms, Reno needs a loss rate near 2×10−10 — one lost packet in five billion.

8.2 CUBIC's idea

Let Wmax be the cwnd at which loss was last detected. The bottleneck probably has not changed in the last second, so return to Wmax quickly, then approach it carefully. Slow start, fast retransmit, fast recovery and timeout behaviour are unchanged.

  1. Back off less: cut to 0.7 × Wmax (30% cut) instead of Reno's 0.5.
  2. Return fast (concave climb): climb steeply back toward Wmax.
  3. Hold (plateau): flatten just below Wmax instead of sailing through and causing another loss. More area under the curve means higher average throughput.
CUBIC window function
W(t) = C·(t − K)³ + Wmax
K = ∛( Wmax·β / C ), β = 0.3 ⇒ W(0) = 0.7·Wmax

t = real elapsed time since the last loss; C = scaling constant; K = deadline, the time at which the window is back at Wmax. K is not fixed: the larger Wmax (the bigger the drop), the later K.

Think of y = x³: steep, flat at the inflection point, steep again. Slide the inflection point to (K, Wmax).

ZoneTimeBehaviour
1 — climb back fastt < KStarts at 0.7·Wmax, very steep, concave rise toward Wmax
2 — probe cautiouslyt ≈ KCurve flattens at the inflection point, window parks just under Wmax
3 — seek new capacityt > KNo loss at Wmax means capacity grew (e.g. a competing flow ended); curve turns steep again to find the new ceiling

8.3 RTT fairness

CUBIC depends on wall-clock time t, not on how many ACK round trips have returned. Two flows share a bottleneck: A with 20 ms RTT, B with 200 ms RTT. In one second A makes 1000/20 = 50 round trips, B only 5. Under Reno (+1 per RTT) A gains +50 MSS and B +5 MSS — 10× faster for A, an inherent RTT bias. With CUBIC, one second after a synchronized loss both flows sit at the same point on the curve, so sharing is much fairer.

8.4 Tahoe vs. Reno vs. CUBIC

All three share the same slow start, detect loss the same way and treat a timeout the same (cwnd = 1 MSS). They differ only in the 3-dup-ACK cut and how fast they climb back.

Kernel ossification — the thesis

"Every fix means changing TCP itself — and TCP lives inside the OS kernel. It helps nobody until every machine is upgraded." Upgrading kernels and middleboxes across billions of endpoints takes a decade or more (private data centers excepted). So engineers moved transport functionality into the application layer, in user space, on top of UDP — giving QUIC and HTTP/3.

10. Introduction to QUIC

QUIC (Quick UDP Internet Connections): designed and deployed by Google in 2012, standardised by the IETF as RFC 9000. It offers TCP-style reliable transport but runs as a user-space application-layer protocol on UDP, with TLS 1.3 built into the transport. It is the transport for HTTP/3 and is heavily deployed in Google servers, Chrome and the YouTube mobile app.

Five reasons QUIC was introduced (limits of HTTP/2 over TLS over TCP)

  1. TCP connection setup adds latency — a full 3-way handshake before anything else.
  2. TLS adds another serial handshake — about 2 RTTs total before data.
  3. TCP gives only one ordered byte stream — all multiplexed objects share it.
  4. Transport-level head-of-line blocking — loss in the stream delays every later byte.
  5. Rigid 4-tuple binding (src IP, src port, dst IP, dst port) breaks mobility, e.g. Wi-Fi → 5G.

Why UDP?

TCP is hard-wired into OS kernels and into middleboxes (routers, NATs, firewalls) that inspect TCP headers and drop unfamiliar options, so upgrading TCP globally is nearly impossible. UDP is accepted and forwarded everywhere, so QUIC implements its logic in user space with no kernel or IP changes.

QUIC's eight built-in functions

(1) Reliability, (2) acknowledgments, (3) retransmission, (4) congestion control, (5) flow control, (6) connection management, (7) stream multiplexing, (8) security (TLS 1.3).

QUIC parallels TCP's loss detection and congestion control (RFC 9000 says readers of TCP will find algorithms that parallel TCP's). Key features: 1-RTT (or 0-RTT) setup that establishes reliability, congestion-control, authentication and encryption state in one handshake; multiple application streams over one connection, each with its own reliable delivery but shared security and congestion control; and HTTP/3 mapping HTTP semantics onto QUIC.

11. QUIC Streams & Head-of-Line Blocking

One QUIC connection holds multiple independent streams (e.g. Stream 1 = HTML, 2 = image, 3 = video), bidirectional or unidirectional. Each stream is an ordered byte sequence. Loss in Stream 2 does not block Streams 1 and 3.

Contrast: with HTTP/1.1 or HTTP/2 over TCP, all GET objects share one TLS pipe and one TCP reliable byte stream, so one lost packet stalls everything. In QUIC each stream has its own reliable-delivery and encryption instance while all share one congestion-control module over UDP.

ScopeStatusExplanation
Between streams (cross-stream HOL)FixedLoss of an image packet does not hold up HTML or video; they are delivered immediately. Under TCP all three would stall.
Within a stream (intra-stream HOL)UnchangedA stream is still ordered. If packet 3 of Stream 2 is lost, packets 4 and 5 of Stream 2 wait in the buffer until packet 3 is retransmitted.

So QUIC shrinks the blast radius of HOL blocking from the whole connection to one stream; saying "QUIC has no HOL blocking" is incomplete.

Why HTTP/2 could not fix this itself

HTTP/2 multiplexed requests above TCP, but TCP only understands one ordered byte stream: one lost segment makes the kernel withhold every later byte, even from unrelated HTTP/2 streams. You cannot fix transport HOL blocking from above TCP — QUIC had to replace the transport layer.

12. QUIC Handshake, 0-RTT & Security

12.1 Connection establishment

  • TCP + TLS: TCP handshake (1 RTT) first, then TLS 1.3 handshake (1 RTT) on top → ~2 RTT before encrypted data.
  • QUIC, first connection: transport parameters and TLS 1.3 hellos travel in the same flight → 1 RTT.
  • QUIC, returning client: the server sent a TLS session ticket earlier; the client caches it and sends encrypted application data in the very first packet → 0 RTT.

12.2 0-RTT replay attack

The client encrypts 0-RTT data with key material left over from an earlier connection, not a fresh key negotiated for this connection; the server has not yet contributed a fresh nonce. An on-path attacker can capture the packet and replay it many times.

  • Safe (idempotent): GET /product/42 replayed 10 times just returns the page 10 times.
  • Dangerous: POST /orders {item:42, qty:1} replayed 10 times may place 10 orders and 10 charges.
  • Rule: the application/browser must send only idempotent requests in a 0-RTT flight.

12.3 QUIC and TLS 1.3

  • QUIC does not replace TLS; it integrates TLS 1.3, which still provides authentication, confidentiality, integrity and key establishment.
  • Split of duties: TLS 1.3 provides the crypto state machines and derives secrets; QUIC handles framing, reliability, retransmission and delivery of the handshake messages.
  • Three-tier secret isolation: (1) handshake secrets protect handshake packets; (2) application secrets encrypt web traffic after the handshake; (3) header-protection secrets obfuscate packet numbers so observers cannot read, correlate or spoof ACKs.

14. How a Browser Knows to Use HTTP/3

A browser can't blindly send QUIC/UDP: the server may not support it, or a firewall may drop UDP and cause a long timeout.

Mechanism 1 — Opportunistic discovery over TCP

  1. First visit over TCP: normal TCP + TLS, send the request.
  2. Server replies with an HTTP/3 hint: the Alt-Svc response header, e.g. Alt-Svc: h3=":443"; ma=86400 (RFC 7838). The browser caches it.
  3. Later requests over QUIC: 1 RTT on the first QUIC connection, 0 RTT on later ones once a session ticket is stored.

Mechanism 2 — DNS

The HTTPS resource record (RFC 9460) advertises h3 in its ALPN field, returned along with the IP during DNS resolution, saving the first TCP round trip.

Why the first visit is never 0-RTT

(1) The browser has not yet learned the server speaks HTTP/3 and (2) no TLS session ticket is stored. So 0-RTT is realistically on the third visit under Alt-Svc discovery, the second under DNS discovery.

15. QUIC's Limits & QUIC vs. TCP + TLS

Where QUIC falls short

  1. UDP not always allowed: campus/corporate firewalls block or rate-limit UDP (incl. port 443), so the browser falls back to TCP.
  2. Higher CPU cost: user-space packet processing, less mature NIC offload, every packet encrypted.
  3. Harder to troubleshoot: nearly everything (even packet numbers) is encrypted, so operators cannot passively measure RTT or loss.
  4. Amplification risk: no handshake proves the source IP before data flows. An attacker can spoof a victim's address. So a QUIC server may send at most 3× the bytes received until the client address is validated.
  5. Fallback hides the problem: the page still loads over HTTP/2/TCP, so operators rarely notice QUIC was never used.

Adoption gap: about 39% of websites support HTTP/3 and almost every browser does, yet only about 21% of real traffic uses it (UDP blocked, enterprise proxies, ignored Alt-Svc, bots on TCP, CDN edge speaking HTTP/3 to browsers but TCP to origin).

16. Overview of the Network Layer

16.1 Services and where it runs

The network layer carries transport segments from a sending host to a receiving host across a mesh of mobile, enterprise, ISP and data-center networks.

  • Sending host: encapsulates each segment into an IP datagram (adds a network header) and passes it to the link layer.
  • Receiving host: takes datagrams from the link layer, extracts the segment and delivers it to TCP or UDP.
  • Everywhere: unlike application and transport protocols (end systems only), network-layer protocols run in every device. A host implements all 5 layers; a router implements network, link, physical.
  • Router job: examine the header fields of every IP datagram and move it from an input port to an output port.

Interplay: the router looks at a header field value (say 0111) and indexes its forwarding table (0100→3, 0101→2, 0111→2, 1001→1), so the packet leaves on link 2. The routing algorithm fills in that table.

16.3 Two control-plane approaches

Per-router control plane

Each router has its own routing algorithm component. Routers exchange routing-protocol messages to compute their own forwarding tables.

SDN control plane

A physically separate, logically centralised remote controller computes the tables and installs them via a Control Agent (CA) in each router. Routers only forward.

16.4 Network service models

Services a network layer could offer — per datagram: guaranteed delivery; guaranteed delivery with bounded delay (e.g. < 40 ms). Per flow: in-order delivery; guaranteed minimum bandwidth; bounded jitter / inter-packet spacing; security.

The Internet offers a single best-effort service — "a euphemism for no service at all". No guarantee of delivery, timing/order or bandwidth.

Why best effort succeeded

  1. Simplicity: simple stateless core routers → wide, cheap deployment.
  2. Sufficient provisioning: over-provisioned links make real-time apps "good enough most of the time".
  3. Replicated application-layer services: data centers and CDNs sit close to or inside access networks.
  4. Congestion control of elastic services: end-to-end TCP backs off politely.

17. What's Inside a Router

Four components split between the hardware data plane and the software control plane.

Data plane (hardware, ns)

  1. Input ports: (a) physical-layer line termination; (b) link-layer processing (decapsulate Ethernet); (c) lookup and forwarding using a local shadow copy of the forwarding table; queue if the fabric is busy.
  2. Switching fabric: connects N inputs to N outputs — "a network inside a network router".
  3. Output ports: buffer packets from the fabric and transmit them (link-layer send + physical line termination).

Control plane (software, ms)

  1. Routing processor: runs routing protocols (OSPF, BGP), maintains routing tables, computes the forwarding table and pushes a shadow copy to each input line card over a bus (e.g. PCI). In an SDN router it talks to the remote controller and installs the flow-table entries.

17.1 Input port processing

Pipeline: line termination (physical bits) → link-layer receive (frames, strip header) → lookup, forwarding, queueing.

  • Decentralised switching: each line card holds its own table copy, so the decision is made locally without interrupting the routing processor per packet ("match plus action").
  • Goal: line speed — finish lookup as fast as packets arrive, otherwise input buffers overflow. Queueing still occurs if arrivals exceed fabric speed.
  • Destination-based forwarding (traditional): uses only the 32-bit destination IP. Generalised forwarding (SDN): any header fields at link, network and transport layers.

19. Router Queueing, Buffering & Scheduling

19.1 Input port queueing & HOL blocking

Input queueing occurs when the fabric is slower than the combined input line rates, or several inputs target the same output (output port contention).

Head-of-the-Line (HOL) blocking: two input queues each have a red packet at the head for the same output. Only one goes; the other is blocked — and a green packet behind it, bound for a completely idle output, must wait too. In a FIFO input-queued crossbar with uniform random traffic, input queues grow without bound at only 58 % (2 − √2 ≈ 0.586) of link capacity.

19.2 Output port queueing

If the fabric runs at N·R but the link at R, packets from several inputs for one output arrive faster than they can leave, so output buffering is needed; persistent mismatch means delay and loss from overflow. Two decisions at an output port: drop/marking policy (which packet to drop, or mark early) and scheduling discipline (which queued packet to send next).

19.3 How much buffering?

"Buffering is like salt — the right amount helps, too much is inedible."

Buffer sizing
RFC 3439 rule of thumb: B = RTT × C
N independent TCP flows: B = RTT × C / √N

Example: C = 10 Gbps, RTT = 250 ms → B = 0.25 × 10 Gbps = 2.5 Gbit. 40 Gbps × 100 ms = 4 Gbit. 1 Gbps × 200 ms = 200 Mbit = 25 MB.

Bufferbloat: too much buffering (e.g. cheap home routers) keeps queues persistently full. Loss-based TCP grows cwnd until the buffer finally overflows, adding hundreds of ms of standing delay — long RTT, bad voice/video/gaming, sluggish TCP. Philosophy of delay-based control: keep the bottleneck just busy, no fuller.

19.4 Drop, marking and scheduling

  • Drop policies (buffer full): tail drop — discard the arriving packet; priority drop — remove a queued lower-priority packet for a higher-priority arrival.
  • Marking / AQM (before full): ECN sets CE bits in the IP header; RED (Random Early Detection) tracks an exponentially weighted average queue length and probabilistically drops or marks as it moves between a min and max threshold.
  • Scheduling: FIFO/FCFS, priority queueing, round robin (RR), weighted fair queueing (WFQ). Scheduling decides who gets the best performance (net-neutrality debates).

21. IP Fragmentation & Reassembly

Every link has an MTU, the largest payload a link-layer frame can carry (Ethernet = 1500 B). If a datagram exceeds the outgoing link's MTU and DF = 0, the router splits it into smaller datagrams, each with its own IP header, sent independently.

21.1 Where reassembly happens

Fragments are reassembled only at the destination host, never at routers: fragments may take different routes, and reassembly in the core would need per-datagram state and buffers. The destination uses the 16-bit Identifier, the MF flag and the Fragment Offset.

21.2 Why the offset is in units of 8 bytes

Total length is 16 bits (up to 65,535 B), but only 13 bits were left for the offset (32 − 16 Identifier − 3 Flags). 13 bits count only to 213−1 = 8191, so IPv4 scales by 216/213 = 8: one offset unit = 8 bytes. Therefore every fragment's data (except the last) must be a multiple of 8 bytes. Largest offset value 8191 → largest byte offset 8191 × 8 = 65,528.

Fragmentation formulas
Data per full fragment = ⌊(MTU − header) / 8⌋ × 8
Fragments = ⌈ payload / data per fragment ⌉
Offsetk = (bytes of data before fragment k) / 8
Total length of a fragment = its data + 20

MF = 1 for all fragments except the last (MF = 0). All fragments carry the same Identifier and DF is unchanged.

Reverse problems

  • Given offset, length, MF = 0: original data = offset × 8 + (total length − header). E.g. offset 100, total length 220, header 20 → 800 + 200 = 1000 B of data (1020 B datagram).
  • Given HLEN, offset, total length: header = HLEN × 4; payload = total − header; first byte = offset × 8; last byte = first + payload − 1. E.g. HLEN 10, total 400, offset 300, MF 0 → header 40, payload 360, bytes 2400–2759, last fragment.
  • UDP datagram: IP data = user data + 8 (UDP header). E.g. 8880 B + 8 = 8888 → 6 × 1480 = 8880, +8 B → 7 fragments, last offset 8880/8 = 1110.
  • Two links in series: fragments are not reassembled in between; fragment each piece again at the smaller MTU.

21.3 Why fragmentation is avoided today

  1. Loss multiplication: IP never retransmits one fragment. If 1 of 5 fragments is lost, the receiver discards the other 4 after the reassembly timer; TCP resends the whole segment. 1 % packet loss ≈ 5 % datagram loss.
  2. TCP sizes MSS to the MTU: 1500 − 20 − 20 = 1460 B MSS, so IP never needs to split.
  3. DF = 1 + ICMP: a router with a smaller-MTU link drops the packet and sends ICMP "Fragmentation Needed / Packet Too Big" with the next-hop MTU.
  4. IPv6 routers never fragment: only the source host may; a too-large packet is dropped with ICMPv6 Packet Too Big.
Path MTU Discovery (PMTUD)

Send with DF = 1 and shrink on ICMP feedback; the sender learns the smallest MTU on the path. On 1500-byte Ethernet, ping -D -s 1472 8.8.8.8 works (1472 data + 8 ICMP + 20 IP = 1500) while -s 1473 fails with "Message too long".

22. IPv4 Addressing, Interfaces & Subnets

An IPv4 address is a 32-bit identifier for a host or router interface, not for the machine. An interface is the boundary between a node and a physical link. A host usually has one or two (Ethernet + Wi-Fi); a router must have several. Wired interfaces without a router in between are joined by Ethernet switches; wireless ones by a Wi-Fi access point.

Dotted-decimal: four octets, each 0–255. Example 223.1.1.1 = 11011111 00000001 00000001 00000001.

22.1 Subnets and masks

A subnet (IP network) is a set of interfaces that can reach each other physically without passing through a router. The address has two parts: the subnet part (network prefix, shared high-order bits) and the host part (remaining low-order bits).

Island recipe

Detach every interface from its host or router. Each isolated island is a subnet. Example 1: 6 hosts + 1 router → 3 subnets (223.1.1.0/24, 223.1.2.0/24, 223.1.3.0/24). Example 2: three routers in a triangle serving three LANs → 6 subnets: 3 LAN subnets plus 3 router-to-router point-to-point links (223.1.7.0/24, 223.1.8.0/24, 223.1.9.0/24) — each point-to-point link is its own subnet.

Host bits all 0 = subnet address; all 1 = directed broadcast; everything between = valid hosts. The next subnet starts right after the broadcast address.

24. Designing Subnets (Fixed-Length & VLSM)

24.1 The four-step method

  1. Requirements: number of subnets (one per LAN and per point-to-point link) and the maximum hosts per subnet.
  2. Subnet bits / host bits: use 2s ≥ subnets (modern CIDR; the legacy rule is 2s − 2) and 2h − 2 ≥ hosts. If several masks fit, favour more subnet bits if more subnets are expected, more host bits if hosts will grow. Don't use up every address immediately.
  3. Subnet addresses: list the borrowed-bit combinations from 000…, host bits 0, convert to dotted decimal.
  4. Host addresses: subnet address (host bits 0) → valid hosts → directed broadcast (host bits 1) → next subnet.

27. Network Address Translation (NAT)

All devices in a local network (e.g. 10.0.0.0/24: hosts 10.0.0.1–3, router LAN interface 10.0.0.4) use private addresses (10/8, 172.16/12, 192.168/16) valid only inside. To the outside they all share one public IPv4 address (e.g. 138.76.29.7 on the router's WAN side). Every outgoing datagram has the same source IP but a different NAT-chosen source port.

27.1 Advantages

  1. Conserves public IPv4 addresses — one address from the ISP serves many devices.
  2. Local autonomy — renumber inside hosts without telling the outside world.
  3. ISP independence — change ISP (new WAN address) without renumbering inside.
  4. Security/privacy — inside devices are not directly addressable from outside.

27.2 How it works — three transparent operations

  1. Outgoing: replace (source IP, port) with (NAT IP, new port). Remote servers reply to (NAT IP, new port).
  2. Remember: store each (source IP, port) ↔ (NAT IP, new port) pair in the NAT translation table.
  3. Incoming: look up the destination (NAT IP, new port) in the table and replace it with the stored (source IP, port).

27.3 Controversies and NAT traversal

  • Violates layering: routers should only process up to layer 3, but NAT rewrites transport-layer port numbers and checksums.
  • Violates the end-to-end argument: hosts should talk directly without intermediate devices rewriting addresses and ports.
  • Architectural purism: the address shortage should be fixed by IPv6.
  • NAT traversal problem: an outside client cannot start a connection to a server behind NAT, because no table entry exists until an inside host sends a packet out.
  • Reality: NAT is here to stay — home, institutional and 4G/5G networks (Carrier-Grade NAT).
Solution — static port forwarding

Statically configure the NAT so incoming requests to a given public port go to the internal server, e.g. (138.76.29.7, port 25000) → 10.0.0.1, port 25000.

28. Software-Defined Networking — Motivation & Characteristics

28.1 Why SDN

Traditionally each monolithic router bundled switching hardware with proprietary implementations of IP, RIP, IS-IS, OSPF, BGP inside a closed vendor OS (e.g. Cisco IOS), and operators bought separate proprietary middleboxes (firewalls, load balancers, NAT boxes). Around 2005 researchers began rethinking the control plane.

Traffic engineering is hard with traditional routing: to split u→z traffic over u-v-w-z and u-x-y-z, or send different flows on different paths, the only lever is to tweak link weights and hope all distributed shortest-path computations converge as desired.

Five reasons for a logically centralised control plane

  1. Easier network management: avoids misconfiguration, more flexibility over flows.
  2. Table-based forwarding (OpenFlow API) lets routers be "programmed".
  3. Centralised programming is easier than distributed programming.
  4. Open (non-proprietary) control-plane implementation.
  5. Fosters rapid innovation — "let 1000 flowers bloom".
DimensionMainframe / monolithic routerPC / SDN
StructureVertically integrated, one vendorHorizontal, disaggregated, open interfaces
HardwareSpecialised proprietaryMerchant silicon / commodity white-box switches
OSClosed (Cisco IOS)Open (Linux etc. / controller NOS such as ONOS, Ryu)
ApplicationsVendor-lockedThird-party network-control apps (routing, access control, load balancing)
ImpactClosed, slow innovationOpen, rapid innovation, huge industry

28.2 Four key characteristics

  1. Generalised flow-based forwarding: forwarding can use any link, network or transport header fields (OpenFlow 1.0 matches 11/12 fields), not just destination IP. Rules live in the switch flow table.
  2. Data/control plane separation: data plane = simple fast switches executing match-plus-action; control plane = separate servers and software computing the flow tables.
  3. Control-plane functions external to switches: software on remote servers in two sub-layers — an SDN controller / network OS (maintains network-wide state, exposes APIs) and network-control applications. Logically centralised but physically a distributed cluster for scalability, fault tolerance and availability.
  4. Programmable: control apps (the "brains") use the northbound API to implement routing, firewalling, load balancing.

  2. Network-wide state-management layer: a distributed, robust database of links, switches, hosts, flow-table counters and copies of each switch's flow tables.
  3. Interface layer to control apps (northbound): exposes the network graph, intent, RESTful API; apps read/write state and register callbacks for state-change events.

30.2 Flow table entry — match plus action

  1. Match (pattern values over 12 fields, wildcards allowed): Link layer (6) ingress port, src MAC, dst MAC, Eth type, VLAN ID, VLAN priority; network layer (4) IP src, IP dst, IP proto, IP ToS; transport (2) TCP/UDP src port, dst port.
  2. Actions: forward to port(s) (unicast, flood, multicast); drop; modify header fields (MAC/IP/port/VLAN); encapsulate and send to controller.
  3. Priority: disambiguates overlapping patterns (higher wins).
  4. Counters: bytes and packets matched, time since last match.

Wildcard examples: src = 10.1.2.3, dst = *.*.*.* → send to controller; src = 1.2.*.* → drop; dst = 3.4.*.* → forward(2). With two matching entries (dst 51.6.0.8 → port 6, priority 10; TCP dst 22 → drop, priority 20) a packet matching both is dropped — higher priority wins.

30.4 Link-failure recovery — 6 steps (s1–s2 fails, reroute via s4)

  1. s1 sends an OpenFlow port-status message to the controller (unlike OSPF there is no flooding between switches).
  2. Controller's communication layer updates the link-state database.
  3. The Dijkstra routing application, which had registered for link-status changes, is called.
  4. It reads the network graph via the northbound API and computes new shortest paths (s1 → s4 → s2).
  5. It hands the paths to the flow-table-computation component, which computes new flow tables.
  6. Controller installs the new rules via modify-state (flow-mod) in s1, s2 and s4.

31. P4 — Programmable Data Planes

OpenFlow still relied on a fixed-function ASIC that understood a predefined protocol list (Ethernet, IPv4, IPv6, TCP, UDP); adding a protocol needed slow standardisation. P4 (Programming Protocol-independent Packet Processors, p4.org) is a domain-specific language for the data plane of switches, routers, SmartNICs and programmable ASICs.

P4 vs. Ryu / ONOS

Ryu and ONOS live in the control plane and decide where packets go by populating flow-table rules. P4 lives in the data plane and defines how packets are parsed and processed inside the switch. It is protocol-independent: you can define your own headers.

A P4 programmer defines five things: (1) packet headers, (2) packet parser, (3) match-action tables, (4) metadata, (5) packet-processing pipeline — compiled and loaded onto the target.

Industry: all major clouds use SDN. VMware bought Nicira → VMware NSX, powering hundreds of thousands of VMs. Modern virtual networks combine SDN + NFV (network function virtualisation) + commodity white-box switches.

31.1 PISA vs. PSA

  • PISA (Protocol Independent Switch Architecture): a single linear pipeline — Parser → (checksum verify) Ingress match-action → Traffic manager (buffers) → (checksum update) Egress match-action → Deparser. It lacks standard target-specific constructs (externs) for complex replication/buffering.
  • PSA (Portable Switch Architecture): lets one P4 program target different hardware; programmable parser, multi-stage match-action (serial or parallel), with hardware-specific externs. Eight stages: (1) parser → (2) checksum validate → (3) ingress match-action → (4) packet buffer and replication → (5) egress match-action → (6) checksum update → (7) deparser → (8) buffer queueing engine. Eight externs: checksum, register, counter, meter, action profile, action selector, random, packet generator.

31.2 Inside a P4 program (Program.p4)

  • Parser: first block; extracts specified header regions with no prior assumptions about protocol meaning.
  • Metadata: extra per-packet state passed between stages on the header/metadata bus — ingress port, destination and queue, timestamps for scheduling, data passed between tables.
  • Entry (ingress) and exit (egress) match-action tables: extracted headers feed them. The entry table determines the queue; packets can be forwarded, copied, discarded or flow-controlled; an action table tracks frame status.

32. Data Center Networking — Scale, Traffic & Design Goals

Data centers hold tens to hundreds of thousands of closely-coupled servers: e-business (Amazon), content (YouTube, Akamai, Apple, Microsoft), search / data mining / AI clusters (Google). A DCN connects servers, storage, applications, VMs and external networks, and must give high bandwidth, low latency, reliability, scalability and security, serve many applications and clients, tolerate faults and balance load.

North–South

User ↔ Internet ↔ data center ↔ server. Traffic entering or leaving the DC (opening a web app from a phone; the finished page going back).

East–West

Server ↔ server ↔ database ↔ storage inside the DC. Dominates modern DCs: distributed apps, cloud, microservices, distributed AI training.

Examples: open a shopping site → N–S; web server asks DB for your cart → E–W; AI model trained on 1000 GPU servers → E–W (heaviest); page returned to the phone → N–S.

The five scorecard tests

  1. High bandwidth between any two servers (most traffic is E–W).
  2. Short, predictable delay — one page fans out to hundreds of microservice calls and waits for the slowest (tail latency).
  3. No single point of failure — with 100,000 servers something is always failing; route around it.
  4. Grow in small steps — add racks without rebuilding or buying one giant core switch.
  5. Cheap, identical switches — scale out, not up.

A hostel Wi-Fi network needs mostly tests 3 and 5; a datacenter is a very different problem.

33. Topologies — Traditional 3-Tier vs. Clos / Leaf–Spine

33.1 Traditional 3-tier

  • Racks: 20–40 server blades each.
  • Access layer — Top-of-Rack (ToR): one switch per rack, 100G–400G down to blades.
  • Aggregation (Tier-2): each connects ~16 ToR switches.
  • Core (Tier-1): each connects ~16 Tier-2 switches; border routers connect to the Internet.

Why it struggles (against the five tests):

  1. Traffic funnels upward (fails 1): rack-to-rack across pods climbs ToR → agg → core → agg → ToR; links near the top become the bottleneck.
  2. Spare links sit idle (fails 1 and 3): Spanning Tree Protocol disables redundant links to avoid L2 loops, so half the cables and ports carry nothing until a primary fails.
  3. Growth means bigger boxes (fails 3 and 5): scale up by replacing the core with costly chassis; the core stays a shared weak point.

33.2 Leaf–spine (Clos)

Flatten into two layers based on a Clos topology (same maths as a router's crossbar fabric): every rack equally close, every link used, capacity added by adding identical cheap switches.

LayerRules
Leaf (bottom)Top of each rack (ToR). Connect down to servers, storage, firewalls, load balancers. Every leaf connects to every spine. Leaves do not connect directly to other leaves.
Spine (top)High-speed backbone. Every spine connects to every leaf, giving multiple equal-length leaf → spine → leaf paths. Spines connect to neither servers nor other spines.
Leaf–spine counts
Links = (#leaf) × (#spine) · equal-cost paths between two leaves = #spine

6 leaves, 4 spines → 24 links, 4 equal-cost paths.

33.3 Oversubscription

Oversubscription ratio
Total downlink bandwidth from servers in a rack / Total uplink bandwidth leaving the ToR

Example: 40 servers × 25 Gbps = 1000 Gbps down; 4 uplinks × 100 Gbps = 400 Gbps up. Ratio = 1000/400 = 2.5 : 1. If all 40 servers send off-rack at once, each gets 400/40 = 10 Gbps instead of 25. Traffic inside the rack is switched locally and unaffected.

  • Why accepted: all servers rarely blast off-rack simultaneously; a 1:1 non-blocking fabric would need 2.5× the spines and optics. About 3:1 is common.
  • Two levers: add uplinks/spines to lower the ratio, or use locality-aware placement so chatty services share a rack and never use the uplinks.

33.4 Growing the fabric

Each leaf needs one port on every spine, so racks ≤ spine port count. A 64-port spine → at most 64 leaves → 64 × 40 = 2,560 servers, versus 100,000+ in hyperscale. To add bandwidth between racks: add spines. To add racks beyond the port limit: add a third Clos layer — self-contained leaf–spine pods joined by super-spines.

Facebook F16: each ToR connects up to 16 fabric switches (4 colour-coded planes of 4); each fabric switch connects up to 16 spine switches across the planes — big bisection bandwidth and rich multipath redundancy.

34. Multipath Routing (ECMP), Load Balancers & a Request's Life

Multipath routing spreads unicast traffic over several parallel paths for (1) load balancing/throughput, (2) congestion avoidance, (3) fast fault tolerance.

ECMP — Equal-Cost Multipath

  1. Every switch routes at layer 3: Leaf A sees four equal-length routes to Leaf B via spines 1–4; none is switched off (unlike STP).
  2. Hash the flow's 5-tuple (src IP, dst IP, src port, dst port, protocol) to pick a spine.
  3. Same flow → same path so packets of a flow never overtake each other.
  4. Failover in ms: if spine 2 fails, remove it from the next-hop set and re-hash flows over the remaining three.
Why hash per flow, not per packet?

Packets on different paths see different queueing delays and arrive out of order; TCP reads out-of-order arrival as 3 duplicate ACKs (loss) and needlessly halves cwnd. Per-flow hashing avoids reordering.

Load balancer — application-layer routing

Near the top of the fabric: (1) receives external requests addressed to the service's public IP; (2) directs the work to an internal server by load and content; (3) returns results, hiding internal servers and private IPs — an application-layer cousin of NAT.

36. Multicast Routing (overview)

Source note

The uploaded notes and slides only mention multicast in passing (Class D addresses, IPv6 multicast, multicast in data centers). This section is a short general overview added to cover the syllabus line "Multicast Routing – Case Study".

  • Unicast = one sender → one receiver; broadcast = to everyone on the network; multicast = one (or more) senders → a group of receivers. Sending the same stream (IPTV, stock feeds, video conferencing, software updates) with N unicast copies wastes bandwidth; multicast sends one copy per link and routers replicate where paths split.
  • Addresses: IPv4 Class D 224.0.0.0 – 239.255.255.255 (first bits 1110); IPv6 ff00::/8. A group address identifies the group, not a host; group members can be anywhere.
  • Group membership — IGMP (IPv4; MLD in IPv6): hosts tell their local router which groups they want to join or leave; routers periodically query to refresh.
  • Multicast routing builds a tree connecting the sender(s) to routers that have members: source-based tree (one shortest-path tree per source, S,G) or group-shared tree (one tree per group, e.g. centred on a rendezvous point). Packets are forwarded with reverse path forwarding (RPF): accept a packet only if it arrived on the interface the router would use to reach the source, which prevents loops and duplicates.
  • Protocols: DVMRP and MOSPF (dense-mode, flood-and-prune style); PIM — dense mode (flood and prune) and sparse mode (explicit join towards a rendezvous point, then optionally switch to a source tree).
  • Case study — IPTV in an ISP: one head-end source sends a channel to a group address; only edge routers with subscribers who joined (via IGMP) receive the stream; the tree is pruned where no one is watching, so a link carries each channel at most once however many viewers share it.

37. Lab 4 — TCP Congestion Window in Wireshark

Task A — capture and plot

  1. Run Wireshark as admin/sudo, capture on the live interface, browse a site, apply the tcp filter and pick the first TCP SYN to the server.
  2. Statistics → TCP Stream Graphs → Window Scaling; observe the congestion/outstanding bytes and the bytes going out and coming in.
  • SYN: flag SYN = 1; the client's initial (relative) sequence number is 0, with MSS, window scale and SACK-permitted options.
  • SYN-ACK: flags SYN + ACK; the server has its own relative sequence 0 and acknowledgment number 1 — the client's ISN + 1, the next byte it expects (a SYN consumes one sequence number). Third segment: ACK with seq 1, ack 1.
  • Plot lines: blue = unacknowledged (outstanding) bytes in flight; green = the receiver's advertised window (rwnd).
  • Who decides cwnd? cwnd is the sender's internal variable and is never carried in a TCP header; Wireshark does not show it directly, you infer it from the bytes in flight. The receiver communicates only rwnd (receive-side flow control, scaled by the window-scale option). Bytes in flight ≤ min(cwnd, rwnd).

Task B — analysing a capture with a loss

  • Phases: outstanding bytes climb steeply (exponential, slow start), then grow roughly linearly (congestion avoidance); a sudden dip marks a loss event; a sawtooth shape means AIMD. A cut to about half with continued linear growth fits Reno (fast recovery) or CUBIC; a drop all the way to ~1 MSS then exponential regrowth fits a timeout (or Tahoe).
  • Three duplicate ACKs: the receiver keeps ACKing the same sequence number because a segment is missing; the sender sees the same ACK number 4 times (original + 3 duplicates) and fast-retransmits the missing segment without waiting for the RTO; filter with tcp.analysis.duplicate_ack and tcp.analysis.fast_retransmission.
  • cwnd falls to 1 MSS on a retransmission timeout (severe congestion — no ACKs coming back), ssthresh = cwnd/2, then slow start doubles it each RTT until ssthresh.
  • After the reduction, the packets show 1 segment, then 2, then 4, … (doubling per RTT) up to ssthresh, then +1 MSS per RTT.
